Agent Reliability：重试、Fallback、Guardrails

从“偶尔能跑”到“生产环境可控、可恢复、可降级”
Author: Senior AI Architect Date: 2026-09-11 Series: Production AI Systems

在构建生产级 LLM Application 的过程中，我们首先解决了“什么问题交给 Agent”（Workflow/Agent），接着解决了“Agent 如何组织”（Single/Multi-Agent），然后引入了记忆、工具调用、评估和可观测性。然而，当一个具有概率性、动态执行路径和外部依赖的系统真正上线时，工程师面对的最大挑战不再是“能不能跑通”，而是“出问题时怎么办”。

本文不打算介绍具体的 Retry 框架或 Guardrails 库，而是试图回答一个更本质的问题：一个具有概率性、动态执行路径和外部依赖的 Agent，如何在真实生产环境中保持可控、可恢复、可降级和可预测？

反直觉观点 1：可靠性不是“让 Agent 永远不失败”

Agent 依赖的 LLM、Tool、API、Database、Retrieval、Memory 等环节均可能失败。真正的目标是：让失败被检测、被分类、被限制、被恢复、被降级，并最终保持在可控边界之内。

Reliability = Detect + Contain + Recover + Degrade + Prevent

反直觉观点 2：Retry 越多不代表系统越可靠

错误的 Retry 可能让系统更不可靠。Tool Timeout 后盲目重试可能导致 DB/API 压力剧增，引发雪崩。Retry 是恢复机制，不是默认行为。是否 Retry 必须基于错误类型、幂等性、预算、超时与副作用。

反直觉观点 3：Fallback 的目标不是保持“系统在线”

而是尽可能保持“业务目标”。Fallback 不应该只是“换一个模型”，它应涵盖 Model、Tool、Strategy、Workflow 等不同故障层的业务降级策略。

反直觉观点 4：Guardrails 不是为了限制 Agent

而是为了让 Agent 可以在明确边界内获得更大的行动自由。模型负责做判断，系统负责定义边界。Guardrails ≠ Prompt 提醒。

反直觉观点 5：可靠的 Agent，不是永远成功

而是失败以后知道什么时候继续、什么时候降级、什么时候停止。最危险的 Agent 不是“不会做事”的 Agent，而是“做错事情以后仍然继续执行”的 Agent。

第一部分：为什么 Agent Reliability 比传统系统更难？

1. 错误边界的扩大

在传统的分布式后端系统中，请求路径相对线性：Request -> Service -> DB -> Response。错误类型明确：HTTP 500、Timeout、DB Error。但在 Agent 系统中，执行路径是动态的循环。

图 1：传统系统与 Agent 系统的失败边界对比

2. Failure Chain：失败不是单点，而是链式传播

不要简单地把日志记录为“Agent Failed”。在真实场景中，一个微小的故障会被 Agent 的推理循环放大。

例如：Tool Timeout -> Retry -> State Changed -> Wrong Decision -> Wrong Tool -> Wrong Answer。

Agent Reliability 设计的核心任务之一，就是阻断这种 Failure Propagation。

4. Error Classification：哪些错误值得 Retry？

在传统工程中，Retry 是一种本能；但在 Agent 工程中，Retry 是一种需要严格审查的权限。必须建立 Retryability Matrix。

Error Type Retry? Engineering Judgment
Network Timeout / 503YES瞬时故障，重试有极大概率恢复
HTTP 429 Rate LimitYES受限后等待 Backoff 可重试
Invalid Arguments / Schema ErrorNO需修正参数，盲目重试只会再次失败

Business Rule ViolationNO如退款金额超限，系统级拒绝
Duplicate RequestCONDITIONAL需先检查幂等性，确认副作用

第三部分：Retry Engineering

Retry 不是简单的 for i in range(3)。我们需要从三个层次思考重试：Infrastructure Retry（网络、连接）、Model Retry（Provider transient error）、Agent Action Retry（Tool Call, Retrieval）。其中，Agent Action Retry 风险最高，因为它直接产生现实副作用。

5. Backoff 与 Retry Budget

delay = base * 2^attempt + jitter。Backoff 的目的不是让重试更优雅，而是避免系统将瞬时故障放大成持续过载。但比 Backoff 更重要的是 Retry Budget。

Agent 不能无限制地消耗时间和 Token。必须定义全局 Budget：

Agent Budget
├── Total Time Budget: 10s
├── Token Budget: 4000 tokens
├── Tool Call Budget: 5 calls
├── Cost Budget: $0.05
└── Steps Budget: 8 iterations
图 2：Retry Budget 与 Timeout Budget 的嵌套约束

6. Retry 与幂等性：副作用是 Agent 的死穴

在电商客服案例中，用户请求：“帮我把这笔订单退款。”

Agent 决定调用 create_refund(order_id=123)。第一次调用后服务端执行成功，但由于网络超时，Agent 没有收到响应。如果 Agent 直接简单 Retry，就会产生 Duplicate Refund。

工程铁律：对有副作用的 Tool，Retry 前必须先解决“我到底有没有成功”的问题。

正确的恢复流：

Timeout on create_refund
 |
 v
Call query_refund_status(order_id=123)
 |
 v
Already Done?
 ├── Yes -> Use Existing Result, Return Success
 └── No  -> Safe to Retry create_refund

这要求 Tool 在设计时必须支持 Idempotency Key 或允许基于业务键的状态查询。Create / Update / Refund 等操作的风险远高于 Query，因为它们改变了现实状态。

第四部分：Fallback Engineering

7. Retry 与 Fallback 的真正区别

维度RetryFallback
定义同一路径重新执行换一条路径继续完成任务
触发条件瞬时故障主路径彻底失败或 Budget 耗尽
业务影响无变化可能降级体验
执行代价低中/高

8. Fallback 的五个层级

成熟的 Fallback 绝不仅是“GPT 失败换 Claude”。它应该是一个多维度的降级体系：

  1. Model Fallback：Primary LLM 失败 -> Secondary LLM
  2. Tool Fallback：Primary API 失败 -> Cached API / Mock Data
  3. Retrieval Fallback：Hybrid Search 失败 -> Keyword Search -> LLM Parametric Knowledge
  4. Strategy Fallback：Auto Refund 失败 -> Manual Review Ticket
  5. Response Fallback：Full Detailed Answer 失败 -> Safe Partial Answer

9. Graceful Degradation：业务目标不能丢

电商客服案例中，自动退款失败。系统不应直接报错“系统异常”，而应执行策略降级：

Auto Refund -> Manual Review -> Create Ticket -> Inform User

第五部分：Guardrails

10. Guardrails 到底解决什么？

模型是概率系统，我们永远无法保证模型下一次的输出绝对安全。因此，Model 决策 ≠ System Authorization。Guardrails 是在 Agent 运行时建立的“不可越过的边界”，保护系统不被概率性输出破坏。

TypeProtection GoalExample
Input Guardrails阻止非法输入驱动 AgentPrompt Injection 检测、Size 限制、敏感数据脱敏
Decision Guardrails限制 Agent 规划与工具选择验证工具是否在白名单内、高危操作要求 Confirmation
Tool Guardrails控制副作用发生点Amount Limit、Tenant Isolation、Rate Limit
Output Guardrails控制最终用户感知Schema Validation、敏感信息泄露阻断、事实性约束

12. 电商客服案例：Guardrails 拦截

用户：“帮我把这笔订单退款，金额是 20,000。”

Agent 分析后决定调用 create_refund(order_id=123, amount=20000)。此时 Tool Guardrails 触发：

if refund_amount > 5000:
    reject_action()
    trigger_human_approval() // Strategy Fallback

系统阻止了 LLM 的直接操作，转而创建人工审核工单。这是生产环境可控的典型表现。

第六部分：Agent Runtime 控制

13. 防止 Agent 永不停止

由于 LLM 的自回归特性，Agent 极易陷入 while not done: think(); act() 的死循环，不断调用 Tool A 和 Tool B。必须强制设置 Max Steps、Max Tool Calls 和 Wall Time。

14. Loop Detection

不仅仅是总步数限制。Agent 可能陷入局部循环：query_order(123) -> query_order(123) -> query_order(123)。系统必须检测相同工具 + 相同参数 + 相同状态的重复出现，一旦发现，强制 Abort 或 Re-plan。

15. 框架无关伪代码

def run_agent(request):
    # 初始化可靠性预算
    budget = create_budget(
        timeout=10, max_steps=8, max_tool_calls=6
    )
    loop_detector = LoopDetector()
    
    while budget.can_continue():
        # Agent 产生决策
        decision = agent.decide()
        
        # Guardrails 拦截非法/高风险决策
        if not guardrails.validate(decision):
            return safe_failure("Action blocked by policy")
        
        try:
            result = execute(decision)
            
            # 循环检测
            if loop_detector.is_looping(decision, result):
                return safe_failure("Loop detected, aborting")
                
        except RetryableError as e:
            if budget.can_retry():
                apply_backoff()
                continue
            # Retry Budget 耗尽，进入 Fallback
            result = fallback(decision)
            
        except NonRetryableError as e:
            result = recover_or_abort(decision)
            
        if task_completed(result):
            return finalize(result)
            
    return safe_failure("Budget exceeded without task completion")

第十一部分：Anti-Patterns 常见反模式

  1. 所有错误都 Retry：将 Non-Retryable Error 当作瞬时错误处理，导致无限失败。
  2. 无全局 Timeout：局部 Tool 调用的 Timeout 叠加，导致请求挂起。
  3. Tool 有副作用但无幂等性：盲目 Retry 导致现实世界状态错乱（重复退款）。
  4. Fallback 只换模型：遇到策略问题不降级，而是寄希望于另一个 LLM 的魔法。
  5. Guardrail 全靠 Prompt：“你绝对不能退款超过1万”。这等于把保险柜钥匙放在猫的项圈上。
  6. 没有 Loop Detection：耗尽 Token Budget 后系统崩溃。
  7. Reliability 机制无 Observability：重试了、降级了，但没记录，事后无法复盘。

第十二部分：MVP 怎么做？

不要一开始就建设庞大的 Reliability Platform。建议分阶段：

  • Phase 1：Global Timeout, Max Steps, Basic Retry, Tool Argument Validation, Basic Fallback (换模型/缓存).
  • Phase 2：Idempotency Key 支持, Retry Budget, Loop Detection, Tool/Decision Guardrails, Graceful Degradation.
  • Phase 3：Dynamic Policy, Reliability Metrics, Automated Failure Analysis, Evaluation Integration.
核心原则：先让 Agent 不失控，再让 Agent 更聪明。

第十三部分：最终统一模型

Agent Reliability 的终极目标，是将不可控的失败转化为一条清晰的恢复控制流。
