RAG Evaluation：从“检索到了”到“回答正确”，Ragas 到底在评估什么？

一个 RAG 系统的评价，从来不是一个分数。它是一条从检索质量、接地性到答案质量的分层链路——而这条链路的起点，是承认 Recall 高不等于回答正确。

Section 01 · Why

为什么 RAG 需要 Evaluation，而不是“看起来对就行”

绝大多数 RAG 系统在 Demo 阶段都让人满意：换一个系统提示词、调一调 top_k、加一个 Reranker，看起来就“能用”。但只要把它推到真实的企业知识库 + 客服场景下，问题很快暴露——同一个问题今天回答对、明天回答错；改了 embedding 模型后，某类问题突然全部崩掉，而团队没有任何一种手段能在上线之前先发现。

这不是模型不够强的问题，而是缺一个工程化的反馈闭环。所谓 Evaluation，本质上要回答三个递进的问题：

Evaluation 的三问

① 系统现在到底怎么样？ —— 需要可量化的指标，而不是“感觉还行”。

② 这次改动变好了还是变差了？ —— 需要可比的实验，而不是发布后看用户投诉。

③ 如果某天突然变差，能不能在它影响用户之前被发现？ —— 需要可自动阻断的门禁，而不是事后复盘。

第一问是本篇的主题：我们要建立一套足以反映 RAG 真实质量的指标体系。后两问，是整个系列剩余三篇的任务——Regression Dataset、Eval Studio、Release Gate 与 CI/CD——它们都建立在第一问的指标之上。如果指标本身是错的、或不足以反映真实问题，后面的一切工程都会在一个有缺陷的地基上空转。

Section 02 · Retrieval Eval

Retrieval Evaluation：Hit Rate、MRR 与它们的盲区

RAG 的第一步是检索。对这一步的传统评测来自信息检索领域，最常用的两个指标是 Hit Rate（top-k 中是否至少命中一条相关文档）和 MRR（Mean Reciprocal Rank，第一条相关文档出现位置的倒数的均值）。它们非常便宜、确定、可离线批量跑，因此往往是大多数团队做 RAG 评测的起点。

Mean Reciprocal Rank
MRR = 1⁄|Q| · Σi=1|Q|  1⁄ranki
ranki 是第 i 个 Query 在 top-k 结果中第一条相关文档的位置；越靠前分越高。

这些指标擅长的事情很清楚：回答“检索器有没有把相关文档拉回来、拉得够不够靠前”。它们在调 embedding 模型、调 chunk 策略、调 Reranker 时是最直接的信号。

但它们有三块明显的盲区，而这恰恰是 RAG 区别于传统搜索的地方：

Retrieval 指标解决不了的三件事

1. 答案对不对，它看不见。 Retrieval 指标评的是“文档是否相关”，而用户最终消费的是 LLM 写出的句子。文档相关、答案仍然可以幻觉。

2. 生成器的退化，它发现不了。 即使你换掉 LLM、改坏 Prompt、把 temperature 调到 1.5，Retrieval 指标一动不动——它对生成侧的回归是盲的。

3. “相关”和“够用”是两件事。 一篇文档提到“可以退款”，但用户问的是“14 天内还能不能退”。文档高度相关，却少了那个关键限定词——Retrieval 指标满分，回答依然错。

换句话说，Retrieval 指标只对 RAG 链路的前半段负责。一旦进入生成阶段，评价的视角必须换一个坐标系。

Section 03 · The Gap

为什么 Recall 高 ≠ 回答正确

把盲区用一个具体例子钉死。还是企业知识库 + 客服场景：

Case · 退款政策

Question：“我在 14 天内买的会员还能退款吗？”

Retriever 拉回的 Context：“会员服务支持退款，退款将原路退回至支付账户，处理周期约为 3–5 个工作日。” —— Hit Rate ✓，MRR = 1.0，Retrieval 指标满分。

Answer（LLM 生成）：“可以的，14 天内购买的会员随时可以全额退款，3–5 个工作日内到账。” —— 看起来流畅、自信、用户满意。

事实：知识库里另一段明确写着“年付会员在购买后 7 天内可全额退款，超过 7 天不予退款。” 那条包含“14 天 / 7 天 / 例外”关键限定的 chunk，被 rank 3 之后截断，没进入 Context。

Retrieval 指标在这里给不出任何警报：top-1 文档确实“相关”（关键词全命中）。但从用户视角看，这是一次彻底的失败——客服给出了一个错误承诺，未来会变成工单甚至投诉。

失败点不止一个：

  • 检索侧：没把那条最关键的 chunk 召回进 top-k → 这是一个“覆盖不足”问题。
  • 生成侧：LLM 在 Context 缺失关键限定的情况下，没有承认“我不确定”，而是补了一句自信的错误陈述 → 这是一个“幻觉”问题。
  • 评价侧：如果只用 Retrieval 指标，这两类失败都被完美掩盖。

所以，一套合格的 RAG 评价体系必须至少覆盖两个独立层面：Retrieval Evaluation 与 Generation Evaluation。这正是本篇接下来要展开的分层模型。

Section 04 · Ragas

Ragas 指标体系总览

把上面两个视角填满，就是 Ragas 的核心贡献：它把 RAG 评测拆成了四条互补的指标——Context Recall、Context Precision、Answer Relevancy、Faithfulness——分别对应“检索拉全了没 / 检索排序优不优 / 答得切不切题 / 答得接不接地”四个独立问题。它们都不是简单的字符串匹配，而是通过结构化的 LLM 判分（或 embedding 相似度）将“判断”收敛成一个分数，从而可以批量、可重复地跑在数据集上saulius.io+1。

理解 Ragas 的关键，不是背公式，而是看清每条指标回答的是“哪一个失败模式”。下表把四个指标与它们各自能捕获的失败、各自解决不了的问题并排放在一起——这张表会在整个系列里被反复引用：

表 1 · Ragas 核心指标一览（本系列通用术语表）
指标评测层次回答的问题计算机制能否独立评出“正确”
Context Recall Retrieval 参考答案里的关键信息，Context 是否覆盖到了？ 把 Reference 拆成原子语句，逐条判“是否可归因到 Context”，取均值saulius.io 否，只评 Context 是否够用
Context Precision Retrieval 拉回来的 chunk 里，有多少真的对答题有用，且排得靠前？ 逐 chunk 判“有用/没用”，按 Average Precision 聚合（排名靠前的有用项权重更高）saulius.io 否，对排序敏感
Answer Relevancy Answer 答案是否直接回应了用户的意图？有没有答非所问 / 冗余？ 用 LLM 从 Answer 反向生成 N 个“它可能回应的问题”，与原 Question 做 embedding 余弦相似度取均值ragas.io 否，对事实错误无感
Faithfulness Groundedness 答案里的每一条陈述，是否都能被 Context 支撑？ 把 Answer 拆成原子 Claim，逐条 NLI 判“能否由 Context 推出”，求支撑比例ragas.io+1 否，只评接地性，不评对错

四条指标各自独立、互补，但都不能单独回答“答案是否正确”。要做到这件事，需要把指标两两组合、交叉判读——这正是接下来 Faithfulness 一节要展开的核心论点。

Section 05 · Deep Dive

Faithfulness 深入：它衡量的是“接住”，而不是“答对”

四个指标里，Faithfulness 在生产中最容易被误读、也最容易造成错误决策。它的定义极其朴素：

Faithfulness 的本质定义

一个 Answer 是 faithful 的，当且仅当它陈述的每一条 Claim，都能从 Context 中被推出。

它是一个 0 到 1 的连续量：被支撑的 Claim 数 ÷ 总 Claim 数ragas.io。任何一条超出 Context 的陈述——无论它是模型脑补的事实、错误的日期、还是一段“看起来很像会是真的”的政策细节——都会直接拉低分数。

Faithfulness Score
Faithfulness = | Σ supported-claims | ⁄ | total-claims |
两阶段计算：① 把 Answer 拆成原子化陈述（Claim Decomposition）；② 对每条陈述做 NLI 判断（Context 是否蕴含它），最后按支撑比例聚合ragas.io+1。

Faithfulness ≠ Correctness

这是本篇最重要的一句话。Faithfulness 衡量的是 “Answer 是否忠实于 Context”，而 Correctness 衡量的是 “Answer 是否与真实世界一致”。这两件事在 RAG 里是互相独立的——因为 Context 本身可能就是错的，或者不完整。让我们用两个反例把这一点钉死。

反例 A · Context 正确，Answer 仍然幻觉

Case A

Question：“公司的年假政策是什么？”

Context（检索正确，包含全部关键信息）：“员工入职满一年享有 10 天年假；满五年 15 天；未休年假可顺延至次年 3 月 31 日。”

Answer（LLM 生成）：“公司提供 10 天带薪年假， additionally 您还可以申请额外的带薪病假 15 天，且未休年假可无限期累积。”

结论：Context 错误，Answer 即使 100% 忠实，Faithfulness 仍然可以是满分，而 Correctness 依然为 0。Faithfulness 在这里没有报警——因为它的定义就决定了它只关心“是否接地”，不关心“接地的地方本身对不对”。

工程上Faithfulness 不可替代的作用

把两个反例并排看，会发现 Faithfulness 的真正价值不在于“评出好答案”，而在于它把“幻觉”这个模糊概念变成了一个可量化、可回归、可阻断的工程信号。在没有 Faithfulness 之前，团队只能通过用户投诉发现幻觉；有了它之后，幻觉率变成了一条曲线，可以放在 CI 报告里、可以设阈值、可以在 Prompt 改坏时第一时间看到分值下滑——这件事，是后续 Release Gate 和 CI/CD 整套体系能够成立的前提。

Faithfulness 解决不了的事

1. 它评不出 Context 错误。 反例 B 中它给满分。Context 是否过期、是否覆盖了参考答案，要靠 Context Recall / Context Precision。

2. 它评不出答案是否切题。 一段完全“基于 Context 编造出来”但答非所问的回答，Faithfulness 可以很高，需要 Answer Relevancy 补位。

3. 它评不出“缺失了什么”。 Faithfulness 是 Answer 视角的指标，Context 漏掉关键限定（如“仅年付会员适用”）它看不见。

Section 06 · Triad

RAG 质量三层模型：Retrieval · Groundedness · Answer

把上面的分析收拢，就得到本篇最核心的认知框架：RAG 的质量不是一维的，而是由三层独立、叠加、互相牵制的维度组成的。任何一层的失败，都会以完全不同的方式呈现，因此也需要完全不同的指标去测量。

读法举例：三个顶点如何互相解释

Faithfulness 低 + Context Recall 高 → 问题在生成器（Prompt / LLM / temperature），先调生成侧。

Faithfulness 高 + Answer Relevancy 低 → LLM 很“老实”但答非所问，可能是 Query 理解或 Prompt 指令问题。

Context Recall 低 + Faithfulness 高 → 检索没拉全关键信息，LLM 只能基于不完整的 Context 老实回答 → 答案会缺关键限定，属于检索层失败。

Context Precision 低 + Faithfulness 高 → 召回的无关 chunk 太多，LLM 被噪声干扰，潜在长尾错误风险高。

这套读法在日常调试里非常实用：看到分数异常，先用三角定位法判断问题出在哪一层，再决定是去调 Embedding、调 Reranker、调 top_k，还是去改 Prompt、换 LLM。它把“RAG 调优”从一个猜测游戏，变成了一个有诊断路径的工程问题。

Section 08 · Pipeline

RAG Evaluation Pipeline 与最小可用代码

把前面的认知落成一个可重复执行的工程流程，就是 Evaluation Pipeline。它的形状不复杂，但每一步的输入输出约定，决定了后续三篇能否顺利搭建出回归与门禁体系。

最小可用代码

下面这段 Python 代码用 Ragas 跑一个最小的评测，作为本系列后续所有实验的基线模板。它做的事很朴素：对每个 Evaluation Case，记录 Question、Context、Answer、Reference，然后让 Ragas 给出四条指标。

# pip install ragas datasets
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import (
    context_recall, context_precision,
    answer_relevancy, faithfulness,
)

# 1. Evaluation Dataset：来自被测 RAG 系统的一次 Evaluation Run
#    注意：contexts 必须是运行时真实拉回的 chunk，不能事后重建
data = {
    "question": [
        "年假可以累积到明年吗？",
        "出差住宿报销上限是多少？",
        "忘记密码怎么办？",
    ],
    "answer": [
        "可以累积，未休年假会顺延，且可无限期累积。",           # 含幻觉
        "国内一线城市每晚 800 元，其他城市 500 元。",
        "请通过企业门户自助重置，或联系 IT 服务台 8000。",
    ],
    "contexts": [
        ["员工手册 v2024：未休年假可顺延至次年 3 月 31 日，过期清零。",
         "HR 公告：本季度团建安排。"],                          # 含噪声 chunk
        ["报销政策：国内一线城市住宿上限 800 元/晚。"],            # 漏掉“其他城市”
        ["IT 服务：忘记密码可通过企业门户自助重置，或拨打 IT 服务台 8000。"],
    ],
    "reference": [
        "未休年假可顺延至次年 3 月 31 日，过期清零。",
        "国内一线 800 元/晚，其他城市 500 元/晚。",
        "通过企业门户自助重置，或联系 IT 服务台 8000。",
    ],
}
ds = Dataset.from_dict(data)

# 2. 一次 Evaluation Run：得到可报告、可比较、可归档的分数
result = evaluate(
    ds,
    metrics=[context_recall, context_precision, answer_relevancy, faithfulness],
)
print(result)

Section 09 · What's Next

留给我们的问题：那个判断，是谁做出的？

回到本篇开头那句朴素的定义——Faithfulness 的核心，是判断 “Answer 中的 Claim 是否被 Context 支撑”。把这句话展开，会立刻浮出一个此前我们一直默认、却从未追问的事实：

一个被默认了很久的前提

Claim 的拆分、NLI 的判断、“是否被支撑”这个二元决定——都不是规则计算的，而是又一次调用了一个 LLM。换句话说，我们在用一个大模型去评另一个大模型saulius.io。

这件事一旦被意识到，整套指标的地基就变得可疑起来：

如果一个 LLM 判断错了“这条 Claim 是否被 Context 支撑”，我们的 Faithfulness 分数就是错的——而所有依赖它的回归阈值、发布决策、Prompt 优化，都会跟着一起错。

更糟的是，这个“Judge LLM”会有它自己的系统性偏差：它可能对某类措辞宽容、对长 Context 失去注意力、对与自己风格相近的生成模型打分更高、对中文的细粒度否定词判断不稳。这些偏差不会以异常报错的形式出现，它们会安静地混在每一次评分里，伪装成“业务表现波动”。
