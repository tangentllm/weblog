为什么需要反馈回路？

传统的 RAG 系统是"静态"的——建好索引、写好 Prompt，之后就不再变化。但现实世界中，用户的需求和知识都在持续演进。一个今天表现良好的检索系统，明天可能因为新数据的加入而变得不够精准。

反馈回路（Feedback Loop）的核心思想很简单：让系统从自己的错误中学习。当用户对回答打分、留下评论时，这些信息可以被用来：

  • 调整检索分数——让高质量的文档在下次获得更高权重
  • 扩充向量索引——将优质 QA 对作为合成文档加入知识库
  • 形成闭环优化——每一次交互都让系统变得更好
💡 类比理解

想象一位图书管理员：起初他按固定分类法帮你找书。但渐渐地，他记住了"张教授喜欢人工智能方向的最新论文"、"李同学经常需要机器学习基础教材"。这些记忆让他下次推荐时更加精准——这就是反馈回路的力量。

这个循环的关键在于两个优化路径：

  1. 相关性调整（E）：用历史反馈调整当前检索结果的分数，无需修改索引
  2. 索引微调（F）：将高质量 QA 对注入向量库，永久改善检索质量

第一步：反馈收集机制

反馈收集是整个回路的起点。我们需要一个结构化的方式来记录用户对每次回答的评价：

def get_user_feedback(query, response, relevance, quality, comments=""):
    """格式化用户反馈为标准结构。

    Args:
        query: 用户的原始查询
        response: 系统生成的回复
        relevance: 相关性评分 (1-5)
        quality: 质量评分 (1-5)
        comments: 用户文字评论（可选）
    """
    return {
        "query": query,
        "response": response,
        "relevance": relevance,
        "quality": quality,
        "comments": comments,
        "timestamp": datetime.now().isoformat()
    }

评分采用 1-5 分制，直觉且易于用户操作：

评分相关性含义质量含义后续处理
1完全不相关无法使用降低权重
2部分相关需要大幅修改轻微降权
3基本相关基本可用基准线（modifier=1.1）
4高度相关质量良好加入索引
5完全精准完美回答加入索引
✅ 实际反馈示例

在我们的测试中，用户对"北京有哪些算力中心？"的回答给出了如下反馈：

  • 相关性评分：4 / 5
  • 质量评分：4 / 5
  • 评论："回答提到了北京人工智能公共算力中心，很有帮助，但希望能补充更多细节"

第二步：相关性分数调整

收集到反馈后，第一个优化路径是调整文档的相关性分数。核心思路：如果某篇文档在过去获得了高评价，那么它在未来的检索中应该获得更高的权重。

调整公式

分数调整的关键在于计算一个 modifier（修正因子）：

modifier = 0.5 + (avg_relevance / 5.0)

这个公式的精妙之处在于：

平均相关性评分modifier 值效果
1 分0.7降权 30%——文档被"惩罚"
2 分0.9降权 10%
3 分1.1加权 10%——基准线
4 分1.3加权 30%
5 分1.5加权 50%——文档被"奖励"

调整流程代码

def adjust_relevance_scores(query, results, feedback_data):
    """根据历史反馈调整检索结果的相关性分数。

    Args:
        query: 当前查询
        results: 原始检索结果 [(doc, score), ...]
        feedback_data: 历史反馈数据列表
    Returns:
        调整后的 [(doc, new_score), ...]
    """
    adjusted = []
    for doc, score in results:
        # 找到与该文档相关的历史反馈
        related_feedback = [
            fb for fb in feedback_data
            if fb["query"] == query
        ]

        if related_feedback:
            avg_relevance = sum(
                fb["relevance"] for fb in related_feedback
            ) / len(related_feedback)

            # 核心公式：modifier = 0.5 + (avg_relevance / 5.0)
            modifier = 0.5 + (avg_relevance / 5.0)
            new_score = score * modifier
        else:
            new_score = score  # 无反馈则保持原分

        adjusted.append((doc, new_score))

    return adjusted
⚠️ 注意：LLM 辅助判断

在实际应用中，查询很少完全相同。因此我们使用 LLM 来判断历史反馈是否与当前查询语义相关，而不是简单的字符串匹配。这将在第 5 节详细讨论。

第三步：索引微调——将优质 QA 注入向量库

第二个优化路径更加深远：将高质量的问答对作为"合成文档"永久加入向量库。这样，未来类似的查询可以直接检索到这些经过验证的知识。

实现代码

def fine_tune_index(current_store, chunks, feedback_data):
    """将高质量 QA 对作为合成文档加入向量库。

    Args:
        current_store: 当前向量存储
        chunks: 原始文档分块
        feedback_data: 历史反馈数据
    Returns:
        增强后的向量存储
    """
    # 筛选高质量反馈（评分 ≥ 4）
    high_quality = [
        fb for fb in feedback_data
        if fb["relevance"] >= 4 and fb["quality"] >= 4
    ]

    if not high_quality:
        return current_store

    # 构造合成文档
    synthetic_docs = []
    for fb in high_quality:
        enhanced_text = (
            f"Question: {fb['query']}\n"
            f"Answer: {fb['response']}"
        )
        synthetic_docs.append({
            "text": enhanced_text,
            "metadata": {
                "type": "synthetic_qa",
                "relevance_score": 1.2,  # 加权，优先检索
                "source": "user_feedback"
            }
        })

    # 将合成文档加入向量库
    new_store = add_documents(current_store, synthetic_docs)
    return new_store
💡 为什么用 "Question: ... Answer: ..." 格式？

这种格式让向量检索能够同时匹配问题语义和答案语义。当未来用户提出类似问题时，"Question:" 部分提供语义锚点，"Answer:" 部分提供精准内容。relevance_score=1.2 的加权确保合成文档在检索中获得优先地位。

LLM 反馈相关性评估

一个关键挑战：用户的查询很少完全相同。"北京有哪些算力中心？"和"北京算力基础设施情况如何？"语义相近但文字不同。我们需要 LLM 来判断历史反馈是否与当前查询相关。

def assess_feedback_relevance(query, doc_text, feedback):
    """用 LLM 评估历史反馈与当前查询的相关性。

    Args:
        query: 当前用户查询
        doc_text: 检索到的文档文本
        feedback: 历史反馈记录
    Returns:
        bool: 反馈是否与当前查询相关
    """
    prompt = f"""判断以下历史反馈是否与当前查询相关：

当前查询：{query}
文档内容：{doc_text[:200]}...
历史问题：{feedback['query']}
历史评分：相关性 {feedback['relevance']}/5

请回答：这个历史反馈对回答当前查询是否有参考价值？
只回答 YES 或 NO。"""

    response = llm.invoke(prompt)
    return "YES" in response.upper()

这个函数在 adjust_relevance_scores 中被调用，替代简单的字符串匹配，实现了语义级别的反馈关联。

核心代码提炼

下面是反馈回路系统的完整核心流程，将三个关键函数串联起来：

class FeedbackLoopRAG:
    """带反馈回路的 RAG 系统。"""

    def __init__(self, vector_store, llm):
        self.vector_store = vector_store
        self.llm = llm
        self.feedback_history = []

    def query_with_feedback(self, query):
        """执行查询并收集反馈。"""
        # 1. 检索（带分数调整）
        raw_results = self.vector_store.similarity_search_with_score(query)
        adjusted_results = adjust_relevance_scores(
            query, raw_results, self.feedback_history
        )

        # 2. 生成回复
        context = "\n".join(doc for doc, _ in adjusted_results[:3])
        response = self.llm.invoke(
            f"基于以下上下文回答问题：\n{context}\n\n问题：{query}"
        )

        return response

    def submit_feedback(self, query, response, relevance, quality, comments=""):
        """提交反馈并触发优化。"""
        # 1. 记录反馈
        fb = get_user_feedback(query, response, relevance, quality, comments)
        self.feedback_history.append(fb)

        # 2. 微调索引（如果评分足够高）
        self.vector_store = fine_tune_index(
            self.vector_store,
            chunks=None,
            feedback_data=self.feedback_history
        )

        return {
            "feedback_recorded": True,
            "index_updated": relevance >= 4 and quality >= 4,
            "total_feedback_count": len(self.feedback_history)
        }

工程实践建议

反馈收集策略

  • 降低反馈门槛：提供简单的 👍/👎 按钮，可选填文字评论
  • 适时请求评分：在用户复制回复内容或停留较长时间后弹出评分
  • 匿名 vs 实名：实名反馈可追踪用户偏好，但需考虑隐私合规

防止反馈回路退化

⚠️ 反馈回路的潜在风险

如果恶意用户持续提交低质量反馈，可能导致系统"学坏"。建议：

  • 设置反馈权重上限，单条反馈不能过度影响系统
  • 对合成文档数量设置上限（如不超过原始文档的 20%）
  • 定期清理低置信度的合成文档
  • 引入反馈可信度评分（基于用户历史反馈质量）

性能与存储

考量建议
反馈存储使用独立数据库，按查询哈希索引
分数调整延迟LLM 评估反馈相关性约 200-500ms，可缓存
索引膨胀合成文档设置 TTL（如 30 天），过期自动清理
反馈聚合同一查询的多次反馈取平均值，减少噪声

下一篇预告：自适应检索

反馈回路让系统从历史反馈中学习。但有时候，系统需要在当前查询中就做出智能决策——是否需要检索？检索几次？检索多少文档？

第 12 篇《自适应检索》将探讨如何让 RAG 系统根据查询的复杂度和特征，动态调整检索策略：

  • 简单事实查询 → 单次检索，快速响应
  • 复杂分析查询 → 多轮迭代检索，逐步深入
  • 模糊查询 → 先澄清再检索
