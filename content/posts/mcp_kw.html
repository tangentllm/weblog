1什么是 MCP？

MCP（Model Context Protocol）是由 Anthropic 于 2024 年 11 月发布的开放标准协议，专门用于解决 AI 模型与外部工具、数据源之间的集成问题。它定义了一套统一的、语言无关的通信规范，让任何 AI 应用都能通过标准化接口连接任意数量的外部能力。

简单类比：如果 LLM 是大脑，MCP 就是神经系统的统一接口标准——就像 USB-C 统一了设备充电接口，MCP 统一了 AI 模型与工具世界的连接方式。

🎯 一句话定义：MCP 是一个开放协议，标准化了 LLM 应用程序如何向外部系统（工具、数据源、服务）提供上下文的方式。它让 AI 应用开发从「逐个定制集成」变为「一次接入，处处可用」。

MCP 提供的三大原语

MCP 协议围绕三个核心概念构建，服务端向客户端暴露能力：

  • Tools（工具）：可被 LLM 调用执行的函数，如查天气、执行代码、写入数据库。类似 Function Calling，但跨应用标准化。
  • Resources（资源）：可供 LLM 读取的数据来源，如文件、数据库记录、API 响应。类似 REST 资源，提供上下文信息。
  • Prompts（提示模板）：预定义的提示词模板，帮助用户以标准化方式与特定工具交互。

2为什么需要 MCP？

在 MCP 出现之前，每当一个 AI 应用需要接入外部服务，开发者就需要从头写集成代码：自定义鉴权、自定义数据格式转换、自定义错误处理……这导致了经典的 N×M 集成困境。

图 1 — 传统集成方式：N×M 混乱

😫 痛点：3 个 AI × 4 个服务 = 12 套完全不同的集成代码。每个团队都在重复造轮子：自定义 Schema 映射、鉴权逻辑、错误处理、版本管理……每次新增一个工具，工作量翻倍。

MCP 的核心价值在于将这个 N×M 问题降维为 N+M 问题——每个 AI 应用只需实现一次 MCP Client，每个外部服务只需实现一次 MCP Server，二者通过统一协议自由组合。

图 2 — MCP 标准化：N+M 清晰架构

3MCP 核心架构

MCP 定义了一个清晰的三角色模型：Host、Client、Server。理解这三者的关系是掌握 MCP 的关键。

图 3 — MCP 三层架构详解

🔑 关键设计：1 Client = 1 Server。一个 MCP Client 只维护与一个 MCP Server 的有状态会话。如果 Host 需要连接 5 个 Server，就需要维护 5 个 Client 实例。这保证了会话的隔离性和安全性。

📌 重要澄清：图中 LLM 与 MCP Client 之间的箭头表示“业务逻辑协调”而非 LLM 直接调用 Client。实际实现中，LLM（如 Claude API）仅返回 tool_use 指令，由 Host 代码（如 run_agent 函数）负责调用 MCP Client 执行工具。LLM 本身不感知 MCP 协议的存在。

4通信协议与传输层

MCP 的消息格式基于 JSON-RPC 2.0，但支持两种物理传输层，适用于不同场景：

图 4 — 两种传输方式对比

JSON-RPC 2.0 消息格式

MCP 所有通信均使用 JSON-RPC 2.0 格式。以下是一次工具调用的完整消息交换：

Client → Server：调用工具
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "北京", "unit": "celsius" }
  }
}
Server → Client：返回结果
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      { "type": "text", "text": "北京当前天气：晴，25°C，湿度 45%" }
    ],
    "isError": false
  }
}

5Function Calling 不够用吗？

这是最常见的疑问：OpenAI 的 Function Calling / Anthropic 的 Tool Use 已经能让模型调用工具了，为什么还需要 MCP？

简短回答：Function Calling 解决的是「模型怎么调用」，MCP 解决的是「工具怎么定义、部署、共享」。两者层次不同，MCP 是对 Function Calling 的补充和架构升级，而不是替代。

对比维度 Function Calling / Tool Use MCP
工具定义位置 硬编码在应用代码中，每个应用单独维护 独立 MCP Server，可被任意 Host 发现和调用
工具复用性 不可复用，A 应用写的工具 B 应用不能直接用 一个 MCP Server 可被多个 Host/Client 共享
工具发现机制 无标准，需手动传入 schema 标准化 tools/list 接口，Client 自动发现
工具服务端会话状态 无，每次调用独立（工具内自己维护状态） 有状态会话，Server 可跨调用复用资源（如 DB 连接池）
能力类型 仅工具调用 工具 + 资源（文件/DB） + 提示模板
模型绑定 绑定特定模型 API（OpenAI / Anthropic） 模型无关，任何支持 MCP 的 Client 均可使用
跨进程通信 无，工具函数在同一进程内 支持跨进程（stdio）和跨网络（HTTP）
安全隔离 工具代码运行在主应用进程中 Server 独立进程运行，天然沙箱隔离
实现复杂度 简单，直接定义 JSON schema + 函数 需要实现 Server + Client，有一定学习成本

💡 澄清：表格中的“状态”是指工具服务端能否在多次调用之间保持内部状态（例如数据库连接池）。LLM 多轮对话的上下文记忆由 Host 的 messages 列表维护，与是否使用 MCP 无关。MCP 不会让 LLM 的对话变得“更有状态”。

什么时候用哪个？

  • 快速原型 / 单体应用 / 工具少于 5 个：直接用 Function Calling，更简单。
  • 工具需要跨多个 AI 应用共享：建 MCP Server，一劳永逸。
  • 工具涉及敏感操作（文件系统、数据库）：用 MCP，进程隔离更安全。
  • 构建 AI 工具平台 / SaaS 集成层：MCP 是正确的架构选择。

6动手写一个 MCP Server

以下是一个完整的 Python MCP Server 实现——一个简单的天气查询服务。使用官方 mcp SDK（pip install mcp）。

weather_server.py — 完整 MCP Server 实现python
# 安装: pip install mcp httpx
import asyncio
import httpx
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.server.models import InitializationOptions
import mcp.types as types

# ① 创建 Server 实例，赋予名称（用于 Client 识别）
app = Server("weather-mcp-server")

# ② 声明该 Server 提供哪些工具（Tool Discovery）
@app.list_tools()
async def list_tools() -> list[types.Tool]:
    return [
        types.Tool(
            name="get_weather",
            description="获取指定城市的当前天气信息，包括温度、湿度、风速",
            inputSchema={
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市名称，如：北京、上海、纽约"
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "description": "温度单位，默认摄氏度",
                        "default": "celsius"
                    }
                },
                "required": ["city"]
            }
        ),
        types.Tool(
            name="get_forecast",
            description="获取城市未来 3 天的天气预报",
            inputSchema={
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"}
                },
                "required": ["city"]
            }
        )
    ]

# ③ 实现工具的实际执行逻辑（Tool Execution）
@app.call_tool()
async def call_tool(name: str, arguments: dict) -> list[types.TextContent]:
    if name == "get_weather":
        city = arguments["city"]
        unit = arguments.get("unit", "celsius")
        
        # 真实场景中这里调用气象 API（如 OpenWeatherMap）
        # 此处用模拟数据演示
        weather_data = {
            "北京": {"temp": 25, "humidity": 45, "wind": "东南风 3级", "desc": "晴"},
            "上海": {"temp": 28, "humidity": 72, "wind": "东风 2级",  "desc": "多云"},
        }
        
        data = weather_data.get(city, {"temp": 20, "humidity": 60, "wind": "微风", "desc": "晴"})
        temp = data["temp"] if unit == "celsius" else data["temp"] * 9/5 + 32
        unit_str = "°C" if unit == "celsius" else "°F"
        
        result = (
            f"📍 {city} 当前天气\n"
            f"🌤 天气状况：{data['desc']}\n"
            f"🌡 温度：{temp}{unit_str}\n"
            f"💧 湿度：{data['humidity']}%\n"
            f"💨 风况：{data['wind']}"
        )
        return [types.TextContent(type="text", text=result)]
    
    elif name == "get_forecast":
        city = arguments["city"]
        forecast = f"📅 {city} 未来 3 天预报\n明天：晴，22-30°C\n后天：多云，20-27°C\n大后天：小雨，18-24°C"
        return [types.TextContent(type="text", text=forecast)]
    
    else:
        raise ValueError(f"未知工具: {name}")

# ④ 启动 Server（stdio 模式，被 Host 作为子进程启动）
async def main():
    async with stdio_server() as (read_stream, write_stream):
        await app.run(
            read_stream, write_stream,
            InitializationOptions(server_name="weather-mcp-server")
        )

if __name__ == "__main__":
    asyncio.run(main())

⚙️ Server 的核心职责只有两件事：
1. list_tools() — 告诉 Client 我有什么工具、每个工具的参数 Schema
2. call_tool() — 接收参数，执行业务逻辑，返回结果

7动手写一个 MCP Client（接入 Claude）

Client 负责启动 Server、发现工具、将工具 Schema 传给 LLM、处理工具调用闭环。

mcp_client.py — 完整 Client + Claude 集成（修复版）python
# 安装: pip install mcp anthropic
import asyncio, json
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client
import anthropic
from anthropic.types import TextBlock, ToolUseBlock

# ① 配置 MCP Server 的启动参数（stdio 模式）
server_params = StdioServerParameters(
    command="python",
    args=["weather_server.py"],
    env=None  # 可传入环境变量（如 API Key）
)

async def run_agent(user_query: str):
    # ② 建立与 MCP Server 的连接
    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            
            # ③ 初始化会话（握手 + 能力协商）
            await session.initialize()
            
            # ④ 发现 Server 提供的所有工具
            tools_result = await session.list_tools()
            
            # ⑤ 将 MCP 工具 Schema 转换为 Anthropic Tool Use 格式
            anthropic_tools = [
                {
                    "name": tool.name,
                    "description": tool.description,
                    "input_schema": tool.inputSchema
                }
                for tool in tools_result.tools
            ]
            
            print(f"✅ 已发现 {len(anthropic_tools)} 个工具: {[t['name'] for t in anthropic_tools]}")
            
            # ⑥ 初始化 Claude 客户端与消息历史
            client = anthropic.Anthropic()
            messages = [{"role": "user", "content": user_query}]
            
            # ⑦ 多轮工具调用循环（Agentic Loop）
            while True:
                response = client.messages.create(
                    model="claude-3-opus-20240229",
                    max_tokens=1000,
                    tools=anthropic_tools,
                    messages=messages
                )
                
                # 收集助手回复中的文本和工具调用
                assistant_text = []
                tool_uses = []
                for block in response.content:
                    if isinstance(block, TextBlock):
                        assistant_text.append(block.text)
                    elif isinstance(block, ToolUseBlock):
                        tool_uses.append(block)
                
                # 如果有文本，先打印（Claude 可能在调用工具前说了话）
                if assistant_text:
                    print(f"\n🤖 Claude: {''.join(assistant_text)}")
                
                # 如果没有工具调用，对话结束
                if not tool_uses:
                    break
                
                # 处理所有工具调用
                tool_results = []
                for tool_use in tool_uses:
                    print(f"🔧 调用工具: {tool_use.name}({json.dumps(tool_use.input, ensure_ascii=False)})")
                    
                    # 通过 MCP Client 调用 MCP Server 上的工具
                    result = await session.call_tool(
                        tool_use.name,
                        arguments=tool_use.input
                    )
                    
                    # 提取 content 文本（MCP 可能返回多个内容块，这里全部拼接）
                    content_text = ""
                    for content_item in result.content:
                        if content_item.type == "text":
                            content_text += content_item.text
                    
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": tool_use.id,
                        "content": content_text   # Anthropic 允许直接字符串
                    })
                
                # 将助手的原始回复（含 tool_use）和工具结果添加到消息历史
                messages.append({"role": "assistant", "content": response.content})
                messages.append({"role": "user", "content": tool_results})
            
            print("\n🏁 对话结束")

if __name__ == "__main__":
    asyncio.run(run_agent("北京今天天气怎么样？顺便告诉我未来 3 天的预报"))

9MCP 的局限性

MCP 是一个优秀的架构标准，但在实际使用中仍有若干值得注意的局限性：

🔐 安全与授权体系尚未完善

MCP 规范对认证和权限控制的定义仍较模糊。HTTP 模式依赖开发者自行实现 OAuth / JWT，存在误操作风险。恶意 MCP Server 可能成为攻击面。

📶 有状态连接难以水平扩展

MCP 会话是有状态的，每个 Client 需持续维持与 Server 的连接。多实例部署时需要会话亲和性（Sticky Session），给云原生横向扩展带来挑战。

🌐 生态分散，标准碎片化

各大厂商（OpenAI、Google）有自己的工具调用方案，MCP 生态主要以 Anthropic 主导的客户端为主，跨模型兼容性参差不齐。

⚡ 性能开销不可忽视

每次工具调用都需经过进程通信（stdio）或 HTTP 往返（SSE），相比直接函数调用有额外延迟。高频率调用场景（如每秒数百次）需要特别评估。

☁️ 无服务器（Serverless）环境支持不友好

stdio 模式无法在 AWS Lambda、Cloudflare Workers 等环境中运行（不允许长期子进程）。HTTP+SSE 模式虽然可能，但要求长连接，与 Serverless 的“按需启动、用完即毁”模型冲突。这是当前 MCP 落地的一个显著障碍。

📏 大规模工具集的上下文压力

当 MCP Server 暴露数十个工具时，所有工具 Schema 都需要传入 LLM 上下文，消耗大量 Token。如何做工具的动态发现和懒加载是待解问题。

🧭 综合建议：MCP 非常适合构建工具生态和多应用共享的能力层，但对于小规模、单一应用、工具少于 10 个的场景，直接用 Function Calling 更简单省力。在生产环境部署 MCP 时，务必重视认证、监控、重试机制的补全，并评估 Serverless 环境的兼容性。

10展望与未来

MCP 仍在快速演进中，以下方向值得关注：

🌐

标准化的 MCP 授权框架

OAuth 2.0 集成进 MCP 规范，让工具访问控制更安全、标准化。

🤖

Multi-Agent 协调

MCP 扩展为 Agent 间通信协议，支持 Agent A 直接调用 Agent B 的能力。

⚡

流式工具响应

MCP 支持工具结果的流式返回，适合长时间运行任务（如代码执行、文件处理）的实时进度推送。

🔌

浏览器原生支持

主流浏览器内置 MCP Client，让 Web 应用无缝接入本地工具链。

🏪

MCP 工具市场

类似 npm/PyPI 的 MCP Server 注册中心，标准化安装、版本管理和发现流程。

🧠

模型无关标准

OpenAI、Google 等厂商接受 MCP 作为跨模型工具调用标准，终结碎片化。

🚀 总结：MCP 代表了 AI 工具集成从「手工作坊」走向「工业标准」的重要一步。它不是银弹，但它是让 LLM 真正融入软件生态的关键基础设施。理解 MCP 的架构与边界，是每一位 AI 工程师的核心竞争力之一。
