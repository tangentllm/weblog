一、问题动机：分块丢了"主题"怎么办？

在前几篇中，我们陆续用重叠分块（第 2 篇）、切块大小调优（第 3 篇）、上下文邻居检索（第 4 篇）改善了检索质量。但这些方案都围绕一个假设：文本块本身的内容足以表达它的语义。

现实往往不是这样。考虑一个 1000 字符的文本块，它可能从某段话的中间开始，缺少主语、缺少主题句。当你把它送入嵌入模型时，向量反映的是一段"无头"文本的语义——这显然不够准确。

⚠️ 类比理解

想象你在书店找书。管理员不告诉你书名，只让你随机翻开一页读一段话，然后让你判断"这本书是不是你要找的"。如果你先看到书名——哪怕只是一句话的标题——你的判断会准确得多。

上下文片段标题（Context Chunk Headers, CCH）的核心思路就是：在嵌入每个块之前，先用 LLM 为它生成一个描述性标题，然后把标题和正文分别嵌入，检索时同时匹配标题和正文，取平均相似度排序。

二、朴素 RAG vs CCH RAG：架构对比

❌ 朴素 RAG

  • 每个块只有一个向量（正文嵌入）
  • 检索只看正文相似度
  • 块缺少"主题标签"，语义表达不完整
  • 当块从段落中间开始时，语义更加模糊

✅ CCH RAG

  • 每个块有两个向量（正文嵌入 + 标题嵌入）
  • 检索同时计算正文相似度 + 标题相似度，取平均
  • 标题充当"语义锚点"，浓缩了块的主题
  • 即使正文被截断，标题仍能传达核心主题

三、核心原理：LLM 生成标题 + 双重嵌入检索

CCH 的创新可以拆成两个关键步骤：

3.1 分块阶段：为每个块生成描述性标题

对每个文本块，调用 LLM（本 notebook 使用 gpt-4o）生成一个简洁、信息丰富的标题。这个标题相当于给块打了一个语义标签。

原始文本块 (1000 字符)
┌──────────────────────────────────────────────────────┐
│ systems. Explainable AI (XAI)                        │
│ techniques aim to make AI decisions more...          │
│ Privacy and Data Protection                          │
│ AI systems often rely on large amounts of data...    │
│ ...                                                  │
│ Chapter 20: Building Trust in AI                     │
│ Transparency and Explainability                      │
│ ...                                                  │
└──────────────────────────────────────────────────────┘
                        │
                        ▼  LLM (gpt-4o)
                        │
┌──────────────────────────────────────────────────────┐
│ 生成标题:                                             │
│ "Building Trust in AI: Explainability, Privacy,      │
│  and Accountability"                                  │
└──────────────────────────────────────────────────────┘
图 2：LLM 从一段"无头"文本中提炼出描述性标题，作为该块的语义锚点

3.2 检索阶段：双重相似度融合

检索时，对用户查询分别计算它与正文嵌入和标题嵌入的余弦相似度，然后取算术平均值作为最终排序分数。

flowchart TD Q["用户查询"] --> QE["查询嵌入"] QE --> ST["sim_text = cos(查询, 正文向量)"] QE --> SH["sim_header = cos(查询, 标题向量)"] ST --> AVG["avg_sim = (sim_text + sim_header) / 2"] SH --> AVG AVG --> SORT["按 avg_sim 降序排序"] SORT --> TOP["返回 Top-K 个块"] style AVG fill:#1f6feb,stroke:#388bfd,color:#fff style TOP fill:#238636,stroke:#3fb950,color:#fff
图 3：双重相似度融合——查询同时匹配正文和标题，取平均后排序
💡 为什么取平均而不是拼接？

拼接（concat）会让标题向量在整体表示中占比过小（标题通常只有几个词，正文有几百个词）。取平均则让标题和正文权重相等，确保标题的语义信号不会被正文淹没。这是一种简单但有效的融合策略。

五、代码解读：LLM 生成块标题

这是 CCH 方案最核心的函数——用 gpt-4o 为每个文本块生成一个简洁标题：

def generate_chunk_header(chunk, model="gpt-4o"):
    """使用 LLM 为给定的文本块生成描述性标题。"""
    system_prompt = "Generate a concise and informative title for the given text."

    response = client.chat.completions.create(
        model=model,
        temperature=0,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": chunk}
        ]
    )
    return response.choices[0].message.content.strip()
🔍 设计要点
  • temperature=0：确保标题生成的一致性，同样的块总是得到同样的标题
  • system prompt 极简：只要求"简洁且有信息量的标题"，不做过多约束
  • 使用 gpt-4o：标题生成需要较强的理解和概括能力，gpt-4o 比 gpt-3.5-turbo 更擅长此任务

实际生成的标题示例：

文本块内容（前几个词） LLM 生成的标题
Understanding Artificial Intelligence... Chapter 1: Introduction... "Introduction to Artificial Intelligence: Historical Context and Development"
systems. Explainable AI (XAI) techniques aim to... "Building Trust in AI: Explainability, Privacy, and Accountability"
inability. Many AI systems, particularly deep learning... "Challenges and Ethical Concerns in AI Development and Deployment"

可以看到，即使文本块从句子中间开始（如"systems."、"inability."），LLM 仍然能准确提炼出该块的核心主题。

六、代码解读：带标题的分块流程

将分块和标题生成整合到一个函数中：

def chunk_text_with_headers(text, n, overlap):
    """将文本分割为片段，并为每个片段生成标题。"""
    chunks = []
    for i in range(0, len(text), n - overlap):
        chunk = text[i:i + n]
        header = generate_chunk_header(chunk)  # 🌟 关键：逐块调用 LLM
        chunks.append({"header": header, "text": chunk})
    return chunks

调用方式：

text_chunks = chunk_text_with_headers(extracted_text, 1000, 200)
# 42 个块 → 42 次 LLM 调用 → 42 个标题
⚠️ 成本提醒

每个块都要调用一次 gpt-4o。42 个块 = 42 次 API 调用。对于大文档，这部分成本和时间不可忽视。notebook 中 42 个块的嵌入耗时约 52 秒（含标题生成 + 嵌入），平均每个块约 1.26 秒。在生产环境中，可以考虑批量生成标题或使用更便宜的模型。

七、代码解读：双重嵌入创建

与朴素 RAG 不同，CCH 为每个块创建两个嵌入向量——一个给正文，一个给标题：

def create_embeddings(text, model="text-embedding-ada-002"):
    """为给定文本创建嵌入向量。"""
    response = client.embeddings.create(model=model, input=text)
    return response.data[0].embedding
embeddings = []
for chunk in tqdm(text_chunks, desc="Generating embeddings"):
    text_embedding = create_embeddings(chunk["text"])       # 正文嵌入
    header_embedding = create_embeddings(chunk["header"])   # 标题嵌入
    embeddings.append({
        "header": chunk["header"],
        "text": chunk["text"],
        "embedding": text_embedding,          # 正文向量
        "header_embedding": header_embedding   # 标题向量
    })
每个块的数据结构变化：

└──────────────────────────────────┘

CCH RAG:

八、代码解读：双重相似度检索（核心）

这是 CCH 的第二个关键差异。检索函数同时计算查询与正文、查询与标题的余弦相似度，然后取平均：

def semantic_search(query, chunks, k=5):
    """基于双重相似度检索最相关的文本块。"""
    query_embedding = create_embeddings(query)
    similarities = []

    for chunk in chunks:
        # 查询 vs 正文
        sim_text = cosine_similarity(
            np.array(query_embedding), np.array(chunk["embedding"])
        )
        # 查询 vs 标题
        sim_header = cosine_similarity(
            np.array(query_embedding), np.array(chunk["header_embedding"])
        )
        # 🌟 关键：取平均
        avg_similarity = (sim_text + sim_header) / 2
        similarities.append((chunk, avg_similarity))

    similarities.sort(key=lambda x: x[1], reverse=True)
    return [x[0] for x in similarities[:k]]
💡 直觉理解

假设查询是"什么是可解释 AI？"。某个块的正文中确实提到了 XAI，但只有一两句话（sim_text = 0.82）。而它的标题是"Building Trust in AI: Explainability, Privacy, and Accountability"——几乎就是查询的"完美摘要"（sim_header = 0.91）。平均后 avg_sim = 0.865，比只看正文的 0.82 更高，这个块更容易被检索到。

九、代码解读：回复生成

将检索到的块以"标题 + 正文"的格式拼接成 prompt：

user_prompt = "\n".join([
    f"Header: {chunk['header']}\nContent:\n{chunk['text']}"

注意 prompt 中显式包含了 Header: 字段。这不仅仅是装饰——它让 LLM 在生成回答时也能"看到"每个块的标题，从而更好地理解上下文的主题方向。

十三、优缺点与适用场景

✅ 优点

  • 语义锚点：标题浓缩了块的核心主题，弥补了正文截断导致的信息丢失
  • 检索精度提升：双重匹配比单一匹配更能抓住相关块
  • 实现简单：核心改动只是"多调一次 LLM 生成标题"+"检索时多算一次相似度"
  • 对 LLM 生成友好：prompt 中包含标题，帮助 LLM 更快理解上下文方向
  • 可与其他技术叠加：可与重叠分块、邻居检索、重排序等组合使用

❌ 缺点

  • 额外 API 成本：每个块需要一次 gpt-4o 调用来生成标题
  • 索引时间增加：标题生成 + 双重嵌入，索引构建时间翻倍以上
  • 标题质量依赖 LLM：如果 LLM 生成了不准确的标题，反而会误导检索
  • 存储开销增加：每个块多存一个标题字符串 + 一个 1536 维向量
  • 平均融合的局限：简单平均假设标题和正文同等重要，但某些场景下正文可能更关键

适用场景

✅ 适合 ❌ 不适合
长文档、多主题文档（每块主题差异大） 短文档或单一主题文档（标题区分度低）
块从段落中间开始的情况多 块天然以标题/完整段落开头
对检索精度要求高，可接受额外成本 对延迟和成本极度敏感的实时场景
文档结构松散、缺少显式章节标题 已有良好结构化标题的文档（可直接用原标题）

十四、本篇小结

CCH（Context Chunk Headers）的核心思想可以用一句话概括：

🎯 核心 takeaway

给每个文本块取个"名字"。标题就像书的封面——即使你只看到封面，也能大致判断这本书是不是你要找的。用 LLM 为每个块生成标题，然后在检索时同时匹配标题和正文，让"语义锚点"帮你找到更精准的上下文。

技术要点回顾：

  1. LLM 生成标题：用 gpt-4o 为每个块生成描述性标题（42 块 = 42 次调用）
  2. 双重嵌入：正文和标题分别用 text-embedding-ada-002 嵌入
  3. 双重相似度：检索时计算 query 与正文、query 与标题的余弦相似度，取算术平均
  4. 评估提升：相同问题，分数从第 4 篇的 0.5 提升到 1.0

本篇的 CCH 技术与第 4 篇的上下文邻居检索并不冲突——你完全可以同时使用"邻居扩展 + 标题增强"，两者从不同角度改善检索质量。后续篇章中我们还会看到更多可以叠加的优化手段。
