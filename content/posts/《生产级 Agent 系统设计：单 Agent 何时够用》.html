01

为什么很多 Agent 系统一开始就做复杂了？

先看一个真实感很强的场景。产品经理提了一个需求：

用户："帮我分析一下最近新能源汽车行业的市场情况，并给出投资建议。"

开发团队开会，很快画出了这样一张架构图：

Planner Agent ↓ Research Agent ↓ Search Agent ↓ Data Agent ↓ Analysis Agent ↓ Writer Agent

六个 Agent，链路清晰，每个都有"专家"身份。评审时大家频频点头：这很 Agentic。但有一个问题很少被认真问过：

这个问题真的需要 6 个 Agent 吗？

事实上，一个 Agent 挂上几个 Tools，大概率就能把这个任务做到可用水平。因此真正的问题不是"Multi-Agent 能不能做"——它能做，只是更贵、更慢、更难调试。真正的问题是：

引入 Multi-Agent 之后，到底解决了什么单 Agent 无法很好解决的问题？

如果这个问题答不上来，那么引入 Multi-Agent 的唯一收益就是架构图看起来更先进。而代价——延迟、Token 成本、故障面、调试难度、评估复杂度——全都要在生产环境里真实支付。

本文的目的，是给出一套可以在架构评审中实际使用的判断方法：什么时候一个 Agent 就够了，什么信号出现时才应该拆分。

02

先定义：什么才是 Single Agent？

很多人对 Single Agent 的理解是"一个简单的 LLM 循环"。这是错误的起点。从架构角度看，一个生产级 Single Agent 是这样的：

必须强调一个事实：

Single Agent ≠ 简单系统。

一个单 Agent 系统完全可以同时具备：多工具、RAG、长期 Memory、Planning、状态机、重试策略、输入输出 Guardrails、离线评估体系、完整的 Observability。这些能力没有任何一项"必须"通过拆分 Agent 来获得。

因此，判断系统中 Agent 数量的正确依据不是"这个系统有多少能力"，而是：

这些能力是否需要被隔离？——职责、上下文、权限、模型、故障边界。如果不需要隔离，所有能力都可以挂在一个 Agent 上；如果需要隔离，才是拆分 Agent 的开始。

03

Single Agent 真正适合解决什么问题？

以下四类场景，Single Agent 通常是正确答案，而且不是"勉强够用"，而是最优解。

3.1 工具数量有限且目标一致

Agent ├── Search ├── RAG ├── Database └── Calculator

四个工具功能不同，但服务于同一个任务目标。模型的 Tool Selection 负担很轻（通常 10 个以内的工具，主流模型的选择准确率都足够高），Tool Description 的上下文开销可以忽略。这种情况下增加一个 Tool 的成本远低于增加一个 Agent。

3.2 任务目标单一

"查询客户订单并判断是否满足退款条件。"

这是一个边界清晰、可完整描述的业务目标。没有多角色博弈，没有多阶段异构处理，没有职责冲突。一个 Agent 端到端处理，意味着状态在同一个 Context 里流转，没有序列化损耗，没有中间结果的信息丢失。

3.3 决策链相对短

理解请求 → 查询数据 → 调用工具 → 生成答案

如果任务的决策路径基本是线性的，拆分 Agent 只会引入额外的调度开销和错误传播点。Agent 化不等于智能化——把一条线性链路拆成五个 Agent，每个 Agent 做的事情并没有变多，只是中间多了四次 LLM 调用。

3.4 不存在明显的专业边界

用户问题 ↓ 客服 Agent ├── 查询订单 ├── 查询物流 ├── 查询优惠 └── 创建售后

查询订单和查询物流用的是不同的 API，但它们属于同一个业务域——Customer Service Domain。共享同一套语气规范、同一套用户上下文、同一套售后政策。没有任何一个能力需要"独立的决策主体"，所以一个 Agent 足够。

04

一个关键判断：Tools ≠ Agents

这是全文最重要的概念区分之一。

ToolsAgents
解决的问题能力扩展决策主体 / 职责边界扩展
谁做决策Agent各 Agent 自己
上下文共享隔离
生命周期随调用生灭独立
失败归属Tool 返回错误，Agent 处理Agent 本身是失败域

举个例子，查天气：

Agent └── Weather Tool ✅ 正确

并不意味着需要：

Weather Agent → Search Agent → Decision Agent ❌ 过度设计

天气查询没有独立目标、没有独立策略、没有独立上下文需求——它只是 Agent 的一次能力调用。那么什么时候一个能力值得"Agent 化"？当它开始具备以下特征时：

信号 1
独立决策
它需要自己判断下一步做什么，而不是被上游完全指定。
信号 2
独立上下文
它需要一套与主任务不同的信息集合。
信号 3
独立目标
它的成功标准和主任务不同。
信号 4
独立策略
它有自己的 Prompt、自己的重试逻辑、自己的评估方式。

如果只是"调用不同能力"，优先使用 Tool；如果已经出现"不同决策主体"，才考虑 Agent。

05

Single Agent 开始失控的信号

"任务复杂就上 Multi-Agent"是一种偷懒的表述。复杂度失控有具体的、可观察的工程信号。以下五个信号，出现得越多，拆分的理由越充分。

5.1 Prompt 开始变成"上帝 Prompt"

你是一名资深客服专家，同时你也是： - SQL 专家，能编写和分析查询 - 法律专家，熟悉消费者保护法规 - 金融专家，理解支付与风控 - 搜索专家，精通信息检索 - 数据分析专家 / 销售专家 / 风控专家 ...

当 System Prompt 超过几千字、充斥着大量"当遇到 X 情况时你应该……"的条件分支时，问题已经不只是难维护：

  • 指令之间开始互相冲突（销售话术 vs 风控红线）；
  • 模型对中间部分的指令遵循度下降；
  • 任何一处修改都可能回归破坏另一处行为，且没有测试能兜住。

上帝 Prompt 是职责混杂的最直接信号。

5.2 Tool 数量快速增长

Agent ├── Search ├── CRM ├── Payment ├── Logistics ├── SQL ├── ERP ├── Refund ├── Recommendation └── Risk ...

当工具超过 20~30 个，Tool Selection 本身成为新的故障源：

  • Tool description 膨胀：每个工具的描述都要几百字，全部塞进 System Prompt，Context 开销急剧上升；
  • Tool collision：query_order 和 search_order 语义高度重叠，模型开始选错；
  • 错误选择的连锁反应：调错工具 → 返回无关数据 → 污染后续推理 → 最终答案错误，而且 Debug 时很难定位是"选错工具"还是"推理错误"。

注意：Tool 过多的第一解法通常不是拆 Agent，而是引入 Router 或工具分组（后文详述）。

5.3 Context 开始污染

研究类任务需要： 客服任务需要： 研究资料 / 搜索结果 用户信息 / 订单 论文 / 行业数据 物流 / 售后政策

如果它们共享同一个 Context，会发生什么：

  • Token 成本线性上涨：每次调用都背着全部历史；
  • 注意力稀释：模型在几万 Token 里找相关信息，推理稳定性下降；
  • 互相干扰：上一轮研究的结论"泄漏"进客服回答，产生幻觉。

当不同任务的信息集合几乎不重叠、且都很大时，Context Isolation 是 Multi-Agent 最实在的价值之一——它不是理念，是直接的成本和准确率收益。

5.4 不同任务需要不同模型

简单意图分类 → 小模型（快、便宜） 复杂推理 → Reasoning Model 代码生成 → Coding Model 图片理解 → Vision Model

如果一个 Agent 强行承担全部任务，架构上就锁死了 One Agent → One Model：分类任务用 Reasoning Model，成本高 10 倍，延迟高 5 倍，能力浪费；复杂推理用小模型，质量不达标。当不同子任务的模型需求出现明显分化时，自然的架构是 Router + 分模型的专项 Agent。

5.5 权限边界开始出现

Research Agent → 只读数据 Customer Service Agent → 可以修改订单 Payment Agent → 可以执行支付

这是生产系统中最容易被忽视、又最致命的信号。如果这些能力全挂在一个 Agent 上，那么：Prompt 注入的一次成功、一次 Tool Selection 的错误、一次模型幻觉，都可能直接触发高危操作。权限粒度只能做到"这个 Agent 有权限调用支付工具"，而无法做到"支付决策必须经过独立的审查流程"。

此时 Multi-Agent 的价值不再是能力或性能，而是安全边界：每个 Agent 拥有最小权限集合，高危操作被隔离在独立的、审计更严格的 Agent 中。

06

什么时候真正应该考虑 Multi-Agent？

把上面的信号收敛成一个判断模型：

Multi-Agent Value = Complexity Isolation （职责隔离） + Context Isolation （上下文隔离） + Capability Specialization （专业能力隔离） + Permission Isolation （权限隔离） + Parallelism （并行协作） + Independent Evolution （独立演进）

只有当这些项中有多项真实成立时，Multi-Agent 的引入成本才划算。逐项说明：

6.1 职责真的不同

Research Agent、Analysis Agent、Writer Agent 的拆分之所以成立，不是因为名字看起来专业，而是因为三者：目标不同（找全信息 vs 得出结论 vs 表达清晰）、上下文不同（原始资料 vs 中间分析 vs 写作规范）、评价标准不同（召回率 vs 逻辑严谨性 vs 可读性）。用不同的标准评估、用不同的 Prompt 约束、用不同的数据集测试——这才是"职责不同"的实质。

6.2 上下文必须隔离

Research Context → Research Agent → 结构化研究结果 Analysis Context → Analysis Agent → 分析结论

每个 Agent 只持有自己需要的信息，通过明确的中间产物（而非共享历史）传递。收益是：每个 Context 更小更聚焦、Token 成本可控、推理更稳定、且中间产物可以被单独缓存和评估。代价也要诚实说明：信息压缩损耗。上游 Agent 传给下游的摘要可能丢失关键细节，这是 Context Isolation 的固有 Trade-off，需要靠设计良好的中间数据结构来缓解。

6.3 可以并行执行

这是 Multi-Agent 最容易量化的价值。

三个子任务互相独立，串行需要 3 × T，并行只需要约 T + 汇总时间。此时 Multi-Agent 不是"角色拆分"，而是 Execution Parallelism——它直接兑换成 P95 延迟的下降。反过来，如果子任务之间存在严格依赖（B 需要 A 的完整输出才能开始），并行的收益归零，只剩调度开销。

6.4 Agent 需要独立演进

Research Agent 和 Customer Service Agent 可能由不同团队维护，迭代节奏完全不同。如果耦合在一个"God Agent"里：

  • Prompt 冲突：两个团队改同一个 Prompt，互相覆盖；
  • 发布风险：客服逻辑的一次修改可能弄坏研究能力，回归测试范围爆炸；
  • 版本耦合：想单独回滚客服能力，做不到。

当"谁来维护"成为问题时，Agent 边界就应该和团队边界对齐——这和微服务拆分中的康威定律是同一个逻辑。

07

不要为了 Multi-Agent 而 Multi-Agent

反面案例值得单独一节。

User ↓ Planner Agent → Research Agent → Search Agent ↓ Analysis Agent → Writer Agent → Reviewer Agent

七个 Agent，串成一条链。看起来非常"Agentic"，实际支付的成本：

7×
一次任务的 LLM 调用次数，延迟逐跳相加
7份
独立 System Prompt，Token 成本成倍增长
6个
跨 Agent 传递点，每一跳都是失败点
7套
需要独立维护的 Prompt、评估集与降级策略

更糟的情况是出现这样的调用链：

Agent A → Agent B → Agent C → Agent D → ...

当系统出错时，没有人能直接回答：

到底是哪一个 Agent 做错了？

是 A 传给 B 的信息就错了？还是 B 的推理错了？还是 C 用错了 B 的输出？每多一层 Agent，归因成本就上升一截。所以请记住这条原则：

Agent 数量本身不是架构能力，能够控制复杂度才是。

08

渐进式演进路线：从 LLM 到 Multi-Agent

正确的做法不是"项目启动时选择架构"，而是让架构随复杂度生长：

Level形态何时进入
0纯 LLM起点
1Prompt 工程需要稳定的输出格式 / 角色约束
2LLM + Tools需要外部数据或执行能力
3Single Agent任务需要多步自主决策（ReAct 循环）
4+ Workflow流程中出现了必须确定的步骤（不信任模型自主规划的关键路径）
5Router + 专项 AgentTool 数量失控 / 模型需求分化 / 权限需要分组
6Multi-Agent System出现上下文隔离、并行、独立演进、故障隔离的复合需求

两点说明：

  • Level 4 常被跳过，但它是性价比最高的一级。很多被拿去做 Multi-Agent 的场景，其实一个"Agent 处理模糊性 + Workflow 固化关键路径"的混合结构就够了。确定性流程用 Workflow，不确定性决策用 Agent。
  • Level 5 是 Level 6 的前置。大多数声称"需要 Multi-Agent"的系统，真正需要的是 Router + 几个专项 Agent。完整的 Multi-Agent（Agent 之间有协商、有动态协作）只在极少数场景下才有必要。

参考实现：三个层级的架构伪代码

Single Agent · Tool Calling# Level 2-3：一个 Agent + 多个 Tools，单循环即可
agent = Agent(
    model="qwen-max",
    system_prompt=SERVICE_PROMPT,          # 一个业务域，一份 Prompt
    tools=[search, query_db, refund_tool],
    max_iterations=8,
)

while not agent.finished:
    action = agent.next_action(user_msg)   # ReAct: 推理 + 选择工具
    result  = action.tool.execute(action.args)
    agent.observe(result)                  # 结果写回同一 Context
Router + Specialized Agents# Level 5：小模型做分发，专项 Agent 各司其职
def handle(user_msg):
    intent = router_model.classify(user_msg)   # 小模型，低成本低延迟

    match intent:
        case "after_sale":  return customer_agent.run(user_msg)   # 可写工单
        case "recommend":   return rec_agent.run(user_msg)        # 只读用户画像
        case "risk":        return risk_agent.run(user_msg)       # 只读 + 独立审计
Multi-Agent Orchestration# Level 6：独立子任务并行执行，汇总生成最终产出
async def research_report(topic):
    # 三个上下文完全隔离的 Agent 并行执行
    industry, competitor, finance = await asyncio.gather(
        industry_agent.run(topic),      # 独立 Context：行业资料
        competitor_agent.run(topic),    # 独立 Context：竞品数据
        finance_agent.run(topic),       # 独立 Context：财务数据
    )
    # 汇总器只消费结构化中间产物，不共享原始历史
    return synthesizer.run(industry, competitor, finance)
09

一个贯穿全文的案例：电商智能客服 Agent

用一条真实的演进路径，展示"系统复杂度如何一步步逼迫架构变化"。

V1：Single Agent 足够

V2：功能持续堆叠，信号开始出现

业务方不断提需求：加商品推荐、加售前咨询、加售后纠纷、加风控审核、加营销活动、加支付协助、加数据分析……一年后，这个 Agent 变成了"God Agent"：

对照第 5 节的信号清单：上帝 Prompt ✅ · Tool 失控 ✅ · Context 污染 ✅ · 模型分化 ✅ · 权限问题 ✅。五个信号全部命中。

V3：Router + Specialized Agents

拆分决策拆分依据（而不是拆分结果）
Customer Agent 独立高频主链路，独享会话上下文，可用小模型降本
Recommendation Agent 独立上下文完全不同（用户行为 vs 会话历史），可独立迭代推荐策略
Risk Agent 独立权限隔离：只读、独立审计、失败时默认拒绝而非默认放行
Router 用小模型意图分类不需要旗舰模型，P95 延迟反而下降

这个结构恰好说明：多数生产系统的终点是 Level 5，而不是 Level 6。真正的 Multi-Agent（含并行研究 + 汇总）在这个系统里只出现在一个场景：大促期间"批量分析十万条客服会话并产出改进报告"——任务天然可并行、上下文天然隔离，此时上并行 Agent 是因为收益可以算清楚。

必须说明：这不是严格的数学模型，而是架构讨论工具。它的作用是迫使团队在评审时逐项论证"为什么加分"，而不是凭感觉说"任务很复杂，上 Multi-Agent 吧"。

11

生产环境真正需要关注的指标

架构决策不能停留在图上。无论单 Agent 还是 Multi-Agent，都应该用同一套指标衡量，让架构选择可以用数据验证。

Reliability
可靠性
Task Success Rate · Tool Call Success Rate（含参数校验失败）· Agent Failure Rate（死循环、放弃、超时）
Quality
质量
Answer Accuracy（基于标注评估集）· Groundedness · Task Completion Rate（用户目标真正达成）
Performance
性能
P50 / P95 Latency（Multi-Agent 尤其要看 P95）· TTFT · Tool Execution Latency（区分模型与工具延迟）
Complexity
复杂度
Agent 数量 · Tool 数量 · Prompt 数量 · State 数量 · Workflow Branch 数量

成本指标：最诚实的那个

Token / Task
单任务 Token 消耗
Calls / Task
单任务 LLM 调用次数，Multi-Agent 的天然劣势项
Cost / Success
成功任务的成本——失败重试也是钱

Cost / Successful Task 是最诚实的成本指标：一次任务失败后重试两次才成功，它的真实成本是三次任务之和。Multi-Agent 架构若提升了成功率但让单次成本翻了三倍，净收益可能是负的——只有这个指标能揭示这一点。

Complexity 指标不直接体现质量，但和维护成本强相关。架构评审时应该要求：每一次架构升级（比如从 V2 到 V3），上述指标都要有 before / after 对比。

生产级 Agent 架构最终应该用业务指标和工程指标证明，而不是用 Agent 数量证明。

12

最终结论

回到开头的问题：什么时候一个 Agent 就够了？一条清晰的决策路径：

问题简单 ↓ Single Agent 问题开始复杂 ↓ Single Agent + Tools 任务出现固定流程、关键路径不容有失 ↓ Workflow（确定性部分） 职责 / Context / Model / Permission 开始分裂 ↓ Router + Specialized Agents 需要并行协作 / 独立演进 / 故障隔离，且可被明确论证 ↓ Multi-Agent

贯穿全文的三句话：

  • Multi-Agent 不是 Single Agent 的自然升级路线，而是为了隔离复杂性、职责和故障边界而引入的架构手段——和微服务、和进程隔离，是同一类决策逻辑。
  • Tools 解决能力扩展，Agents 解决决策主体扩展。只是需要"调用不同能力"时，永远先考虑 Tool；只有出现"不同决策主体"的证据时，才考虑 Agent。
  • 每一次拆分都要能回答：它解决了什么单 Agent 无法解决的问题？付出的是什么代价？答不出第一个问题不要拆，答不出第二个问题也不要拆。

"生产级 Agent 系统的高级，不是拥有更多 Agent，
而是用尽可能少的 Agent，构建出足够可靠、可控、可演进的系统。"
