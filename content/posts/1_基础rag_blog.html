一、为什么需要 RAG？

大语言模型（LLM）虽然强大，但存在两个致命短板：

  • 知识截止：训练数据有时间截止日，无法回答最新信息。
  • 幻觉问题：面对不了解的问题，LLM 倾向于"编造"看似合理的答案。

RAG（Retrieval-Augmented Generation，检索增强生成）的核心思路非常直觉——既然模型"记不住"，那就让它"开卷考试"。在生成回答之前，先从外部知识库中检索相关文档，把检索到的内容作为上下文拼入 Prompt，让模型"有据可依"地生成回答。

💡 类比理解

把 LLM 想象成一位博学但无法联网的专家。RAG 就是给这位专家配了一个智能资料柜——遇到问题时，先打开柜子找到相关资料，再结合自己的理解给出答案。

整个流程分为两个阶段：

三、Step 1 — 从 PDF 提取文本

一切从数据源开始。我们使用 PyMuPDF（即 fitz）库从 PDF 文件中逐页提取纯文本。

核心代码

import fitz  # PyMuPDF

def extract_text_from_pdf(pdf_path):
    mypdf = fitz.open(pdf_path)
    all_text = ""
    for page_num in range(mypdf.page_count):
        page = mypdf[page_num]
        text = page.get_text("text")
        all_text += text
    return all_text

这段代码的逻辑非常直接：打开 PDF → 遍历每一页 → 提取文本 → 拼接为一个大字符串。注意这里返回的是一整块连续文本，还没有进行任何结构化处理。

⚠️ 注意

PDF 提取的文本质量取决于 PDF 本身的结构。扫描版 PDF（图片型）需要先做 OCR，而排版复杂的 PDF 可能出现段落错乱。在生产环境中，这一步往往需要更多的预处理工作。

四、Step 2 — 文本分块（Chunking）

提取出的长文本不能直接丢给检索系统——太长的文本会稀释语义信息，导致检索不精确。因此需要将其切分为更小的块（chunk）。

分块策略：滑动窗口 + 重叠

本教程采用最简单的固定长度滑动窗口策略，每个块 n 个字符，相邻块之间重叠 overlap 个字符：

def chunk_text(text, n, overlap):
    chunks = []
    for i in range(0, len(text), n - overlap):
        chunks.append(text[i:i + n])
    return chunks

实际调用时，设置 n=1000（每块 1000 字符），overlap=200（重叠 200 字符）：

text_chunks = chunk_text(extracted_text, 1000, 200)
# 输出：Number of text chunks: 42

为什么要重叠？

重叠（overlap）是为了防止一个完整的语义单元被硬生生切断。下图直观展示了分块与重叠的关系：

图 2：文本分块与重叠示意图 — 相邻块之间共享 200 字符的重叠区域，防止语义被截断

五、Step 3 — 创建向量嵌入（Embedding）

文本块准备好后，下一步是将每个块转换为数值向量。这一步是语义检索的基础——只有将文本映射到向量空间，才能用数学方法度量"语义相似度"。

我们使用 OpenAI 的 text-embedding-ada-002 模型，它会将每段文本映射为一个 1536 维的浮点数向量：

def create_embeddings(text, model="text-embedding-ada-002"):
    response = client.embeddings.create(
        model=model,
        input=text
    )
    return response

# 一次性为 42 个文本块创建嵌入
response = create_embeddings(text_chunks)

图 3：文本到向量的转换 — Embedding 模型将每段文本映射为 1536 维浮点向量，使语义相似度可以用数学方法计算

六、Step 4 — 语义搜索（Semantic Search）

有了向量之后，检索就变成了一个向量相似度计算问题。我们使用经典的余弦相似度（Cosine Similarity）来度量查询向量与每个文本块向量之间的相似程度。

余弦相似度

图 4：余弦相似度原理 — 通过计算两个向量的夹角余弦值来衡量语义相似程度，值越接近 1 表示语义越相近

核心代码

import numpy as np

def cosine_similarity(vec1, vec2):
    return np.dot(vec1, vec2) / (np.linalg.norm(vec1) * np.linalg.norm(vec2))

def semantic_search(query, text_chunks, embeddings, k=5):
    # 1. 将查询也转为向量
    query_embedding = create_embeddings(query).data[0].embedding
    
    # 2. 计算查询向量与每个文本块向量的余弦相似度
    similarity_scores = []
    for i, chunk_embedding in enumerate(embeddings):
        score = cosine_similarity(
            np.array(query_embedding),
            np.array(chunk_embedding.embedding)
        )
        similarity_scores.append((i, score))
    
    # 3. 按相似度降序排列，取 top-k
    similarity_scores.sort(key=lambda x: x[1], reverse=True)
    top_indices = [idx for idx, _ in similarity_scores[:k]]
    
    return [text_chunks[idx] for idx in top_indices]

这段代码是 Simple RAG 检索的核心：查询向量化 → 逐一计算相似度 → 排序取 Top-K。在实际生产环境中，这一步通常由向量数据库（如 Pinecone、Milvus、FAISS）来高效完成，而不是像这里一样暴力遍历。

💡 工程提示

本教程的暴力遍历方式时间复杂度为 O(N)，当文档数量达到百万级时，需要借助 ANN（近似最近邻）算法和专用向量数据库来将检索时间降到 O(log N)。

七、Step 5 — 生成回复（Generation）

检索到最相关的文本块后，最后一步是将它们作为上下文拼入 Prompt，交给 LLM 生成最终回答。

system_prompt = (
    "You are an AI assistant that strictly answers based on the given context. "
    "If the answer cannot be derived directly from the provided context, "
    "respond with: 'I do not have enough information to answer that.'"
)

def generate_response(system_prompt, user_message, model="gpt-4o"):
    response = client.chat.completions.create(
        model=model,
        temperature=0,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_message}
        ]
    )
    return response

Prompt 的构造方式：

# 将检索到的文本块拼接为上下文
user_prompt = "\n".join([
    f"Context {i+1}:\n{chunk}\n====="
    for i, chunk in enumerate(top_chunks)
])
user_prompt = f"{user_prompt}\nQuestion: {query}"

注意 temperature=0 的设置——在 RAG 场景中，我们希望模型的回答尽可能确定性和忠实于上下文，而不是天马行空地发挥创造力。

九、优缺点与适用场景

✅ 优点

  • 实现简单：整个流程不到 200 行代码，易于理解和调试。
  • 减少幻觉：通过引入外部知识约束 LLM 的生成，显著降低"编造"风险。
  • 知识可更新：只需更新文档库，无需重新训练模型。
  • 可溯源：回答可以追溯到具体的检索文本块，便于验证。

❌ 缺点

  • 分块策略粗糙：固定长度切分可能破坏语义完整性（如段落、句子被截断）。
  • 检索精度有限：仅依赖单次向量相似度，没有重排序（Reranking）机制。
  • 上下文窗口浪费：检索到的块中可能包含大量无关信息，占用宝贵的上下文窗口。
  • 扩展性差：暴力遍历检索在大规模文档集上效率低下。

🎯 适用场景

场景 适合度 说明

大规模文档检索 ⭐⭐ 需要向量数据库 + ANN 索引

📌 小结

Simple RAG 用不到 200 行代码实现了完整的"检索 → 生成"管线，是理解 RAG 思想的最佳起点。核心流程：文档提取 → 分块 → 嵌入 → 余弦相似度检索 → LLM 生成。虽然简单，但它奠定了所有高级 RAG 技术的基础框架。
