LLM-as-Judge：
让大模型给 RAG 打分，真的可靠吗？

上一篇我们把 Faithfulness 定义为「答案中的每一条陈述，都能被检索到的 Context 所支撑」。 但当评测本身需要理解自然语言时，一个更根本的问题浮现了：谁来执行这个「支撑」判断？ 本篇深入生产级 Judge 的完整设计——从 Claim Extraction 到 Rubric，从 Structured Output 到偏差治理。

00 / PROLOGUE

一个无法用 if-else 写出的判断

系列第一篇的结尾，我们留下了一个悬而未决的问题。现在，是时候正面回答它了。

回顾一下我们的场景：企业知识库 + 客服 RAG 系统。用户问「年假未休完可以折现吗？」， 系统检索到 HR 制度文档，生成了一段答案。上一篇我们确立了 Faithfulness 的定义—— 答案中的每一条 Claim（陈述），都必须能被 Context（检索到的证据）支撑。 这个指标是 RAG 生成质量的基石，因为它直接对应生产环境中最致命的故障模式：幻觉。

但定义是优美的，执行是残酷的。「这条陈述能否被这段证据支撑」——这个判断本质上是 一次语义推理，而不是一次字符串匹配。它没有正则可以写，没有规则可以穷举。 当你试图用传统 NLP 指标去填补这个空位时，问题会立刻暴露出来。

◆ 本篇要回答的四个问题

① 为什么 BLEU、ROUGE、Embedding 相似度在 Faithfulness 评测上全部失效？
② 一个生产级 Faithfulness Judge 应该长什么样——Prompt、Rubric、Schema、代码？
③ Judge 会以哪些方式系统性地撒谎？Position Bias、Self Preference、Judge Drift 如何治理？
④ 当 Judge 本身也是一个模型，我们如何评测这个「评测者」？

01 / WHY

为什么传统规则评测不够

三种经典方案的连续失败

在 LLM-as-Judge 出现之前，业界对生成质量的自动评测基本依赖三类方案。我们把它们逐一放到 客服场景的一个真实 Case 上检验：

Question
未休完的年假可以折算成工资吗？
Context
《员工假期管理制度》第 7 条：当年未休法定年假，经员工申请并经部门审批，可按日工资的 200% 折算，折算申请须于次年 3 月 31 日前提交。
Answer
可以。未休完的年假可按日工资的 200% 折算为现金，但需在次年 3 月 31 日前提交申请并获部门审批。[可被支撑]

这是一条完美的回答。现在看系统的输出——以及三种指标分别给出什么分数：

TABLE 01 · 三类传统评测方案在 Faithfulness 场景下的失效分析
方案原理在 Faithfulness 上失败的原因
n-gram 重叠
BLEU / ROUGE		 统计 Answer 与 Reference 的词面重叠率 衡量的是「和参考答案像不像」，不是「有没有依据」。一个完全忠实但彻底改写的答案，ROUGE 可能低于 0.3；而一条把 Context 中两个不相关句子拼接出的幻觉，重叠率反而可能很高。它评的是文风，不是事实。
Embedding 相似度 Answer 与 Context 向量余弦距离 语义相似 ≠ 语义支撑。「年假可以折现」和「年假不可以折现」的余弦相似度通常超过 0.9——向量空间对否定词、条件限定、数值边界几乎不敏感，而这些恰恰是幻觉的高发区。
关键词 / 规则匹配 校验 Answer 中数值、日期是否出现在 Context 只能覆盖「字面抄写型」错误，无法处理同义改写（「200%」→「双倍」）、跨句推理（Context 分两处陈述条件）和实体共指（「该制度」→「假期管理制度」）。规则越多，维护成本越接近重写一个 NLU 系统。

三种方案失败在同一个点上：它们都把「支撑关系」降维成了某种表面统计量。 而「支撑」本质上是一次推理——需要理解陈述的含义、证据的含义，以及二者之间的逻辑关系。 恰好，这正是一个足够强的 LLM 每天在做的事情。

如果被评测的能力本身就是「语言理解」，那么评测器也必须具备语言理解。 这就是 LLM-as-Judge 诞生的唯一根本理由——它不是赶时髦，而是问题的结构决定的。 —— 本系列的立场声明，贯穿后续三篇

但请先泼一盆冷水

「让 GPT 来打分」听起来像是一条捷径：一行 Prompt，一个分数，结束。大量团队正是这样起步的， 也是这样在生产中翻车的。一个未加约束的 Judge Prompt 会表现出惊人的不稳定性： 同一条 Evaluation Case，今天打 0.8，明天打 0.6；换一个模型打 0.9；把 Evidence 挪个位置，分数掉 0.2。

Judge 不是一行 Prompt，而是一条完整的、需要被工程化约束的 Pipeline。 下面我们逐层搭建它。

02 / ARCHITECTURE

Judge Pipeline：把「打分」拆成五段流水线

生产级 Judge 的第一原则：不要让一个 LLM 调用同时完成所有事。 一次性把 Question、Context、Answer 全塞进去然后要求输出 Faithfulness 分数， 意味着模型在单次前向中要同时完成阅读理解、逻辑比对、评分校准三件事——每一件都会被另外两件干扰。

我们采用的架构是把 Judge 拆成五段：先把 Answer 打散成独立的 Claim， 再对每条 Claim 独立验证，然后聚合分数，最后通过结构化输出保证可解析性。 整条流水线如下：

◆ 为什么必须先做 Claim Extraction

直接问「这个答案 Faithful 吗」，模型会给出一个整体印象分——心理学上称为 halo effect： 一条答案里 9 句有据可查、1 句幻觉，整体评分会飘到 0.85 以上，幻觉被平均掉了。

而 Claim 级评测把粒度压到最细：9 条 supported + 1 条 unsupported = Faithfulness 0.9， 那条幻觉不但拉低了分数，还附带了自己的 evidence 定位和 reason—— 这就是分数从「一个数字」变成「一份诊断报告」的关键。

03 / STEP-BY-STEP

Claim Extraction：先把答案拆成可判定的原子

什么是一条合格的 Claim

Claim Extraction 看似简单，实际是整条 Pipeline 中最影响最终质量的一步。 一条合格的 Claim 必须满足三个性质：

① 原子性——一条 Claim 只包含一个可独立判定真伪的断言。 「年假可按 200% 折算且需在 3 月 31 日前申请」必须拆成两条，否则任何一条不成立都会让整条 Claim 无法判定。
② 自包含性——脱离原文也能读懂。需要把代词还原：「它需要审批」→「年假折算需要部门审批」。
③ 可判定性——不含主观修饰。「这个政策很人性化」不是 Claim，它无法被 Context 支撑或反驳，应在提取阶段剥离。

Answer
可以折现。未休完的年假能按日工资 200% 折算成现金，不过你需要在次年 3 月 31 日前提交申请，而且要获得部门审批才行。这套流程其实挺人性化的。
Claims ↓
C1 · 未休完的年假可以折算为现金 C2 · 折算比例为日工资的 200% C3 · 折算申请须于次年 3 月 31 日前提交 C4 · 折算需要获得部门审批
Stripped
「这套流程其实挺人性化的」——主观评价，不可判定，提取阶段直接丢弃，不计入分母。

提取 Prompt 的两个关键约束

Claim Extraction 本身也是一次 LLM 调用（用一个便宜的小模型即可）。它的 Prompt 需要两条硬约束： 忠实复述（只允许同义改写，禁止合并、推断、补充）和数量上限（防止单条长答案被拆出 几十条碎片 Claim 导致验证成本爆炸——我们生产环境设置上限 12 条，超出则按语义合并）。

judge/claim_extraction.py — 原子化提取（节选） 
# 提取阶段的系统 Prompt 核心约束（完整 Judge Prompt 见第 04 节）

CLAIM_EXTRACTION_PROMPT = """
你是一个严谨的文本分析器。将下面的 Answer 拆解为原子化的陈述（Claim）列表。

规则：
1. 每条 Claim 只能包含【一个】可独立判定真伪的事实断言
2. Claim 必须自包含：还原所有代词与省略的主语
3. 只允许忠实复述，禁止合并、推断、补充原文没有的信息
4. 剥离主观评价、语气词、礼貌用语——它们不是 Claim
5. 最多输出 12 条；若超出，将语义相近的陈述合并
6. 若 Answer 中没有任何可判定的事实断言，返回空列表

输出 JSON：{"claims": [{"id": "C1", "text": "..."}, ...]}
"""

def extract_claims(answer: str) -> list[Claim]:
    resp = llm.call(
        model="small-fast-cheap",          # 提取用小模型即可
        messages=[{"role": "system", "content": CLAIM_EXTRACTION_PROMPT},
                  {"role": "user", "content": answer}],
        response_format="json",            # Schema 校验见第 05 节
    )
    return [Claim(**c) for c in resp["claims"]]
⚠ TECHNICAL NOTE · 提取偏差会向下游传导

Claim Extraction 的召回率直接决定了 Faithfulness 分数的可信度： 如果提取器漏掉了一条幻觉陈述，下游验证再精确，这条幻觉也会永远拿不到扣分。 我们在灰度期人工核对了 200 条 Answer 的提取结果，将提取召回作为独立指标监控—— 这是「Judge 本身也要被评测」的第一处落点（详见第 07 节）。

04 / DESIGN

Rubric 与 Faithfulness Judge 的完整设计

先定标准，再写 Prompt

很多团队的 Judge Prompt 里只有一句「请评估答案是否忠实于上下文，0 到 1 打分」。 这相当于把评分标准的设计权完全交给了模型——每次调用，模型都在用一套略微不同的内心标尺打分。 生产级 Judge 的做法是：Rubric 先行，Prompt 只是 Rubric 的载体。

我们的 Faithfulness 采用 0–3 的整数档位而非 0–1 连续分数。原因很直接： 连续分数制造了虚假的精度——模型根本无法区分 0.73 和 0.78 的语义差别，只会输出噪声； 而粗粒度档位让每一次打分都必须落在有明确定义的语义区间内，稳定性显著更高。 Claim 级 Rubric 如下：

TABLE 02 · Per-Claim Verification Rubric（0–3 档，冻结于 v1，修订需走版本流程）
档位语义定义判定标准客服场景判例
3 完全支撑
Fully Supported		 Context 中存在明确陈述，与 Claim 语义等价（允许同义改写、数值等价换算） Claim「折算比例为日工资的 200%」↔ Context「按日工资的 200% 折算」
2 部分支撑
Partially Supported		 需要跨句拼接、简单推理才能支撑，或 Claim 遗漏了 Context 中的关键限定条件 Claim「任何人都可以申请折现」——Context 说「经员工申请并经部门审批」，Claim 丢掉了审批限定
1 无法判定
Not Verifiable		 Context 完全没有相关信息，但也无法断定 Claim 为假（可能来自其他知识源） Claim「折算需缴纳个人所得税」——Context 未提及，不得直接判 0
0 矛盾 / 幻觉
Contradicted		 Context 中存在与 Claim 直接冲突的陈述 Claim「公司规定年假不可折现」——与 Context 第 7 条直接矛盾，典型幻觉
◆ Rubric 设计中最容易踩的坑：1 档的存在理由

如果只有「支撑 / 不支撑」两档，Judge 在 Context 没提、但 Claim 可能来自模型参数知识时会被迫二选一， 结果大量噪声。引入「无法判定」档后，我们将这类情况与真幻觉分离—— 「Not Verifiable」按 0.5 折算计入分数，而「Contradicted」计 0。 这个区分在生产复盘时至关重要：前者提示检索覆盖缺口，后者才是生成幻觉。

完整的 Judge Prompt

下面是验证阶段的完整 Prompt。注意四个设计决策：角色锁定（审计员而非助手，抑制「帮忙」倾向）、 Context 优先原则（明确禁止用参数知识补证）、引用强制（每个 verdict 必须给出 Context 原文切片）、 先推理后结论（CoT 结构，reason 字段置于 verdict 之前生成）。

judge/prompts.py — Faithfulness Verifier Prompt v3.2（生产冻结版） 
FAITHFULNESS_JUDGE_PROMPT = """
# 角色
你是一名严格的审计员（Auditor），任务是逐条核验陈述（Claim）是否能够被
给定的证据（Context）支撑。你不是客服，不是助手——你没有义务让答案"看起来更好"。

# 输入
- Context：系统检索到的证据文本（唯一合法的判定依据）
- Claims：待核验的陈述列表

# 判定原则（按优先级排序）
P1. 只依据 Context 判定。你自己的知识、常识、其他资料一律不可作为支撑或反驳的依据。
P2. 同义改写、数值等价换算视为支撑；增加 Context 中不存在的限定条件视为降档。
P3. Claim 与 Context 无关时，判为 "not_verifiable"（1 分），不要猜测地判为矛盾。
P4. 每个 verdict 必须引用 Context 中的原文切片作为 evidence；
    若为 not_verifiable / contradicted，evidence 引用相关（或应存在而缺失）的原文位置。
P5. 拿不准时，向下取档——你的职责是发现风险，不是给出宽容。

# 评分档位
3 = fully_supported    Context 有明确陈述与 Claim 语义等价
2 = partially_supported 需跨句推理支撑，或 Claim 遗漏关键限定条件
1 = not_verifiable     Context 未涉及，无法证实亦无法证伪
0 = contradicted       Context 中存在与 Claim 直接冲突的陈述

# 输出
对每条 Claim 依次输出：先写 reason（含 evidence 引用），再给出 verdict。
严格按 response_schema 输出 JSON，不输出任何其他文本。
"""
⚙ TECHNICAL NOTE · Prompt 的版本治理

注意文件头中的 v3.2（生产冻结版）。Judge Prompt 必须像代码一样走版本管理： 每次修改 Prompt，等同于更换了一把尺子——新旧尺子量出来的分数不可直接对比。 我们要求任何 Prompt 变更都必须附带一次 Judge 回归：在固定的 Calibration Set（见第 07 节）上重跑， 确认与人工标注的一致率没有显著退化才能合入。这一点在下一篇的 Regression Dataset 中会形成完整闭环。

Structured Output：用 Schema 把自由文本焊死

Judge 的输出必须直接写入评测数据库、驱动 Release Gate 判断——这意味着它必须可机器解析。 我们使用 JSON Schema 硬约束 + 解析失败自动重试：

judge/schema.py — Judge 输出契约 
JUDGE_OUTPUT_SCHEMA = {
    "type": "object",
    "required": ["case_id", "faithfulness", "claim_verdicts"],
    "properties": {
        "case_id":   { "type": "string" },
        "faithfulness": {                       # Case 级聚合分数
            "type": "number",
            "minimum": 0, "maximum": 1
        },
        "claim_verdicts": {
            "type": "array",
            "items": {
                "type": "object",
                "required": ["claim_id", "verdict", "evidence", "reason"],
                "properties": {
                    "claim_id": { "type": "string" },
                    "verdict": {
                        "enum": ["fully_supported", "partially_supported",
                                 "not_verifiable", "contradicted"]
                    },
                    "evidence": { "type": "string" },  # Context 原文切片，强制非空
                    "reason":   { "type": "string" }
                }
            }
        }
    }
}

# 聚合规则（在代码中执行，不交给 LLM）：
#   fully_supported=1.0, partially=0.7, not_verifiable=0.5, contradicted=0.0
#   faithfulness = mean(claim 权重) —— 加权计算，绝不依赖模型自行汇总
◆ 设计决策：分数由代码算，不由模型算

注意 Schema 注释里的最后一行：聚合在代码中执行。 让 Judge 自己汇总 Claim 分数等于引入一次额外的算术出错机会和不稳定来源。 LLM 只负责它擅长的语义判定，所有确定性的计算都收回工程层——这是 LLM 系统设计的一条通用法则， 在下一篇的 Regression Engine 中会反复出现。

ROUGE-L = 0.87，表面看「高分通过」。但如果这是一个 Release Gate，一条真实的限定条件遗漏就被平均掉了，没有任何归因信息告诉工程师该改哪里。

✗ Judge 视角0.925 + 定位

Faithfulness 0.925 看似更高，但附带了一份精确的诊断：C4 partially_supported + 完整 reason。工程师直接知道是「条件从属关系」被压平了——这是可行动的信号。

这个对比揭示了 Judge 的真正价值：不是分数更准，而是分数之外携带了 Evidence 与 Reason—— 评测结果从「验收章」变成了「病历」。第四篇的 Eval Studio 之所以能做 diff 视图与根因分析， 正是因为 Judge 在今天埋下了结构化的种子。

06 / BIAS

Judge 会系统性地撒谎：三类偏差与治理

到这里为止，我们搭建了一个看起来相当严谨的 Judge。但如果你因此相信它输出的每一个数字， 你会在某天早晨发现：同一套 RAG 系统、同一份 Evaluation Dataset，仅仅因为更换了底层模型， Faithfulness 分数发生了 0.15 的「提升」——而业务侧完全感受不到任何变化。 这是 Judge 在骗你。以下是三种最常见的骗术。

偏差一：Position Bias —— 位置决定命运

LLM 对输入序列中信息位置存在系统性偏好。在成对比较任务中（A 答案 vs B 答案哪个更好）， 大量研究复现了一个稳定现象：排在前面（或紧邻指令）的选项更容易被偏好。 在我们的 Faithfulness 场景中，它以更隐蔽的形式出现——当 Context 很长时， 出现在 Context 开头和结尾的陈述更容易被判为支撑（中间信息被弱化，即 lost-in-the-middle 的评测版）。

治理方案：Swap Pair + 位置去敏聚合。

标准做法是让 Judge 对两种顺序各判一次：只有两次结论一致才采纳； 结论翻转（如上图的 A 选 Answer-1、B 选 Answer-2）则记为 inconclusive， 按平局处理或升级人工。代价是成本翻倍，因此我们只对进入回归对比的两个版本之间的 Case 使用成对评测， 绝对分数仍走单侧打分——成本的刀要花在刀刃上。

偏差二：Self Preference —— 裁判偏爱自己的笔迹

当 Judge 模型与被评测的生成模型来自同一个家族时，Judge 会系统性地给自己家族的输出打高分。 这不是阴谋，是分布匹配：同一预训练谱系的模型对「什么是好答案」的内在偏好高度一致。 在我们的实测中（细节见下方统计卡），这个偏差足以让「我们切换到 Judge 同族模型后质量大幅提升」 这种结论变成彻底的幻觉。

治理方案：Judge 与 Generator 的谱系隔离。 规则很简单：Judge 的模型家族必须与当前被评测的生成模型不同，并且——这是关键—— 这个组合关系要记录进每一次 Evaluation Run 的元数据。 因为当你切换生成模型时，可能需要同步切换 Judge，而换 Judge 就换了尺子（见偏差三）， 两次 Run 的分数便失去可比性。这个依赖链必须在元数据里显式可见，而不是埋在配置文件里。

偏差三：Judge Drift —— 尺子本身在变形

即使 Prompt 冻结、模型版本锁定，Judge 的打分分布仍可能漂移：推理基础设施变更、 温度采样的随机性、上游模型的静默更新（对于 API 形式的 Judge 你并不真正拥有它）。 Drift 最大的危害不是分数绝对值变化，而是悄悄破坏了 Run 之间的可比性—— 而可比性正是下一篇 Regression Dataset 和第四篇 Release Gate 的全部基础。

治理方案：Calibration Set 作为「标准砝码」。

维护一个 50–100 条、人工标注定稿的 Calibration Set（其中刻意混入各档位的难例， 包括 not_verifiable 与 contradicted 的边界样本）。每次生产评测前，Judge 先跑一遍 Calibration Set：

  • 与人工标注的一致率 ≥ 阈值（我们设 85%）→ 本次 Run 的分数可用；
  • 低于阈值 → 分数标记为 uncalibrated，禁止进入趋势对比，触发告警；
  • 连续两次漂移 → 回溯定位：是 Prompt、模型版本还是采样参数的问题。
◆ 一句话总结三类偏差的治理矩阵

Position Bias → Swap Pair（成对场景）；Self Preference → 谱系隔离 + 元数据记录（全场景）； Judge Drift → Calibration Set 门前校验（每次 Run）。 三者共同指向同一个原则：不要信任 Judge 的任何一次输出，只信任被校验过的输出。

07 / META-EVAL

Cross-model Evaluation：评测者也需要被评测

本篇最重要的一个观点，值得用一整节来展开：

Judge 本身也是一个需要被 Evaluation 的系统。 它有输入、输出、失效模式和回归风险——所以它必须被纳入与被评测系统完全相同的质量工程框架。 —— 如果只记住本篇的一句话，记住这句

「用什么来评测 Judge？」——黄金标准是人工标注。但人不能标注所有数据，所以工程上的解法是 Cross-model Evaluation：用多个不同家族的模型作为 Judge，对同一批样本独立打分， 再用一个小的金标人工集合（Calibration Set）锚定。

judge/meta_eval.py — Judge 的每日自检（伪代码） 
def daily_judge_healthcheck(calibration_set, judge_pipeline):
    # 1. Judge 跑金标集
    preds = judge_pipeline.run(calibration_set, seed=42)

    # 2. 与人工标注对齐（Judge 也是被评测系统：用同一套指标语言）
    report = {
        "accuracy":   accuracy(preds, calibration_set.gold),   # 总体一致率
        "kappa":      cohen_kappa(preds, calibration_set.gold),# 去除随机一致
        "recall_c0":  per_class_recall(preds, gold, cls="contradicted"),
                       # ↑ 最关键的指标：幻觉抓取召回率，漏抓幻觉代价最高
        "drift":      psi(preds.distribution, baseline.distribution),
    }

    # 3. 门禁：不合格则当日所有 Evaluation Run 打上 uncalibrated 标记
    if report["kappa"] < 0.75 or report["recall_c0"] < 0.85:
        mark_all_runs_uncalibrated(date=today)
        alert("judge-degraded", report)
    return report
⚙ TECHNICAL NOTE · 递归的尽头

细心的读者会问：评测 Judge 的指标（kappa、recall）由代码计算，这没问题； 但 Calibration Set 的人工金标本身也有标注者间不一致的问题。答案是：递归必须在人工层终止—— 我们通过双人独立标注 + 仲裁解决金标质量，并接受金标是「高置信近似」而非绝对真理。 工程上重要的是知道误差停在哪一层，而不是追求无穷递归的纯净。

但仍然存在一个关键问题

现在，我们拥有了一把经过校准、偏差受控、输出结构化的精密尺子。 整套 Judge Pipeline 随时可以对任意一条 Evaluation Case 给出 分数 + 证据 + 归因。一切看起来已经完备。

直到你意识到一个问题：这把尺子，该去量什么？

假设团队明天要上线新的 Reranker，需要跑一次回归评测。最自然的做法是： 大家花一个下午，凭经验凑 100 个「比较典型的问题」，跑一遍，分数不错，上线。 两周后，客服后台的真实 question 流里出现了「孕期能用年假折算抵扣社保基数吗」这样的 长尾复合问题——RAG 答得一无是处，而昨天的评测报告上写着 Faithfulness 0.94，全绿。

问题不出在 Judge——Judge 对这条 Case 如果真的去评，一定会抓出问题。 问题在于这条 Case 根本不在那 100 个问题里。随机或拍脑袋准备的评测集， 测的是「我们想象中的用户」，不是生产中的用户：它没有覆盖真实问题的分布， 没有权衡难度分层，没有难例与边界样本，更没有随业务演进持续更新。

◆ 遗留问题

一把完美的尺子，量错了布料，得到的仍然是一个错误的结论。
拿哪些问题来测试，才能让评测分数真正代表生产质量？

这正是评测工程中承上启下的核心构件：Regression Dataset—— 它如何从真实流量中采样？如何分层、如何加权、如何纳入bad case？如何与版本管理绑定， 让每一次 Evaluation Run 之间真正可比？这些问题，我们下一篇见。
