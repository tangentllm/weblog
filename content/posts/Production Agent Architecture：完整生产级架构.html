Production Agent Architecture：完整生产级架构

从一个 Agent Demo 到可上线、可观测、可治理、可扩展的生产系统

引言：系列定位与核心问题

在前面的系列文章中，我们逐一拆解了构建 Agent 的各个核心维度：从 Workflow 与 Agent 的抉择，到单/多 Agent 的系统设计；从 Memory、Tool Calling 的能力扩展，到 Evaluation、Observability 与 Reliability 的工程保障。这些组件单独看都有一套复杂的工程实践，但当它们真正要组合成一个系统时，问题才刚刚开始。

本篇必须完成最终架构收束：如何把这些能力组合成真正能够进入生产环境的 Agent System。 我们不再独立介绍 RAG、Memory 或 Tool Calling，而是站在系统架构层，把这些能力放到正确的位置。

全文围绕以下 10 个核心问题展开：

  1. 一个 Demo Agent 和 Production Agent 到底差在哪里？
  2. Production Agent 的完整架构应该是什么？
  3. Agent Runtime 为什么应该独立出来？
  4. Control Plane 和 Data Plane 如何划分？
  5. Agent 如何管理 State、Memory 和 Execution？
  6. Model、Tool、RAG、Memory 如何成为可插拔能力？
  7. Evaluation、Observability、Reliability 如何进入 Runtime？
  8. 如何做多租户、权限、安全与审计？
  9. 如何控制成本、延迟和资源？
  10. 如何让 Agent 从“一个应用”演化为“Agent Platform”？

核心观点声明

  1. Production Agent 不是一个 Prompt + LLM + Tools 的组合，而是一套拥有 Runtime、State、Policy、Execution、Observability 和 Recovery 能力的分布式系统。
  2. 模型负责概率性决策，Runtime 负责确定性执行。 Agent 不应该拥有所有控制权。
  3. Production Agent 最重要的变化是从“模型调用”变成“Runtime”。
  4. Production Agent Architecture 应该把“智能层”和“系统层”分离。
  5. 真正的 Agent Platform，不是提供一个 Agent SDK，而是提供一个可治理的 Agent Runtime。
  6. Agent 的生产化，本质上是把不确定性限制在确定性边界之内。
  7. 完整 Production Agent 最终应形成：Think → Plan → Act → Observe → Recover → Evaluate → Improve 的闭环。

01. Agent Demo 与 Production Agent 的分水岭

让我们从一个极简的电商客服 Demo 开始：

response = llm.invoke(prompt)
# 甚至是一个带 Tool 的循环：
while not done:
    decision = llm.decide()
    tool.execute(decision)

这段代码在 Demo 阶段、在 sunny path（理想路径）下完美运行。用户说“我要退款”，Agent 决定调用退款 Tool，Tool 执行成功，返回结果。但如果真的上线以后，够吗？显然不够。

在真实的线上环境中，你面临的不是理想路径，而是无数的长尾故障：

  • 基础设施故障： 模型超时、LLM Provider 不可用、网络抖动。
  • 执行异常： Tool 超时、Tool 参数错误（幻觉导致）、Tool 服务自身 5xx。
  • 系统级问题： 权限问题（A 用户退了 B 用户的单）、重复执行（用户狂点按钮）、Agent Loop（死循环调用同一 Tool）、Memory 污染（历史数据带偏当前决策）、RAG 错误（检索到过期政策）。
  • 安全与合规： 数据泄露（把 C 用户的订单信息返回给 A 用户）、并发冲突、多租户隔离被穿透。
  • 资源与运维： 成本失控（Token 用量激增）、P95 延迟超标（链路太长）、灰度发布困难、Prompt/Model 版本漂移导致回归。

这就引出了 Demo 和 Production 的本质区别：

Demo 的核心是“能不能跑”；Production 的核心是“能不能长期、稳定、安全、可治理地运行”。
维度 Demo Agent Production Agent
核心关注点 “能不能跑通主流程” “能否长期、稳定、安全、可治理地运行”
状态管理 内存变量，随进程销毁 Durable State，支持 Checkpoint 与恢复
错误处理 抛出异常，直接崩溃 Retry, Fallback, Circuit Breaker, Safe Stop
权限与安全 无，或硬编码在 Prompt 中 Policy Engine, Tenant Isolation, Agent Identity Chain
可观测性 Print 日志 Distributed Tracing, Metrics, Token Cost Track
版本控制 Git 代码版本 Prompt, Model, Tool, Policy 联合快照版本

02. Production Agent 的完整架构

这是全文最重要的一张架构图。Production Agent 并非简单的线性调用，而是一个包含控制面与数据面的复杂拓扑。它将“智能层”（LLM 决策）和“系统层”（执行控制）严格分离。

03. Agent Runtime：生产系统最核心的组件

Agent Runtime 是 Production Agent 的核心。 如果说 LLM 是大脑，那么 Runtime 就是小脑和脊髓，负责条件反射、平衡和运动控制。

它至少负责以下能力：

  • Execution Loop & Step Management: 控制 Think-Act-Observe 循环，防止死循环。例如，当 Agent 连续 3 次调用同一 Tool 且参数相同时，Runtime 应主动中断并返回 Fallback 答案。
  • State Management: 管理当前 Run 的所有中间状态。
  • Timeout & Budget: 强制执行时间限制和成本限制。如果 Agent 执行到第 5 步时 Token 预算已耗尽 80%，Runtime 会注入 System Message 强制要求 Agent 总结现有信息并返回最终响应。
  • Retry & Fallback: 在 LLM 或 Tool 失败时进行恢复。
  • Tool Execution & Validation: 在执行 Tool 前进行参数和权限校验。
  • Event Emission & Checkpoint: 记录每一步并支持持久化恢复。
  • Cancellation & Recovery: 支持任务取消和崩溃后的断点续传。

案例深潜：电商客服 Agent 的长流程恢复

假设用户请求退款，Agent 在第 2 步查询了订单，第 3 步发起了退款申请，但系统在第 4 步等待人工审批时由于节点重启导致进程被 Kill。

如果是 Demo 架构，用户需要重新输入指令，Agent 重新执行所有步骤（可能导致重复发起退款申请）。而 Production Runtime 会在每一步执行后向 State Store 写入 Checkpoint。进程重启后，Runtime 从 State Store 恢复上下文，发现当前处于“等待审批”状态，直接重连消息队列等待审批结果，用户毫无感知，也不会产生副作用。

反直觉观点 1： Production Agent 的核心不是更强的模型，而是更强的 Runtime。模型负责概率性决策，Runtime 负责确定性执行。

为什么不能把这些能力散落在业务代码里？因为一旦你有 Agent A、Agent B、Agent C，每个业务团队都自己实现 Retry、Timeout 和 State，最终会导致平台能力碎片化。线上的配置更改、故障排查和统一升级将变成灾难。Runtime 与 Agent 的区别是什么？ Agent（或 Planner）是基于 LLM 的概率性决策组件，它决定“下一步做什么”；而 Runtime 是确定性的执行环境，它决定“这个决策是否被允许执行、如何执行、失败了怎么办”。Runtime 是 Agent 的操作系统。

04. Control Plane vs Data Plane

这是生产架构必须跨越的门槛。将系统拆分为 Control Plane（控制面）和 Data Plane（数据面）。

特征 Data Plane (数据面) Control Plane (控制面)
核心职责 一次 Agent Run 的实时执行 Agent 系统如何被配置、治理、评估和发布
包含组件 Agent, Runtime, State, Tool, Model, Memory Agent Registry, Prompt Registry, Policy, Version Management, Eval
关注点 延迟、吞吐量、并发、可靠性 配置、权限、评估、版本、多租户治理
Trade-off 决策 优化执行路径，尽量无状态化或快速状态恢复 优化管理界面与一致性，允许较高延迟
反直觉观点 4： 一个 Agent Platform 最重要的不是“能创建 Agent”，而是“能治理 Agent”。没有 Control Plane，Agent 很容易停留在“应用代码”；有了 Control Plane，才开始接近 Agent Platform。

05. Agent Registry 与版本化

Agent Registry 解决了 Agent 的版本化与配置寻址问题。在生产环境中，我们面临的痛点是：当线上 Agent 出现异常行为时，我们无法确定它当时运行的是哪个 Prompt、用的是哪个 Model 版本、调用了哪个 Tool。

{

  "version": "1.2.0",
  "prompt_ref": "prompt_v8_refund_policy",
  "model_ref": {"primary": "gpt-4o-2024-08-06", "fallback": "claude-3-5-sonnet"},
  "tools": ["query_order", "create_refund", "check_policy"],
  "memory_policy": {"window": 10, "summary_strategy": "rolling"},
  "guardrails": ["no_cross_tenant", "max_refund_5000"],
  "budget": {"max_tokens": 5000, "max_steps": 10}
}

06. Model Gateway / Model Router

生产架构应该避免 Agent 直接耦合特定的 LLM Provider。Model Gateway 把模型依赖从 Agent 业务逻辑中隔离出来。它提供 Provider abstraction, Model routing, fallback, rate limit, quota, cost routing, latency routing 等能力。

例如，在电商客服场景中，对于简单的“查物流”意图，Gateway 可以路由到便宜快速的 GPT-4o-mini；而对于涉及“高额退款谈判”的意图，路由到 GPT-4o。当 OpenAI 集群限流时，Gateway 自动 fallback 到 Azure OpenAI。

07. Tool Gateway / Tool Runtime

不要让 Agent 直接调用任意 API，而应该通过 Tool Runtime。它负责 schema validation, authentication, tenant isolation, timeout, retry, idempotency, audit。

在电商客服案例中，当 LLM 幻觉生成一个错误的 JSON 参数（如 order_id="abc" 传给 query_order），Tool Runtime 的 Schema Validation 会直接拦截并返回结构化错误，提示 LLM 重新生成，而不是导致底层业务系统崩溃。

反直觉观点 3： Tool 越多不代表 Agent 越强；Tool Governance 往往比 Tool 数量更重要。当 Tool 增加到 100 个时，如果没有 Tool Gateway 的权限和路由治理，Agent 将陷入选择困难和安全灾难。

08. State、Memory、RAG 如何进入架构？

这三者不能混为一谈，必须划清边界：State 是当前运行状态（如暂存的 Tool 返回的巨大 JSON）；Memory 是跨时间的信息（如用户历史偏好）；RAG 是外部知识（如退换货政策）。Runtime 应该负责 Context Assembly。

09. Context Builder：被低估的核心组件

模型上下文不是数据库，不能什么都塞进去。Context Builder 负责优先级排序与 Token Budget 控制。在电商退款场景中，它优先保留 System Prompt 和 RAG 片段，截断冗长的 Tool Result（如支付流水号列表），确保 LLM 拿到的是最精简、最相关的上下文。

10. Policy Engine

这是 Production Agent 和 Demo Agent 的重要分水岭。Policy 决定可以调用什么 Tool、什么 Tool 需要确认、最大金额等。当电商客服 Agent 决定调用 create_refund 工具，且金额为 6000 时，Policy Engine 会拦截并要求人工审批。

反直觉观点 5： 生产 Agent 不应该追求完全自动化，而应该追求可控自动化。Policy 不应该藏在 Prompt 里（“请不要退款超过 5000” LLM 可能不听），应该是机器可执行的确定性约束。

11. Security Architecture

安全架构不仅是对外防黑客，更是对内防 Agent 幻觉。包括 Authentication（谁在调用）、Authorization（允许做什么）、Tenant Isolation（谁可以看到什么）、Tool Permission（Agent 可以调用什么）、Data Security、Secret Management（严禁进入 Prompt）和 Audit。

12. Agent Identity

传统系统是 User -> Service，服务自己持有身份。Agent 系统是 User -> Agent -> Tool -> Business Service。因此 Tool 执行时必须知道：这是哪个用户通过哪个 Agent 发起的？建立 Agent Identity Chain 透传 user identity, tenant, agent identity, request id, trace id, authorization scope。如果缺少这一环，退款 API 会以为是 Agent 这个服务账号在退款，导致审计失败和越权风险。

13. Multi-Tenant Architecture

生产 Agent 平台通常服务多个企业。Memory、RAG、Tool、Configuration 都必须隔离 Tenant。最危险的 Agent Bug 之一，是跨 Tenant 数据泄露。 例如，A 公司的客服 Agent 在进行 RAG 检索时，如果索引没有按租户分片，可能会检索到 B 公司的产品手册。

14. Execution State 与 Checkpoint

Agent 运行通常不是一个瞬时函数。因为 Agent 可能超时、进程重启、Tool 长时间运行，所以 Runtime 需要 Durable State。

Trade-off State 存储 无状态执行
适用场景 长任务，多步骤，需人工介入，高可靠性（如电商长流程退款） 无状态查询，简单 RAG，单次推理任务（如简单的物流查询）
优势 支持恢复、暂停、审计，进程崩溃不丢数据 极致伸缩性，无数据库瓶颈
劣势 存储成本，状态机复杂度增加，可能有一致性问题 不可恢复，并发控制困难，长任务 HTTP 超时

15. Human-in-the-Loop (HITL)

有些任务必须进入人工审核。当 Policy Engine 判定高风险时，Agent Runtime 将 State 挂起并持久化，推送到人工审核队列。审核通过后，Runtime 恢复 State，继续执行 create_refund。

16. Async Agent 与长任务

很多 Agent 不适合 HTTP 同步等待。当 Agent 需要执行深度研究、大规模文档处理、多 Agent 协作时，HTTP 连接会在 60 秒后超时。

Trade-off 同步 异步
适用场景 单次问答，快速 Tool 调用，SLA < 10s 深度研究，人工审批，SLA > 30s
实现 HTTP Request -> Response Create Run -> Run ID -> Event/Webhook/Polling -> Result

17. Event-Driven Agent Runtime

当执行时间、并发、可靠性和解耦需求真正出现时，再引入事件驱动。通过 Kafka/Queue 将 Agent 步骤解耦为独立 Worker。优势是解耦、异步、重试、扩展。但不要为了“微服务化”而复杂化。

反直觉观点 6： 架构复杂度不是越低越好，也不是越高越先进；正确的架构是复杂度与真实业务规模匹配。只有当真正需要时，再引入 Kafka，而不是为了显得“企业级”而无脑加入。

18. Observability 在架构中的位置

不要把 Observability 放在架构图最底部当成附属模块。它应该横向贯穿整个 Runtime。Production Agent 没有 Trace，就没有真正的运行可见性。因为 Agent 的执行路径是概率性的，你无法通过阅读代码预知它走了哪条路。必须通过 Trace 追踪每一步的 LLM 输入输出、Tool 执行耗时、Token 消耗。

Trade-off 全量 Trace Sampling (采样)
适用场景 核心链路，高风险操作，Debug 阶段，复杂多步推理 高频简单查询，成本敏感场景，线上稳定期
优势 100% 可追溯，不遗漏任何长尾 Bug 节省存储成本，降低 Trace 系统写入压力
劣势 存储成本极高，Trace 系统 (如 Jaeger) 可能成为瓶颈 难以捕捉偶发错误，可能导致关键审计缺失

19. Evaluation 在架构中的位置

Evaluation 不应该只是上线前跑一下测试。生产架构应当形成 Continuous Evaluation（持续评估闭环）。从线上提取 Trace，转化为 Eval Dataset，在离线环境对新版本 Prompt/Model 进行 Regression 测试，作为 Release Gate。

20. Reliability Layer

把 Reliability 正式落地。Runtime 应该拥有 Reliability Controller，包含 Timeout, Retry, Fallback, Budget, Circuit Breaker, Loop Detection, Safe Stop。Reliability 不是业务逻辑的一部分，而应该成为 Runtime Capability。

伪代码 1：Agent Runtime 主循环（展示框架无关的执行逻辑）

def run_agent_runtime(request: Request):
    # 1. 构建上下文
    context = context_builder.build(request)
    state = state_store.load(request.session_id)
    
    # 2. 执行循环，受 Runtime 控制
    while runtime.can_continue(state):
        try:
            # 2.1 Agent 决策 (LLM)
            decision = agent.decide(context=context, state=state)
            
            # 2.2 Policy & Guardrails 校验
            policy.validate(decision, user_scope=request.user)
            
            # 2.3 执行器执行
            result = executor.execute(decision)
            
            # 2.4 状态更新与持久化
            state = state_manager.update(state, result)
            observability.record_trace(state, decision, result)
            
            if task_completed(state):
                break
                
        except LoopDetectedError:
            runtime.safe_stop(state)
            break
        except BudgetExceededError:
            runtime.trigger_fallback(state)
            break
        except ToolTimeoutError:
            executor.retry_with_fallback(decision)
            
    return response_builder.build(state)

21. Cost Architecture

生产环境不能只看 Task Success，还必须关注 Cost / Successful Task。成本来自 LLM + Embedding + Reranker + Tool + Storage + Network。建立 Cost Budget -> Agent Run -> Track -> Limit -> Alert 的控制链路。通过 token budget, model routing, cache, semantic cache 优化成本。

反直觉观点 2： Agent 越智能，不代表系统越可靠；智能越强，越需要确定性的边界控制。成本失控往往就是因为 Agent 在死循环中不断消耗 Token。

22. Performance Architecture

Total Latency = LLM + Tool + Retrieval + Memory + Network + Queue。指出 Agent latency 通常不是一个模型调用决定的。通过 parallel tool calls, streaming, speculative execution, caching, timeout budget 优化。例如，电商客服在查询订单的同时，可以并行查询物流状态，而不是串行等待。

23. Deployment Architecture

从 Single Process 演化到 API -> Agent Runtime Cluster -> Worker Cluster -> Tool Services -> Model Gateway。推荐 模块化单体 → 服务化 → Agent Platform，而不是一上来几十个微服务。这降低了初期的运维成本和调试复杂度。

Trade-off 单体架构 微服务架构
适用场景 初创期，业务边界模糊，团队规模小（<10人） 多业务线，需独立扩容，团队规模大
优势 开发快，无网络开销，Debug 简单，无分布式事务问题 故障隔离，独立伸缩，技术栈解耦
劣势 一崩全崩，代码冲突多，无法局部扩容 运维成本极高，调试困难，强一致性难以保证

24. Versioning Architecture

生产 Agent 至少需要同时版本化：Agent, Prompt, Model, Tool, Policy, Knowledge, Evaluation。因为线上 Bug 必须能够回答：“当时运行的到底是哪一个版本？”

版本组件 变更频率 回滚策略
Agent Version中Registry 路由切流
Prompt Version高文本回滚
Model Version低Gateway Router 切换
Tool Version中Tool Registry 切换
Policy Version低Policy Engine Reload
Knowledge Version高Vector DB Snapshot

25. Release Strategy

介绍 Shadow（旁路执行）, Canary（小流量）, A/B, Rollback。Agent 特别需要 Prompt / Model / Tool / Policy 的联合版本发布。例如，新 Prompt 导致 LLM 倾向于调用一个新 Tool，如果只灰度了 Prompt 没有灰度 Tool，会导致大量调用失败。

26. Agent Configuration vs Code

哪些应该配置化？Tools, Models, Prompt, Budget, Policies, Routing, Guardrails。哪些应该代码化？Core runtime, Security enforcement, State machine, Recovery logic。核心原则：业务策略可以配置化，安全边界不能依赖普通配置。

27. 一个完整生产级 Agent Run

用一个完整的电商智能客服 Agent 案例贯穿：“帮我把这个订单退掉”。

[User] -> "帮我把这个订单退掉"
  ↓
[API Gateway] -> Auth: User A, Tenant: E-commerce Co. -> 路由至 Runtime
  ↓
[Agent Runtime]
  ├── [Context Builder]
  │     ├── State: (无历史执行)
  │     ├── Memory: 提取 User A 是 VIP，历史满意度低
  │     ├── RAG: 检索"大家电退款政策" (基于用户当前订单类目)
  │     └── Token Budget: 4000 (截断部分政策片段)
  ↓
  ├── [Agent / Planner] (LLM 决策)
  │     └── LLM Output: Intent=refund, Action=query_refund_eligibility(order_id=123)
  ↓
  ├── [Policy Check] 
  │     └── Allow: query_refund_eligibility
  ↓
  ├── [Execution Controller] -> Tool Runtime
  │     ├── Schema Validation: OK
  │     └── Call API: query_refund_eligibility(order_id=123)
  │           └── Response: Eligible=true, Amount=6000
  ↓
  ├── [Agent / Planner] (LLM 决策)
  │     └── LLM Output: Action=create_refund(order_id=123, amount=6000)
  ↓
  ├── [Policy Check]
  │     └── Constraint: Amount(6000) > AutoLimit(5000) -> HIGH RISK
  ↓
  ├── [Human-in-the-Loop Triggered]
  │     └── Save Checkpoint to State Store, push to Audit Queue
  ↓ (人工审批通过，触发恢复)
  ├── [Runtime Resume]
  │     └── Load Checkpoint, Continue Execution
  ↓
  ├── [Execution Controller] -> Tool Runtime
  │     ├── Idempotency Token: generated
  │     ├── Call API: create_refund
  │     │     └── Tool Timeout (Network Issue)
  │     ├── Retry 1: Exponential Backoff
  │     │     └── Fallback Triggered -> Fallback Tool: queue_manual_refund
  │     └── Result: Refund Queued Successfully
  ↓
  ├── [State Update] -> Update final status
  ↓
  ├── [Observability] -> Record Full Trace, Token Cost, Latency
  ↓
  └── [Final Response] -> "已为您发起退款申请，由于金额较大，已进入加急处理队列"

异常场景验证：如果发生 Tool Timeout，Runtime 通过 Retry 机制恢复；如果发生 Duplicate Refund（用户狂点），Idempotency Token 阻断；如果发生 High-risk approval，系统不会崩溃而是进入挂起状态。这就是 Production Architecture 的威力。

28. 从 Agent Application 到 Agent Platform

Agent Application 解决一个具体业务。Agent Platform 提供 Runtime, Tool Registry, Model Gateway, Memory, Knowledge, Policy, Evaluation, Observability, Deployment, Governance。当你的公司需要同时上线电商客服、内部 IT Helpdesk、销售助手时，你需要的是 Platform。

Trade-off 应用内实现 Platform 化
适用场景 单业务线，快速验证，团队规模小 多业务线，多租户，需要统一治理与复用
何时选择 当验证想法比稳定性更重要时 当应用数 >3，且跨团队开发时

29. 什么时候应该建设 Agent Platform？

不需要 Platform：只有一个 Agent，Tool 很少，没有多租户。开始需要：Agent 多个，Tool 复用，多 Provider，高频迭代 Prompt。真正的平台化：当 Runtime 成为多个 Agent 的公共基础设施。

31. 生产级 Agent 的最小架构 (MVP)

第一版不一定需要 Kafka, Service Mesh。核心原则：先建立 Runtime，再逐渐平台化。 MVP Architecture：API Gateway -> Agent Runtime (State, Context Builder, Tool Runtime, Guardrails, Reliability, Trace) -> Model Gateway -> Business Services。

32. Production Checklist

  • Runtime: Timeout, Max Steps, State, Cancellation, Checkpoint
  • Tools: Schema, Permission, Idempotency, Audit
  • Model: Gateway, Fallback, Rate Limit
  • Memory/RAG: Tenant Isolation, Versioning, Retrieval Control
  • Reliability: Retry, Fallback, Budget, Loop Detection, Safe Stop
  • Observability: Trace, Metrics, Logs, Cost
  • Evaluation: Golden Set, Regression, Release Gate
  • Security: Authentication, Authorization, Data Isolation, Secret Management, Audit

34. 最终统一公式与结论

Production Agent = Intelligence + Runtime + State + Tools + Policy + Reliability + Observability + Evaluation + Governance

Agent 本身只是系统的一部分。真正进入生产环境的是 Agent System。

Production Agent 的核心，不是把 Demo 做大，而是把“智能”放进一个可治理的运行时。

一个真正生产级的 Agent 系统应该具备完整的运行时、状态管理、策略执行、恢复机制和可观测性。也因此，Agent Engineering 最终会从“Prompt Engineering”走向“Systems Engineering”。
