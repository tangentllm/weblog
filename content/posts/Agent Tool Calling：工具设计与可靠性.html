AGENT ENGINEERING · 系列第 5 篇

Agent Tool Calling：
工具设计与可靠性

Agent 的能力上限，很大程度取决于它能够可靠调用什么工具；而 Agent 的稳定性，又取决于这些工具是否被正确设计。本文不解释 Function Calling 语法，只讨论 Tool Design 与 Tool Reliability 两个生产级核心问题。

系列：Workflow → Single Agent → Multi-Agent → Memory → Tool Calling 阅读：~25 min 级别：Production / Architect
◈ 本文在系列中的位置

上一篇 Agent Memory 解决的是：过去的信息如何进入当前决策。本文解决的是它的对偶问题——当前决策如何转化为外部世界的行动。

Agent ├── Context ├── State ├── Memory ← 记住过去 └── Tools ← 改变现在 ↓ Action
01

Agent 为什么需要 Tool Calling

先建立一个贯穿全文的判断标准，再谈设计。

当 Agent 只需要推理、总结、改写文本时，LLM 本身就够了。但当 Agent 需要访问实时数据、执行外部动作或改变业务状态时，语言模型与真实世界之间就出现了一条鸿沟——模型能"说"出答案，却无法"做"出结果。Tool 正是跨越这条鸿沟的能力边界。

因此，Tool Calling 不应该被理解为"给 LLM 挂几个 API"。它是在 Agent 与真实世界之间建立一层可控的行动接口。Tool 的本质是 Agent 的 Action Interface：

Tool Calling = Decision + Contract + Execution + Recovery + Observation，
而不是 LLM → Function → Result
图 1 · Tool Calling 的基本闭环：Action → Observation → Next Decision
02

Tool Calling 到底解决什么问题

从一个最朴素的场景开始。用户对电商 Agent 说："帮我查一下订单 123456。"

Agent 需要完成一条完整的链路：理解意图 → 选择 query_order → 生成参数 → 调用 API → 读取结果 → 生成回答。没有 Tool 时，LLM 只能生成文字——它或许能"编"出一个订单状态，但那不是事实。有 Tool 之后，链路变成了闭环：

LLM ↓ Decision（选择工具 + 生成参数） Tool ↓ External World（真实的订单系统） ↓ Observation（结构化事实返回） ↓ Next Decision（基于事实继续推理）
CORE INSIGHT

Tool Calling 的本质，是把 LLM 的语言决策连接到确定性的外部执行系统。模型负责"决定做什么"，Tool 负责"确定地做到"。这两个职责一旦混淆——比如让模型猜业务规则、让 Tool 替模型做选择——系统就会同时失去灵活性和可靠性。

03

Tool 应该设计成多大

这是 Tool Design 中第一个真正需要做权衡的决策，也是大多数团队踩的第一个坑。

方案 A：超级 Tool（God Tool）

handle_customer_request( request )

所有事情交给一个 Tool。看似简单，实际上 Schema 完全不透明——模型无法从一个 request 字符串中理解系统能力边界；权限无法按动作控制；一次失败无法定位是查询出错还是退款出错；观测数据也失去了区分度。

方案 B：过度细粒度（Tool Explosion）

get_order_id() get_order_product() check_order_status() get_order_payment() get_order_logistics() get_order_refund_status() ...

能力确实清晰了，但代价是 Tool 数量爆炸：选择空间变大导致选错概率上升；Agent 需要多次串联调用，推理链变长、延迟累加；任何一步失败都会打断整个任务。

方案 C：业务能力级 Tool（通常更合理）

query_order() query_refund_status() create_refund() cancel_order()

每个 Tool 对应一个稳定的业务动作。这就是本文的粒度原则：

DESIGN PRINCIPLE

Tool 的粒度应该围绕"Agent 需要做出的业务动作"设计，而不是围绕底层 API 的粒度设计。底层 API 可能有二十个端点，但 Agent 的业务动作可能只有四个。

表 1 · Tool 粒度 Trade-off
设计优点缺点适用场景
粗粒度调用链短、决策次数少能力边界模糊、权限难控、错误难定位能力单一、低风险场景
中等粒度能力清晰、可选性适中、权限可按动作划分需要认真设计业务边界绝大多数生产系统
细粒度每个能力精确、可组合Tool Explosion、选择成本高、链路脆弱仅当组合确实由模型动态决定时

一个实用的反例检验：如果某两个 Tool 总是被一起调用，它们大概率应该合并成一个业务动作；如果某个 Tool 的参数里藏着一个"动作类型"枚举（action: query|cancel|refund），它大概率应该拆开。粒度不是越细越好，也不是越粗越好，而是围绕稳定业务能力取中。

一个能力到底该不该设计成 Tool？

在确定粒度之前，还有一个更前置的判断：这个能力是否值得做成 Tool。

一个能力是否应该设计成 Tool？ │ ↓ 是否需要外部系统 / 实时数据 / 副作用？ │ ┌────┴─────┐ No Yes ↓ ↓ 普通推理 Tool Candidate （无需 Tool） │ ↓ 是否有清晰业务边界？ │ ┌──────┴──────┐ No Yes ↓ ↓ 重新定义边界 Tool （不要包装成"万能函数"） （明确能力 / 输入 / 输出 / 副作用 / 权限）

换句话说，不是所有 API 都应该包装成 Tool。Tool 不应该成为"万能函数"——一个合格的 Tool 必须有明确能力、明确输入、明确输出、明确副作用、明确权限边界。如果一个能力无法回答"它的业务边界在哪"，正确的做法是先重新定义边界，而不是急着暴露给模型。

04

Tool Contract：工具能力的边界

一旦确定了粒度，下一步是把每个 Tool 定义成一份完整的契约——而不只是一个函数签名。

一个面向生产系统的 Tool Contract 至少包含以下部分：

图 2 · Tool Contract 的八个维度：Schema 只是其中一角

逐项来看容易被忽略的几个：

  • Preconditions：调用前提。例如"订单必须存在且属于当前用户"。前提条件应尽量由系统校验，而不是指望模型自己判断。
  • Side Effects：是否有副作用、是否可逆。这直接决定该 Tool 是否需要确认机制（见第 12 节）。
  • Idempotency：同一请求重复执行是否安全。这决定了超时后能不能重试（见第 11 节）。
  • Error Model：失败时返回什么。结构化错误语义是重试决策的依据（见第 10、13 节）。

以退款为例，一个合格的工具定义长这样：

tool_contract.json · create_refund
// Schema 不是文档，而是 Agent 与 Tool 之间的机器可读契约
{
  "name": "create_refund",
  "description": "Create a refund request for an eligible order.",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "The order ID to refund, e.g. 123456"
      },
      "reason": {
        "type": "string",
        "enum": ["damaged", "wrong_item", "quality_issue"],
        "description": "Structured refund reason, must be chosen from enum"
      }
    },
    "required": ["order_id", "reason"]
  }
}
05

Tool Description：如何让模型理解工具

模型是否正确调用 Tool，很大程度取决于 Name、Description、Schema、Enum、Constraints 这些"说明书"的质量。换句话说——Tool Schema 本质上也是 Prompt Engineering 的一部分。

先看一个真实的反例。很多团队这样写描述：

❌ "查询订单"

这句话没有告诉模型任何决策所需的信息：能查到什么？订单不存在怎么办？用户没给订单号时该做什么？应该写成像这样的完整说明书：

✓ "查询指定订单的当前状态、支付状态、物流状态以及可执行的售后操作。 仅适用于已经存在的订单。 如果用户没有提供订单号，不要猜测，应先向用户询问订单号。"

注意第二段：告诉模型"什么时候不要使用"，往往比"什么时候使用"更能减少错误调用。query_refund_status 和 create_refund 的混淆，多数时候就是靠描述里的"不要"条款解决的。

DESCRIPTION CHECKLIST

一份优秀的 Tool Description 至少回答六个问题：What（做什么）、When（何时使用）、When NOT（何时不该用）、Input（参数怎么来）、Output（返回什么结构）、Constraints（有什么限制）。

06

Tool Selection：如何选择正确工具

Tool 越多，不代表 Agent 越强。

用户问："我的订单什么时候能退款？"Agent 手上有 query_order、query_refund_status、create_refund、cancel_order……它必须选择 query_refund_status 而不是 create_refund——选错后者，就是一个真实的退款单被创建了。Tool Selection 本质上是一个 Capability Routing 问题：

图 3 · Tool Selection Pipeline：意图 → 召回 → 选择 → 参数 → 校验

几十个甚至上百个工具，全部暴露给 LLM 吗？

通常不应该。所有工具的 Schema 都会进入上下文，直接推高 Token 成本和延迟；更重要的是，选择空间越大，模型选错的概率越高。工程上有几种渐进的解法：

  • Tool Group：按业务域分组（订单组、售后组、商品组），先路由到组，再在组内选择。
  • Tool Router：用轻量模型或嵌入检索做第一跳路由，只把候选工具暴露给主 Agent。
  • Dynamic Tool Discovery：依托 Tool Registry（第 20 节），按意图动态召回相关工具，而非静态全量注入。
  • Hierarchical Selection：先选"能力类别"，再选"具体动作"，两层决策各自缩小空间。

当工具规模超过约 20 个时，这些机制就不再是优化项，而逐渐成为必要项（具体阈值取决于模型能力与任务复杂度，需要实测）。

07

Schema：如何约束参数

Schema 决定可靠性——因为能在 Schema 层表达的约束，就不应该依赖 Prompt 或模型自觉。

对比同一个参数的三种写法：

schema_evolution · 从"能用"到"可靠"
// ① 差：语义不明，模型只能靠猜
{ "order": { "type": "string" } }

// ② 好：名称明确 + 示例描述
{ "order_id": { "type": "string",
    "description": "The user's order ID, e.g. 123456789" } }

// ③ 更好：用 enum 把自由文本变成受控词表
{ "reason": { "type": "string",
    "enum": ["damaged", "wrong_item", "quality_issue"] } }

第 ③ 种写法的价值在于：reason 从"模型自由发挥的字符串"变成了"从有限集合中选择"。自由文本意味着下游系统要做模糊匹配，而模糊匹配就意味着不确定性。

CONSTRAINT PUSHDOWN

约束应该逐层前推：能用 Schema 表达的，不要留给 Prompt；能用系统校验的，不要留给模型判断。即 LLM Reasoning → Schema Constraint → System Validation，约束越靠前，不确定性越少。

08

Argument Validation

Tool Calling 在生产中最常见的问题，不是调用失败，而是参数错误。

典型症状：API 要求 order_id 是字符串，模型给了数字 123456；参数为空串；或者 reason 填了 "我觉得商品坏了"这种 enum 无法匹配的自由文本。所以执行前必须有一条完整的校验链：

LLM Output ↓ JSON Schema ← 结构合法吗 ↓ Type Validation ← 类型 / 必填 / Enum / Format ↓ Business Validation ← 业务上允许吗 ↓ Permission Validation ← 这个用户可以吗 ↓ Execution

这里必须严格区分两类校验，它们对应完全不同的错误处理策略：

◆ Schema Validation vs Business Validation

Schema Validation 解决"格式正确"：类型、必填、Enum、Format。失败意味着模型生成的参数不合法，通常可以通过错误信息让模型重新生成。

Business Validation 解决"业务上允许"：订单是否存在、用户是否拥有该订单、是否已过退款期、是否已退款。失败不重试、也不该让模型再猜——需要把结构化错误返回给模型或转人工。

pseudocode · 三层校验（框架无关）
def validate(tool, args, user):
    # 第一层：Schema 校验 —— 格式是否正确
    errors = json_schema_validate(args, tool.input_schema)
    if errors:
        return Reject(errors, ask_user=True)

    # 第二层：业务校验 —— 业务上是否允许
    order = order_repo.find(args["order_id"])
    if order is None:
        return StructuredError("ORDER_NOT_FOUND")
    if order.owner != user.id:
        return StructuredError("PERMISSION_DENIED")
    if order.status not in REFUNDABLE:
        return StructuredError("NOT_REFUNDABLE")

    # 第三层：权限校验
    if not policy.allows(user, tool, args):
        return StructuredError("FORBIDDEN")

    return Pass()
09

Tool Reliability 模型

不要把可靠性寄托在"API 成功率"上。一次工具调用有六个可能失败的层面。

Tool Reliability │ ├── Selection ← 选错工具 ├── Argument ← 参数错误 ├── Permission ← 越权调用 ├── Execution ← 超时 / 5xx / 限流 ├── Result ← 返回内容无效 └── Recovery ← 失败后无法恢复

这些失败还会级联放大：选错工具 → 必然生成错误参数 → 触发业务校验失败 → 模型重试又选错 → 进入循环。所以生产系统不能只看 API 成功率，而要看 End-to-End Tool Success Rate：从"用户表达意图"到"业务动作正确完成"的全链路成功率。

图 4 · Reliability Pipeline：每一层都是独立的失败点，错误沿链条级联
10

Retry / Timeout / Circuit Breaker

Tool 失败后是否一定 Retry？答案是不一定——而且"失败就重试"在生产环境里是危险行为。

Agent Tool 可能调用支付、物流、搜索、CRM 等各种下游，任何一个都可能变慢或抖动。重试决策必须基于错误语义分类：

◆ 可以 Retry vs 不应该 Retry

✓ 可以重试：Network Timeout（前提是幂等）、Temporary 5xx、Rate Limit、Temporary Service Unavailable —— 这些是瞬时故障，重试有期望收益。

✗ 不应重试：Invalid Argument、Permission Denied、Business Rule Violation、Resource Not Found —— 这些是语义性失败，重试只会得到相同结果，还可能放大副作用。

pseudocode · 基于错误语义的恢复策略
def run_with_recovery(tool, args, ctx):
    for attempt in range(tool.max_retries + 1):
        try:
            return tool.execute(args, timeout=ctx.timeout)
        except Timeout:
            if not tool.idempotent:
                raise          # 非幂等工具不能盲目重试！
            backoff(attempt)   # 指数退避
        except RateLimit as e:
            backoff(e.retry_after)
        except (InvalidArgument, PermissionDenied,
                NotFound, Conflict) as e:
            return structured_error(e)  # 语义失败：重试无意义
        except DependencyDown:
            if breaker.is_open(tool.name):
                return fallback(tool, ctx)  # 熔断打开，走降级
            backoff(attempt)
    return structured_error(ExhaustedRetries())

Timeout 是预算，不是单点配置

最常见的错误配置：每个 Tool 超时 30 秒。这意味着一个调用 5 个工具的任务，最坏情况要等 150 秒——用户早就离开了。正确的做法是把超时当成整条请求的时间预算来分配：

Request Budget = 10s Tool A = 2s → Tool B = 3s → Retry = 2s → LLM = 3s 而不是：Tool A timeout 30s，Tool B timeout 30s ……

配套机制包括：区分 Connection Timeout 与 Read Timeout、维护 Retry Budget（限制重试总耗时）、对持续故障的下游启用 Circuit Breaker（快速失败 + 降级答案）、以及对单个工具设置并发上限。核心思想只有一个：任何单个工具都不允许拖垮整条请求。

11

Idempotency

生产级 Tool Calling 绕不开的一课：重试 + 非幂等 = 重复副作用。

考虑一个真实的故障序列。Agent 调用 create_refund()，网络超时——但下游其实已经执行成功。系统判定失败并重试，于是：

Call → Timeout → Retry → Call Again 结果： Refund #1 （第一次调用，实际已成功） Refund #2 （重试产生的重复退款）

解决方案是 Idempotency Key：由业务语义构造一个确定性键，例如 user_id + order_id + action + request_id。下游在执行前先检查该键是否已处理过，处理过则直接返回上次结果：

Agent ↓ Tool Call（携带 Idempotency Key） ↓ Idempotency Check ↓ Execute Once ← 相同 Key 只会真正执行一次 ↓ Result
PRODUCTION RULE

所有具有副作用的 Tool，都应该认真考虑幂等性。判断标准很简单：这个 Tool 被意外执行两次，业务上能接受吗？退款、下单、发消息、改地址——答案几乎总是否定的。而纯查询类工具天然幂等，无需额外处理。

12

副作用与确认机制

Tool 必须按风险分级——查询类和修改类工具，不能用同一套执行策略。

表 2 · Read Tool vs Write Tool
类型典型工具风险执行策略
Read-onlyquery_order · search_product · query_logistics低（只读，可逆，无副作用）可直接自动执行
Side-effectcreate_refund · cancel_order · submit_order · send_message中到高（改变业务状态，可能不可逆）确认 / 授权后执行

Agent 应该直接执行高风险动作吗？

答案不是简单的 Yes 或 No，而是一个四级决策，依据风险、金额、用户授权、可逆性和业务规则综合判断：

Tool（有副作用） ├─ 低风险 + 可逆 + 用户已授权 → Auto Execute （如修改收货地址） ├─ 中风险 / 涉及资金 → Human Confirmation （Agent 展示摘要，用户点确认） ├─ 高风险 / 大额 / 不可逆 → Human Approval （进入人工审批队列） └─ 违反业务规则或权限不足 → Reject （直接拒绝并说明原因）

实践中最容易被低估的是中间两级：很多团队做到了"退款需要确认"，却忘记了大额退款和普通退款应该走不同的通道。风险分级应该是连续的，而不是二值的。

13

Tool Result 与 Error Design

多数人只打磨 Input，但 Output 同样重要——Tool Result 是 Agent 下一步决策的 Observation。

最糟糕的返回方式是把整个 API Response 原样塞回上下文：字段冗余、结构混乱，模型需要"猜"哪个字段是关键信息，且白白消耗 Token。正确的做法是为 Agent 设计专门的返回结构：

tool_result · 成功与失败都应结构化
// 成功：只返回 Agent 决策需要的字段
{
  "success": true,
  "order": {
    "id": "123456",
    "status": "shipped",
    "refund_eligible": true   // 预计算的业务标志，避免模型自行推断
  }
}

// 失败：错误也必须结构化，携带机器可读语义
{
  "success": false,
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "Order does not exist"
  }
}

refund_eligible 这个字段值得特别一提：与其让模型根据 status、paid_at、refund_window 自行推断"能不能退"，不如由系统预计算后直接返回结论。能由确定性逻辑得出的判断，就不应该交给概率性推理。

错误不应该只返回 Exception

把 Java 堆栈直接丢给模型，它既读不懂也不知道该怎么办。应该建立错误分类体系，每一类错误对应明确的处理动作：

Tool Error │ ├── Validation Error （参数不合法） ├── Authentication Error （身份失败） ├── Authorization Error （权限不足） ├── Not Found （资源不存在） ├── Conflict （业务冲突） ├── Rate Limit ├── Timeout ├── Dependency Failure （下游不可用） └── Unknown Error

Agent Loop 与 Tool Calling

现在把前面所有组件组装成标准循环。

Tool Calling 的本质不是"一次函数调用"，而是 Agent Decision Loop 中的 Action → Observation → Next Decision。每一次工具调用的结果都会改变状态，状态又驱动下一次决策：

图 5 · Agent Tool Loop：一个有边界的决策状态机，而非无限循环
pseudocode · Agent Tool Loop（框架无关）
MAX_STEPS = 8              # 最大循环步数
REQUEST_BUDGET = 10.0      # 整条请求的时间预算（秒）

state = init_state(user, conversation, memory)

for step in range(MAX_STEPS):
    if elapsed() > REQUEST_BUDGET:
        return degrade(state)          # 预算耗尽，降级回答

    decision = agent.decide(state)     # LLM 决策

    if decision.is_final:
        return decision.answer         # 无需工具，输出最终答案

    if is_repeated(decision, state):   # 重复调用检测
        return fallback(state)

    tool = registry.lookup(decision.tool)
    if tool is None or not authorized(user, tool):
        state.observe(error("PERMISSION_DENIED"))
        continue

    result = executor.run(
        tool, decision.args,
        timeout=remaining_budget(),
        idempotency_key=make_key(user, decision),
    )

    state.observe(result)              # Observation 进入状态，驱动下一轮
15

防止无限调用

一个真实发生过的事故模式：Agent 反复调用 query_order，每次结果都一样，但它"觉得"再查一次也许就好了。

Agent → query_order → query_order → query_order → …（永不停止）

这不会自己停下来。所以 Agent 必须是一个有边界的状态机，至少配置五道护栏：

  • Max Tool Calls：单次任务允许的工具调用总数上限。
  • Max Loop Steps：推理循环步数上限。
  • Time Budget：整条请求的挂钟时间预算。
  • Repeated Call Detection：相同工具 + 相同参数（归一化后）的重复调用，直接命中即终止或降级。
  • Duplicate Request Detection：借助 Idempotency Key 识别语义重复的请求。

这些护栏在上一节的循环伪代码中都有体现。触发护栏后的行为同样重要：不是抛异常，而是优雅降级——告诉用户"目前无法完成，已为您转人工"，同时携带完整 Trace 供排查（见第 17 节）。

16

Security 与 Authorization

真正的危险场景往往不是"Agent 被攻破"，而是更平凡的一种：Agent 获得了超过用户权限的工具能力。

系统架构上，调用链是 User → Agent → Tool → Business System。如果 Agent 以自己的服务账号调用下游，那么任何用户——包括不拥有该订单的用户——都可能通过 Prompt 让 Agent 查询或修改别人的数据。正确的身份链应该是：

User Identity ↓ Agent Context（携带身份 + 租户 + 会话） ↓ Authorization（按用户身份校验，而非 Agent 身份） ↓ Tool → Business System
SECURITY PRINCIPLE

不要因为 Agent 可以调用 Tool，就默认 Agent 有权限调用 Tool。Agent 是行动的代理者，不是权限的授予者。权限永远来自它所代表的用户。

生产清单至少包括：

  • Authentication / Authorization：每个 Tool 调用前按用户身份鉴权，工具粒度的权限矩阵。
  • Tenant Isolation：多租户场景下，查询参数与数据范围必须强制绑定租户。
  • User Scope / Tool Scope：普通用户与客服坐席可用的工具集合不同；同一工具的参数范围也可不同（如退款金额上限）。
  • Sensitive Parameters：支付凭证、身份证号等敏感参数尽量不经过模型——由前端安全通道直传，模型只持有引用句柄。
  • Audit Log：所有副作用调用必须留痕：谁、在什么会话中、批准人是谁、执行了什么。
  • Secret Management：下游 API 密钥只存在于执行层，永不进入模型上下文和日志。
17

Tool Observability

无法观测的 Agent 无法调试。Tool Calling 必须留下完整的痕迹。

每一次工具调用至少记录：

request_id · trace_id · agent_id · tool_name · arguments start_time · duration · status · error_code · retry_count user_id / tenant_id

但要注意一条红线：敏感参数不能无条件进入日志。日志层应做字段级脱敏——金额可以留，卡号、手机号应掩码或哈希。观测的目标是回答三个问题：

这个 Tool？

失败？

而非堆栈字符串

EVALUATION PRINCIPLE

最终评价 Tool Calling 的标准不是"函数调用成功"，而是 "Agent 是否完成了正确的业务目标"。一个工具 100% 调用成功、但选错了工具导致用户流失的系统，比一个偶尔超时但能正确恢复的系统差得多。

完整案例：电商客服退款

把前面所有环节串到一条真实链路上。

用户："我的 123456 订单商品坏了，帮我退款。"

Intent（退款诉求） ↓ query_order(order_id="123456") ← 查订单，确认存在且属于该用户 ↓ Check Order（status=delivered, paid=true） ↓ check_refund_eligibility(order_id) ← 预计算的业务判断，而非模型推断 ↓ Need Confirmation? ← 写操作 + 涉及资金 → 需要 Human Confirmation ↓ create_refund(order_id, reason="damaged", idempotency_key=…) ↓ Observe Result（success=true, refund_id=…） ↓ Final Response（"退款已提交，预计 1–3 个工作日到账"）

为什么不能只设计一个 refund() 大一统工具？因为这个案例里的每一步都依赖工具边界的存在：query_order 是只读的所以能自动执行；check_refund_eligibility 把业务规则从模型推理中拿走；create_refund 是写操作所以触发确认与幂等保护；query_refund_status 支撑后续的"退款到账了吗"追问。一个黑盒 refund() 会把这四件事全部搅在一起——参数不透明、业务规则隐藏、权限无法分级、错误无法归因。

Tool Registry：能力目录

当系统从 3 个工具增长到 50 个、甚至 500 个时，硬编码的工具列表就失效了。

Tool Registry 保存的不再只是函数引用，而是每个能力的完整元数据：

Tool Metadata ├── Name / Description / Category ├── Risk Level ← 驱动确认策略（第 12 节） ├── Permission ← 驱动鉴权（第 16 节） ├── Input / Output Schema ├── Availability ← 熔断状态，驱动动态下线 └── Version ← Schema 变更可追溯

有了 Registry，工具发现就变成了一条独立的链路：User Intent → Tool Discovery → Candidate Tools → Tool Selection。下游服务临时不可用时，Router 可以自动把该工具从候选集中摘除，Agent 甚至不会感知到故障。

REGISTRY PRINCIPLE

Tool Registry 是大型 Agent 系统的能力目录，而不是简单的函数列表。它承载的是治理：哪些能力存在、谁能用、现在是否可用、风险等级是什么。没有 Registry 的 500 工具系统，本质上是一堆无法治理的硬编码。

十个常见反模式

每个反模式都标注了成因、后果与改法，可作 Code Review 时的对照表。

01
God Tool

成因：追求快速上线，把整个业务域塞进一个函数。后果：Schema 不透明、权限无法分级、错误无法归因。改法：按业务动作拆分，参考第 3 节方案 C。

02
Tool Explosion

成因：按底层 API 一比一包装成工具。后果：选择空间爆炸、上下文膨胀、链路脆弱。改法：按业务动作聚合 + Registry 动态召回。

03
Ambiguous Tool

成因：多个工具功能相近，描述却含糊。后果：模型选错工具，如误触 create_refund。改法：Description 写清 When / When NOT（第 5 节）。

04
Weak Schema

成因：所有参数都是 string。后果：类型错误、格式混乱全靠下游兜底。改法：严格类型 + enum + format，约束前推（第 7 节）。

05
Hidden Side Effect

成因：工具名叫 get_xxx，实际会写数据。后果：Agent 按只读策略自动执行，造成意外修改。改法：副作用必须在契约中显式声明并驱动策略。

06
Blind Retry

成因：失败就重试，不区分错误类型。后果：参数错误重试一万次也不会对；非幂等操作被重复执行。改法：按错误语义分类重试（第 10 节）。

07
No Idempotency

成因：写操作没有幂等键。后果：超时重试导致双倍退款。改法：所有副作用工具强制携带 Idempotency Key（第 11 节）。

08
Tool Result Dump

成因：把整个 API Response 塞进上下文。后果：Token 浪费、模型在噪音中找关键信息、输出不稳定。改法：为 Agent 定制结构化返回（第 13 节）。

09
No Authorization

成因：Agent 用服务账号调用下游。后果：任何用户都能通过 Prompt 越权访问他人数据。改法：按用户身份鉴权，租户强制隔离（第 16 节）。

10
Infinite Tool Loop

成因：循环无边界、无重复检测。后果：成本失控、请求永不返回。改法：Max Steps + Time Budget + 重复检测（第 15 节）。

总结：一个统一模型

全文收敛为一句话：Tool 是 Agent 的 Action Interface，而 Interface 的质量决定了 Agent 能否可靠地行动。

Agent │ Decision │ Tool Selection │ Tool Contract │ ┌────────┴────────┐ ↓ ↓ Validation Authorization │ │ └────────┬────────┘ ↓ Execution │ ┌─────────┼─────────┐ ↓ ↓ ↓ Retry Timeout Fallback │ │ │ └─────────┼─────────┘ ↓ Observation ↓ State Update ↓ Next Decision

回到开头的判断：Agent 的智能决定了它想做什么，而 Tool 的设计决定了它能否安全、准确地把"想做什么"变成真正做到了什么。成熟的 Agent Tool Calling 不应该追求更多工具，而应该追求——清晰的能力边界、严格的契约、可控的执行、可靠的恢复，以及完整的可观测性。

Good Agent = Good Decision + Good Tool Contract
+ Reliable Execution + Safe Action + Observable Outcome
