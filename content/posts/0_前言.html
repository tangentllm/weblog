为什么需要 RAG？—— 大模型的「知识焦虑」

大语言模型（LLM）虽然展现出惊人的语言理解和生成能力，但它们本质上是一个「被冻结的知识快照」—— 训练数据截止于某个时间点，无法感知此后发生的事件，也无法访问企业内部的私有文档。

这种局限性带来了三个核心痛点：

知识时效性

模型的知识停留在训练截止日期。例如，GPT-4 无法回答 2024 年之后的新闻事件，也无法获取实时股价。

🔒 私有知识缺失

企业内部的 SOP 文档、产品手册、客服记录等私有数据从未进入模型训练集，LLM 对此一无所知。

幻觉问题

当模型缺乏相关知识时，它会「自信地编造」答案（hallucination），在医疗、法律等高风险场景尤为致命。

💡 核心洞察
与其花数百万美元重新训练模型来更新知识，不如在推理时（inference time）为模型注入相关的外部上下文。 这就是 RAG 的核心思想——Retrieval-Augmented Generation，检索增强生成。

🔍 什么是 RAG？—— 双流程架构总览

RAG 的全称是 Retrieval-Augmented Generation（检索增强生成），由 Lewis 等人在 2020 年的论文 "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" 中首次提出。 其核心思路可以用一句话概括：

🎯 RAG 一句话定义
在 LLM 生成回答之前，先从外部知识库中检索与用户问题最相关的文档片段， 将这些片段作为上下文拼接到 Prompt 中，让模型基于真实证据生成回答。

RAG 系统由两条并行的流水线（Pipeline）组成——离线文档处理流程和在线查询检索流程。 下图展示了完整的双流程架构：

⚙️ RAG 核心架构详解

3.1 离线文档处理流程

这条流水线在系统部署前或文档更新时运行，负责将原始文档转化为可检索的向量表示：

步骤操作关键工具 / 模型输出
文档加载读取 PDF / Word / HTML 等格式PyMuPDF, Unstructured, LangChain原始文本
② 文本解析提取纯文本，去除格式噪声pdfplumber, BeautifulSoup结构化文本
文本分块将长文档切为固定或语义块RecursiveCharacterTextSplitterChunks（512~1024 tokens）
④ 向量化将文本块编码为高维向量OpenAI text-embedding-3, BGEEmbedding Vectors
向量存储存入向量数据库并建立索引FAISS, Chroma, Pinecone, Milvus可检索的向量索引

以下代码展示了使用 LangChain 构建文档处理流水线的核心逻辑：

from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings

# 1. 文本分块 —— 按字符递归切分，保持语义完整性
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,      # 每块最大 token 数
    chunk_overlap=200,    # 块间重叠，避免信息在边界丢失
    length_function=len
)
chunks = text_splitter.split_documents(documents)

# 2. 向量化 + 存储 —— 使用 OpenAI Embedding 模型
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = FAISS.from_documents(chunks, embeddings)

# 3. 持久化到磁盘，避免重复计算
vectorstore.save_local("faiss_index")
⚠️ 分块策略的重要性
chunk_size 和 chunk_overlap 是 RAG 系统最关键的超参数之一。 块太大会引入噪声、降低检索精度；块太小会丢失上下文。本系列第 2~3 篇将深入探讨语义分块和切块大小选择。

3.2 在线查询检索流程

当用户提出问题时，系统执行以下步骤：

from langchain_openai import ChatOpenAI
from langchain.chains import RetrievalQA

# 1. 查询向量化 —— 使用与文档相同的 Embedding 模型
query = "特斯拉2023年的毛利率是多少？"

# 2. 相似度检索 —— 在向量库中查找 Top-K 最相似的文档块
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})
relevant_docs = retriever.invoke(query)

# 3. 上下文组装 + LLM 生成
llm = ChatOpenAI(model="gpt-4o", temperature=0)
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    retriever=retriever,
    return_source_documents=True  # 返回来源，便于追溯
)
result = qa_chain.invoke({"query": query})

print(result["result"])          # 生成的答案
print(result["source_documents"])  # 引用的文档块

整个流程可以概括为：Query → Embed → Search → Assemble → Generate， 其中 Embedding 模型保证了查询和文档在同一向量空间中进行语义匹配， 而非简单的关键词匹配。

底层基石：Transformer 与注意力机制

RAG 系统中的 Embedding 模型和 LLM 都建立在 Transformer 架构之上。 理解 Transformer 的核心——自注意力机制（Self-Attention），有助于我们理解 RAG 为何有效。

4.2 为什么 Attention 对 RAG 至关重要？

RAG 的本质是将检索到的文档片段作为额外的上下文注入到 Prompt 中。 当 LLM 处理这个扩展后的输入时，自注意力机制会自动计算用户问题（Query tokens） 与检索文档（Context tokens）之间的关联权重，从而让模型「聚焦」在最相关的信息上生成回答。

这也是为什么 RAG 的效果高度依赖于检索质量——如果检索到的文档与问题不相关， 注意力机制会将权重分散到噪声上，导致生成质量下降。

️ RAG vs 朴素 LLM：对比分析

朴素 LLM（无 RAG）

  • 知识局限于训练数据，无法获取最新信息
  • 对企业私有文档一无所知
  • 容易产生幻觉，编造看似合理但错误的答案
  • 答案无法追溯来源，缺乏可信度
  • 更新知识需要昂贵的重新训练
  • 长上下文窗口浪费大量 token 在无关信息上

✅ RAG 增强 LLM

  • 实时检索外部知识库，知识永不过时
  • 可接入任意私有文档库，打破知识边界
  • 基于检索证据生成，大幅降低幻觉率
  • 答案附带引用来源，可验证可追溯
  • 更新知识只需更新文档库，零训练成本
  • 只检索相关片段，高效利用上下文窗口

以下是本系列涵盖的核心技术，按功能维度分为四大类：

📦 数据预处理

基础

语义分块（Semantic Chunking）

采用百分位法、标准差法和 IQR 法进行语义感知的文本分割，相比固定长度分块可提升 15-20% 的检索准确率。

基础

上下文分块头（Contextual Chunk Headers）

为每个文本块添加文档标题/章节头信息，解决传统分块导致的上下文丢失问题。

进阶

命题分块（Proposition Chunking）

将文档分解为原子性事实陈述，实现更精确的细粒度检索。

检索优化

进阶

融合检索（Fusion Retrieval）

结合向量搜索与 BM25 关键词检索，通过分数归一化和加权融合提升召回率。

进阶

上下文压缩（Contextual Compression）

对检索结果进行二次过滤，保留与查询最相关的 30-50% 内容，降低噪声干扰。

基础

重排序（Reranking）

使用 Cross-Encoder 对初步检索结果进行精细排序，显著提升 Top-K 精度。

💡 查询优化

基础

查询转换（Query Transformations）

实现查询重写、退步提示和子查询分解三种技术，使原始查询的意图表达更充分。

进阶

假设文档嵌入（HyDE）

通过 LLM 生成假设性答案文档作为查询扩展，有效解决短查询与长文档的语义鸿沟。

动态

自适应检索（Adaptive Retrieval）

根据问题类型（事实型/分析型/观点型）动态选择最优检索策略。

🔄 动态优化与自进化

动态

自优化 RAG（Self-RAG）

引入检索必要性判断、文档相关性评估等 6 个反射点，实现生成过程的自监督。

动态

纠错 RAG（CRAG）

当本地知识不足时自动触发网络搜索，动态校正检索结果。

动态

强化学习 RAG（RL RAG）

基于用户反馈构建奖励模型，持续优化检索和生成策略。

总结与学习路线建议

RAG 是当前大语言模型落地应用的最关键工程范式之一。它巧妙地绕开了重新训练模型的高昂成本， 通过在推理时注入外部知识，实现了知识可更新、来源可追溯、幻觉可控制的增强生成系统。
