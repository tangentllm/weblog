一、为什么需要分层检索？

在标准 RAG 中，我们将文档切分为大量小块后直接进行向量检索。当文档较长（如几十页的 PDF）时，这种方式面临几个核心问题：

标准 RAG 的痛点
  • 语义稀释：小块缺乏上下文，向量表示不够精确
  • 检索噪声：Top-K 结果可能来自文档中不相关的章节
  • 上下文浪费：每个块都需要消耗 LLM 的上下文窗口

分层索引检索（Hierarchical RAG）通过引入两级搜索机制解决上述问题：先用粗粒度的页面摘要定位相关区域，再在限定的页面范围内检索细粒度的详细块。这种方式类似于人类查阅文档的过程——先翻目录找到相关章节，再仔细阅读具体内容。

四、索引构建：摘要存储 + 详细块存储

4.1 页面摘要生成

对每一页文本调用 LLM 生成简洁摘要，保留该页的核心信息：

from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate

def generate_page_summary(page_text: str) -> str:
    """为单页文本生成摘要"""
    llm = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)
    prompt = ChatPromptTemplate.from_template(
        "请用 2-3 句话概括以下文本的核心内容：\n\n{text}"
    )
    chain = prompt | llm
    return chain.invoke({"text": page_text}).content

4.2 分层文档处理

将 PDF 按页处理，同时构建摘要列表和详细分块列表：

from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_core.documents import Document

def process_document_hierarchically(pdf_path: str):
    """分层处理文档：构建摘要存储和详细块存储"""
    # 1. 按页提取 PDF 文本
    loader = PyPDFLoader(pdf_path)
    pages = loader.load()  # 每个 page 带有 page 元数据
    print(f"📄 文档共 {len(pages)} 页")

    # 2. 为每页生成摘要
    summaries = []
    for i, page in enumerate(pages):
        summary = generate_page_summary(page.page_content)
        summaries.append(Document(
            page_content=summary,
            metadata={"page": i + 1, "source": f"page_{i+1}_summary"}
        ))
    print(f"📝 生成 {len(summaries)} 个页面摘要")

    # 3. 每页详细分块 (1000 字符, overlap=200)
    text_splitter = RecursiveCharacterTextSplitter(
        chunk_size=1000,
        chunk_overlap=200,
        length_function=len
    )
    detailed_chunks = []
    for i, page in enumerate(pages):
        chunks = text_splitter.split_text(page.page_content)
        for j, chunk in enumerate(chunks):
            detailed_chunks.append(Document(
                page_content=chunk,
                metadata={
                    "page": i + 1,
                    "chunk_id": j,
                    "source": f"page_{i+1}_chunk_{j}"
                }
            ))
    print(f"🧩 生成 {len(detailed_chunks)} 个详细块")

    # 4. 构建两个向量存储
    embeddings = OpenAIEmbeddings()
    summary_store = FAISS.from_documents(summaries, embeddings)
    detailed_store = FAISS.from_documents(detailed_chunks, embeddings)

    return summary_store, detailed_store
真实数据 在本教程的 15 页 PDF 上，该函数生成了 15 个摘要和 47 个详细块。摘要存储仅有 15 个向量，搜索速度极快；详细块存储有 47 个向量，远小于全量分块的规模。

五、分层检索实现

分层检索的核心是先粗后细的两步查询，通过页码元数据将两步关联起来：

def retrieve_hierarchically(query, summary_store, detailed_store,
                            k_summaries=3, k_chunks=5):
    """分层检索：先摘要定位，再详细块搜索"""

    # 第一步：在摘要存储中搜索 Top-K 相关摘要
    summary_results = summary_store.similarity_search(
        query, k=k_summaries
    )

    # 第二步：提取相关摘要对应的页码
    relevant_pages = list(set(
        doc.metadata["page"] for doc in summary_results
    ))
    print(f"📌 相关页码: {relevant_pages}")

    # 第三步：仅在相关页面中搜索详细块
    def filter_func(doc):
        return doc.metadata["page"] in relevant_pages

    detailed_results = detailed_store.similarity_search(
        query,
        k=k_chunks,
        filter_func=filter_func  # 关键：过滤函数
    )

    return summary_results, detailed_results
filter_func 的作用 filter_func 是 FAISS 向量存储支持的过滤机制。它在相似度计算之后过滤结果，确保返回的块只来自摘要阶段定位的相关页面。这大幅缩小了搜索范围，提高了检索的针对性。

六、缓存机制与完整管道

由于摘要生成涉及 LLM 调用（耗时且消耗 token），我们使用 pickle 缓存索引：

import pickle
import os

CACHE_DIR = "./cache"

def hierarchical_rag(query, pdf_path, regenerate=False):
    """完整分层 RAG 管道（含缓存）"""
    os.makedirs(CACHE_DIR, exist_ok=True)
    cache_file = os.path.join(CACHE_DIR, "hierarchical_stores.pkl")

    if not regenerate and os.path.exists(cache_file):
        print("📂 从缓存加载索引...")
        with open(cache_file, "rb") as f:
            summary_store, detailed_store = pickle.load(f)
    else:
        print("🔨 构建分层索引...")
        summary_store, detailed_store = \
            process_document_hierarchically(pdf_path)
        with open(cache_file, "wb") as f:
            pickle.dump((summary_store, detailed_store), f)

    # 执行分层检索
    summaries, chunks = retrieve_hierarchically(
        query, summary_store, detailed_store
    )

    # 打印摘要定位结果
    print("\n📋 匹配的摘要：")
    for s in summaries:
        print(f"  第 {s.metadata['page']} 页: {s.page_content[:80]}...")

    return chunks  # 返回给 LLM 生成答案

标准 RAG 的对比基线实现：

def standard_rag(query, pdf_path, k=15):
    """标准 RAG：直接全量检索"""
    loader = PyPDFLoader(pdf_path)
    pages = loader.load()
    full_text = "\n".join(p.page_content for p in pages)

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=1000, chunk_overlap=200
    )
    chunks = splitter.split_text(full_text)

    embeddings = OpenAIEmbeddings()
    store = FAISS.from_texts(chunks, embeddings)
    results = store.similarity_search(query, k=k)
    return results

八、评估结果与分析

在同一个查询上对比两种方法的实际检索表现：

分层 RAG 检索结果
  • 匹配摘要：第 2、5、8 页（共 3 页）
  • 检索详细块：10 个（仅来自 3 个相关页面）
  • 信息密度：高 —— 所有块都与查询主题直接相关
标准 RAG 检索结果
  • 检索块数：15 个（来自全部 15 页）
  • 信息密度：中 —— 包含多个不相关页面的块
  • 覆盖面广但噪声较多

评估结论 分层 RAG 用更少的块提供了更有针对性的信息，在检索质量上更优（更聚焦）。标准 RAG 覆盖面更全面，但引入了较多噪声。对于需要精确回答的查询，分层 RAG 是更好的选择；对于需要全面综述的场景，标准 RAG 也有其价值。

九、优缺点与适用场景

优势

  • 检索更精准：摘要级预筛选有效缩小搜索范围，减少噪声
  • 上下文效率高：用更少的块传递更相关的信息，节省 LLM 上下文窗口
  • 符合人类阅读习惯：先概览再深入，两级粒度互补
  • 可扩展：支持多级层次结构（章节 → 页 → 段落）

劣势

  • 索引构建成本高：需要额外调用 LLM 生成摘要
  • 检索延迟略增：两次向量搜索 + 过滤，比单次搜索慢
  • 摘要质量依赖 LLM：摘要不准确会导致后续检索偏离
  • 页码过滤的局限：跨页内容可能被割裂

适用场景

✅ 适合❌ 不适合
长文档（几十页以上）短文档（1-3 页）
结构化文档（报告、论文、手册）非结构化碎片文本
需要精确回答的 QA 场景需要全面综述的场景
上下文窗口有限的 LLM上下文窗口极大的 LLM

十、总结与展望

分层索引检索通过引入摘要-详细块的两级结构，在检索精度和上下文效率之间取得了优秀的平衡。其核心思想——先粗后细，逐步聚焦——是处理长文档 RAG 的重要策略。

本篇核心要点
  • 构建两个向量存储：摘要存储（粗粒度）+ 详细块存储（细粒度）
  • 通过页码元数据关联两级索引
  • 检索时先摘要定位页面，再在相关页面中搜索详细块
  • 用更少的块（10 vs 15）实现更精准的检索
  • pickle 缓存避免重复构建索引
