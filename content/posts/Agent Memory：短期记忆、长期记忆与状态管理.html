Agent Engineering · Series 04

Agent Memory：短期记忆、长期记忆与状态管理

当 Agent 开始跨任务、跨 Session 持续运行时，一个被严重低估的问题浮出水面：它如何管理过去的信息？本文讨论 Memory 与 Context、State、History、RAG 的边界，以及生产级的 Memory 生命周期设计。

读者对象 有 LLM / RAG / Agent 开发经验的工程师与架构师 前置阅读 Workflow vs Agent · Single Agent · Multi-Agent 拆分 关键词 Memory · Context Engineering · Information Lifecycle
Abstract

Agent Memory 不是“保存更多历史”，而是让 Agent 在未来的决策中，能够以可控的成本重新获得真正有价值的过去信息。本文建立 Context / State / Memory 的概念边界，给出 Memory 写入策略、生命周期、存储与检索的工程框架，并以电商客服 Agent 为例，完整推演一个生产级 Memory 系统的决策路径。核心结论：Memory 的本质不是 Storage，而是 Context Engineering + Information Lifecycle Management。

01

为什么 Agent 需要 Memory

从一个具体场景开始。

用户第一次告诉 Agent：“我是一名后端开发，主要使用 Python 和 Go。”几天后，用户回来问：“帮我设计一个 Agent 服务。”

如果 Agent 完全不知道过去的信息，它必须重新询问：“你主要使用什么语言？”这不是智能，是失忆。用户视角下，这是同一个人在同一段关系里对话——Agent 视角下，这是两个陌生人。

Core Problem

Agent 如何在一次对话之外保持连续性？无 Memory 的 Agent 每次都从零开始；有 Memory 的 Agent 在 Request 与 LLM 之间插入 Memory Retrieval 与 Context Assembly，并在 Response 之后完成 Memory Update。

到这里，一个危险的直觉会出现：“所以把所有历史对话保存下来就行了。”

这个直觉是错的，而且是生产事故的常见起点。反例立刻可以列出：

  • 历史越多，Context 越大，无关信息比例上升，Token 成本线性增长；
  • 检索噪声增加，长 Context 中间的信息会被模型忽略（“lost in the middle”）；
  • 旧信息可能已经失效——用户三个月前的技术栈和今天未必一致；
  • 错误信息可能被永久记住，并在未来的每一次检索中污染决策；
  • Memory Retrieval 本身引入额外延迟与失败点。
Reframe

Memory 的问题不是“记不记”，而是记什么、什么时候记、什么时候取、什么时候忘。这四个决策任何一个做错，Memory 都会从资产变成负债。

02

Context Window 为什么不等于 Memory

上下文窗口在变大——128K、1M token 逐渐成为标配。于是另一个直觉出现了：“窗口够大，把历史全部塞进去，就是 Memory 了。”

这个等式不成立，原因在生命周期：

Context Window = 模型当前请求能够看到的信息范围
Memory = 系统过去保存并能够在未来重新取回的信息

Context 是一次性的：请求结束即消失。Memory 是持久的：跨越请求、跨越会话、跨越任务。两者之间靠一条管道连接——信息从 Storage 经过 Retrieval，才能进入 Context：

Storage → Retrieve → Select → Compress → Inject → Context → LLM → Decision
Memory 中的信息只有经过这四步加工，才可能被模型看到

因此，一个准确的表述是：Context 是 Memory 的一个消费结果。说“Context 越大等于 Memory 越好”，等于说“餐桌越大等于仓库越好”——餐桌上的菜来自仓库，但仓库的价值在于选菜、保鲜和补货，而不在于把所有存货一次性端上桌。

03

Short-term Memory

第一个常见错误是把 Short-term Memory 等同于 Conversation History。历史消息只是短期记忆的一部分——而且往往是最不结构化、最占 Token 的那部分。

短期记忆更准确的定义是：当前任务 / 会话范围内，对推进任务有直接价值的信息集合。它可以结构化地拆为：

  • Recent Messages —— 最近几轮对话的原文；
  • Working Memory —— 任务过程中的关键中间信息（目标、约束、已做的决策）；
  • Current Goal / Plan —— 当前任务目标与执行计划；
  • Intermediate Results —— 中间计算结果、工具返回的摘要；
  • Temporary Variables —— 临时变量；
  • Current Decisions —— 本次会话中已经确认的选择。

其中 Working Memory 是最容易被忽略、也最值得投入的部分。一个典型形态：

working_memory.json
{
  "goal": "设计电商客服 Agent",
  "constraints": ["支持退款", "支持订单查询"],
  "current_step": "tool_selection",
  "selected_tool": "query_order"
}

注意 Working Memory 和 State 的关系：Task State（“Intent Detection → Order Query → Refund Confirmation → Complete”）更接近系统运行状态，而不是 Memory。它是引擎的仪表盘，不是司机的经验。两者的边界我们会在第 10 节专门讨论。

短期记忆的工程要点是压缩：会话变长时，将早期对话滚动摘要为 Compact Summary，保留事实与决策，丢弃寒暄与冗余。这不是可选项——不做压缩的长会话，成本和准确率都会持续劣化。

一个必须马上泼的冷水：不是所有历史事件都应该升级为长期 Memory。“用户上个月问过天气”是 Episodic Candidate，但它的 Future Utility 接近于零。判断标准我们在下一节展开。

05

什么信息值得被记住：Memory Write Policy

Memory 系统的第一个决策点不是检索，而是写入。写入策略错误的代价是延迟性的——当下看不出来，两周后以检索噪声的形式还回来。

一个候选信息要经过这样的评估链才能落库：

Memory Candidate → Importance → Future Utility → Stability → Privacy / Risk → Write

可以把它压缩为一个工程判断框架（不是严格数学模型，是启发式）：

Memory Value = Future Utility × Stability × Relevance − Risk − Storage / Retrieval Cost
任何一项为负或接近零，都不应该写入
维度核心问题正例反例
Future Utility未来决策真的会用到吗？用户技术栈偏好一次性的闲聊内容
Stability这条信息会很快失效吗？用户职业身份“用户今天心情不错”
Relevance与用户 / 任务的长期上下文相关吗？长期项目背景无关的时事讨论
Risk包含隐私、敏感或权限越界信息吗？—用户口述的手机号、身份证号
Cost存储与未来检索的代价是否超过价值？—低价值的大段原始对话

据此，值得长期保存的典型信息：用户长期偏好、稳定个人信息、长期项目背景、明确的用户习惯、重要历史决策、经用户确认的事实。

不应该长期保存的：一次性闲聊、临时状态、已失效信息、低价值工具结果、大量原始对话、未经用户确认的模型推断。

Critical Rule

模型推断 ≠ 用户事实。用户说“我最近经常使用 Go”，这是候选 Memory；模型由此推断“用户永远喜欢 Go”并写入——这不是记忆，是偏见固化。凡是模型推断出的结论，要么不写入，要么必须打上 inferred=true 与更低的 confidence 标签。

06

Memory Lifecycle：全文最核心的工程部分

把 Memory 当作一个数据库表来设计，和当作一个生命周期系统来设计，是两种完全不同的工程。后者才是生产级的形态：

6.1Observe 与 Extract

从 User Message、Tool Result、Agent Action、Task Outcome 中发现潜在 Memory。Extract 阶段把非结构化信息转为结构化条目：

memory_candidate.json
{
  "memory": "用户偏好简洁的技术回答",
  "type": "preference",
  "source": "conversation",
  "confidence": 0.91
}

6.2Evaluate：写入前的守门人

回答五个问题：是否值得记？是否稳定？是否可信？是否敏感？是否已经存在（去重与合并）？这一步通常由一次独立的 LLM 调用或规则引擎完成——它是 Memory 系统里 ROI 最高的组件。

6.3Update：冲突覆盖，而不是追加

旧信息：用户使用 Python。新信息：用户现在主要使用 Go。错误的实现是两条都存，让 LLM 在检索时自己猜。正确的实现是带时间与来源元数据的版本化覆盖：

memory_record.json
{
  "memory": "用户主要开发语言",
  "value": "Go",
  "valid_from": "2026-03-01",
  "valid_to": null,
  "supersedes": "mem_0a3f…",
  "confidence": 0.88,
  "source": "user_statement"
}

6.4Forget：为什么删除是必需品

Memory 不衰减的系统必然熵增。遗忘机制至少包括：TTL（低稳定性信息自动过期）、用户主动删除（合规要求，不可妥协）、低价值淘汰（长期未被检索命中的条目降权或归档）、冲突覆盖（见 6.3）、定期压缩（同类事件聚合为摘要）。

Design Principle

一个只增不减的 Memory 系统不是一个“更聪明的 Agent”，而是一个随时间线性变差的知识库。设计遗忘机制的优先级，应当高于设计写入机制。

07

Memory Storage 应该怎么设计

存储选型应从数据形态出发，而不是从产品出发：

Storage适合的数据形态典型 Memory 用法
RedisSession / State / 高频短期数据Working Memory、会话级缓存、TTL 自然对齐
SQL强结构化 Memory用户画像、版本化事实、审计日志
Document DB半结构化 Memory事件记录、 episodic 条目
Vector DB语义检索Memory 的 Embedding 索引层
Graph DB实体与关系用户—项目—偏好之间的关联网络
Object Storage原始历史数据冷归档、回溯审计、重放

生产级 Memory 通常不是一个数据库，而是多个存储层的组合：Session 层（Redis）+ State 层（SQL）+ Long-term 层（Vector + SQL 双写，语义索引与结构化元数据分离）。

Common Mistake

Vector DB ≠ Memory。Vector DB 只解决“语义相似检索”这一个环节，它不负责写入决策、冲突更新、权限控制与生命周期。把 Vector DB 当作 Memory 系统，等于把文件系统当作图书馆。

08

Memory Retrieval：不是全部塞进 Context

检索阶段的错误比写入阶段更常见，因为它的失败是即时的：检索到什么，Context 就是什么。

一个简化的排序模型：

Score = α·Similarity + β·Recency + γ·Importance + δ·Relevance + ε·Confidence
系数需要按场景调优；Recency 对 Preference 类 Memory 的权重应低于 Semantic 类
Key Insight

相似度最高的 Memory，不一定是最应该注入 Context 的 Memory。一条六个月前与 Query 高度相似的过时偏好，价值低于一条昨天写入的中等相关事实。纯 Similarity 排序的 Memory 系统，天然偏好“旧而泛”的信息。

09

Memory 与 RAG 的区别

这是实践中最容易混淆的一对概念。先给边界：

维度RAGMemory
来源外部知识（文档、知识库）Agent / User 的交互历史
目标获取知识保持连续性
数据文档用户事实、事件、偏好
更新随文档更新（批处理）随交互持续更新（在线）
检索模式Query → KnowledgeContext → Relevant Memory
生命周期文档生命周期用户生命周期

一句话版本：RAG 回答“外部知识在哪里”，Memory 回答“关于这个用户/这个任务，过去发生了什么”。文档不会因为一次对话而改变，用户偏好会——这是两者在更新语义上的本质差异，也是 RAG 系统通常无需考虑冲突覆盖与衰减，而 Memory 系统必须考虑的原因。

但必须同时指出：两者在工程实现上高度共享基础设施——Embedding 模型、Vector DB、Reranker 往往是同一套。因此合理的架构视角是：它们是同一个 Context Engineering 框架下的两个数据源分支，而不是两套独立技术栈。

Architecture View

Context Engineering 之下：RAG 分支对接 External Knowledge（文档生命周期、离线更新），Memory 分支对接 User History（用户生命周期、在线更新、有遗忘机制）。共享的是检索基础设施，不同的是信息生命周期管理。

10

Memory 与 State 到底有什么区别

这是另一对高频混淆概念。用电商客服 Agent 的同一时刻对比：

task_state.json — 这是 State
{
  "order_id": "123456",
  "intent": "refund",
  "refund_reason": "damaged",
  "confirmation_required": true,
  "current_step": "await_user_confirmation"
}
Contrast
同一时刻的 Memory 视角

“用户过去多次因为商品破损申请退款，偏好快速处理。”——这条信息不在任何当前任务的结构里，它跨任务存在，服务于未来的每一次交互。它是 Memory。

State = 现在发生到哪里了？（What is happening now?）
Memory = 过去发生过什么，而且未来可能有用？（What happened before that matters later?）

更精确的分界线是生命周期归属：State 属于某个任务实例——任务完成即销毁（订单退款确认后，上面那个 JSON 没有存在意义）；Memory 跨任务存在——用户对破损退款的偏好在下一次购买时仍然有效。

两者也有交互：State 的终态是 Memory 的候选来源。任务成功完成的 outcome（“退款在 2 分钟内完成，用户满意”）可以被 Observe → Extract → Evaluate 后升级为 Episodic Memory。但这是写入策略的决策，不是自动过程。

11

Memory 与 Multi-Agent

沿用本系列前文关于 Multi-Agent 拆分的结论：当系统拆出多个 Agent 后，Memory 出现了一个新的架构问题——共享还是隔离？三种模式各有代价：

模式优点问题
Shared Memory信息共享充分，协作简单Context Pollution、权限模糊、Agent 之间互相污染检索池
Private Memory上下文隔离，职责清晰，检索噪声可控信息重复存储、跨 Agent 协作成本上升
Hybrid（生产系统更常见）全局事实统一，专有经验隔离需要维护全局 / 私有的写入路由与权限模型

Hybrid 模式的典型分层：

  • Global Memory —— User Profile、Shared Facts、Important Events（所有 Agent 可按权限读取）；
  • Private Memory —— Planner Memory（任务分解的经验）、Researcher Memory（检索质量的自适应调整）、Customer Service Memory（客诉处理的模式）。
Design Principle

Memory 的共享边界，本质上就是 Agent 的权限与职责边界。一个能读到 Researcher 全部私有 Memory 的 Planner，和一个能越权调度的 Manager 没有区别。这条原则与前一篇文章中“按职责拆分 Agent”的结论是对偶的：职责怎么拆，Memory 就怎么隔离。

生产级 Agent Memory 架构

把前文的组件装配成一个完整架构：

用伪代码表达这个主循环（框架无关）：

agent_loop.py
def run_agent(user_input):

    state = load_state()

    memories = retrieve_memory(          # 检索决策
        query=user_input,
        user_id=state.user_id
    )

    context = build_context(             # Context Engineering
        input=user_input,
        state=state,
        memories=memories
    )

    result = agent.run(context)

    state = update_state(state, result)

    candidates = extract_memory_candidates(  # 写入决策
        user_input, result
    )

    memories = evaluate_memories(candidates)

    save_memory(memories)
    save_state(state)

    return result
Where the Difficulty Is

真正困难的部分不是 save_memory()——那是五行数据库代码。困难的是 evaluate_memories() 与 retrieve_memory()。Memory 系统的核心不是存储，而是写入决策 + 检索决策 + 生命周期管理。

Memory 的典型失败模式

以下六种失败模式，在生产环境中的出现频率依次递减，但危害不减：

F1Everything Memory

什么都保存。这是“Memory 越多越智能”直觉的直接产物：

↑
Memory 总量
线性增长，无上限
↑
检索噪声
无关召回比例上升
↑
Token 成本
注入量随库膨胀
↓
决策准确率
噪声稀释有效信号

F2Memory Pollution

错误信息被写入 Memory（模型幻觉、推断当事实、对话误解）。之后每一次检索都会重新注入这条错误——错误被系统性地放大，而不是一次性出现。防御手段：写入必须经过 Evaluate；推断类信息标记 inferred 且降低 confidence；关键事实建议经用户确认后升级。

F3Stale Memory

旧信息没有更新：用户已从 Python 转向 Go，Memory 仍在回答 Python。防御手段：版本化字段（valid_from / valid_to）、低 Stability 条目设置 TTL、检索时 Recency 参与排序。

F4Memory Retrieval Failure

真正重要的 Memory 存在，但没有被召回。这是最隐蔽的失败——系统“看起来正常”，只是持续地不够聪明。需要通过检索命中率（recall@k）的离线评测来发现，仅靠线上观察很难定位。

F5Memory Over-injection

检索到了太多 Memory：相关的 + 无关的 + 过时的 + 互相冲突的，一起进入 Context。模型面对矛盾信息时倾向折中或随机采信，注入越多，判断越差。防御手段：注入预算（token budget）、Top-K 硬截断、冲突消解在 Context Builder 完成，而不是留给 LLM。

F6Memory Security

Memory 中积累的恰恰是最敏感的数据：用户隐私、企业内部信息、权限边界信息、历史行为轨迹。安全设计是一条完整链路：

Memory → Access Control → Data Isolation → Retention Policy → Deletion → Audit

其中 Deletion（用户主动删除权，合规上不可妥协）要求存储层支持物理删除——这直接排除了某些只做软删除的存储方案。多租户场景下，Data Isolation 必须在存储层强制（而非仅在检索层过滤），否则一条跨租户的检索 bug 就是数据泄露事故。

14

什么时候不需要 Long-term Memory

为了避免本文被误读为“所有 Agent 都应该上 Memory”，这一节专门给出反例。以下场景通常完全不需要 Long-term Memory：

  • Stateless API Agent（请求间本就无依赖）；
  • 一次性任务（生成一份报告、跑一次数据分析）；
  • 临时 Workflow（会话结束即整体销毁）；
  • 用户不需要跨会话连续性（匿名工具型产品）；
  • 所有必要信息都来自 RAG（纯知识问答场景）；
  • State 本身已经足够（单任务、短生命周期的客服工单）。

总结

回到全文的四条边界：

Context ≠ Memory  ·  State ≠ Memory  ·  History ≠ Memory  ·  RAG ≠ Memory
  • Context 回答“模型当前需要知道什么”——它是 Memory 的消费结果，不是 Memory 本身；
  • State 回答“当前任务进行到哪里”——它随任务生灭，不跨生命周期；
  • History 是原始素材——未经提取、评估与压缩的历史，只会带来噪声与成本；
  • RAG 回答“外部知识在哪里”——它与 Memory 共享检索基础设施，但生命周期语义完全不同。

Memory 回答的是另一个问题：未来 Agent 是否应该重新看到这些信息，以及以什么形式看到。这个问题由一条完整的生命周期支撑——Observe、Extract、Evaluate、Write、Retrieve、Update、Forget——其中写入决策与遗忘机制，比存储本身重要得多。

Final Takeaway

Memory 的本质不是 Storage，而是 Context Engineering 加上 Information Lifecycle Management。评估一个 Memory 系统的标准，不是它记住了多少，而是它在每一次决策时注入的信息的信噪比，以及它对错误、过时与敏感信息的处置速度。

成熟的 Agent Memory，不是让 Agent 记住更多，而是让它在正确的时间记住正确的信息，并且能够知道什么时候应该忘记。
