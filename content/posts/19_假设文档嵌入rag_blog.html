1. 为什么短查询嵌入不够好？

在传统的 RAG 系统中，检索的第一步是将用户的查询文本通过嵌入模型（如 text-embedding-ada-002）转化为向量，然后在向量存储中搜索最相似的文档块。然而，这种方式存在一个根本性的问题：

⚠️ 核心痛点：语义不对称

用户查询通常只有 5~15 个词，而文档块通常有 200~500 个词。嵌入模型将这两种截然不同的文本映射到同一向量空间时，短查询的向量往往无法充分表达用户的真实信息需求，导致与长文档的向量距离较远。

举个例子：

  • 用户查询："AI ethics"（2 个词，约 10 个字符）
  • 文档块："The development of artificial intelligence systems raises significant ethical concerns including bias in training data, lack of transparency in decision-making processes, and the potential for privacy violations through mass data collection..."（约 400 个字符）

这两个文本在语义上是高度相关的，但在嵌入空间中的距离可能并不近 — 因为短查询缺少了文档中涉及的许多语义维度。

2. HyDE 的核心思想

HyDE（Hypothetical Document Embeddings）由 Gao 等人在 2022 年提出，其核心洞察非常优雅：

与其嵌入一个短查询去匹配长文档，不如先让 LLM 生成一个假设性的回答文档，然后嵌入这个假设文档去检索。因为假设文档与真实文档在长度、风格和语义结构上更加接近，所以检索效果更好。

💡 关键洞察

嵌入模型在训练时见过大量完整的段落和文档，因此长文本的嵌入质量通常优于极短文本。HyDE 正是利用了这一特性：通过 LLM 将短查询"翻译"成一段长文本，让嵌入模型能更好地捕捉语义信息。

5. Step 1 — 文档处理与向量存储

文档处理阶段与标准 RAG 完全一致：从 PDF 提取文本，按固定大小分块，为每个块生成嵌入并存入向量存储。

文本分块

使用 chunk_size=1000 字符、overlap=200 字符的重叠分块策略：

def chunk_text(text, chunk_size=1000, overlap=200):
    """将文本分割为重叠的块。"""
    chunks = []
    for i in range(0, len(text), chunk_size - overlap):
        chunk = text[i:i + chunk_size]
        if chunk:
            chunks.append({
                "text": chunk,
                "metadata": {
                    "start_pos": i,
                    "end_pos": i + len(chunk)
                }
            })
    print(f"Created {len(chunks)} text chunks")
    return chunks

向量存储

使用 NumPy 实现的简单向量存储，通过余弦相似度进行检索：

class SimpleVectorStore:
    """使用 NumPy 实现的简单向量存储。"""
    def __init__(self):
        self.vectors = []
        self.texts = []
        self.metadata = []

    def add_item(self, text, embedding, metadata=None):
        self.vectors.append(np.array(embedding))
        self.texts.append(text)
        self.metadata.append(metadata or {})

    def similarity_search(self, query_embedding, k=5):
        """余弦相似度检索 Top-K。"""
        query_vector = np.array(query_embedding)
        similarities = []
        for i, vector in enumerate(self.vectors):
            similarity = np.dot(query_vector, vector) / (
                np.linalg.norm(query_vector) * np.linalg.norm(vector)
            )
            similarities.append((i, similarity))
        similarities.sort(key=lambda x: x[1], reverse=True)

        results = []
        for i in range(min(k, len(similarities))):
            idx, score = similarities[i]
            results.append({
                "text": self.texts[idx],
                "metadata": self.metadata[idx],
                "similarity": float(score)
            })
        return results

完整处理管道

将 PDF 提取、分块、嵌入和存储串联起来。在我们的实验中，一份 15 页的 AI 主题 PDF 被处理为 48 个文档块：

def process_document(pdf_path, chunk_size=1000, chunk_overlap=200):
    """处理文档：提取 → 分块 → 嵌入 → 存入向量存储。"""
    pages = extract_text_from_pdf(pdf_path)  # 提取15页内容

    all_chunks = []
    for page in pages:
        page_chunks = chunk_text(page["text"], chunk_size, chunk_overlap)
        for chunk in page_chunks:
            chunk["metadata"].update(page["metadata"])
        all_chunks.extend(page_chunks)

    # 为所有块创建嵌入
    chunk_texts = [chunk["text"] for chunk in all_chunks]
    chunk_embeddings = create_embeddings(chunk_texts)

    # 构建向量存储
    vector_store = SimpleVectorStore()
    for i, chunk in enumerate(all_chunks):
        vector_store.add_item(
            text=chunk["text"],
            embedding=chunk_embeddings[i],
            metadata=chunk["metadata"]
        )

    print(f"Vector store created with {len(all_chunks)} chunks")
    return vector_store

6. Step 2 — 假设文档生成

这是 HyDE 的核心创新步骤。我们使用 gpt-3.5-turbo 根据用户查询生成一个假设性的回答文档。关键在于提示词的设计 — 要求模型生成一段约 1000 字符的、类似权威来源的详细内容：

def generate_hypothetical_document(query, desired_length=1000):
    """
    生成一个假设的文档来回答查询。

    参数:
        query (str): 用户查询
        desired_length (int): 假设文档的目标长度

    返回:
        str: 生成的假设文档
    """
    system_prompt = f"""You are an expert document creator.
    Given a question, generate a detailed document that would directly
    answer this question.
    The document should be approximately {desired_length} characters
    long and provide an in-depth, informative answer to the question.
    Write as if this document is from an authoritative source
    on the subject. Include specific details, facts, and explanations.
    Do not mention that this is a hypothetical document - just write
    the content directly."""

    user_prompt = (
        f"Question: {query}\n\n"
        f"Generate a document that fully answers this question:"
    )

    response = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ],
        temperature=0.1  # 低温度：保证假设文档的确定性
    )

    return response.choices[0].message.content
📌 设计要点

为什么 temperature=0.1？假设文档的目标是提供一个"标准答案"式的参考文本，而非创意写作。低温度确保生成内容的确定性和一致性，减少随机性对检索质量的影响。

⚠️ 注意：假设文档不需要是正确的

HyDE 的精妙之处在于，即使假设文档中包含事实性错误，它仍然可以提升检索效果。因为我们只需要它的嵌入向量来搜索相似文档，而不是直接使用它的内容作为答案。最终答案是基于检索到的真实文档生成的。

7. Step 3 — HyDE RAG 管道

将假设文档生成、嵌入和检索串联为完整的 HyDE RAG 管道：

def hyde_rag(query, vector_store, k=5, should_generate_response=True):
    """
    使用假设文档嵌入（HyDE）执行 RAG。

    核心流程:
    1. 用 LLM 生成假设文档（~1000字符）
    2. 嵌入假设文档（而非原始查询）
    3. 用假设文档的嵌入检索相似块
    4. 基于检索结果生成最终回答
    """
    print(f"\n=== Processing query with HyDE: {query} ===\n")

    # 第一步：生成假设文档
    print("Generating hypothetical document...")
    hypothetical_doc = generate_hypothetical_document(query)
    print(f"Generated hypothetical document of "
          f"{len(hypothetical_doc)} characters")

    # 第二步：嵌入假设文档
    print("Creating embedding for hypothetical document...")
    hypothetical_embedding = create_embeddings([hypothetical_doc])[0]

    # 第三步：基于假设文档检索
    print(f"Retrieving {k} most similar chunks...")
    retrieved_chunks = vector_store.similarity_search(
        hypothetical_embedding, k=k
    )

    results = {
        "query": query,
        "hypothetical_document": hypothetical_doc,
        "retrieved_chunks": retrieved_chunks
    }

    # 第四步：生成最终回答
    if should_generate_response:
        print("Generating final response...")
        response = generate_response(query, retrieved_chunks)
        results["response"] = response

    return results

8. Step 4 — 标准 RAG 对比基线

为了评估 HyDE 的效果，我们需要一个标准 RAG 基线。它直接将短查询嵌入后检索，没有假设文档生成步骤：

def standard_rag(query, vector_store, k=5,
                 should_generate_response=True):
    """使用直接查询嵌入执行标准 RAG。"""
    print(f"\n=== Processing query with Standard RAG: {query} ===\n")

    # 第一步：直接嵌入查询
    print("Creating embedding for query...")
    query_embedding = create_embeddings([query])[0]

    # 第二步：检索
    print(f"Retrieving {k} most similar chunks...")
    retrieved_chunks = vector_store.similarity_search(
        query_embedding, k=k
    )

    results = {
        "query": query,
        "retrieved_chunks": retrieved_chunks
    }

    if should_generate_response:
        print("Generating final response...")
        response = generate_response(query, retrieved_chunks)
        results["response"] = response

    return results

❌ 标准 RAG

  • 直接嵌入短查询（~10 字符）
  • 查询向量语义维度有限
  • 与长文档块的嵌入距离较远
  • 检索可能遗漏相关段落

✅ HyDE RAG

  • 嵌入假设文档（~1000 字符）
  • 文档向量语义维度丰富
  • 与长文档块的嵌入距离更近
  • 检索更精准，覆盖更全面

📊 评估结论

HyDE 表现更好的场景：当查询涉及复杂概念关系、需要深入解释或涉及多个子主题时，HyDE 的假设文档能提供更丰富的语义锚点，检索到更多相关段落。

标准 RAG 表现更好的场景：当查询简单直接、答案可以在文档中直接找到时，标准 RAG 更高效 — 因为它省去了 LLM 调用的延迟和成本。

11. 何时使用 HyDE？适用场景与局限

✅ 适合使用 HyDE 的场景

  • 查询简短但涉及复杂主题
  • 文档库以长段落为主
  • 需要深度理解而非关键词匹配
  • 对检索质量要求极高
  • 可接受额外的 LLM 调用延迟
  • 领域专业术语较多

❌ 不适合使用 HyDE 的场景

  • 查询本身就是完整的长句子
  • 需要极低延迟的实时检索
  • 文档库以短文本为主（如 FAQ）
  • 预算有限，需控制 API 调用成本
  • 查询涉及最新事件（LLM 可能生成过时内容）
  • 精确事实查找（如"X 的股价是多少"）
⚠️ HyDE 的局限性
  • 额外延迟：每次查询需要多一次 LLM 调用（通常 1~3 秒）
  • 额外成本：假设文档生成消耗 LLM token
  • 幻觉风险：如果 LLM 生成的假设文档严重偏离主题，可能导致检索方向错误
  • 语言偏差：假设文档的语言风格可能与真实文档不匹配

实用建议

策略 说明
混合方案 同时用标准查询嵌入和 HyDE 嵌入检索，合并结果（Reciprocal Rank Fusion）
缓存假设文档 对常见查询预生成并缓存假设文档，避免重复 LLM 调用
查询分类 简单查询走标准 RAG，复杂查询走 HyDE RAG
调整假设文档长度 根据文档块的典型长度调整 desired_length 参数

🎯 核心要点回顾
  • 核心思想：用 LLM 生成假设性回答文档，嵌入假设文档（而非原始短查询）去检索
  • 解决的问题：弥合短查询（~10 字符）与长文档块（~1000 字符）之间的语义差距
  • 关键优势：假设文档与真实文档在长度、风格和语义结构上更相似，嵌入对齐更好
  • 实验结果：在复杂查询上，HyDE 在关系捕捉和详细解释方面显著优于标准 RAG
  • 权衡取舍：额外一次 LLM 调用带来延迟和成本，适合对检索质量要求高的场景

在下一篇中，我们将探讨动态纠正 RAG（Corrective RAG） — 一种在检索后自动评估文档相关性，并在相关性不足时动态调整检索策略的方法。这与 HyDE 形成了有趣的互补：HyDE 在检索前增强查询，而 CRAG 在检索后纠正结果。
