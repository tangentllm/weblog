一、问题动机：一把钥匙开所有锁？

在前面的篇章中，我们陆续学习了语义分块（第 2 篇）、上下文增强（第 4 篇）、标题提取（第 5 篇）、反馈回路（第 11 篇）等 RAG 优化技术。但这些方案都有一个共同假设：所有查询都用同一种检索策略——嵌入查询 → 向量相似度 → Top-K。

然而，用户的查询千差万别。"北京的面积是多少？"和"如何看待远程办公对团队协作的影响？"这两个查询，虽然都可以用向量检索来找答案，但最优的检索方式截然不同。

⚠️ 类比理解

想象你去图书馆找资料。如果你问"《红楼梦》是哪年出版的？"，馆员会直接查数据库给你一个精确答案。但如果你问"比较红楼梦与金瓶梅的叙事手法"，馆员会带你到三个不同的书架，分别找文学评论、比较文学和古典小说研究。再比如你问"如果曹雪芹活在当代，他会怎么写？"——馆员需要先理解你的隐含假设，然后从相关领域找材料。

不同的问题需要不同的查找策略。RAG 也一样。

自适应检索（Adaptive Retrieval）的核心思路是：先用 LLM 对用户查询进行意图分类，然后根据分类结果动态选择最合适的检索策略。本系列将其归纳为四种查询类型，每种类型对应一套专门的检索流程。

二、四种查询类型与对应策略

事实性 Factual

精确查找 → LLM 评分重排

  • 查询特征：有明确、客观的答案
  • 策略：LLM 增强查询精确性 → 向量检索 → LLM 评分重排 → 取 Top-K
  • 典型问题：“Python 的 GIL 是什么？”、“公司的年假政策？”
分析性 Analytical

拆解子问题 → 分别检索

  • 查询特征：需要多角度分析或比较
  • 策略：生成 3 个子问题 → 分别检索 → 去重合并保证多样性
  • 典型问题：“比较 React 和 Vue 的优缺点”
观点性 Opinion

识别视角 → 确保覆盖

  • 查询特征：涉及主观判断或争议性话题
  • 策略：识别 3 个不同视角 → 组合查询检索 → 确保每个视角至少一个文档
  • 典型问题：“远程办公是否提高了生产力？”
情境性 Contextual

推断上下文 → 重构查询

  • 查询特征：含有隐含前提或省略的上下文
  • 策略：推断隐含上下文 → 重构查询 → 按上下文相关性排序
  • 典型问题：“这对我们有什么影响？”（需要知道"这"指什么、"我们"是谁）
💡 核心思想

传统 RAG 是"一个策略打天下"，自适应 RAG 是"看菜下饭"。查询分类器充当路由器的角色——它不改变底层向量数据库或嵌入模型，只改变查询的处理方式和结果的筛选逻辑。

五、代码解读：查询分类

查询分类是整个自适应检索的"路由器"。它用 LLM 判断查询属于哪种类型：

def classify_query(query, model="gpt-4o"):
    """根据查询内容将其分类为四种类型之一。"""
    response = client.chat.completions.create(
        model=model,
        temperature=0,
        messages=[
            {"role": "system", "content": """Classify the following query into one of these categories:
- 'factual': seeks specific, objective facts or data
- 'analytical': requires multi-angle analysis or comparison
- 'opinion': involves subjective judgments or controversial topics
- 'contextual': contains implicit context or missing background

Return only the category name."""},
            {"role": "user", "content": query}
        ]
    )
    return response.choices[0].message.content.strip().lower()
🔍 设计要点
  • temperature=0：分类需要确定性输出，同样的查询应始终归入同一类别
  • 四类互斥：prompt 明确要求只返回一个类别名称，不做多标签分类
  • 默认回退：当查询特征不明显时，LLM 倾向于归为"事实性"——这是最安全的默认选择
  • 使用 gpt-4o：分类需要较强的语义理解能力，gpt-4o 比 gpt-3.5-turbo 更准确

六、代码解读：事实性检索策略

事实性查询的核心需求是精确。策略分三步：增强查询 → 检索 → LLM 评分重排。

def factual_retrieval_strategy(query, vector_store, k=4):
    """事实性查询：LLM增强查询 → 检索 → LLM评分重排 → Top-K。"""
    # 步骤1：用 LLM 增强查询精确性
    enhanced_query_response = client.chat.completions.create(
        model="gpt-4o",
        temperature=0,
        messages=[
            {"role": "system", "content": "Rewrite the query to be more specific and precise for fact retrieval."},
            {"role": "user", "content": query}
        ]
    )
    enhanced_query = enhanced_query_response.choices[0].message.content

    # 步骤2：向量检索（扩大候选集）
    candidates = vector_store.similarity_search(enhanced_query, k=k * 3)

    # 步骤3：LLM 评分重排
    scored_docs = []
    for doc in candidates:
        score = score_document_relevance(enhanced_query, doc.page_content)
        scored_docs.append((doc, score))

    scored_docs.sort(key=lambda x: x[1], reverse=True)
    return [doc for doc, _ in scored_docs[:k]]

💡 为什么需要 LLM 评分重排？

向量相似度只能衡量语义"距离"，但无法判断文档是否真正回答了问题。例如查询"Python 的 GIL 是什么？"，向量检索可能返回大量提到"Python"和"性能"的文档，但其中一些可能完全没有解释 GIL。LLM 评分能精确判断每个文档对查询的实际相关度，从而过滤掉"语义相近但答非所问"的文档。

七、代码解读：分析性检索策略

分析性查询需要多角度覆盖。策略是拆解成子问题，分别检索，再合并去重。

def analytical_retrieval_strategy(query, vector_store, k=4):
    """分析性查询：生成子问题 → 分别检索 → 去重合并保证多样性。"""
    # 步骤1：生成 3 个子问题
    subqueries_response = client.chat.completions.create(
        model="gpt-4o",
        temperature=0.7,
        messages=[
            {"role": "system", "content": """Break down the query into 3 distinct sub-questions
that together would provide a comprehensive answer.
Return each sub-question on a new line."""},
            {"role": "user", "content": query}
        ]
    )
    subqueries = subqueries_response.choices[0].message.content.strip().split("\n")

    # 步骤2：分别检索每个子问题
    all_docs = []
    seen_content = set()
    per_query_k = max(k, 2)

    for subquery in subqueries[:3]:
        docs = vector_store.similarity_search(subquery.strip(), k=per_query_k)
        for doc in docs:
            # 步骤3：去重——基于内容哈希
            content_hash = hash(doc.page_content[:100])
            if content_hash not in seen_content:
                seen_content.add(content_hash)
                all_docs.append(doc)

    return all_docs[:k]

🔍 设计要点
  • temperature=0.7：子问题生成需要一定的创造性，避免三个子问题过于雷同
  • 去重机制：基于内容前 100 字符的哈希值去重，防止同一文档被多个子问题重复检索
  • 多样性保证：每个子问题独立检索，确保结果覆盖不同角度

八、代码解读：观点性检索策略

观点性查询需要多视角覆盖，确保不遗漏任何立场。

def opinion_retrieval_strategy(query, vector_store, k=4):
    """观点性查询：识别视角 → 组合查询 → 确保每个视角有文档。"""
    # 步骤1：识别 3 个不同视角
    perspectives_response = client.chat.completions.create(
        model="gpt-4o",
        temperature=0.7,
        messages=[
            {"role": "system", "content": """Identify 3 distinct perspectives or viewpoints
on this topic. Return each perspective on a new line,
formatted as a search query."""},
            {"role": "user", "content": query}
        ]
    )
    perspectives = perspectives_response.choices[0].message.content.strip().split("\n")

    # 步骤2：组合查询检索
    all_docs = []
    perspective_docs = {}

    for i, perspective in enumerate(perspectives[:3]):
        docs = vector_store.similarity_search(perspective.strip(), k=2)
        perspective_docs[f"perspective_{i+1}"] = docs
        all_docs.extend(docs)

    # 步骤3：确保每个视角至少一个文档
    final_docs = []
    seen = set()
    # 先从每个视角取第一个文档
    for key, docs in perspective_docs.items():
        if docs and hash(docs[0].page_content[:100]) not in seen:
            seen.add(hash(docs[0].page_content[:100]))
            final_docs.append(docs[0])
    # 再补充剩余文档直到达到 k
    for doc in all_docs:
        if len(final_docs) >= k:
            break
        content_hash = hash(doc.page_content[:100])
        if content_hash not in seen:
            seen.add(content_hash)
            final_docs.append(doc)

    return final_docs

九、代码解读：情境性检索策略

情境性查询的难点在于隐含信息。策略是推断上下文、重构查询。

def contextual_retrieval_strategy(query, vector_store, k=4, user_context=None):
    """情境性查询：推断隐含上下文 → 重构查询 → 按上下文相关性排序。"""
    # 步骤1：推断隐含上下文
    context_response = client.chat.completions.create(
        model="gpt-4o",
        temperature=0,
        messages=[
            {"role": "system", "content": """Given the query and any available user context,
infer the implicit context and rewrite the query to be
self-contained and explicit. Include what 'this', 'it',
or other pronouns refer to."""},
            {"role": "user", "content": f"Query: {query}\nUser context: {user_context or 'None'}"}
        ]
    )
    rewritten_query = context_response.choices[0].message.content

    # 步骤2：用重构后的查询检索
    docs = vector_store.similarity_search(rewritten_query, k=k * 2)

    # 步骤3：按上下文相关性重新排序
    scored_docs = []
    for doc in docs:
        score = score_document_relevance(rewritten_query, doc.page_content)
        scored_docs.append((doc, score))

    scored_docs.sort(key=lambda x: x[1], reverse=True)
    return [doc for doc, _ in scored_docs[:k]]

🔍 关键设计

user_context 参数是可选的。当提供用户上下文时（如用户画像、对话历史），LLM 能更准确地推断隐含信息。即使不提供，LLM 也会尝试从查询本身推断——只是准确度可能略低。

十、代码解读：自适应检索核心

最后，将所有策略整合到一个入口函数中：

def adaptive_retrieval(query, vector_store, k=4, user_context=None):
    """自适应检索核心：分类查询 → 选择策略 → 执行检索。"""
    # 步骤1：分类查询
    query_type = classify_query(query)
    print(f"查询分类结果: {query_type}")

    # 步骤2：根据分类选择策略
    if query_type == "factual":
        return factual_retrieval_strategy(query, vector_store, k)
    elif query_type == "analytical":
        return analytical_retrieval_strategy(query, vector_store, k)
    elif query_type == "opinion":
        return opinion_retrieval_strategy(query, vector_store, k)
    elif query_type == "contextual":
        return contextual_retrieval_strategy(
            query, vector_store, k, user_context
        )
    else:
        # 未知类型默认使用事实性策略
        return factual_retrieval_strategy(query, vector_store, k)

💡 架构优势

这种设计遵循策略模式（Strategy Pattern）——每种检索策略是独立的函数，可以单独测试、替换和扩展。如果未来需要增加第五种查询类型（如"导航性"查询），只需新增一个策略函数并在 adaptive_retrieval 中添加一个分支即可。

十一、代码解读：LLM 文档评分

score_document_relevance 是事实性和情境性策略的关键组件——用 LLM 为每个文档的相关性打分（0-10）：

def score_document_relevance(query, document, model="gpt-4o"):
    """使用 LLM 评估文档对查询的相关性，返回 0-10 的评分。"""
    response = client.chat.completions.create(
        model=model,
        temperature=0,
        messages=[
            {"role": "system", "content": """Rate the relevance of the document to the query
on a scale of 0 to 10, where:
- 0: completely irrelevant
- 5: partially relevant
- 10: directly and fully answers the query
Return only the numeric score."""},
            {"role": "user", "content": f"Query: {query}\n\nDocument: {document}"}
        ]
    )
    try:
        return int(response.choices[0].message.content.strip())
    except ValueError:
        return 0
🔍 设计要点
  • 0-10 评分：比二元相关/不相关更细粒度，能区分"部分相关"和"完全匹配"
  • temperature=0：确保评分的一致性和可重复性
  • 异常处理：当 LLM 返回非数字时，默认评分为 0（保守策略）
  • 性能考量：每个候选文档需要一次 LLM 调用，因此先用向量检索扩大候选集（3K），再用 LLM 精排取 Top-K
⚠️ 成本与延迟权衡

LLM 评分重排是"用时间和金钱换精度"。对于事实性策略，如果候选集为 3K=12 个文档，则需要 12 次额外的 LLM 调用。在生产环境中，可以考虑：(1) 使用更小的模型做评分；(2) 先用嵌入相似度粗筛，再用 LLM 精排少量候选；(3) 缓存常见查询的评分结果。

十三、优缺点与适用场景

✅ 优点

  • 策略匹配需求：不同类型的查询使用最适合的检索方式
  • 提升精确度：事实性查询通过 LLM 评分过滤噪声文档
  • 增强覆盖面：分析性和观点性查询能触达多角度文档
  • 处理模糊查询：情境性策略能将指代不明的查询转化为精确查询
  • 模块化设计：各策略独立，可单独优化和测试
  • 可扩展：新增查询类型只需添加策略函数

❌ 缺点

  • 分类开销：每次查询需要额外的 LLM 分类调用
  • 策略内 LLM 调用：事实性和情境性策略需要多次 LLM 评分调用
  • 分类准确度：错误的分类会导致选择错误的策略，反而降低效果
  • 复杂度增加：相比统一策略，系统复杂度显著提升
  • 延迟不可预测：不同策略的 LLM 调用次数不同，响应时间波动大
  • 调试困难：出问题时需排查分类是否正确、策略是否合适

适用场景

✅ 适合 ❌ 不适合
查询类型多样化的通用问答系统 查询类型单一的垂直领域系统
需要处理模糊、指代性查询的对话系统 对延迟极度敏感的实时检索场景
需要多视角覆盖的研究辅助工具 成本敏感的批量处理场景
文档库覆盖多个主题领域的大型知识库 文档主题单一的小型知识库
⚠️ 与 Self-RAG 的关系

本篇的"自适应检索"是在检索前做决策——根据查询类型选择策略。下一篇将介绍的 Self-RAG（自适配 RAG）则是在检索后做决策——让 LLM 自行判断是否需要检索、检索结果是否有用。两者从不同维度实现"自适应"，可以互补使用。

十四、本篇小结

自适应检索的核心思想可以用一句话概括：

🎯 核心 takeaway

不是所有查询都该用同一种检索方式。先用 LLM 识别查询意图（事实性 / 分析性 / 观点性 / 情境性），再动态选择最合适的检索策略——精确评分、子问题拆解、多视角覆盖、或上下文重构。让策略匹配需求，而不是让需求迁就策略。

技术要点回顾：

  1. 查询分类：classify_query() 用 LLM 将查询分为四种类型
  2. 事实性策略：LLM 增强查询 → 扩大检索 → LLM 评分重排 → Top-K
  3. 分析性策略：生成 3 个子问题 → 分别检索 → 去重合并保证多样性
  4. 观点性策略：识别 3 个视角 → 组合查询 → 确保每个视角至少一个文档
  5. 情境性策略：推断隐含上下文 → 重构查询 → 按上下文相关性排序
  6. 统一入口：adaptive_retrieval() 作为路由器分发到各策略
  7. 评估结论：标准检索全面性更好，自适应检索简洁性和深度更好

自适应检索与前面学过的所有优化技术都不冲突——你可以在自适应检索的每种策略内部，继续使用语义分块、上下文增强、标题提取等技术。它是更高层的"策略选择"，而非替代底层优化。
