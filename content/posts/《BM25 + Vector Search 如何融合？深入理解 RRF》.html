BM25 + Vector Search 如何融合？深入理解 RRF

一、开篇：两个搜索系统都说自己“第一”

让我们从一个真实的企业级 Query 开始：

“RTC SDK 4.6.2 Android 出现 RTC-10027 错误怎么办？”

假设此时系统执行了 Hybrid Retrieval，得到以下两路结果：

Dense Retrieval 结果

Rank 1 → 文档 A

Rank 2 → 文档 C

Rank 3 → 文档 D

Rank 4 → 文档 B

BM25 结果

Rank 1 → 文档 D

Rank 2 → 文档 A

Rank 3 → 文档 B

Rank 4 → 文档 E

两套检索系统都认为自己的 Top 结果最重要。最终到底应该相信谁？

我们真正需要解决的，不是“哪个 Score 更大”，而是“一个文档在不同检索系统中的 Ranking 有多重要”。

二、为什么 Vector Score 和 BM25 Score 不能直接相加？

在考虑融合时，最朴素的想法是把两个分数加起来。看下面这个例子：

文档 A

Dense: 0.83
BM25: 11.7

文档 B

Dense: 0.79
BM25: 16.2

如果直接 0.83 + 11.7 计算，会有什么问题？

  • Score Range 不一致： Dense Score 通常在 [0, 1] 之间，而 BM25 Score 取值范围理论上可以从 0 到无穷大。
  • Score Distribution 不一致： Dense Score 可能是正态分布，BM25 则是长尾分布。
  • Score Semantics 不一致： Dense Score 衡量的是语义空间的距离（如余弦相似度），BM25 衡量的是词项匹配的统计概率。它们连物理量纲都不一样。
  • Calibration 难度高： 不同检索器的分值没有天然统一标准，强行线性相加会让某一方的方差直接淹没另一方。
不同 Retrieval System 的原始 Score 通常不能直接放在同一个排序空间中比较。

三、Score Fusion 与 Rank Fusion

1. Score Fusion

尝试将两个分数归一化后线性组合：

Score = α S_dense + (1-α) S_sparse

分析这种方法的缺陷：

  • 需要精细的 Score Normalization。
  • 超参数 α 需要调试。
  • 对 Score Distribution 敏感。
  • 不同 Retriever 的 Calibration 难度较高。

2. Rank Fusion

另一种思路是：不再关心 Score 到底是多少，而关心 文档排在第几名？

Dense：A → #1, C → #2, D → #3

BM25：D → #1, A → #2, B → #3

这样两个 Ranking 就可以被统一处理，彻底绕开分数尺度不统一的问题。

四、RRF 到底是什么？

RRF（Reciprocal Rank Fusion，倒数排名融合）是 Rank Fusion 中最经典的方法。其公式如下：

RRF(d) = ∑ (1 / (k + rank_r(d)))
  • d：候选文档
  • R：多个 Retrieval Result 集合
  • rank_r(d)：文档在某个 Retriever 结果中的排名
  • k：平滑常数
一个文档在多个 Retrieval System 中排名越靠前，它的 RRF Score 越高。

五、用一个完整例子算 RRF

必须手工计算一次，才能理解其本质。假设两路检索结果如下：

Dense: A #1, B #2, C #3, D #4

BM25: D #1, A #2, E #3, B #4

假设常数 k = 60。计算过程：

  • RRF(A) = 1/(60+1) + 1/(60+2) = 1/61 + 1/62 ≈ 0.01639 + 0.01613 = 0.03252
  • RRF(B) = 1/(60+2) + 1/(60+4) = 1/62 + 1/64 ≈ 0.01613 + 0.01563 = 0.03176
  • RRF(C) = 1/(60+3) = 1/63 ≈ 0.01587
  • RRF(D) = 1/(60+4) + 1/(60+1) = 1/64 + 1/61 ≈ 0.01563 + 0.01639 = 0.03202
  • RRF(E) = 1/(60+3) = 1/63 ≈ 0.01587
Document Dense Rank BM25 Rank RRF Score
A 1 2 0.03252
D 4 1 0.03202
B 2 4 0.03176
C 3 - 0.01587
E - 3 0.01587

最终排序为：A > D > B > C = E。可以看到，A 在两路检索中都名列前茅，最终登顶。

六、RRF 为什么有效？

从直觉解释：如果一个文档在 Dense 检索中排第 1，在 BM25 检索中也排第 1，说明两种完全不同的检索机制（一个看语义，一个看词频）都认为它重要。这种结果通常具有极高的可信度。

反之，如果文档在 Dense 检索排 #1，但在 BM25 中排 #100，意味着它可能主要依赖语义相似，而词面相关性并不强。RRF 成功利用了 “多路检索的一致性”。

七、RRF 的核心优势

1. 无需归一化

因为只使用 Rank

2. 极简

计算复杂度极低

3. 稳定

不依赖 Scale

4. 易扩展

支持多路检索

不仅可以用于 Dense + BM25，还可以引入 Metadata Search、Multi-Query Retrieval 结果进行统一 Fusion。

八、RRF 的局限性

不能把 RRF 写成“万能融合算法”，它有明显局限：

1. 它只看到 Rank

它不知道 #1 和 #2 之间的 Score 到底差多少。信息损失了。

2. 不考虑 Score Magnitude

例如 Dense A=0.99, B=0.51 与 A=0.99, B=0.98 在 Ranking 上都是 A #1, B #2。RRF 无法直接感知这种差异。

3. Retriever Quality 不同时

两个系统不一定拥有相同的可信度，强行 1:1 融合可能劣化结果。由此引出 Weighted RRF。

九、Weighted RRF

引入权重的 RRF 公式：

WRRF(d) = ∑ ( w_r * (1 / (k + rank_r(d))) )
  • w_r：Retriever 权重。

当不同检索器的质量不同，可以通过权重体现其可信度。例如在部分企业场景中，BM25 权重可能需要高于 Dense。

权重不是拍脑袋设置的，应该通过 Evaluation Dataset 验证。

十、RRF 中的 k 到底是什么？

常数 k 出现在分母 1 / (k + rank) 中，它的作用是平滑。

  • 当 k 很小（如 k=1）：Rank 之间的差异会被放大，第 1 名和第 10 名的分数差距巨大。
  • 当 k 很大：不同 Rank 的影响会变得平缓。

k 实际上控制 Ranking Contribution 的衰减速度。在业界实践中，k=60 是一个常见的默认值（源于 Elasticsearch 等搜索引擎的实践），但这只是经验值，并非普适最优值。

十一、RRF 如何处理未出现的文档？

文档 C 没有出现在 BM25 结果中，该如何计算？规则是：对该 Retriever 不计贡献。

形式上可以视为 rank = ∞ 且 contribution = 0。在代码实现中，不要真的把无限值送入程序，只需“只遍历出现过的文档”即可。

十二、RRF 的完整工程流程

RRF 位于 Retrieval 与 Reranker 之间。它负责将多路 Candidate Ranking 合并为一个 Candidate Ranking。

十三、RRF 与 Reranker 的关系

不要混淆两者的概念：

RRF 解决：

多路 Retrieval 如何融合？(粗排后融合)

Reranker 解决：

融合之后，哪些候选最相关？(精排)

完整链路：Dense + BM25 → RRF → Candidate Top-K → Reranker。两者职责不同。

十四、RRF 与 Top-K 的关系

Dense Top-20 和 BM25 Top-20 可能产生最多 40 个 Candidates，由于交集存在，实际可能更少。然后经过 RRF 截断成 Top-20 喂给 Reranker。

  • Retrieval Top-K：单路检索器各自召回的数量。
  • Fusion Candidate Size：去重后的总候选集大小。
  • Rerank Top-K：最终送入大模型或展示的结果数。

十五、如何确定 Dense / BM25 的权重？

对于 Weighted RRF，设计实验流程：

权重应该通过企业自己的 Query Distribution 与 Ground Truth Dataset 决定，没有普适最优解。

十六、RRF 如何评估？

建立 Baseline 对比：Dense Only vs BM25 Only vs RRF vs Weighted RRF。

评估指标：Recall@K, Precision@K, MRR, NDCG。

同时观察：Fusion Latency, Candidate Size, Reranker Cost。

RRF 的成功标准不是“RRF Score 更高”，而是最终 Retrieval Quality 更高。

十七、Python 实现

def reciprocal_rank_fusion(
    result_lists: list[list[str]],
    k: int = 60,
) -> list[tuple[str, float]]:
    """
    RRF 实现
    :param result_lists: 多个检索器返回的结果列表（按相关性排序）
    :param k: 平滑常数
    :return: 融合后的 (doc_id, rrf_score) 列表
    """
    if not result_lists:
        return []
    
    rrf_score = {}
    
    for result_list in result_lists:
        for rank, doc_id in enumerate(result_list, start=1):
            if doc_id not in rrf_score:
                rrf_score[doc_id] = 0.0
            rrf_score[doc_id] += 1.0 / (k + rank)
            
    # 按照累加的 score 降序排序
    sorted_results = sorted(rrf_score.items(), key=lambda x: x[1], reverse=True)
    return sorted_results

def weighted_rrf(
    result_lists: list[list[str]],
    weights: list[float],
    k: int = 60,
) -> list[tuple[str, float]]:
    """
    Weighted RRF 实现
    :param result_lists: 多个检索器返回的结果列表
    :param weights: 每个检索器的权重
    :param k: 平滑常数
    :return: 融合后的 (doc_id, wrrf_score) 列表
    """
    if not result_lists or len(result_lists) != len(weights):
        raise ValueError("Result lists and weights must have the same length")
    
    rrf_score = {}
    
    for result_list, w in zip(result_lists, weights):
        for rank, doc_id in enumerate(result_list, start=1):
            if doc_id not in rrf_score:
                rrf_score[doc_id] = 0.0
            rrf_score[doc_id] += w * (1.0 / (k + rank))
            
    sorted_results = sorted(rrf_score.items(), key=lambda x: x[1], reverse=True)
    return sorted_results

十九、生产环境中的常见问题

问题 1：Dense 和 BM25 都很强，RRF 却没有明显提升

原因： 两者召回高度重叠；Dataset 不适合 Hybrid；Fusion 不能创造不存在的信息。

问题 2：BM25 很弱，却强行和 Dense 50/50

解决： 通过 Evaluation 调整权重，降低 BM25 权重。

问题 3：Top-K 太小

导致： 真正需要融合的候选在进入 RRF 之前就已经被截断。

问题 4：RRF 后候选过多

导致： Reranker 成本高，Latency 增加。

问题 5：只看 RRF Score，不看最终 Recall / MRR

这是本末倒置，一切以最终评估指标为准。

二十、一个非常重要的认知：RRF 不会创造信息

Dense 没召回 + BM25 也没召回 → RRF 无法凭空发现正确文档。

Fusion 的上限受输入 Retriever 的召回能力限制。RRF 只是更合理地组织已有候选。

二十一、RRF 不是所有场景都必须使用

  • 可以只用 Dense： 语义表达高度自然、专业标识符少、Query 与 Document 词面差异大。
  • 可以只用 BM25： 关键词搜索、产品代码、SKU、错误码、精确 API 名称。
  • 更适合 Hybrid + RRF： 企业知识库、技术文档、FAQ、多来源知识库、中英文混合内容。
架构复杂度必须由业务收益 justify。

二十二、最终架构

RRF 是 Retrieval Fusion Layer，而不是整个 RAG 的核心业务逻辑。

二十三、最终形成认知

Dense Retrieval： 负责语义覆盖

BM25： 负责词项精确匹配

RRF： 负责多路 Ranking 融合

Reranker： 负责候选集精细排序

LLM： 负责基于证据生成答案

核心观点： Hybrid Retrieval 解决“从不同搜索视角尽可能找到候选”，RRF 解决“如何把不同搜索结果放到同一套排名体系中”，Reranker 才负责进一步判断候选与 Query 的真实相关性。
