01Agent Communication 的三种模式

Agent 之间通信，本质上只有三种范式。选型错误不会立刻爆炸，但会在系统规模变大时让你付出十倍代价。

Pattern A

Shared State

A 把结果写入共享空间（Dict / Redis / DB），B 从中读取。简单直接，但所有 Agent 耦合在同一份存储结构上。

Pattern B

Message Passing

A 构造结构化消息点对点发给 B，B 处理后回执。契约清晰，链路可追踪，是中型系统的主力模式。

Pattern C

Event Driven

A 只发布事件到总线，不关心谁消费。扩展性最强，但事件扩散后链路追踪与调试成本陡增。

六维度对比

维度Shared StateMessage PassingEvent Driven
延迟低 直接读写中 点对点投递较高 经过队列
一致性强 共享同一份数据中 依赖消息可靠性最终一致
解耦差 绑定存储结构好 只依赖协议最好 发布者不知消费者
可扩展性差 存储是瓶颈中高 水平扩展消费者
可追踪性好 状态集中好 消息即轨迹差 事件链路难追
调试难度低中高
经验法则：原型阶段用 Shared State，最快跑通；生产中型系统用 Message Passing，契约清晰；Agent 数量超过 10 个、需要动态扩缩容时，才考虑 Event Driven。一个常见错误是一开始就上 Event Bus，结果调试一个五步任务要翻三遍事件日志——通信复杂度要匹配系统规模。

02Agent Contract：全文的重点

无论选哪种通信模式，Agent 之间传递的都必须是结构化契约，而不是一段自由文本。

Agent Contract · Schema v1.0
// 每一条跨 Agent 消息都必须符合这份契约
{
  "task_id":      "task-8f3a21",      // 哪个任务
  "trace_id":     "trace-0c41de",     // 哪条链路
  "source_agent": "researcher",       // 谁发的
  "target_agent": "writer",           // 发给谁
  "input":        { "findings": ["fact-1", "fact-2"] },
  "context":      { "task_goal": "写一篇关于 Multi-Agent 的文章" },
  "constraints":  { "timeout_ms": 3000, "max_tokens": 1000 },
  "output":       {},
  "status":       "success",
  "error":        null,
  "metadata":     { "schema_version": "1.0",
                    "idempotency_key": "task-8f3a21:writer",
                    "attempt": 1 }
}

逐字段深入解释

七个必须认真对待的字段

① Schema Validation（模式校验） — 消息在发出前和接收后都要校验。缺 trace_id 的消息宁可拒收，也不要让它进入系统——否则它出问题时你连查都查不到。

② Versioning（版本化） — schema_version 是契约的生命线。今天 Researcher 输出 findings: list[str]，明天变成 list[dict]，Writer 立刻全挂。有了版本号，可以让 Writer 同时兼容 v1 / v2，灰度迁移。

③ Idempotency（幂等性） — idempotency_key = task_id + agent_name。网络抖动导致重试时，同一个 key 的重复消息只应被处理一次。没有幂等，任何 Retry 机制都是灾难的放大器。

④ Error Code（结构化错误码） — 错误不要写成一句「这个东西我搞不定」。要结构化，下游才能决定重试、降级还是终止：

{
  "error": {
    "code": "E_TIMEOUT",
    "retryable": true,
    "message": "LLM call exceeded 3000ms"
  }
}

⑤ Timeout（超时） — 每个契约必须携带 constraints.timeout_ms。一个没有超时的 Agent 调用，等于把系统的命运交给一个可能永远不返回的黑盒。

⑥ Trace ID（追踪） — task_id 标识「哪个任务」，trace_id 标识「哪条链路」。一个任务经过 6 个 Agent，6 条消息共享同一个 trace_id，可观测性全靠它。

⑦ Metadata（元数据） — 重试次数、时间戳、模型版本等运维信息统一放 metadata，不污染业务字段。

一条必须刻在墙上的原则：Agent 不应该依赖自然语言作为系统间唯一通信协议。自然语言适合做 Agent 的「思考」和「与人交互」的界面，但作为系统协议，它不可校验、不可靠、昂贵且充满噪声。

  • 不可校验 — 你无法对一段散文做 schema 验证；
  • 不可靠 — 「写 800 字」和「写大约 800 字左右」在系统语义上不可控；
  • 昂贵且充满噪声 — 把完整上下文写成自然语言传下去，是在烧 Token 买混乱。
  • 正确姿势：协议用结构化数据（JSON），自然语言只出现在字段值的内部。

03State 如何设计：五层状态模型

把所有状态塞进一个全局对象，是最常见也最致命的设计错误。正确做法是先分层：

什么应该共享，什么必须隔离？

✓ 可以共享
  • 任务目标
  • 全局约束（字数、风格、deadline）
  • 前序 Agent 的产出结果（而非过程）
  • 用户偏好中与本任务相关的部分
✗ 必须隔离
  • Agent 的内部推理过程
  • Agent 的中间草稿
  • 工具调用的原始返回
  • 其他 Agent 的失败重试细节

一条分界线：Research Agent 可以访问任务上下文，但不应该拥有 Writer Agent 的全部内部状态。理由有三：最小知识原则（Writer 的内部状态对 Research 是噪声）、Token 成本（每多传一段无用状态，下游每次 LLM 调用都在为它付费）、安全边界（内部状态可能包含不该扩散的信息）。

04Memory 与 State 的区别

这两个概念经常被混用，但它们回答的是完全不同的问题：

State

「系统现在进行到哪一步？」

快照 · 结构化 · 可校验

Memory

「系统过去知道什么？」

沉积 · 可检索 · 有衰减

Memory 继续拆分为四种，各自的生命周期和存储方式完全不同：

Memory 类型存什么例子典型存储
Short-term当前任务链条内的信息本轮任务的 findings、错误记录内存 / Redis
Long-term跨任务的持久知识用户是资深工程师，偏好技术细节向量库
Conversation对话轮次历史「上一轮你说要更简洁」会话存储
Working当前推理步的上下文窗口本步 Prompt 里塞了什么LLM Context
一个判断口诀：需要精确恢复的，用 State；需要模糊回忆的，用 Memory。 想用向量检索恢复「任务进行到第几步」，一定会出事。

05Context 传播：一个生产事故的根源

这是 Multi-Agent 系统在生产环境中最隐蔽的杀手。设想一个任务经过 6 个 Agent：

如果不断传完整上下文，会发生什么？

五个具体恶果：

  • Context Explosion — A 的上下文是 1KB，到 F 手里可能是 1MB，每一跳都在叠加；
  • Token Cost — F 的每一次 LLM 调用都在为 A~E 的全部历史付费；
  • Noise — 上下文越长，模型注意力越稀释，输出质量反而下降；
  • Information Loss（反直觉但真实） — F 忘记字数限制，不是因为约束没传，而是它埋在 50K Token 里；
  • Context Compression 的陷阱 — 很多人最后被迫加一个「压缩 Agent」，而压缩本身有损，可能恰好丢掉关键信息。
Context 最小化原则：让 Agent 只获得完成当前任务所需要的信息。具体操作——① 传递产物，不传递过程（Writer 需要 findings，不需要 Researcher 搜索了哪些 URL）；② 按需裁剪，由编排器决定每个下游能看到哪些 context key；③ 大文件传引用（ID / URI）代替拷贝；④ timeout、字数、schema 这类硬约束永远直传，放在 constraints 里，不参与压缩。

06并发与状态一致性

只要允许并行（如上一篇的 Parallel 模式），就一定会遇到：两个 Agent 同时修改同一个 State 怎么办？ 例如两个 Writer 分支并行写稿，最后都要写 article_draft 这个 key。

五种武器

机制原理适用时机
Version每个状态条目带版本号，写操作必须基于自己读到的版本——这是一切的基础默认启用
Optimistic Lock写入时校验 expected_version == current_version，不匹配即拒绝Agent 间冲突本质低频，先乐观，真频繁再升级
Event Sourcing不存「当前状态」只存「事件序列」，状态由事件重放得出；天然可回放、可审计大规模系统再引入，实现复杂度高
State Snapshot关键步骤保存快照，出问题时回滚到上一个一致点——工程上的「后悔药」所有长流程任务
Conflict ResolutionLast Write Wins（各写各 key）/ Merge（交给 Mediator Agent 合并）/ Human in the Loop（高价值内容升级给人）冲突真实发生后的三种出路

07代码实现：Contract 驱动的协作

以下代码已验证可运行。实现了 Task、AgentMessage（Contract 载体）、AgentState、StateStore（乐观锁），以及三个 Agent 通过 Contract 端到端协作：

import json, uuid, threading
from enum import Enum
from dataclasses import dataclass, field
from typing import Any, Optional

# ============ 0. Task：任务实体 ============
class TaskStatus(str, Enum):
    PENDING = "pending"; RUNNING = "running"
    SUCCESS = "success"; FAILED = "failed"

@dataclass
class Task:
    task_id: str
    trace_id: str
    goal: str
    status: TaskStatus = TaskStatus.PENDING

# ============ 1. AgentMessage：Agent Contract 的载体 ============
@dataclass
class AgentMessage:
    task_id: str
    trace_id: str
    source_agent: str
    target_agent: str
    input: dict = field(default_factory=dict)
    context: dict = field(default_factory=dict)       # 最小化上下文
    constraints: dict = field(default_factory=dict)   # timeout / max_tokens
    output: dict = field(default_factory=dict)
    status: str = "success"
    error: Optional[dict] = None
    metadata: dict = field(default_factory=dict)      # schema_version / idempotency_key

    def validate(self):
        """Schema Validation：必填字段校验，不合格宁拒收"""
        required = ["task_id", "trace_id", "source_agent", "target_agent"]
        missing = [k for k in required if not getattr(self, k)]
        if missing:
            raise ValueError(f"Contract validation failed, missing: {missing}")
        self.metadata.setdefault("schema_version", "1.0")
        return True

# ============ 2. AgentState：Agent 本地状态（严格私有） ============
class AgentState:
    def __init__(self, agent_name: str):
        self.agent_name = agent_name
        self._state, self._version = {}, 0
        self._lock = threading.Lock()

    def update(self, key: str, value: Any):
        with self._lock:
            self._state[key] = value
            self._version += 1

    def snapshot(self) -> dict:
        """对外只暴露快照副本，绝不泄漏可变引用 —— 这就是「隔离」的代码体现"""
        with self._lock:
            return {"agent": self.agent_name,
                    "version": self._version, "state": dict(self._state)}

# ============ 3. StateStore：共享状态 + 乐观锁 ============
class ConflictError(Exception): ...

class StateStore:
    def __init__(self):
        self._data, self._versions = {}, {}
        self._lock = threading.Lock()

    def write(self, key, value, expect_version: Optional[int] = None):
        with self._lock:
            cur = self._versions.get(key, 0)
            if expect_version is not None and expect_version != cur:
                raise ConflictError(
                    f"conflict on '{key}': expected v{expect_version}, actual v{cur}")
            self._data[key] = value
            self._versions[key] = cur + 1
            return self._versions[key]

    def read(self, key):    return self._data.get(key)
    def version(self, key): return self._versions.get(key, 0)

# ============ 4. BaseAgent ============
class BaseAgent:
    def __init__(self, name: str, store: StateStore):
        self.name, self.store = name, store
        self.local_state = AgentState(name)

    def handle(self, msg: AgentMessage) -> AgentMessage:
        raise NotImplementedError

    def reply(self, req: AgentMessage, output: dict) -> AgentMessage:
        """构造符合 Contract 的回执，透传裁剪后的最小上下文"""
        return AgentMessage(
            task_id=req.task_id, trace_id=req.trace_id,
            source_agent=self.name, target_agent=req.source_agent,
            input=req.input, context=req.context,
            constraints=req.constraints, output=output,
            metadata={**req.metadata,
                      "idempotency_key": f"{req.task_id}:{self.name}"})

# ============ 5. 具体 Agent ============
class RouterAgent(BaseAgent):
    """负责 Context 最小化裁剪 —— Context 最小化原则的执行者"""
    ALLOWED_KEYS = {"task_goal", "topic"}

    def handle(self, msg: AgentMessage) -> AgentMessage:
        msg.context = {k: v for k, v in msg.context.items()
                       if k in self.ALLOWED_KEYS}
        self.local_state.update("forwarded", msg.task_id)
        return msg

class ResearchAgent(BaseAgent):
    def handle(self, msg: AgentMessage) -> AgentMessage:
        topic = msg.context.get("topic")   # 只能看到被授权的最小上下文
        self.local_state.update("last_topic", topic)
        return self.reply(msg, {"topic": topic,
                                "findings": ["fact-1", "fact-2"]})

class WriterAgent(BaseAgent):
    def handle(self, msg: AgentMessage) -> AgentMessage:
        findings = msg.input.get("findings", [])
        cur = self.local_state.snapshot()["state"].get("draft_count", 0)
        self.local_state.update("draft_count", cur + 1)
        return self.reply(msg,
            {"article": f"基于 {len(findings)} 条素材生成的文章草稿"})

# ============ 6. 端到端协作演示 ============
store = StateStore()
router = RouterAgent("router", store)
researcher = ResearchAgent("researcher", store)
writer = WriterAgent("writer", store)

trace_id = str(uuid.uuid4())[:8]
task = Task(task_id=str(uuid.uuid4())[:8], trace_id=trace_id,
            goal="写一篇关于 Multi-Agent 的文章")

full_context = {                      # 原始上下文很大，充满噪声
    "task_goal": task.goal,
    "topic": "Multi-Agent State Management",
    "user_history": ["x" * 200],      # 噪音
    "raw_docs": ["y" * 500],          # 噪音
}

# A. Orchestrator -> Router：裁剪上下文
msg = AgentMessage(
    task_id=task.task_id, trace_id=task.trace_id,
    source_agent="orchestrator", target_agent="router",
    context=full_context,
    constraints={"timeout_ms": 3000, "max_tokens": 1000},
    metadata={"idempotency_key": f"{task.task_id}:router"})
msg.validate()
msg = router.handle(msg)
assert set(msg.context.keys()) == {"task_goal", "topic"}  # 噪声已被裁掉 ✓

# B. Router -> Researcher
msg.target_agent = "researcher"
msg = researcher.handle(msg)

# C. Researcher -> Writer：只透传 findings
msg.target_agent = "writer"
msg.input = msg.output
msg = writer.handle(msg)
print(json.dumps(msg.output, ensure_ascii=False))

# D. 并发冲突：两个 Writer 同时写同一个 key（乐观锁生效）
def agent_write(name, value, expect_v):
    try:
        v = store.write("article_draft", value, expect_version=expect_v)
        print(f"{name} 写入成功, version={v}")
    except ConflictError as e:
        print(f"{name} 写入失败 -> {e}")

store.write("article_draft", "v0草稿")
cur = store.version("article_draft")
t1 = threading.Thread(target=agent_write, args=("writer-1", "草稿A", cur))
t2 = threading.Thread(target=agent_write, args=("writer-2", "草稿B", cur))
t1.start(); t2.start(); t1.join(); t2.join()
运行输出
{"article": "基于 2 条素材生成的文章草稿"}
writer-1 写入成功, version=2
writer-2 写入失败 -> conflict on 'article_draft': expected v1, actual v2
注意三个设计点：① RouterAgent 演示了 Context 最小化——噪声上下文在进入业务 Agent 前就被裁掉；② AgentState 的 snapshot() 只返回副本——本地状态对外没有可变引用泄漏，这就是「隔离」的代码体现；③ StateStore 的乐观锁——writer-2 基于过期版本写入被拒绝，冲突被显式暴露而不是静默覆盖。

通信解决「说得上话」，可靠性解决「靠得住」

到这里，你的 Agent 已经能通信、能共享状态、能通过 Contract 精确协作了。但请清醒一点：Agent 能通信、能共享状态，并不意味着系统可靠。

真实的 LLM 系统里，失败是常态而非异常：模型输出超时、Tool 调用抛异常、API 限流、某个分支 Agent 挂了而其他分支已经成功……这些时刻，你精心设计的通信契约只有一个问题要回答——失败了，然后呢？
