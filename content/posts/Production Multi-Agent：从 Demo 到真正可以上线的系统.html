SECTION 01Production Architecture：生产架构全景

先看一个真实可上线的 Multi-Agent 系统长什么样。注意三条主线：请求主线自上而下贯穿，基础设施横向支撑，而所有外部访问在 Tool Gateway 处收口。

核心设计原则只有三条：

  • Agent 不是 Prompt，是 Runtime Component。每个 Agent 都有独立的运行时：生命周期、超时、预算、权限。
  • 所有外部访问必须经过 Tool Gateway。不允许 Agent 直接调用外部服务。
  • 所有组件默认无状态，状态外置。这是后面水平扩展的前提。
Demo 里这三条都可以省，生产里一条都不能少。

SECTION 02API 与鉴权：三层权限模型

生产系统的权限不是一层，而是三层：User Permission（用户能做什么，业务层）、Agent Permission（Agent 被允许做什么，编排层）、Tool Permission（工具实际开放什么能力，执行层）。

用户有权限，不意味着 Agent 就拥有所有 Tool 权限。

举例：一个付费用户有权限导出报表，但负责「摘要生成」的 Agent 不应该有调用 export_data 工具的权限——即使这个请求来自这个用户。正确的模型是三者取交集：

effective_permission = user_permission ∩ agent_permission ∩ tool_policy
机制说明
AuthenticationAPI Key / JWT / OAuth2，Gateway 层统一完成
RBAC角色 → 权限集合，Agent 本身也是一种「角色」
Tenant每个请求必须携带 tenant_id，向下贯穿到 Tool 调用与数据隔离
API Key面向机器调用，区分 scope（read / write / admin）
Agent PermissionAgent 注册时声明允许的工具与模型，存入 Policy 配置
Tool PermissionTool Gateway 执行前做最后一次校验
auth/policy.pypython
# Agent 注册时声明权限（最小权限原则）
SEARCH_AGENT_POLICY = AgentPolicy(
    allowed_tools=["web_search", "fetch_url"],
    allowed_models=["gpt-4o-mini", "glm-4-air"],
    max_tool_calls_per_task=10,
    max_cost_per_task_usd=0.5,
    allowed_data_scopes=["public"],
)
最小权限原则必须同时作用于 Agent 和用户，缺一不可。

SECTION 03Agent Runtime：从 Prompt 到运行时组件

Demo 里的 Agent 是一段 Prompt + 一个循环。生产里的 Agent Runtime 必须负责八项职责：

Lifecycle

初始化 → 运行 → 挂起 → 终止的完整生命周期管理

State

状态的加载 / 持久化 / 恢复，支持任意时刻续跑

Timeout

步级超时 + 任务级超时双层控制

Retry

接入前文的 Retry / Fallback 机制，平台级保障

Trace

自动创建 Span、注入 trace_id，无需业务代码埋点

Tool Access

所有工具调用强制经 Tool Gateway，无旁路

Model Routing

按任务类型 / 成本自动选择模型

Budget

Token / 成本 / 步数上限，强制执行

agents/runtime.pypython
class AgentRuntime:
    def __init__(self, spec: AgentSpec, ctx: TaskContext):
        self.spec = spec
        self.ctx = ctx          # trace_id, tenant_id, budget, state_ref

    async def run(self, task: Task) -> AgentResult:
        span = tracer.start_agent_span(self.spec.name, self.ctx)
        state = await self.state_store.load(self.ctx.task_id)

        try:
            async with self.budget.track(self.ctx):      # 成本预算
                async with timeout(self.spec.timeout):   # 超时控制
                    result = await self._execute(task, state)
            await self.state_store.save(self.ctx.task_id, result.state)
            return result
        except BudgetExceeded:
            return self.fallback("budget_exceeded")
        except Exception as e:
            return await self.retry_or_fallback(e, task)
        finally:
            span.end(record_tokens=True)
Runtime 的价值在于：把可靠性（Retry/Fallback）、可观测性（Trace）、经济性（Budget）从「每个 Agent 自己写」变成「平台统一保证」。这是从 Demo 到 Production 最重要的抽象升级。

SECTION 04Tool Gateway：独立的工具访问层

为什么不能让 Agent 直接调工具？因为工具调用是整个系统中风险最高、成本最不透明、最难审计的环节。生产级的调用链必须是：

独立 Tool Access Layer 的四个理由：

  1. 安全收口——Prompt Injection 的最终防线在这里。即使 Agent 被注入恶意指令，Gateway 的 Policy 会拦截越权工具调用。
  2. 审计完整性——所有外部副作用（写库、发邮件、调付费 API）都有单一审计点，出事可追溯。
  3. 成本管控——付费工具的调用预算、限流在 Gateway 统一执行，不依赖 Agent 自觉。
  4. 可替换性——换搜索供应商、加缓存、做 Mock（测试环境），只改 Gateway，不动 Agent。
tools/gateway.pypython
class ToolGateway:
    async def execute(self, call: ToolCall, ctx: TaskContext) -> ToolResult:
        await self.auth.check(call.tool, ctx.agent_id, ctx.tenant_id)
        await self.policy.validate(call)          # 参数 schema + 数据边界
        await self.rate_limiter.acquire(ctx)      # 按 tenant + tool 限流

        if cached := await self.cache.get(call):  # 幂等工具可缓存
            return cached

        result = await with_timeout(
            self.executor.run(call), self.tool_timeout(call.tool)
        )
        await self.audit.log(call, result, ctx)   # 事后审计
        return result

SECTION 06Evaluation：三层评测体系

没有评测的 Agent 系统，每次改 Prompt 都是一次赌博。评测必须分三层：

Agent Level

  • Routing Accuracy：路由正确率
  • Tool Selection：工具选对了吗
  • Argument Accuracy：参数正确吗
  • Agent Success：单 Agent 产出达标吗

Workflow Level

  • Task Completion：整体完成率
  • Planning Quality：拆分是否合理
  • Coordination Success：交接是否丢失信息

System Level

  • End-to-End Success
  • Latency（P50 / P99）
  • Cost per Task
  • Failure Rate

落地机制

evaluation/ 目录结构text
evaluation/
├── regression_dataset/     ← 回归数据集：历史 case + 期望结果
├── offline/                ← 每次发版前跑全量回归
├── online/                 ← 线上抽样 + 用户反馈回流
├── llm_judge/              ← LLM-as-Judge 打分（附 rubric）
└── trace_eval/             ← 基于 Trace 做链路级归因
  • Offline Evaluation——发版门禁。新版本必须跑完回归数据集，关键指标不回退才能上线。
  • Online Evaluation——线上按 1%~5% 抽样，用 LLM-as-Judge 评分，配合用户 👍/👎。
  • LLM-as-Judge——定义明确 rubric（事实性、完整性、格式符合度），Judge 模型要与被评模型不同，避免自评偏置。
  • Trace Evaluation——失败 case 不要只看最终输出，回放 Trace 定位是 Planner 拆错、Agent 执行错还是 Tool 返回错。这是 Multi-Agent 评测区别于单 LLM 评测的核心。

SECTION 07Cost Engineering：成本模型与优化手段

先建立成本模型：

cost modeltext
Total Cost =
    LLM Cost            ← 通常占 60~80%
  + Embedding Cost
  + Rerank Cost
  + Tool Cost           ← 搜索 API / 付费数据源
  + Infrastructure Cost ← 计算 / 存储 / 网络
  + Retry Cost          ← 最容易被忽略：失败重试放大倍数
Retry Cost 值得单独强调：如果某 Agent 失败率 20%，重试一次，LLM 消耗直接 ×1.25；若失败的是长上下文 Agent，放大更狠。降低失败率本身就是最大的成本优化。

核心优化手段

手段说明典型收益
Model Routing简单任务用小模型（摘要/分类用 flash 级），复杂推理才用大模型30~60%
Cache语义缓存（相似问题命中）+ 工具结果缓存20~40%
Context Compression多轮历史摘要化、工具结果截断、无关 Agent 上下文裁剪30~50% token
Parallelism无依赖的 Agent 并行执行，省的是延迟而非成本，但提升单位成本产出—
Early ExitReviewer 通过即终止，不再追加轮次；置信度足够高提前返回10~20%
Token Budget每个 Task 设硬上限，Runtime 强制执行（见第 3 节）兜底
models/router.pypython
# Model Routing 示例
def route_model(task: Task) -> str:
    if task.complexity == "high" or task.requires_reasoning:
        return "glm-4-plus"
    if task.type in ("summarize", "classify", "extract"):
        return "glm-4-flash"
    return "glm-4-air"   # 默认
成本必须按 tenant / agent / tool 三个维度记账，否则优化无从下手，计费也无法落地。

SECTION 08性能与扩展

核心问题：哪些组件 Stateless，哪些 Stateful？

Stateless（可随意水平扩展）

  • API Gateway / Auth
  • Orchestrator
  • Agent Runtime Workers
  • Tool Gateway Workers
  • Evaluation Service

Stateful（数据外置，本身无本地状态）

  • Redis —— 热状态：会话、分布式锁、缓存
  • PostgreSQL —— 持久状态：任务、审计、业务数据
  • Vector DB —— Embedding
  • MQ —— 任务队列
  • Object Storage —— 文件与归档
关键原则：Agent Runtime Worker 必须 Stateless。Worker 挂掉后，另一个 Worker 能从 Redis/PG 中恢复 State 继续执行——这是第 3 节 State 外置的直接收益，也是 Kubernetes 滚动更新的前提。

扩展路径：

  1. Async——所有 LLM / Tool 调用异步化，单 Worker 并发处理多任务。
  2. Queue + Worker——Orchestrator 收到请求后写入 MQ 即返回 task_id，Agent Workers 消费执行。削峰、解耦、失败重投全靠它。
  3. Concurrent Agents——无依赖子任务并行派发，结果汇聚（fan-out / fan-in）。
  4. Horizontal Scaling——Worker 按 MQ 队列深度自动扩缩容（KEDA）。
  5. Kubernetes——Deployment 管理 Worker，HPA / KEDA 自动伸缩，探针保证滚动更新不丢任务。
MQ 队列划分建议text
agent_tasks          ── 按 agent 类型分 consumer group
tool_calls           ── 慢工具独立队列，避免阻塞
evaluation_samples   ── 低优先级，离线消费

SECTION 09部署架构

Kubernetes 部署拓扑。注意 Agent Worker 与 API 服务分开部署、分开扩缩容——它们负载特征完全不同（API 是 IO 短请求，Worker 是长任务）。

Docker 化要点：

  • docker/ 下每个服务独立 Dockerfile，多阶段构建，镜像最小化。
  • LLM Provider 的 API Key 通过 K8s Secret / Vault 注入，不进镜像。

SECTION 10安全：八个必答题

风险防御
Prompt Injection输入侧：用户输入与检索内容隔离标记、指令过滤；执行侧：Tool Gateway Policy 是最后防线——即使 Agent 被劫持，也无法调用未授权工具。核心思想：不信任任何 LLM 输出中的「指令」
Tool AbuseRate Limit + 参数校验 + 每 Task 工具调用次数上限 + 危险操作二次确认（写操作需人工审批）
Data Leakage输出过滤：LLM 响应中不得包含 Secret、其他 Tenant 数据；跨 Tenant 检索强制 filter
Tenant Isolationtenant_id 贯穿全链路：Vector DB 按 Tenant 分 namespace / 加 metadata filter，PG 行级隔离
Secret ManagementVault / K8s Secret / 云 KMS，密钥不落日志、不进代码、不进 Trace
PII入口检测与脱敏，日志与 Trace 中对 PII 做 mask
Audit所有工具调用、权限变更、Agent 决策落审计日志，不可篡改，保留合规期限
Agent Permission见第 2 节，三层权限取交集，默认拒绝
安全设计的心智模型：把 Agent 当作「不可信的内部用户」对待。它可能被注入、可能幻觉、可能越权，所以每一次有副作用的动作都要经过独立的校验层。

SECTION 13生产级 Checklist

从 Architecture 到 Deployment，九个维度的完整检查框架。每个维度都应在你上线前逐项打勾：

Architecture

  • Agent 是 Runtime Component，不是 Prompt 字符串
  • 所有外部访问经 Tool Gateway，无旁路
  • Agent Runtime Stateless，状态外置（Redis/PG）

Communication

  • Agent 间通信有明确协议与 schema 校验
  • 异步任务走 MQ，长任务返回 task_id
  • 消息有 trace_id 贯穿

State

  • Task State 可持久化、可恢复、可回放
  • 会话记忆与业务状态分离
  • 状态写入与任务推进是原子 / 幂等的

Reliability

  • 步级 + 任务级超时
  • 幂等操作自动 Retry（指数退避），非幂等操作走补偿
  • 每个 Agent 有 Fallback 路径
  • 死信队列 + 人工介入流程

Security

  • User / Agent / Tool 三层权限取交集，默认拒绝
  • Prompt Injection 纵深防御（输入 + 输出 + Gateway Policy）
  • Tenant 隔离贯穿至 Vector DB / DB / 工具参数
  • Secret 走 Vault/KMS，不落日志
  • PII 脱敏 + 完整审计日志

Observability

  • 全链路 OTel Trace，Span 含 token/cost/prompt_version
  • 指标：QPS / P99 / 错误率 / 成本 / 队列深度
  • 告警：错误率、成本突增、队列积压
  • 日志与 trace_id 关联

Evaluation

  • 回归数据集 + 发版门禁
  • Agent / Workflow / System 三层指标
  • 线上抽样 + LLM-as-Judge
  • 失败 case 有 Trace 归因流程

Cost

  • 按 tenant/agent/tool 记账
  • Model Routing + Cache + Context Compression 生效
  • 每 Task 有 Token / 成本硬预算
  • Retry 成本被监控（失败率是成本指标）

Deployment

  • 服务分部署（API 与 Worker 分离）
  • KEDA / HPA 自动扩缩容
  • 滚动更新不丢任务（State 外置验证过）
  • 本地 docker-compose 一键起开发环境

SECTION 14最后总结：从 0 到 Production 的工程落地路径

到这里可以给出最终认知了：

Multi-Agent 并不是「多个 Agent + 一个框架」。

而是 —— Orchestration + Agent Runtime + Communication + State + Tools + Reliability + Observability + Evaluation + Infrastructure。

九个词，一个都不能少。框架只解决了前两个的一小部分，剩下七个都是你自己的工程问题。给出一条可执行的落地路径，按阶段推进：

PHASE 0

单 Agent 跑通

验证业务价值，不碰架构

完成标志：真实用户愿意用
PHASE 1

拆出 Orchestration

Planner + 2~3 个 Agent，进程内通信

完成标志：多步任务稳定完成
PHASE 2

引入 State Store

任务可恢复，Agent 无状态化

完成标志：杀掉 Worker 任务能自动恢复
PHASE 3

建 Tool Gateway

权限 / 限流 / 审计收口，安全底线

完成标志：无任何旁路工具调用
PHASE 4

全链路 Trace

没有观测，后面所有优化都是盲调

完成标志：线上问题 10 分钟内定位到 Span
PHASE 5

评测体系

回归数据集 + 发版门禁

完成标志：改 Prompt 不再靠赌
PHASE 6

Reliability

Retry / Fallback / Budget / 死信

完成标志：SLA 达标，故障可自愈
PHASE 7

Cost Engineering

记账 → Routing → Cache → 压缩

完成标志：单任务成本可解释、可预测
PHASE 8

生产部署

MQ + K8s + 自动扩缩容 + 告警值班

完成标志：滚动更新零事故

Agent 逻辑决定系统的能力上限，
基础设施决定它能不能活在线上。

最后一句实话：从 Demo 到 Production，代码量大约是 Demo 的 5~10 倍，但其中 80% 不是 Agent 逻辑，而是这一篇讲的这些基础设施。这很正常——五篇下来，这条路径你已经完整走了一遍。剩下的，就是把它落地到你自己的业务里。

—— Multi-Agent 工程系列 · 完 ——

Architecture → Communication → State → Reliability → Security → Observability → Evaluation → Cost → Deployment
