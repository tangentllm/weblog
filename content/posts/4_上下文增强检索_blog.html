一、问题动机：朴素 RAG 的"断章取义"

在第 1 篇中，我们实现了最基础的 Simple RAG：把文档切成固定大小的块，对每个块独立做向量嵌入，检索时返回相似度最高的 Top-K 个块，然后喂给 LLM 生成答案。

这种方案有一个致命缺陷：每个文本块是"孤立"的。当检索命中某个块时，它的前因后果——前面那段铺垫、后面那段补充——全部丢失了。

⚠️ 类比理解

想象你在图书馆找资料，管理员只给你一本书的第 37 页，不告诉你前面讲了什么、后面要讲什么。即使这一页正好包含你需要的信息，你也可能因为缺少上下文而误解它的含义。

具体表现：

  • 语义截断：一个完整的概念被切到两个块里，单独看任一块都不完整
  • 指代不明：块中出现"它"、"该方法"等代词，但指代对象在上一个块中
  • LLM 困惑：模型收到一段没头没尾的文本，生成的答案容易跑偏或遗漏关键信息

上下文增强检索（Context-Enriched Retrieval）就是为了解决这个问题——检索时不仅返回命中的块，还自动把前后相邻的块也一起带上，让 LLM 看到完整的上下文。

二、朴素 RAG vs 上下文增强 RAG：架构对比

❌ 朴素 RAG

  • 分块之间无重叠
  • 检索只返回命中的块本身
  • 每个块是"信息孤岛"
  • 容易出现语义截断

✅ 上下文增强 RAG

  • 分块时设置重叠区域（overlap）
  • 检索返回命中块 + 前后邻居块
  • 上下文连续、语义完整
  • LLM 获得更充分的信息

三、核心原理：重叠分块 + 邻居检索

上下文增强检索的核心思路可以拆成两步：

3.1 重叠分块（Overlapping Chunking）

在切块时，让相邻块之间有一段重叠区域。比如块大小 n=1000 字符，重叠 overlap=200 字符，那么：

  • Chunk 1：字符 0 ~ 1000
  • Chunk 2：字符 800 ~ 1800（与 Chunk 1 重叠 200 字符）
  • Chunk 3：字符 1600 ~ 2600（与 Chunk 2 重叠 200 字符）
  • …依此类推
文档全文 ████████████████████████████████████████████████

Chunk 1   ██████████████████
Chunk 2        ██████████████████
Chunk 3             ██████████████████
Chunk 4                  ██████████████████

          ↑ overlap ↑
图 2：重叠分块示意图——相邻块共享一段重叠区域，减少边界处的信息丢失

3.2 邻居检索（Neighbor Retrieval）

检索时，先找到最匹配的块（Top-1），然后自动把它前后的 context_size 个邻居块也一并返回。

例如 context_size=1 时，如果最匹配的是 Chunk #5，则实际返回 Chunk #4、#5、#6 三个块给 LLM。

💡 为什么重叠分块和邻居检索要配合使用？

重叠分块确保相邻块之间有共享信息，即使邻居块本身不是最匹配的，它和命中块的重叠部分也能帮助 LLM 理解上下文。而邻居检索则直接扩大了 LLM 的"视野范围"。两者结合，效果最佳。

五、代码解读：PDF 文本提取

使用 PyMuPDF（fitz）库逐页提取 PDF 中的纯文本：

def extract_text_from_pdf(pdf_path):
    """从 PDF 文件中提取全部文本。"""
    mypdf = fitz.open(pdf_path)
    all_text = ""
    for page_num in range(mypdf.page_count):
        page = mypdf[page_num]
        text = page.get_text("text")
        all_text += text
    return all_text

这段代码很直白：打开 PDF → 遍历每一页 → 提取文本 → 拼接成一个大字符串。这是 RAG 流水线的标准第一步，与朴素 RAG 完全一致。

六、代码解读：带重叠的文本分块

这是本方案与朴素 RAG 的第一个关键差异点。分块函数接受两个参数：n（块大小）和 overlap（重叠字符数）。

def chunk_text(text, n, overlap):
    """将文本分割为长度为 n 的片段，相邻片段之间有 overlap 个字符的重叠。"""
    chunks = []
    for i in range(0, len(text), n - overlap):
        chunks.append(text[i:i + n])
    return chunks
🔍 关键细节

步长是 n - overlap 而不是 n。这意味着每次起始位置只前进 n - overlap 个字符，从而产生重叠。在本 notebook 中，n=1000、overlap=200，步长为 800。一本 PDF 最终被切成了 42 个块。

七、代码解读：嵌入创建

使用 OpenAI 的 text-embedding-ada-002 模型，将所有文本块批量转换为向量：

def create_embeddings(text, model="text-embedding-ada-002"):
    """使用 OpenAI 模型为文本创建嵌入向量。"""
    response = client.embeddings.create(model=model, input=text)
    return response

response = create_embeddings(text_chunks)

这一步与朴素 RAG 无异——所有块一次性发送给嵌入 API，返回每个块对应的 1536 维向量。

八、代码解读：上下文感知检索（核心）

这是本方案的第二个关键差异点，也是整个上下文增强检索的灵魂。先看一下余弦相似度的计算：

def cosine_similarity(vec1, vec2):
    """计算两个向量之间的余弦相似度。"""
    return np.dot(vec1, vec2) / (np.linalg.norm(vec1) * np.linalg.norm(vec2))

然后是核心的检索函数：

def context_enriched_search(query, text_chunks, embeddings, k=1, context_size=1):
    """获取最相关的片段及其邻近片段。"""
    # 1. 将查询转为嵌入向量
    query_embedding = create_embeddings(query).data[0].embedding

    # 2. 计算查询与每个块的余弦相似度
    similarity_scores = []
    for i, chunk_embedding in enumerate(embeddings):
        score = cosine_similarity(
            np.array(query_embedding),
            np.array(chunk_embedding.embedding)
        )
        similarity_scores.append((i, score))

    # 3. 按相似度降序排序
    similarity_scores.sort(key=lambda x: x[1], reverse=True)

    # 4. 取最匹配的块的索引
    top_index = similarity_scores[0][0]

    # 5. 🌟 关键步骤：扩展上下文窗口
    start = max(0, top_index - context_size)
    end = min(len(text_chunks), top_index + context_size + 1)

    # 6. 返回命中块 + 前后邻居
    return [text_chunks[i] for i in range(start, end)]

图 4：上下文感知检索流程——找到最匹配块后，自动扩展 ±1 个邻居块
🔍 为什么用 max(0, ...) 和 min(len, ...)？

边界保护。如果最匹配的块是第 0 个或最后一个，向前/向后扩展时会越界。这两个函数确保索引始终在合法范围内。

九、代码解读：回复生成

将检索到的多个上下文块拼接成 prompt，交给 gpt-3.5-turbo 生成回答：

system_prompt = "You are an AI assistant that strictly answers based on the given context. \
If the answer cannot be derived directly from the provided context, respond with: \
'I do not have enough information to answer that.'"

# 拼接上下文
user_prompt = "\n".join([
    f"Context {i + 1}:\n{chunk}\n=====================================\n"
    for i, chunk in enumerate(top_chunks)
])
user_prompt = f"{user_prompt}\nQuestion: {query}"

# 生成回答
ai_response = generate_response(system_prompt, user_prompt)

注意 system_prompt 中的严格约束：模型只能基于给定上下文回答，如果上下文中没有答案，必须明确说"信息不足"。这是 RAG 系统的标准做法，可以有效减少幻觉。

十、代码解读：LLM 自动评估

使用另一个 LLM 调用作为"评审员"，将 AI 回答与标准答案对比打分：

evaluate_system_prompt = """You are an intelligent evaluation system...
If the AI assistant's response is very close to the true response → Score: 1
If incorrect or unsatisfactory → Score: 0
If partially aligned → Score: 0.5"""

evaluation_prompt = f"""User Query: {query}
AI Response:\n{ai_response}
True Response: {data[0]['ideal_answer']}
{evaluate_system_prompt}"""

这种"LLM-as-Judge"的评估方式虽然不如人工评估精确，但胜在快速、可自动化，适合在开发阶段快速迭代。

十二、优缺点与适用场景

✅ 优点

  • 实现简单：只需在检索后加几行代码扩展上下文窗口
  • 效果显著：为 LLM 提供更连贯的上下文，减少"断章取义"
  • 与重叠分块协同：overlap 确保邻居块与命中块有信息交集
  • 参数可调：context_size 可灵活控制上下文范围
  • 无额外模型成本：不需要额外的嵌入或排序模型

❌ 缺点

  • Token 消耗增加：返回多个块意味着更多 token 送入 LLM
  • 可能引入噪声：邻居块中可能包含不相关信息
  • 固定窗口：context_size 是全局固定的，不能按查询动态调整
  • 依赖分块质量：如果分块本身不合理，邻居块可能毫无帮助
  • 仅适用于顺序文本：对表格、代码等非连续结构效果有限

适用场景

✅ 适合 ❌ 不适合
长文档问答（论文、报告、书籍） FAQ 类短问答
叙事性/连贯性强的文本 表格、数据库记录
需要上下文才能理解的专业文档 关键词精确匹配即可的场景
Token 预算相对充裕 对延迟和成本极度敏感的场景

十三、本篇小结

上下文增强检索 RAG 是对朴素 RAG 的一个简单但有效的改进。它的核心思想可以用一句话概括：

🎯 核心 takeaway

检索时不要只给 LLM 一个"光秃秃"的文本块——把前后邻居也带上，让它看到完整的上下文。就像读书不能只看一页，至少要看看前后几页才能理解意思。

技术要点回顾：

  1. 重叠分块（overlap=200）：确保相邻块之间有信息共享，减少边界截断
  2. 邻居检索（context_size=1）：命中块的前后各取 1 个邻居，共返回 3 个块
  3. LLM-as-Judge 评估：自动对比 AI 回答与标准答案，给出 0/0.5/1 分

在第 2 篇和第 3 篇中，我们探讨了分块策略和切块大小对检索质量的影响。本篇的上下文增强检索可以看作是这些分块优化的自然延伸——不仅要把块切好，还要在检索时"多看几块"。
