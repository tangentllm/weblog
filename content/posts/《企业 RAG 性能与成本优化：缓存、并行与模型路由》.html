一、开篇：为什么 Demo 很快，上线以后却变慢？

几乎每个做过企业 RAG 落地的团队都经历过同一条曲线：POC 惊艳，灰度勉强，全量上线之后 P95 延迟暴涨、GPU 曲线诡异、Token 账单失控。

场景 01某 SaaS 客服知识库：POC 到全量的滑坡

POC 阶段，链路是教科书式的单请求路径：Query → Embedding → Vector Search → Reranker → LLM → Answer。知识库只有几千个 chunk，检索毫秒级返回，Reranker 只处理十几个候选，LLM 一次性生成答案。延迟很好看。

全量上线后，环境完全变了：上千并发用户、知识库膨胀到几十万 chunk、链路升级为 Hybrid Retrieval + Reranker + Query Rewrite + 长上下文。三周内陆续出现：

  • P95 延迟暴涨——平均延迟看起来还行，但长尾用户几乎不可用；
  • QPS 上不去——GPU 总体利用率却忽高忽低，有的卡排队，有的卡空闲；
  • Reranker 成为瓶颈——候选数随召回策略扩张而膨胀；
  • LLM Token 成本失控——上下文越拼越长，账单线性上涨；
  • Redis 命中率很低——缓存加了，但 key 设计与真实流量不匹配；
  • 大量重复 Query 重复计算——客服场景同类问题高度重复，却每次都走全链路。
▸ 教训：POC 衡量的是单请求的质量，生产衡量的是系统在流量、规模、故障下的行为。这是两个完全不同的问题域。

于是团队自然会问：RAG 的性能问题究竟发生在哪一层？在回答之前，我们必须先建立模型，否则任何"优化"都只是猜测。

三、性能优化第一原则：先定位瓶颈，再优化

我见过太多团队在没有任何 Profiling 的情况下直接开药方：

"加 Redis。" · "换更快的模型。" · "把所有服务都异步化。" · "上 GPU 推理。"

这些不是方案，是条件反射。如果瓶颈在 LLM 的输出 token 数上，加 Redis 对长尾毫无帮助；如果瓶颈在排队延迟，换更快的模型反而可能让 P95 更差。正确的路径只有一条：

Measure → Profile → Locate Bottleneck → Optimize → Benchmark → Regression

要执行这条路径，必须先统一度量语言。企业 RAG 至少要盯住这几个指标：

P50 / P95 / P99
长尾视角
平均延迟不能代表真实线上体验——用户体验由分布的长尾决定。
TTFT
首 Token 时间
流式场景下用户"感觉开始回答"的时刻，是感知延迟的核心。
TPOT
逐 Token 间隔
决定流式输出的"打字机顺滑度"，与解码吞吐直接相关。
QPS / Error Rate
吞吐与稳定
吞吐不是单机压测数字，而是故障注入下依然成立的吞吐。
关键提醒 平均延迟掩盖长尾。一个 P50 = 2s、P99 = 40s 的系统，均值可能依然漂亮，但对那 1% 的用户（往往是高价值用户或复杂 Query 用户）系统等于不可用。企业 SLA 通常应锚定 P95/P99，而不是 mean。

五、并行化：RAG 最直接的性能优化

定位瓶颈之后，第一件值得做的事往往不是买硬件，而是消灭不必要的串行等待。很多 RAG 实现里，检索阶段的写法是这样的：

Dense Retrieval ↓（等待） BM25 ↓ RRF

这是完全错误的执行顺序：Dense 和 BM25 之间没有任何数据依赖，却在互相等待。正确结构是：

同理，以下操作在没有数据依赖时都可以并行执行：

  • Query Embedding 与 Permission Lookup——权限解析不依赖 query 向量；
  • Metadata Retrieval 与 Dense / BM25 检索；
  • 多路 Retrieval（如面向不同知识域的多索引检索）；
  • Cache 查询与 Embedding 计算（乐观并行，命中则丢弃计算结果）。
判据 并行化的前提是无数据依赖。Query Rewrite 产生的改写 Query 是 Embedding 的输入，二者不能并行——这也是"所有请求强制 Rewrite"是反模式的原因之一：它把整个前置链路串行拉长。

六、Async 与 Concurrency

结构上可并行，工程上要用异步并发把它落地。以 Python asyncio 为例：

hybrid_retrieve.py · Python / asyncio并行检索 + 超时 + 取消
# 并行执行 Dense 与 BM25，带独立超时与失败降级
async def hybrid_retrieve(query: str, tenant: TenantCtx) -> FusedResult:

    dense_task = asyncio.create_task(dense_search(query, tenant))
    sparse_task = asyncio.create_task(bm25_search(query, tenant))

    try:
        # 两个子任务并发执行，整体设置检索阶段预算
        dense, sparse = await asyncio.wait(
            {dense_task, sparse_task},
            timeout=RETRIEVAL_BUDGET_SECONDS,   # 超出预算的请求不能无限等待
        )
    except asyncio.TimeoutError:
        # 超时的任务必须显式取消，否则任务泄漏、连接池耗尽
        dense_task.cancel()
        sparse_task.cancel()
        raise RetrievalTimeout()

    if dense_task.exception() and sparse_task.exception():
        raise RetrievalUnavailable()        # 双路失败才真正失败
    if dense_task.exception():
        return fuse_from_single(sparse_task.result())   # 单路降级

    return fuse(dense_task.result(), sparse_task.result(), k=60)

这段代码体现了并发工程里最容易被忽略的几个细节：Connection Pool（并发任务共享下游连接，池太小则并发只是排队搬家）、Timeout（并发不等于可以无限等待）、Cancellation（超时后任务必须真正被取消）。

并发不是免费午餐
  1. Backpressure：上游并发无上限时，压力会以排队延迟的形式转移到最弱的下游（往往是 Reranker GPU 服务）。需要信号量 / 限流 / 准入控制。
  2. Queue Delay：并发度提高后，单请求延迟 = 计算时间 + 排队时间。P95 恶化往往来自后者。
  3. Retry 风暴：并发下的失败重试如果没有退避与上限，故障时刻流量会指数放大（详见第十九章）。
  4. Circuit Breaker：对持续失败的依赖快速熔断，把等待时间换成快速降级路径。
异步提升了吞吐与资源利用率，但单个请求的端到端延迟是否下降，取决于它消除的是"等待"还是制造了"排队"。

七、四层缓存体系：Embedding / Retrieval / Semantic / Response

并行解决的是"不必要的串行"，缓存解决的是"不必要的重复计算"。企业 RAG 的缓存不是一个 Redis，而是四层结构化体系——每一层缓存的对象不同、失效条件不同、风险不同：

7.1 Embedding Cache（L1）

最朴素的一层：对规范化后的 Query 做哈希，命中则跳过 Embedding 调用。适合高频 Query、重复 Query、FAQ 场景。Cache Key 必须包含版本信息：

cache_key = hash(normalized_query) + embedding_model_version + tenant
版本隔离 模型升级后，Embedding 向量空间整体改变。Embedding Cache 必须包含模型版本维度，否则旧向量会与新索引中的向量做跨空间的相似度计算，检索质量静默劣化——没有报错，只有召回悄悄变差。

7.2 Retrieval Cache（L2）

缓存检索结果（候选 ID 列表）。三个可选粒度中：

  • Dense Top-K 与 BM25 Top-K：粒度细，可组合，但需两份缓存、两个版本维度；
  • RRF 融合结果：粒度最粗但收益最大——命中即同时省掉 Embedding、两路检索与融合。

RRF 结果依赖多个检索器与索引状态，因此可以缓存，但 Key 必须携带索引版本：

Cache Key = query + tenant + permission_scope + index_version

7.3 Semantic Cache（L3）

场景 02某金融合规知识库：一次险些上线的权限污染

团队为了压降客服场景的 LLM 成本引入 Semantic Cache：把 Query 向量化后与缓存中的历史 Query 比对，相似度超过阈值即直接返回历史答案。灰度两周，延迟和成本指标都非常好看。

上线前的安全评审发现了两个致命问题：其一，"个人客户经理的权限边界"与"机构客户经理的权限边界"两条 Query 语义相似度很高，但答案对应完全不同的合规文档——False Positive；其二，缓存 Key 只含 query 向量，不含租户与权限过滤条件，理论上 B 部门的用户可以命中 A 部门用户产生的缓存答案。一旦发生，这是数据泄露事故，不是性能问题。

▸ 教训：Semantic Cache 的"相似"并不等于"答案可以复用"。相似度阈值只能过滤表层，无法理解业务意图差异；权限维度必须进入 Key 或进入命中后的二次校验。

Semantic Cache 的收益（降低 LLM 调用、降低延迟、降低成本）是真实的，但风险清单必须逐项处理：

  • Semantic False Positive：表层相似、意图不同 → 提高阈值 + 命中后附加轻量校验（如意图分类一致）；
  • 权限污染：租户 / 权限 scope 必须参与隔离；
  • 知识过期 / 答案时效性：缓存答案必须绑定 index_version 与短 TTL，知识更新即失效。

7.4 Response Cache（L4）

是否缓存最终答案，取决于Query 的答案稳定性：

✓ 适合缓存

"公司的年假政策是什么？" —— 答案稳定、来自政策文档、更新频率低。可设较长 TTL + index_version 绑定。

✗ 不适合缓存

"今天订单状态是什么？" —— 答案随时间实时变化，任何 TTL 的 Response Cache 都可能返回过期事实。

因此需要把缓存策略做成 Query 类型驱动的决策：

Query Type（事实型 / 时效型 / 个性化型） → Cache Policy → TTL → Version 绑定

八、Cache Invalidation：企业 RAG 缓存最大的难题

缓存的所有收益，都建立在"数据没有变"这个假设上。而企业知识库天然是活的：

工程上有两条路径，通常组合使用：

  • 版本化失效（推荐为主）：Cache Key 内嵌 index_version，索引更新时版本自增，旧缓存自然不命中，无需精准删除，实现简单且无遗漏风险；
  • 主动失效（补充）：对 Response/Semantic Cache 中命中了被更新文档的条目，可按文档 ID 维度维护反向索引并删除，缩短窗口期。
衔接第 11 篇 权限变更同样必须触发缓存失效。某用户组失去对一批文档的访问权限后，所有缓存了基于旧权限可见候选的 Retrieval Cache / Response Cache 条目都不能再被该用户组命中。这也是为什么 permission_scope 必须进入 Cache Key——最稳妥的做法是让 Key 随权限版本变化，而不是依赖删除逻辑的完备性。

九、Reranker 性能优化：最易失控的乘法

回顾第 8 篇：Reranker 的计算量是 候选数 × 模型推理成本 的乘法关系，这使它成为整条链路中最容易失控的组件：

Candidate = 20

可控。Reranker 只需对 20 个 (query, doc) 对打分，延迟稳定。

Candidate = 100

计算量 ×5。若为召回"保险"继续放大到 200、500，Reranker 将成为 P95 的决定性因素。

场景 03某制造企业内部文档库：Top 50 → Top 500 的翻车

评测显示扩大召回候选数可以提升小幅度 Recall，团队遂将 Reranker 输入从 Top 50 扩大到 Top 500，期望"宁滥勿缺"。结果：Reranker 服务 GPU 排队，请求延迟从稳定分布变成双峰分布——大部分请求快速返回，落入排队批次的请求延迟数倍增长，P95 与 P50 严重脱节。更糟的是，最终答案质量几乎没有提升：Reranker 排名靠前的文档与 Top 50 场景高度重合，多出来的 450 个候选绝大多数被排到尾部，从未进入 Context。

▸ 教训：Reranker 优化的不是"换一个更小的模型"，而是控制进入它的乘法项——Recall 应该靠检索侧（多路、改写）保证，Reranker 只精排一个经过裁剪的候选集。

正确的优化组合是：

Retrieve Recall（召回侧保底） → Candidate Pruning（粗排/去重/过滤） → Efficient Reranking（精排可控量）
  • Top-K 控制：先裁剪，后精排——候选集大小必须作为容量规划参数管理；
  • Early Filtering：在 Reranker 之前用轻量规则（权限、时间、文档级元数据）先过滤；
  • Batch 推理：提高 GPU 利用率（但见下节警告）；
  • 模型侧：更小 / 量化 / 蒸馏的 Reranker，或 Cross-Encoder → ColBERT 式 late-interaction 的结构降本。

十三、Batch Reranking：吞吐与尾延迟的博弈

batch_rerank.py · Python批推理 + 候选裁剪
# 先裁剪候选，再批量打分 —— 顺序很重要
candidates = prune_candidates(fused, top_k=32, dedup=True)

pairs = [(query, c.text) for c in candidates]

scores = reranker.predict(
    pairs,
    batch_size=16,   # batch_size 需要结合 GPU 显存与排队延迟实验确定
)

ranked = sort_by_score(candidates, scores)[:10]  # 精排后再选 Top-N 进入 Context

Batch 通常能提高硬件利用率、提升吞吐——但线上系统同时要付一笔Queue Delay 的账：

场景 04某电商客服中台：Batch 越大，P95 反而越差

团队将 Reranker 批大小从 8 逐步调到 128，GPU 平均利用率大幅提升，单卡吞吐翻倍，压测报告非常漂亮。灰度上线后，P50 略有改善，P95 却明显恶化。原因：大 batch 意味着批凑齐时间变长，到达时刻不凑巧的请求要在队列里等待凑批，恰好这批"不凑巧"的请求全部落进了长尾。压测的匀速流量掩盖了线上突发的泊松到达特性。

▸ 教训：Batch 越大 ≠ 线上 P95 越好。batch_size 是吞吐与尾延迟的权衡参数，必须用接近真实到达模式的流量（含突发）验证，而不是匀速压测。

Batch 设计需要同时考虑：Batch Size（与显存的匹配）、GPU Memory（OOM 与碎片）、Queue Delay（凑批等待）、Tail Latency（长尾请求分布），以及动态 batch（带最大等待上限的微批策略）。

十、Context Optimization：性能、成本、质量的三重收益

上下文是 RAG 中少数"一处优化、三处收益"的杠杆：

Context ↑ ⇒ Token ↑ + Latency ↑ + Cost ↑ + Noise ↑（质量反而可能下降）

因此 Context 构建必须是一段被预算约束的处理管线（衔接第 10 篇），而不是简单拼接：

Reranker 精排 → Selection（Top-N 选取） → Dedup（去重去冗余） → Compression（摘要/抽取压缩） → Context Budget（Token 预算封顶）
核心认知 Context Optimization 同时是性能优化（更少的 prefill 计算）、成本优化（更少的 input token 计费）和质量优化（更少的噪声、更聚焦的证据）。它是三个优化方向上罕见的不冲突点——但前提是压缩与选取不能破坏证据完整性，这需要评测兜底（见下一篇）。

LLM Token 成本模型

对按 token 计费的 LLM 服务，请求成本的基本式为：

Cost = InputTokens × Cinput + OutputTokens × Coutput 企业 RAG 中 InputTokens 的大头通常是 Context Token（拼入的检索证据 + 系统提示 + 历史对话）——这也是为什么 Context 优化是成本治理的第一杠杆。

可操作的优化维度：Context Size（预算封顶）、Prompt Length（系统提示精简与复用）、Output Length（结构化输出约束、避免车轱辘话）、Model Selection（路由，见下节）、Cache（四层缓存直接减少调用次数）。

十一、Model Routing：让复杂度匹配资源

本文的核心内容之一：不要让所有 Query 都使用同一个模型。

Model Routing 的核心不是"便宜模型替代大模型"，而是让不同复杂度的任务匹配不同资源。

路由决策的常见信号：意图分类结果、Query 复杂度、检索证据的数量与类型、用户/业务等级。同时要设计升级路径（小模型低置信时升级重试），并把路由准确率纳入评测——路由错误会把简单问题交给贵模型（浪费钱），或把复杂问题交给弱模型（牺牲质量）。

Embedding Model Routing：谨慎，再谨慎

同样的思路能否用于 Embedding 模型？理论上可以，但工程代价显著更高：

  • 不同 Embedding Space：不同模型产出的向量彼此不可比，检索必须走对应索引；
  • Index Compatibility：意味着要为每类 query 维护独立的向量索引，或维护多套索引副本；
  • Cache Complexity：Embedding Cache 的版本维度从一个变成多个，命中率被分摊；
  • Evaluation Difficulty：多套索引各自的召回质量都要独立评测与回归。
结论 Embedding Model Routing 比 LLM Routing 更容易引入索引与一致性的复杂度。除非有明确、被验证的收益，不要为了优化而优化。LLM 路由是无状态决策，Embedding 路由是有状态的索引级决策——两者风险量级不同。

十二、Streaming：优化感知延迟，而非总计算量

用户感知的"快"，不完全等于 Total Latency。流式输出改变了延迟的体验结构：

TTFT（首 token 时间） → 用户看到答案开始出现 → Streaming Tokens（TPOT 决定顺滑度） → 答案完成

企业 RAG 的流式链路：

Retrieve → Context 构建 → LLM Streaming → 用户逐步看到答案

关键点必须说清楚：

准确认知 Streaming 不能减少模型的总计算量——prefill 与所有 output token 的解码计算一个都不少，端到端完成时间基本不变。它改善的是感知延迟：把"漫长等待后一次性给出答案"变成"很快开始、逐步呈现"。因此优化目标应聚焦在压缩 TTFT（前置链路预算 + prefill 时间），并用 TPOT 保障呈现顺滑。TPOT 严重不稳定的流式输出，用户体验甚至可能差于稳定的整体返回。

十三、Timeout / Retry / Circuit Breaker / Fallback

企业 RAG 的每一个依赖都可能失败：Embedding Service、Vector DB、Search Engine、Reranker、LLM、Redis。高可用设计的基本骨架：

Timeout → Retry（带退避） → Fallback → Circuit Breaker

Retry：三个纪律

  • 指数退避 + 抖动：避免故障时刻的重试洪峰对下游造成二次打击；
  • 最大次数：有限次重试，超出即进入 Fallback，不能无限等待；
  • 幂等：重试的请求必须无副作用（或携带幂等键），尤其对计费型 LLM 调用。

Timeout：每个阶段必须有预算

任何下游调用都不能无限等待——这与第二十四章的 Performance Budget 直接对应：阶段超预算即放弃，把剩余预算留给关键路径（通常是 LLM）。

Fallback：在质量可接受范围内预设计

典型例子：

Reranker unavailable → Skip Reranker → 返回基础 Retrieval 结果（RRF 排序）

但必须强调：Fallback 应该在质量可接受的范围内设计。降级路径的答案质量必须事先被评测过，而不是想当然。跳过 Reranker 直接使用 RRF 排序，对多数场景质量损失可控；但"跳过权限过滤"或"跳过检索直接让 LLM 自由发挥"就绝对不可接受——前者是安全事故，后者是幻觉事故。

降级策略：失去一个组件后，系统还能不能工作？

高可用系统必须预先定义：失去一个组件之后，系统还能不能工作、以什么质量工作。

十四、成本治理：建立完整的 Cost Model

单位请求成本

Costrequest = CostEmbedding + CostRetrieval + CostRerank + CostLLM 缓存命中时各项趋近于零；路由决定了 CostLLM 的单价档位；候选控制决定了 CostRerank 的量级。

但企业真正应该关注的是 Cost per Successful Answer，而不仅仅是 Cost per Request：

一次便宜但错误的回答 → 用户重新提问（成本 ×2）→ 人工介入（成本 ×N）→ 业务损失（不可计价）
口径建议 把失败率、用户重复提问率、人工转接率折算进成本模型。表面上便宜的方案如果答案质量差，真实单位成本可能反而更高——这也是下一章 Trade-off 的出发点。

十五、Performance × Quality × Cost：三角权衡

这是全文最重要的工程认知：性能优化的每一个旋钮，几乎都同时拨动着质量：

优化动作性能 / 成本影响质量代价
更大 Candidate— Latency ↑ / Rerank 成本 ↑Recall ↑（收益），但噪声候选增加
更强 Reranker— Latency ↑Precision ↑（收益），尾延迟风险 ↑
更长 Context— Token / Latency / Cost ↑信息覆盖 ↑，但 Noise ↑ → 模型被干扰甚至幻觉风险
更大的 LLM— Cost ↑ / Latency ↑能力 ↑（对复杂任务），对简单任务是浪费
更激进的 Cache— Latency / Cost ↓↓Freshness / Correctness 风险 ↑（过期答案、错误命中）
性能优化不能脱离质量指标。任何一项优化上线，都必须回答"质量变化了多少"，否则只是把成本从账单转移到了用户体验和业务风险上。

十六、Performance Budget 与可观测性

Per-component latency budget

把 P95 目标分解为各组件预算，是约束链路不失控的关键机制：

预算的价值在于决策纪律：如果 Retrieval 已经消耗了大量预算，就不能无限增加 Reranker 输入与 Query Rewrite 层级——要么砍别处，要么接受 P95 上移。不要使用任何"通用毫秒数"，预算必须来自你自己的 Trace 分布与业务 SLA。

可观测性：没有 Trace，就没有优化

优化的一切前提是每个请求的完整分布式 Trace：

Request → Query Rewrite → Embedding → Dense → BM25 → RRF → Reranker → Context → LLM

十七、完整性能与成本优化架构

优化闭环：不是项目，是循环

优化不是一次性项目，而是持续工程。知识库在变、流量在变、模型在变——三个月前的最优配置，今天就可能是新的瓶颈。

十八、十个常见失败案例

以下每一个案例都在真实企业项目中出现过。它们的共性是：跳过了定位与验证，直接执行了"听起来对的优化"。

失败 01没做 Profiling 就加缓存

团队听说缓存能提速，直接上线 Redis 层。三个月后复盘：命中率长期在低位徘徊，瓶颈（LLM 输出 token 数）压根不在被缓存的位置，反而新增了缓存一致性负担。

▸ 先确认重复流量真实存在、且落在可缓存的层，再建缓存。
失败 02所有请求强制 Query Rewrite

为了提升召回，把 LLM 改写挂到所有请求的前置链路。结果：前置串行链路被显著拉长，TTFT 恶化；而流量中大量简单事实型 Query 根本不需要改写，改写反而偶发引入歧义。

▸ Rewrite 应该按需触发（简单/清晰 Query 直通），且作为可降级组件。
失败 03Candidate 从 Top 50 扩到 Top 500，Reranker 爆炸

即场景 03：乘法失控，GPU 排队，P95 与 P50 严重脱节，质量几乎无收益。

▸ 候选集大小是容量参数，扩展前必须评估 Reranker 的推理乘法。
失败 04Context 越拼越长，没有 Token Budget

每新增一个知识域，就往 Context 里多塞一类文档。没有预算约束的上下文持续膨胀，成本与延迟同步上涨，且模型被噪声干扰，答案质量不升反降。

▸ Context 必须有 Token Budget 硬约束，膨胀需走预算评审。
失败 05Semantic Cache 没考虑 Tenant / Permission

即场景 02 的前半段：缓存 Key 只有语义向量，跨租户、跨权限命中同一答案。上线前被评审拦下，否则即是数据泄露事故。

▸ 权限与租户必须进入 Key 或命中校验，安全优先于性能。
失败 06缓存没有 Index Version

文档大版本更新（政策重写）后，缓存继续返回基于旧索引的候选与旧答案，用户拿到过期政策长达缓存 TTL 的整个周期。业务方投诉"AI 在说旧规矩"。

▸ Cache Key 必须绑定 index_version，让索引更新自动失效缓存。
失败 07所有 Query 都用最大模型

架构上"图省事"，统一调用旗舰模型。账单中占比极大的部分来自简单 FAQ 类请求；同时旗舰模型的高 TTFT 拉长了所有请求的首字时间。

▸ 让复杂度匹配资源：路由不是替代，是分发。
失败 08Batch Reranker 导致 Queue Delay，P95 反而增加

即场景 04：匀速压测验证的 batch_size，在线上突发到达下产生凑批等待，长尾恶化。

▸ Batch 是吞吐-尾延迟权衡，须用真实到达模式验证，并设最大凑批等待。
失败 09Retry 无 Backoff，故障时级联放大

某下游短暂抖动，所有失败请求立即原样重试，瞬时流量成倍放大，把"短暂抖动"升级为"持续雪崩"，熔断器形同虚设。

▸ 指数退避 + 抖动 + 最大次数 + 熔断，缺一不可。
失败 10为降延迟直接关掉 Reranker，未验证质量损失

延迟告警压力下，工程师把 Reranker 整体下线。延迟立刻达标，两周后质检抽检发现答案的证据相关性明显下滑，检索质量指标同步回退，被迫回滚。

▸ 每个降级开关都必须有对应的质量评测基线，先测后降。

十九、最终核心认知

把整篇文章压缩成两条公式：

Performance =

Less Work
+ Parallel Work
+ Cached Work
+ Right Model
+ Right Context

Cost Optimization =

Fewer Tokens
+ Fewer Model Calls
+ Smaller Models（匹配复杂度）
+ Higher Cache Hit
+ Efficient Retrieval

但最重要的结论是这一句：

企业 RAG 的优化目标不是"最快"，也不是"最便宜"，而是在质量约束下获得最优的性能与成本。Performance × Quality × Cost 三者必须共同优化——脱离质量谈性能是赌博，脱离质量谈成本是转移损失。
