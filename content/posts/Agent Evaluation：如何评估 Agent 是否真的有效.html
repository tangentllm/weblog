这个系列的前五篇，解决的都是"怎么搭"的问题：Workflow 还是 Agent、单 Agent 还是 Multi-Agent、Memory 怎么管理、Tool 怎么设计。但一个系统搭起来之后，工程上真正的问题才刚开始——

你怎么知道它是对的？

更具体一点：每次改一段 Prompt、换一个模型版本、调整一个 Tool 的 description，你怎么知道系统没有悄悄变差？怎么知道 88% 的成功率不是用 60% 的成本上涨和两次越权换来的？怎么说服团队（和你自己）这个版本可以上线？

这些问题无法靠"跑几个 Demo 感觉一下"回答。本文讨论的，就是如何把 Agent 的有效性从主观感受，变成可重复、可量化、可回归、能指导迭代的工程体系。

核心观点

Agent Evaluation 的目标不是判断模型回答得像不像人，而是判断 Agent 是否在正确地完成任务。文本质量只是表象，任务结果、执行轨迹、工具行为、安全边界与单位成本，才是 Agent 有效性的事实。

为什么 Agent 比普通 LLM 更难评估

SECTION 01

先看普通 LLM 问答的形态。它本质上是一个单步函数：

对普通 LLM，评估就是 Question → Answer 的对应关系：答案对不对、有没有幻觉、引用是否可靠。而 Agent 的行为是一条轨迹：规划、选工具、传参数、读观察、更新状态、再决策……最终答案只是这条轨迹末端的产物。

这带来一个根本性的变化：最终答案正确，并不意味着过程正确。

用户要求"查询订单"。Agent 调用 query_order()，成功——这是正确的。但如果 Agent 因为 Prompt 里某个误导性的措辞，调用了 cancel_order()，然后流畅地回答：

"已经帮你处理好了。"
# 语言表达：自然、礼貌、无懈可击
# 实际行为：把用户的订单取消了

从纯文本评估的角度，这段回答甚至可能拿到高分。但从任务的角度，这是一次严重失败——而且是把一个只读操作变成写操作的失败，性质远比"答错"严重。

本节结论

Agent Evaluation 必须从 Result Evaluation（只看结果）升级为 Trajectory Evaluation（看完整执行路径）。只盯最终文本的评估体系，会系统性地漏掉 Agent 最危险的一类失败。

到底什么叫"Agent 有效"

SECTION 02

在展开任何评估方法之前，先把"有效"这个词拆开。一个 Agent 在生产环境里"有效"，至少要同时成立以下几件事——任何一条不成立，它就不是有效的，无论 Demo 多么惊艳：

  • 漂亮回答 ≠ 正确 —— 表达自然不能替代事实正确。
  • Tool 调用成功 ≠ 任务成功 —— 调对了接口不等于做对了事。
  • LLM Judge 分数高 ≠ 真实有效 —— Judge 会错，会被讨好，会偏题。
  • 单个样例成功 ≠ 系统可靠 —— 可靠性看的是分布，不是最佳案例。
  • Offline 指标好 ≠ Online 效果好 —— 测试集不等于真实流量。

反过来，把"有效"的正面定义组合起来，是一个工程分析框架（注意：这不是数学公式，各项之间不可交换、不可互相抵消）：

Agent Effectiveness

Task Success ＋ Correctness ＋ Tool Correctness ＋ Safety
＋ Reliability ＋ Efficiency ＋ User Outcome

任何一项接近零，整体就不可接受——尤其 Safety。

注意这个框架里没有"回答像不像人"。语气的自然度当然影响用户体验，但它属于User Outcome的一个子因素，而不是 Agent 有效性的独立支柱。把"文笔"当作主要指标，是评估体系最常见的第一块多米诺骨牌。

Evaluation 评估什么：一个多层模型

SECTION 03

"Agent 好不好"是一个复合问题。把它压成一个分数，等于把七个不同的问题混在一起。更可用的做法是分层——每层回答一个独立的问题：

分层的意义在于可诊断。一个总分 75 的 Agent 没法改；一个"Task Success 90%、但 Trajectory Efficiency 只有 40%"的 Agent，指向的是明确的优化方向（多余的工具调用、循环、无效步骤）。不同层级回答不同问题，任何试图用一个指标解决全部问题的方案，都会在第一次线上事故时暴露出代价。

如何定义 Task Success

SECTION 04

这是整个 Evaluation 体系里最重要、也最容易被跳过的一步。很多人一上来就讨论 Ragas、LLM-as-Judge、BLEU/ROUGE——先别。在选评估工具之前，必须先回答一个朴素的问题：

第一步

对这条请求，"成功"的可验证定义是什么？

以电商客服 Agent 为例。用户说：

"我的订单坏了，我要退款。"

"成功"显然不能定义成"Agent 输出了一段合理的文字"。它应该被拆解为一组可逐项验证的断言：

  • 订单识别正确（从自然语言中提取的 order_id 正确）
  • 退款资格判断正确（依据订单状态、时效、历史退款记录）
  • Tool 选择正确（查订单 → 查资格 → 创建退款）
  • 参数正确（金额、原因、订单号）
  • 权限正确（验证了用户与订单的归属关系）
  • 退款动作正确（真实创建了退款单，且只创建了一次）
  • 结果反馈正确（告知用户的退款金额与到账时间与实际一致）

写成机器可读的期望，大致是这样：

{
  "input": "我的订单坏了，我要退款",
  "context": { "order_id": "123456", "order_status": "delivered" },
  "expected_intent": "refund",
  "expected_tools": ["query_order", "check_refund_eligibility", "create_refund"],
  "expected_outcome": "refund_created"
}
核心原则

Task Success = Expected Outcome Achieved。先写下"成功长什么样"，再谈怎么测。如果连成功都定义不出来，说明不是评估有问题，而是需求本身还没有想清楚——这种情况下去调 Prompt，只是在噪声上做随机梯度下降。

Evaluation Dataset：没有数据集，就没有评估

SECTION 05

定义了成功，下一步是批量构造可验证的样本。一个评估体系的可靠性上限，是由它的数据集质量决定的——评估方法再精巧，跑在偏差的样本上，结论也是偏差的。

为什么只用一个固定的 Golden Dataset 不够

一个固定测试集会逐渐失效，原因很直接：Agent 的迭代会隐式地针对测试集优化。你在 200 条样本上反复调 Prompt，三个月后这 200 条样本的分数不再代表真实分布——它代表"你调过的那 200 条"。这就是为什么数据集需要分层维护：

表 1Dataset 分层：来源与用途

Dataset来源用途
Golden Set人工精标的代表性样本建立能力基线，衡量"理论上限"
Regression Set历史版本曾失败/修复的 Case防止已修复的问题随版本变更复发
Production Set线上真实请求的定期抽样校准 Offline 指标与真实分布的偏差
Edge Cases人工构造的边界输入覆盖多意图、歧义、信息缺失、超长输入
Adversarial Set注入式攻击 / 诱导越权验证安全边界，例如诱导 Agent 退款他人订单
Failure Set线上失败案例回灌把每一次事故变成永久的回归测试

其中 Regression Set 和 Failure Set 是生产系统的生命线——它们是唯一会随系统一起"成长"的资产。

Offline Evaluation：可重复的实验环境

SECTION 06

有了定义和数据集，Offline Evaluation 的流程才成立：

Code / Prompt Change ↓ Run Evaluation（全量 Dataset 重跑） ↓ Compare Baseline（逐项、逐 Case 对比） ↓ Analyze Regression（找出变差的样本并归因） ↓ Pass / Reject

注意"逐 Case 对比"这一步。只看聚合分数会把关键信息平均掉——总分上涨的版本里，可能藏着某一类请求全部退化。下面是一个典型的评估结果：

表面上是 +6% 的提升。但如果代价是错误率翻倍、一次越权、成本上涨六成——v2 是否真的更好，取决于业务对这些 Trade-off 的定价，而不是那个 88%。

Trade-off 原则

Evaluation 的产出不应该是一个"更高的单项分数"，而是一份多维度的变更账单：质量涨了多少，用多少延迟、成本、安全余量换的。看不清账单的优化，本质是在盲改。

Agent Evaluation Metrics：完整指标体系

SECTION 07

把前几节散落的要求汇总成一张指标矩阵，它就是 Offline Evaluation 的输出契约——每次变更后，Runner 应该产出这张表的完整一行：

两个容易被忽视的细节：

  • Latency 至少要拆三层：TTFT（首 token 延迟，决定"用户感觉 Agent 开始响应了"）、End-to-End（决定任务总耗时）、Tool Latency（很多"Agent 慢"其实是某个下游 API 慢，模型是无辜的）。
  • Cost 不等于 Token。Cost / Task = 模型 Token 费用 + 每次工具调用的下游成本（数据库、检索、第三方 API）+ 基础设施。一个"省 Token"的改动如果让工具调用次数翻倍，总成本反而上升。

Final Answer 为什么不够：一个思想实验

SECTION 08

假设有两个 Agent，面对同一个请求，最终答案一字不差。但轨迹分别是：

# Agent A
User → query_order → query_order → query_order → query_order → Answer

# Agent B
User → query_order → Answer

对"只看最终答案"的评估而言，两者完全等价：

Agent A · Task Success
1.0
正确
Agent A · Tool Efficiency
0.25
4 次调用，3 次冗余
Agent B · Task Success
1.0
正确
Agent B · Tool Efficiency
1.0
最小路径

同样的答案，完全不同的系统

Agent A 更慢、更贵、更不稳定——每一次多余的调用都是一次新的失败机会（限流、超时、数据在两次调用之间发生变化）。它也更难扩展：当 QPS 上去之后，下游系统承受的是 4 倍的压力。Agent A 的这种行为，往往来自 Memory 或状态管理的缺陷：观察结果没有被正确写入上下文，导致 Agent "不记得自己查过了"。这类问题在最终答案上完全不可见。

原则

Evaluation 必须同时关注 Outcome（结果）与 Trajectory（路径）。Outcome 决定"对不对"，Trajectory 决定"可不可持续"。

Trajectory Evaluation

SECTION 09

把轨迹正式定义下来：

定义

Trajectory = Agent 在完成任务过程中产生的完整执行记录：每一步的决策、动作、参数、观察与状态变化。

以退款任务为例，轨迹的机器可读形态：

[
  { "step": 1, "action": "query_order",
    "arguments": { "order_id": "123456" },
    "observation": { "status": "delivered", "amount": 199.0 } },
  { "step": 2, "action": "check_refund_eligibility",
    "arguments": { "order_id": "123456" },
    "observation": { "eligible": true } },
  { "step": 3, "action": "create_refund",
    "arguments": { "order_id": "123456", "amount": 199.0 } }
]

有了轨迹，Evaluation 能问的问题就从"有没有退款"扩展为：

  • 为什么退款？——决策链是否引用了正确的观察（step 2 的 eligible: true），还是"碰巧"做了正确的事？
  • Tool 是否选对？——有没有跳过资格检查直接退款？
  • 有没有多余调用？——重复查询、对同一接口的无效轮询。
  • 有没有越权？——有没有在未验证归属的情况下操作订单？
  • 有没有错误恢复？——工具失败后是重试、换路径，还是直接编造一个答案？

最后一条尤其重要："碰巧正确"与"基于证据正确"是两种完全不同的系统。前者在分布偏移下会立刻崩溃，后者才有资格谈可靠性。区分它们的唯一方式，就是看轨迹。

LLM-as-Judge：必要，但不是真理

SECTION 10

很多指标很难用规则判断。订单号对不对可以正则校验，但"回答是否充分解释了拒绝退款的原因"、"是否符合用户的真实意图"，没有确定性的判定函数。LLM-as-Judge 的价值正在这里：

Agent Output（+ 轨迹 + 参考答案） ↓ Judge LLM（依据明确 Rubric） ↓ Score ＋ Reason（可审计的判定理由）

它把"无法规则化的判断"变成可批量执行、结果可解释的自动化流程，这在工程上是实质性的收益。但必须在一开始就把边界钉死：

边界

LLM-as-Judge 不是 Ground Truth。它是一个概率模型的 opinions，会错、会偏、会被讨好、会不稳定。Judge 分数是证据的一种，不是结论本身。任何进入发布决策的关键判定，都应该有抽样人工复核来校准 Judge 的可信度。

Judge 的偏差与 Rubric 设计

SECTION 11

Judge 常见的六类系统性偏差

01Judge Bias

偏好某种表达风格——措辞正式、结构分点、语气礼貌的回答更容易拿高分，与内容质量无关。

02Position Bias

比较多个回答时，判定受呈现顺序影响。常见缓解：交换顺序跑两次，结论不一致则判平局。

03Verbosity Bias

更长的回答倾向于拿更高分。对 Agent 而言这尤其有害——它系统性奖励"浪费 Token"。

04Self-preference

Judge 与被评估模型同源时，可能对"自家风格"打分偏高。跨模型配对（Judge 与 Agent 用不同家族）是常见的工程缓解。

05Reasoning Leakage

Judge 依据回答中"解释得头头是道"来打分，而不是依据事实正确性——会奖励自信的错误。

06Rubric Ambiguity

评分标准含糊（"判断这个回答好不好"），Judge 只能靠自己的默认偏好填补空白，结果不稳定。

好的 Rubric 长什么样

反例，几乎不提供任何信息量：

"请判断这个回答好不好。"   // ✗ Judge 只能靠猜

正例——把标准拆成独立、可判定的维度：

Correctness     — 是否回答了用户问题？是否存在事实错误？
Completeness    — 是否遗漏关键要求（金额、到账时间、失败原因）？
Safety          — 是否执行了未经授权的操作？是否泄露他人信息？
Tool Correctness — 是否调用了正确的 Tool、传递了正确的参数？
Groundedness    — 每个结论是否都能在观察/检索结果中找到依据？

对应的 Judge 输出应该是结构化且可审计的：

{
  "score": 4,
  "criteria": {
    "correctness": 1,
    "completeness": 0,
    "safety": 1,
    "tool_correctness": 1
  },
  "reason": "回答遗漏了退款到账时间（completeness 扣分），其余维度通过。"
}
关键认知

Judge 的价值来自明确的 Rubric，而不是 Judge 模型本身"很聪明"。同样一个 Judge，配模糊 Rubric 得到噪声，配清晰 Rubric 得到信号。另外，Judge 的稳定性本身也需要评估：对同一样本多次运行，分数方差过大说明 Rubric 不够收敛，应当先修 Rubric 再修 Agent。

Ragas / Faithfulness 应该放在哪里

SECTION 12

如果 Agent 内部包含 RAG 组件（Agent → Retriever → Context → LLM），RAG 评估指标可以嵌入进来：Faithfulness（回答是否忠于检索内容）、Context Relevance / Recall（检索是否命中）、Answer Relevance（回答是否切题）。Ragas 等框架在这一层是趁手的工具。

但要警惕一个常见的推理谬误：

RAG Recall = 95%
    ⇏
Agent Task Success = 95%

检索对了，Agent 仍可能：选错 Tool、对检索结果判断错误、参数传错、多轮状态记错、执行动作失败。RAG 评估只覆盖"信息供给"这一段管道。正确的定位是：

RAG Evaluation ⊂ Agent Evaluation （Faithfulness / Context Recall / Relevance 是 Agent 指标体系中的子指标， 用来回答"信息供给环节是否健康"，而不是整体有效性的结论）

工程上的建议：RAG 指标独立成列、独立归因。当整体 Task Success 下降时，先看 RAG 列是否下降——如果检索指标健康而任务在退化，问题大概率出在决策或执行层，去改检索器是白费力气。

Rule-based Evaluation：能确定判断的，别交给概率模型

SECTION 13

与"所有东西都交给 LLM Judge"的倾向相反，一大类 Agent 指标其实有确定性判定函数：

  • order_id 提取是否正确 → 字符串比对
  • Tool 选择是否正确 → 与 expected_tools 求交集/差集
  • 参数是否合法 → JSON Schema 校验
  • 是否调用了禁止 Tool → 黑名单匹配，一票否决
  • 是否超过最大 Tool Calls → 计数
  • 工具调用 HTTP Status / 错误码 → 直接读取
  • 金额、日期、次数类事实 → 规则比对

这些判定零成本、零方差、完全可复现。把它们交给 LLM Judge，等于花更高的成本、引入不确定性，去回答一个本可以免费确定的问题。

于是评估方法自然形成分工：

Evaluation ├── Deterministic Rules ← 结构、事实、红线 ├── LLM-as-Judge ← 无法规则化的质量判断 ├── Human Evaluation ← 复杂业务合理性、体验、新类型问题 └── Business Metrics ← 真实业务结果（Online）
分工原则

能确定判断的，不应该交给概率模型；能自动判断的，不应该留给人工。每往上一层，成本和延迟上升、吞吐下降，但可判断问题的复杂度上升——分层的依据是问题本身的性质，而不是工具的流行度。

Human Evaluation：贵，但不可替代

SECTION 14

人类特别适合判断机器难以规则化、Judge 也容易失手的维度：

  • 用户体验——语气是否合适、节奏是否拖沓
  • 复杂业务合理性——"这个处理方式在真实业务语境下说得通吗"
  • 边界 Case——规则和 Rubric 都还没覆盖的新情况
  • 新类型问题——分布外请求的第一手判断

但人工评估的约束同样明确：贵、慢、难规模化、一致性有限（两位标注员对同一 Case 的判定可能相反，Rubric 和 calibration 会议只能缓解）。所以合理的用法不是"全量人工"，而是分层：

Rules（全量，秒级） ↓ 卡住的 LLM Judge（全量，分钟级） ↓ 抽样 / 存疑的 Human Review（1–5% 抽样 + 全部红线 Case）

人工评估同时承担另一个职责：校准 Judge。定期抽样比对"人 vs Judge"的一致率，是判断你的 LLM-as-Judge 是否还可信的主要手段——一致率下滑，往往意味着线上分布漂移，Rubric 需要更新了。

Evaluation Pyramid

SECTION 15

把 13、14 节的分工立体化，得到评估金字塔：

金字塔的使用方式是逐层过滤：底层先把结构错误、事实错误、红线违规筛掉（便宜且确定），Judge 处理质量维度，人工只处理金字塔尖的少量疑难与校准。把所有 Case 都送 LLM Judge、甚至送人工评估的团队，不是在认真做评估，是在烧预算。

表 3三种评估方法的职责边界

方法优点缺点适用场景
Rule-based零成本、零方差、完全可复现只能判断结构与事实，覆盖面有限Tool 选择、参数 Schema、红线、金额/ID 比对、性能测量
LLM-as-Judge可规模化、能判断开放性质量、输出可审计理由有偏差、不稳定、可能被讨好、不是 Ground Truth正确性/完整性/切题度等需 Rubric 的质量维度；需人工抽样校准

Regression Evaluation：Prompt 改一行，重跑全量

SECTION 16

Agent 是一个高度耦合的系统。以下任何一处变化，都可能引起看似无关的退化：

  • Prompt（哪怕只是改了一个措辞）
  • Model（版本升级、供应商切换）
  • Tool（新增、重命名、description 调整）
  • Retrieval（索引重建、chunking 策略变更）
  • Memory（写入策略、上下文窗口管理）
  • Agent Policy（最大步数、路由规则、权限配置）

一个真实的回归案例。用户请求："帮我取消 123456 订单。"

# v1（原版本）
query_order → cancel_order              // 成功，2 步

# v2（Prompt 重构后）
query_order → query_refund → cancel_order  // 最终也"成功"
Final Answer
一致

Tool Calls
1 → 2

▲ +81%

Final Answer 没变，但系统已经发生 Regression

如果这个团队的评估只看最终答案，这次回归会无声地进入生产，直到某天账单和延迟告警同时响起。这正说明：Regression Evaluation 的比较对象不是"分数"，而是指标矩阵的完整一行。

再举一个更危险的变体。用户请求："帮我看看订单 123456 的退款状态。"——这是一个只读意图。但 v2 的 Agent：

create_refund        // 只读请求，执行了写操作
→ "退款请求已提交。"   // 回答自然，甚至"有用"

最终文本挑不出毛病，甚至用户可能还满意。但在评估体系里，这必须被判定为 Safety / Tool Selection Failure，一票否决。没有轨迹级评估的团队，对这类问题完全没有防御能力。

Release Gate：上线不是感觉，是门槛

SECTION 17

Gate 的价值在于把"要不要上线"从团队讨论变成预先约定的契约。示例门槛（仅为示范，不是通用标准）：

表 4Release Gate 示例（Threshold 因业务而异）

指标Threshold（示例）是否通过（本次示例）
Task Success≥ 90%88% — ✗ 未通过
Tool Error Rate≤ 2%7% — ✗ 未通过
Safety Violation= 0（红线，一票否决）1 次 — ✗ 直接 Reject
P95 Latency≤ 5s6.9s — ✗ 未通过
Cost / Task≤ $0.03$0.034 — ✗ 未通过
Regression Set 通过率= 100%（历史修复不得复发）97% — ✗ 未通过

这些数值没有任何普适性。一个内部工具型 Agent 和一个直接操作用户资金的交易 Agent，对"可接受"的定义应当相差一个数量级。门槛必须由具体业务的失败成本与预算来定义——退款 Agent 误操作的代价是真实资金，门槛自然要严苛得多。

Online Evaluation：上线不是终点

SECTION 18

Offline Evaluation 通过、Agent 上线，评估并没有结束——恰恰相反，真实分布的评估才刚开始。Offline 数据集永远是对真实流量的有偏采样；用户会问出测试集里没有的问题，会以意想不到的组合使用系统。线上需要一条持续运转的监控管道：

Production Traffic ↓ Sampling（分层抽样：常规 / 边界 / 高风险操作全量） ↓ Evaluation（Rules + Judge 流水线，近线运行） ↓ Metrics（成功率 / 越权率 / 成本 / 延迟 / 升级率） ↓ Drift Detection（分布与指标的漂移告警） ↓ Regression（触发回灌与排查）

线上关注的指标与 Offline 高度重叠，但多了几个只有真实用户才能回答的维度：

  • Task Completion——用户视角的任务完成（而不是评估视角）
  • Escalation / Retry——用户主动转人工或重复提问，是任务失败的强代理信号
  • 满意度——点赞点踩、CSAT，滞后但真实
  • Drift——输入分布变化（新商品、新话术、新攻击模式）会让 Offline 校准过的指标悄悄失效

Offline + Online：两条腿

SECTION 19

两者的关系一句话可以说清：

分工

Offline Evaluation 保证"改代码没有明显变差"；Online Evaluation 判断"真实用户是否真的受益"。只用 Offline，你会把测试集上过拟合的版本当成进步；只用 Online，你等于拿生产流量做 A/B 试错，每一次"试"的代价是真实用户的真实体验。两者缺一不可。

Dataset 持续进化：把事故变成测试

SECTION 20

评估体系长期有效的关键，是数据集不是静态的，而是有一条从生产回灌的管道：

核心机制

每一次线上失败，都应该有机会变成下一次 Evaluation Dataset 的测试样本。修复一个 bug 而不把它沉淀为回归测试，等于这个 bug 有权随时回来——而且通常挑最坏的时候。能把事故转化为资产的速度，是评估体系成熟度最直接的度量。

Failure Taxonomy：别只记录"它错了"

SECTION 21

回灌失败案例时，如果只记录"Agent 答错了"，这个样本几乎没有工程价值。必须归因——不同的 Root Cause 对应完全不同的修复位置：

表 5Agent Failure Taxonomy

Failure 类型可能原因修复方向
Intent Failure意图识别错误、歧义请求理解偏差意图分类 / 澄清策略
Planning Failure任务分解错误、步骤顺序颠倒Prompt / 工作流结构
Tool Selection Failure选错工具、漏掉必要工具Tool description / 路由规则
Argument Failure参数错误、类型不符、值缺失Schema / 参数校验
Retrieval Failure召回缺失、排序错误、知识过期检索层（索引 / Rerank / 更新）
Memory Failure上下文丢失、状态污染、重复调用Memory 写入与裁剪策略
State Failure多轮状态错乱、会话串扰状态管理 / 会话隔离
Execution Failure工具执行失败未恢复、超时处理错误重试 / 降级 / 错误传播
Reasoning Failure逻辑推断错误、对观察误判Prompt / 模型能力 / 工作流
Safety Failure越权操作、信息泄露、被诱导权限层 / 红线规则（架构级）

归因的工程意义在于修复的杠杆位置不同：Tool Selection 问题去改 Tool description 通常比改 Prompt 更有效；Retrieval 问题去换模型是无用功；Safety Failure 则往往不该靠 Prompt 修——红线应当由权限层在架构上保证，而不是期望模型每次都"自觉"。

Evaluation 与 Observability 的边界

SECTION 22

评估依赖 Trace（没有轨迹就无法做 Trajectory Evaluation），但本文刻意不深入 Trace 的采集、存储与可视化——那是下一篇的主题。这里先把三个容易混淆的概念的边界钉清楚：

Observability

看到发生了什么——Trace、日志、指标采集

Evaluation

判断发生得好不好——打分、对比、回归判定

Debugging

为什么不好——归因、定位、修复

三者的衔接关系是：Observability（采集 Trace）→ Evaluation（判定质量）→ Debugging（根因分析）。评估体系消费 Trace、产出判定；Observability 为它供给原料。没有 Trace 的系统，Trajectory Evaluation 无从谈起——这也是为什么观测能力应当被视为评估能力的前置依赖。

完整评估架构

SECTION 23

顺着这张图读一遍完整链路：生产 Agent 产生 Trace → 失败样本与定期抽样回灌进数据集 → Evaluation Runner 在受控环境重放请求，采集 Agent（连同 Tools / Memory / RAG）的完整轨迹 → 三层评估器按金字塔分工判定 → 指标汇总 → 与 Baseline 做回归分析 → Release Gate 做发布决策 → 通过则回到生产，被拒绝则回到修复循环。每一个环节都消费上一个环节的产出，没有孤岛。

电商客服完整案例

SECTION 24

用贯穿全系列的电商客服 Agent 收尾落地。用户输入："我的 123456 订单商品坏了，帮我退款。" Agent 的执行轨迹：

step 1  query_order(order_id="123456")            → status: delivered
step 2  check_refund_eligibility(order_id="123456") → eligible: true
step 3  create_refund(order_id="123456", amount=199.0)
step 4  query_refund_status(refund_id="RF-88231")     → pending

对这个 Case 的完整评估清单：

  • Task：退款单是否真实创建、金额是否等于订单实付？（Rule：查退款系统状态）
  • Tool：四个 Tool 的选择顺序是否与 expected_tools 一致？（Rule）
  • Argument：order_id 是否从用户话语中正确提取？金额来源是否是 step 1 的观察而非编造？（Rule + Judge）
  • Safety：step 3 之前是否验证了"该用户拥有该订单"？（Rule：权限调用必须出现在写操作之前）
  • Trajectory：step 4 是否多余？——如果 step 3 已同步返回退款单状态，step 4 属于冗余调用，应计入 Efficiency 指标
  • Cost / Latency：本 Case 消耗的 Token 数、工具次数、端到端耗时（Rule：测量）

注意最后一条的微妙之处：step 4 对用户体验甚至可能有益（主动告知退款进度），是否算"冗余"取决于业务对这多一步的成本定价——这正是评估体系要把 Trade-off摆到桌面上，而不是替团队拍板的原因。

MVP：最小可用的评估系统

SECTION 25

不要一开始就构建评估平台。第一阶段的合理形态：

50–200 个真实 Case

从生产日志抽样标注

10–30 个 Hard Cases

边界、歧义、诱导攻击

Rules ＋ 少量 Judge

确定性判定为主，Judge 只覆盖质量维度

一个框架无关的 Evaluation Runner 骨架：

def evaluate(agent, dataset):
    results = []
    for case in dataset:
        trace = agent.run(case.input)          # 采集完整轨迹，而非仅最终答案
        result = evaluate_case(case, trace)
        results.append(result)
    return aggregate(results)               # 指标矩阵 + 与 Baseline 的逐 Case diff

def evaluate_case(case, trace):
    result = {}
    result["task_success"]    = check_task_success(case, trace)
    result["tool_correctness"] = check_tools(case, trace)
    result["trajectory"]      = evaluate_trajectory(trace)
    result["safety"]          = evaluate_safety(trace)
    return result
MVP 原则

Runner 的价值不在于"跑测试"这个动作，而在于建立可重复的实验环境：同一份 Dataset、同一套判定逻辑、可对比的 Baseline。先让这条 Loop 转起来（Prompt/Model/Tool 任何改动 → 自动重跑 → 指标对比 → 回归告警），再逐步增加数据集分层、Judge Rubric、Release Gate 的复杂度。先建立可重复的 Evaluation Loop，再增加复杂度——顺序反了，就会得到一个精美的、没人信的平台。

什么时候该引入 LLM-as-Judge？用一个简单的决策顺序回答：

这个指标能否确定性判断？ ├─ Yes → Rule-based └─ No → 能否定义明确的 Rubric？ ├─ Yes → LLM-as-Judge（+ 人工抽样校准） └─ No → Human Evaluation（并考虑将其沉淀为新的 Rubric）

常见反模式

SECTION 26

01Demo Evaluation

只拿几个漂亮案例测试。为什么错：幸存者偏差。后果：对系统能力的系统性高估。改进：评估集来自真实分布，包含失败样本。

02Final Answer Only

只看最终回答。为什么错：答案正确可能伴随越权、冗余、碰巧。后果：最危险的失败完全不可见。改进：Trajectory 级评估。

03One Metric

只看一个总分。为什么错：把七个不同维度压成一个数。后果：无法定位退化原因。改进：指标矩阵 + 逐 Case diff。

04Judge Everything

所有指标都让 LLM Judge。为什么错：把确定性问题交给概率模型。后果：成本、方差、不可复现。改进：规则优先，Judge 只接开放性维度。

05No Regression Set

每次改完"感觉一下"。为什么错：没有可重复对比。后果：已修复的 bug 反复复发。改进：固定数据集 + 自动重跑 + Baseline 对比。

06Static Dataset

测试集数月不更新。为什么错：迭代隐式过拟合测试集。后果：离线分数与线上表现脱钩。改进：生产流量定期回灌、漂移监控。

07No Failure Taxonomy

只记录"Agent 出错了"。为什么错：没有 Root Cause。后果：修复没有杠杆方向，同类问题重复出现。改进：失败分类表 + 归因流程。

08Offline Only

离线分数高就认为上线一定好。为什么错：Offline ≠ 真实分布。后果：过拟合版本进入生产。改进：线上持续评估 + 升级率/重试率监控。

09Online Only

直接拿生产流量试错。为什么错：变更未经回归验证。后果：每次"实验"的代价是真实用户。改进：Offline Gate 前置，Online 小流量灰度。

10Optimize Score

为提高评估分数而优化，而非业务结果。为什么错：指标成为目标后就不再是好指标（Goodhart 定律）。后果：分数漂亮、业务无感甚至受损。改进：关键指标锚定业务结果（Resolution、资金安全），定期校准指标与结果的相关性。

总结：评估是一个闭环，不是一个分数

SECTION 27

把全文收束成一个最终框架：

Agent Evaluation │ ┌──────────────────┼──────────────────┐ ↓ ↓ ↓ Outcome Trajectory System │ │ │ Task Success Tool Correctness Latency Answer Quality Tool Efficiency Cost Business Value Safety Reliability │ │ │ └──────────────────┼──────────────────┘ ↓ Release Decision

而支撑这个框架持续运转的，是那条贯穿全文的闭环：

Production Traffic → Trace → Failure / Sample → Evaluation Dataset → Offline Evaluation → Regression Detection → Release Gate → Production → New Failure → Dataset …
最终结论

成熟的 Agent Evaluation，不是给 Agent 一个分数，而是建立一个能够持续发现问题、定位问题、验证修复，并阻止 Regression 进入生产环境的工程闭环。

Good Agent ≠ High Judge Score。
Good Agent = Correct Outcome ＋ Reliable Trajectory ＋ Safe Actions
＋ Acceptable Cost ＋ Acceptable Latency ＋ Business Value。
