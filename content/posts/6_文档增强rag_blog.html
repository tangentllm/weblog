一、问题动机：用户的"问"与文档的"述"之间的鸿沟

在前面的篇章中，我们用了语义分块、切块大小调优、上下文邻居检索、CCH 标题提取等多种手段来改善检索。但所有这些方法都面临一个根本矛盾：

⚠️ 类比理解

想象你去图书馆找书。你问管理员："中国政府对 AI 大模型有哪些支持政策？"管理员却只能从书架上抽出一本本陈述句写成的报告来逐页翻找。报告里写的是"我国高度重视人工智能的发展，将其上升为国家战略，出台一系列扶持政策……"——内容完全匹配，但表达方式截然不同：你用的是疑问句，文档用的是陈述句。

嵌入模型虽然能捕捉语义相似性，但当查询是疑问句而文档是陈述句时，向量空间中的距离可能比预期更远。文档增强 RAG（Document Augmented RAG）的核心思路就是：既然用户用"问题"来检索，那我们就在向量存储里也放入"问题"——用 LLM 为每个文本块生成可以被该块回答的问题，然后将这些问题的嵌入也存入向量存储。

二、朴素 RAG vs 文档增强 RAG：架构对比

❌ 朴素 RAG

  • 向量存储中只有文本块
  • 用户查询直接与陈述性文本做相似度匹配
  • 疑问句 vs 陈述句的表达鸿沟可能导致漏检
  • 35 个块 → 35 条向量记录

✅ 文档增强 RAG

  • 向量存储中同时包含文本块 + 生成的问题
  • 用户查询可以匹配到语义更接近的问题
  • 问题充当"语义桥梁"，弥合疑问句与陈述句的差距
  • 35 个块 → 35 + 35×3 = 140 条向量记录

三、核心原理：用 LLM 生成"可被回答的问题"

文档增强 RAG 的关键创新可以概括为一个转换：把"这段文本说了什么"变成"这段文本能回答什么"。

3.1 索引阶段：从陈述到疑问

对每个文本块，调用 LLM 生成 N 个可以被该块直接回答的问题。这些问题与用户可能提出的查询在表达方式上高度一致（都是疑问句），因此在嵌入空间中距离更近。

3.2 检索阶段：双重类型匹配

向量存储中同时存在两种类型的记录：文本块（chunk）和生成的问题（question）。检索时，用户查询同时与这两种记录做余弦相似度匹配。由于问题与查询在表达形式上更接近（都是疑问句），问题匹配往往能提供更高的相似度分数，从而通过 metadata 回溯到对应的原始文本块。

🔍 设计要点
  • metadata.type：区分记录是"文本块"还是"问题"，便于后续分类处理
  • metadata.chunk_index：问题记录指向其来源的块索引，检索命中问题后可以回溯到原始块

六、代码解读：LLM 生成问题

这是文档增强 RAG 最核心的函数——用 gpt-4o 为每个文本块生成可以被该块回答的问题：

def generate_questions(text_chunk, num_questions=5, model="gpt-4o"):
    """根据给定的文本块生成可以被该块直接回答的问题。"""
    system_prompt = (
        "你是一名擅长从文本中提炼关键信息并生成相关问题的专家。"
        "请只用中文，根据给定文本生成可以用该文本直接回答的简明问题，"
        "聚焦于核心信息和重要概念。"
    )

    user_prompt = f"""
请根据以下文本内容，生成 {num_questions} 个不同的问题，
这些问题都可以仅通过该文本内容来回答：

{text_chunk}

请只用中文作答，输出格式为编号的问题列表，不要有其他多余内容。
"""

    response = client.chat.completions.create(
        model=model,
        temperature=0.7,       # 适度随机，让问题更多样
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ]
    )

    # 从回复中提取并清理问题
    questions_text = response.choices[0].message.content.strip()
    questions = []
    for line in questions_text.split('\n'):
        cleaned_line = re.sub(r'^\d+\.\s*', '', line.strip())
        if cleaned_line and cleaned_line.endswith('？'):
            questions.append(cleaned_line)
    return questions
🔍 设计要点
  • temperature=0.7：与 CCH 标题生成（temperature=0）不同，这里刻意引入随机性，让同一块生成的多个问题更多样化，覆盖不同角度的查询
  • 中文 prompt：因为目标文档和预期用户查询都是中文，用中文 prompt 确保生成的问题与用户查询的语言风格一致
  • 正则提取：LLM 输出格式为"1. xxx？\n2. xxx？"，用正则 ^\d+\.\s* 去除编号，只保留问题文本
  • 过滤条件：只保留以"？"结尾的行，过滤掉可能的多余输出

七、代码解读：SimpleVectorStore 向量存储

由于需要同时存储两种类型的记录（chunk 和 question），notebook 用 NumPy 实现了一个轻量级向量存储：

class SimpleVectorStore:
    """使用 NumPy 实现的简单向量存储。"""
    def __init__(self):
        self.vectors = []    # 嵌入向量列表
        self.texts = []      # 原始文本列表
        self.metadata = []   # 元数据列表

    def add_item(self, text, embedding, metadata=None):
        """添加一条记录：文本 + 嵌入 + 元数据。"""
        self.vectors.append(np.array(embedding))
        self.texts.append(text)
        self.metadata.append(metadata or {})

    def similarity_search(self, query_embedding, k=5):
        """用余弦相似度查找最相似的 top-k 条记录。"""
        query_vector = np.array(query_embedding)
        similarities = []
        for i, vector in enumerate(self.vectors):
            similarity = np.dot(query_vector, vector) / (
                np.linalg.norm(query_vector) * np.linalg.norm(vector)
            )
            similarities.append((i, similarity))

        similarities.sort(key=lambda x: x[1], reverse=True)

        results = []
        for i in range(min(k, len(similarities))):
            idx, score = similarities[i]
            results.append({
                "text": self.texts[idx],
                "metadata": self.metadata[idx],
                "similarity": score
            })
        return results
🔍 设计要点
  • 统一存储：chunk 和 question 记录存在同一个列表中，检索时统一排序，不做类型区分
  • metadata 区分类型：通过 metadata["type"] 区分"chunk"和"question"，后续处理时分类
  • 余弦相似度：标准的向量相似度度量，适合归一化后的嵌入向量
  • 轻量实现：生产环境中可替换为 FAISS、Chroma、Pinecone 等专用向量数据库

八、代码解读：文档增强处理管道

process_document 函数将所有步骤整合为一个完整的管道：

def process_document(pdf_path, chunk_size=1000, chunk_overlap=200,
                     questions_per_chunk=5):
    """处理带有问题增强的文档。"""
    # 1. 提取文本
    extracted_text = extract_text_from_pdf(pdf_path)

    # 2. 重叠分块
    text_chunks = chunk_text(extracted_text, chunk_size, chunk_overlap)
    print(f"Created {len(text_chunks)} text chunks")

    vector_store = SimpleVectorStore()

    # 3. 逐块处理：嵌入 + 生成问题 + 问题嵌入
    for i, chunk in enumerate(tqdm(text_chunks, desc="Processing Chunks")):
        # 为块本身创建嵌入
        chunk_embedding = create_embeddings(chunk).data[0].embedding
        vector_store.add_item(
            text=chunk,
            embedding=chunk_embedding,
            metadata={"type": "chunk", "index": i}
        )

        # 为该块生成问题
        questions = generate_questions(
            chunk, num_questions=questions_per_chunk
        )

        # 为每个问题创建嵌入并添加到向量存储
        for question in questions:
            question_embedding = create_embeddings(question).data[0].embedding
            vector_store.add_item(
                text=question,
                embedding=question_embedding,
                metadata={
                    "type": "question",
                    "chunk_index": i,
                    "original_chunk": chunk
                }
            )

    return text_chunks, vector_store

⚠️ 成本提醒

每个块需要 1 次 gpt-4o 调用（生成问题）+ 1 次嵌入调用（块嵌入）+ 3 次嵌入调用（问题嵌入）= 5 次 API 调用/块。35 个块总计 175 次 API 调用。相比朴素 RAG 的 35 次嵌入调用，API 成本增加了约 5 倍。在生产环境中需要权衡效果提升与成本。

九、代码解读：上下文准备与回复生成

检索结果中混合了 chunk 和 question 两种类型。prepare_context 函数的职责是将它们统一回溯到原始块并去重：

def prepare_context(search_results):
    """从搜索结果中准备统一的上下文。"""
    chunk_indices = set()
    context_chunks = []

    # 先添加直接匹配的文本块
    for result in search_results:
        if result["metadata"]["type"] == "chunk":
            chunk_indices.add(result["metadata"]["index"])
            context_chunks.append(
                f"Chunk {result['metadata']['index']}:\n{result['text']}"
            )

    # 再通过问题回溯到原始块（去重）
    for result in search_results:
        if result["metadata"]["type"] == "question":
            chunk_idx = result["metadata"]["chunk_index"]
            if chunk_idx not in chunk_indices:
                chunk_indices.add(chunk_idx)
                context_chunks.append(
                    f"Chunk {chunk_idx} "
                    f"(referenced by question '{result['text']}'):\n"
                    f"{result['metadata']['original_chunk']}"
                )

    return "\n\n".join(context_chunks)
💡 设计巧妙之处

无论查询匹配到的是文本块本身还是生成的问题，最终送入 LLM 的上下文都是原始文本块。问题只是"检索入口"，真正的"答案来源"还是原始文档内容。通过 chunk_indices 集合去重，避免同一块被重复送入上下文。

回复生成函数与前面篇章类似，使用 gpt-4o 基于合并后的上下文生成回答：

def generate_response(query, context, model="gpt-4o"):
    """根据查询和上下文生成回复。"""
    system_prompt = (
        "You are an AI assistant that strictly answers based on "
        "the given context. If the answer cannot be derived directly "
        "from the provided context, respond with: 'I do not have "
        "enough information to answer that.'"
    )
    user_prompt = f"""
        Context:
        {context}

        Question: {query}

        Please answer the question based only on the context provided
        above. Be concise and accurate.
    """
    response = client.chat.completions.create(
        model=model,
        temperature=0,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ]
    )
    return response.choices[0].message.content

十三、优缺点与适用场景

✅ 优点

  • 语义桥梁：生成的问题与用户查询在表达方式上高度一致，弥合了疑问句与陈述句的鸿沟
  • 检索精度提升：问题匹配的最高相似度（0.9389）远高于朴素 RAG 的块匹配
  • 多角度覆盖：每个块生成多个问题，覆盖不同角度的查询意图
  • 实现直观：核心逻辑简单——生成问题、嵌入问题、统一检索
  • 可与其他技术叠加：可与 CCH、邻居检索、重排序等组合使用

❌ 缺点

  • 索引成本大幅增加：每块需要 1 次 LLM 调用 + 4 次嵌入调用 = 5 次 API 调用
  • 存储膨胀：向量存储从 35 条膨胀到 140 条（4 倍），大规模场景下更显著
  • 检索延迟增加：更大的向量空间意味着更长的相似度计算时间
  • 问题质量依赖 LLM：如果生成的问题偏离了块的核心内容，可能引入噪声
  • temperature 调参：问题生成的 temperature 需要调优——太低则问题雷同，太高则问题偏离

适用场景

✅ 适合 ❌ 不适合
用户查询以疑问句为主的场景 关键词匹配即可满足的简单检索
文档为陈述性长文本（报告、论文） 文档本身已是 FAQ 格式
对检索召回率要求高的场景 对索引成本和延迟极度敏感的场景
查询角度多样、难以预测用户怎么问 查询模式固定、可枚举的场景

十四、本篇小结

文档增强 RAG 的核心思想可以用一句话概括：

🎯 核心 takeaway

既然用户用"问题"来检索，那就在向量存储里也放入"问题"。用 LLM 为每个文本块生成可以被该块回答的问题，然后将问题和原文一起嵌入向量存储。检索时，用户查询可以匹配到语义更接近的问题，再通过 metadata 回溯到原始文本块。问题充当了用户"疑问句"与文档"陈述句"之间的语义桥梁。

技术要点回顾：

  1. LLM 生成问题：用 gpt-4o（temperature=0.7）为每个块生成 3 个可回答的问题
  2. 双重类型嵌入：文本块和生成的问题分别用 text-embedding-ada-002 嵌入
  3. 统一向量存储：35 块 + 105 问题 = 140 条记录，通过 metadata.type 区分
  4. metadata 回溯：问题匹配通过 chunk_index 回溯到原始块，确保上下文来自原文
  5. 效果提升：评估分数从朴素 RAG 的 0.5 提升到 0.8（提升 60%）

本篇的文档增强技术与第 5 篇的 CCH 技术思路相似但策略不同：CCH 生成的是"标题"（描述块说了什么），本篇生成的是"问题"（块能回答什么）。两者可以叠加使用——用标题做语义锚点，用问题做检索桥梁，进一步提升检索质量。
