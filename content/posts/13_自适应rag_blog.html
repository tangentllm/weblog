一、问题动机：传统 RAG 的"盲目"检索

在前面的系列中，我们逐步优化了 RAG 的各个环节——从语义分块、切块大小调优到上下文增强检索，核心目标都是让检索更精准。然而，这些方案都建立在一个隐含假设上：每次查询都需要检索。

但现实中并非如此。考虑以下场景：

  • 用户问"你好"——这显然不需要检索任何文档
  • 用户问"什么是神经网络"——这是常识性问题，LLM 自身知识就足够
  • 用户问"2024 年中国 AI 政策有哪些"——这需要检索最新信息

传统 RAG 对所有查询一视同仁：检索 → 拼接 → 生成。这带来两个问题：

  1. 不必要的检索：浪费时间和 token，还可能引入噪声干扰 LLM 生成
  2. 缺乏质量把控：检索到的文档可能不相关，生成的回复可能缺乏依据，但系统不会"反思"这些问题
⚠️ 类比理解

想象一个学生参加考试。传统 RAG 就像一个"逢题必翻书"的学生——不管题目是"1+1=?"还是"量子力学原理"，他都要翻一遍教科书。更糟的是，翻到相关段落后，他可能抄了一段不相关的内容当答案，却从不检查自己写的是否正确。Self-RAG 就是教会这个学生：先判断要不要翻书，翻到的内容是否相关，写完答案后还要检查一遍。

Self-RAG（自适应 RAG）的核心思路是：在检索和生成过程中引入反思点（reflection points），让系统能够动态决策——是否需要检索、检索到的文档是否相关、生成的回复是否有据可依、整体质量如何。

二、传统 RAG vs Self-RAG：架构对比

❌ 传统 RAG

  • 固定流程：每个查询都执行"检索→生成"
  • 无检索决策：不判断是否需要检索
  • 无质量评估：不检查文档相关性
  • 无自我反思：不评估回复是否有据可依
  • 噪声敏感：不相关文档可能误导生成

✅ Self-RAG（自适应 RAG）

  • 动态决策：按需检索，简单问题直接回答
  • 相关性过滤：逐个评估文档是否相关
  • 支持度检查：验证回复是否被上下文支持
  • 实用性评分：对回复质量打 1-5 分
  • 最优选择：从多个候选中选出最佳回复

五、代码解读：检索决策

Self-RAG 的第一步是判断查询是否需要检索。这是一个二分类问题——LLM 只需回答"是"或"否"：

def determine_if_retrieval_needed(query):
    """判断给定的查询是否需要检索。"""
    system_prompt = """你是一名AI助手，负责判断回答一个查询时是否需要检索外部信息。
    如果是事实性问题、具体信息请求，或关于事件、人物、概念的问题，请回答"是"。
    如果是观点、假设场景，或常识性简单问题，请回答"否"。
    只需回答"是"或"否"，不要包含其他内容。"""

    user_prompt = f"查询：{query}\n\n准确回答该问题是否需要检索？"

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ],
        temperature=0  # 确保判断的一致性
    )

    answer = response.choices[0].message.content.strip().lower()
    return "是" in answer
🔍 设计要点
  • temperature=0：确保同样的查询总是得到同样的判断结果
  • 判断标准明确：事实性问题 → 需要检索；观点/常识 → 不需要
  • 返回布尔值：简单 True/False，下游逻辑据此分支

六、代码解读：相关性评估

检索到 Top-K 文档后，Self-RAG 不是直接使用它们，而是逐个评估每个文档与查询的相关性：

def evaluate_relevance(query, context):
    """评估上下文与查询的相关性。"""
    system_prompt = """你是一名AI助手，负责判断文档内容是否与查询相关。
    请判断文档中是否包含有助于回答查询的信息。
    只需回答"相关"或"不相关"，不要包含其他内容。"""

    # 截断过长上下文，避免超出 token 限制
    max_context_length = 2000
    if len(context) > max_context_length:
        context = context[:max_context_length] + "... [已截断]"

    user_prompt = f"""查询：{query}
    文档内容：
    {context}

    该文档内容是否与查询相关？只需回答"相关"或"不相关"。"""

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ],
        temperature=0
    )

    answer = response.choices[0].message.content.strip().lower()
    return answer  # 返回 "相关" 或 "不相关"
⚠️ 注意：返回值是中文

这个函数返回的是中文字符串——"相关" 或 "不相关"，而不是英文的 "relevant"。这个细节在下游代码中引发了一个重要的匹配问题，我们将在踩坑分析章节详细讨论。

七、代码解读：支持度评估

生成回复后，Self-RAG 会检查：这个回复是否有上下文作为依据？ 这是防止 LLM "幻觉"的关键机制。

def assess_support(response, context):
    """判断生成的回复是否由上下文充分支持。"""
    system_prompt = """你是一名AI助手，负责判断回复内容是否由给定的上下文充分支持。
    请评估回复中的事实、论断和信息是否都能在上下文中找到依据。
    只需从以下三个选项中选择一个作为答案：
    - "完全支持"：回复中的所有信息都能被上下文直接支持。
    - "部分支持"：回复中有些信息能被上下文支持，但有些不能。
    - "不支持"：回复中有大量信息在上下文中找不到或与上下文相矛盾。"""

    max_context_length = 2000
    if len(context) > max_context_length:
        context = context[:max_context_length] + "... [已截断]"

    user_prompt = f"""上下文：
    {context}

    回复：
    {response}

    该回复在多大程度上得到上下文的支持？只需回答"完全支持"、"部分支持"或"不支持"。"""

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ],
        temperature=0
    )

    return response.choices[0].message.content.strip().lower()
    # 返回 "完全支持" / "部分支持" / "不支持"
支持度评估的三种结果：

│  ⚠️ 部分支持 (partially supported)                               │

├─────────────────────────────────────────────────────────────────┤
│  ❌ 不支持 (no support)                                          │

│     → support_score = 0                                         │
└─────────────────────────────────────────────────────────────────┘

八、代码解读：实用性评估

除了检查回复是否有据可依，Self-RAG 还会对回复的整体实用性打分（1-5 分）：

def rate_utility(query, response):
    """对回复的质量进行评分（1-5 分）。"""
    system_prompt = """你是一名AI助手，负责对回复对于查询的有用性进行评分。
    请考虑回复对问题的解答程度、完整性、正确性和帮助性。
    按照1到5分的标准进行评分，其中：
    - 1：完全无用
    - 2：略有用
    - 3：一般有用
    - 4：非常有用
    - 5：极其有用
    只需返回1到5中的一个数字，不要包含其他内容。"""

    user_prompt = f"""查询：{query}
    回复：
    {response}

    请对该回复的有用性按1到5分进行评分："""

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ],
        temperature=0
    )

    rating = response.choices[0].message.content.strip()
    rating_match = re.search(r'[1-5]', rating)
    if rating_match:
        return int(rating_match.group())
    return 3  # 解析失败时返回中间值
🔍 设计要点
  • 多维度评估：评分标准涵盖解答程度、完整性、正确性和帮助性
  • 容错处理：如果 LLM 返回了非标准格式，用正则提取数字，失败则回退到默认值 3
  • 与支持度互补：支持度关注"是否有据"，实用性关注"是否有用"——一个回复可以有据但无用（如只重复上下文），也可以有用但缺乏依据（如 LLM 自身知识丰富）

九、代码解读：完整 Self-RAG 管道

将所有反思点串联起来，就是完整的 Self-RAG 管道。核心逻辑是：对每个相关上下文生成候选回复，评估后选最佳。

def self_rag(query, vector_store, top_k=3):
    """实现完整的 Self-RAG 管道。"""
    # Step 1: 判断是否需要检索
    retrieval_needed = determine_if_retrieval_needed(query)

    best_response = None
    best_score = -1
    metrics = {
        "retrieval_needed": retrieval_needed,
        "documents_retrieved": 0,
        "relevant_documents": 0,
        "response_support_ratings": [],
        "utility_ratings": []
    }

    if retrieval_needed:
        # Step 2: 检索 Top-K 文档
        query_embedding = create_embeddings(query)
        results = vector_store.similarity_search(query_embedding, k=top_k)
        metrics["documents_retrieved"] = len(results)

        # Step 3: 逐个评估相关性
        relevant_contexts = []
        for i, result in enumerate(results):
            relevance = evaluate_relevance(query, result["text"])
            if relevance == "relevant":       # ⚠️ 注意：这里用英文判断
                relevant_contexts.append(result["text"])

        metrics["relevant_documents"] = len(relevant_contexts)

        if relevant_contexts:
            # Step 4-6: 对每个相关上下文生成回复并评估
            for context in relevant_contexts:
                response = generate_response(query, context)       # Step 4
                support = assess_support(response, context)        # Step 5
                utility = rate_utility(query, response)            # Step 6

                # 计算综合得分
                support_score = {
                    "fully supported": 3,
                    "partially supported": 1,
                    "no support": 0
                }.get(support, 0)
                overall_score = support_score * 5 + utility

                if overall_score > best_score:
                    best_response = response
                    best_score = overall_score

        # 如果没有相关上下文或得分太低，回退到直接生成
        if not relevant_contexts or best_score <= 0:
            best_response = generate_response(query)
    else:
        best_response = generate_response(query)

    return {"query": query, "response": best_response, "metrics": metrics}
⚠️ 关键 Bug 位置

注意第 3 步中的判断条件 relevance == "relevant"——但 evaluate_relevance() 返回的是中文 "相关"！这个中英文不匹配导致所有文档都被判定为"不相关"，系统始终回退到直接生成模式。这是一个典型的隐性 Bug，我们将在踩坑分析中详细讨论。

十一、踩坑分析：中英文匹配陷阱

这是本 notebook 中最值得深入分析的"意外发现"。让我们追踪这个 Bug 的完整链路：

Bug 链路追踪：

evaluate_relevance() 返回:
  → "相关"   (中文, 因为 prompt 要求回答"相关"或"不相关")
  → "不相关"

self_rag() 中的判断:
  → if relevance == "relevant":     ← 英文 "relevant"
      relevant_contexts.append(...)

匹配结果:
  → "相关"   != "relevant"   ❌ 永远不匹配！
  → "不相关" != "relevant"   ❌ 永远不匹配！

后果:
  → relevant_contexts 始终为空列表 []
  → 系统始终进入 "No suitable context found" 分支
  → 回退到 generate_response(query) —— 无上下文直接生成
  → Self-RAG 退化为"带检索决策的传统 RAG"
图 5：中英文匹配 Bug 的完整链路——一个字符串比较导致整个反思机制失效
⚠️ 修复方案

修复很简单——将判断条件改为匹配中文：

# 修复前（Bug）
if relevance == "relevant":
    relevant_contexts.append(context)

# 修复后（方案 A：匹配中文）
if relevance == "相关":
    relevant_contexts.append(context)

# 修复后（方案 B：让 evaluate_relevance 返回英文）
# 修改 system_prompt 为 "Answer 'relevant' or 'irrelevant'"
if relevance == "relevant":
    relevant_contexts.append(context)
💡 教训

在使用 LLM 做分类任务时，返回值语言必须与下游代码的判断逻辑一致。这是一个典型的"隐性 Bug"——代码不报错、不崩溃，但核心功能完全失效。在生产环境中，这类 Bug 比显式错误更危险，因为它可能长期潜伏而不被发现。建议：要么在 prompt 中明确指定英文返回值，要么在判断时同时支持中英文。

十二、评分机制详解

Self-RAG 使用一个综合评分公式来选择最佳回复：

overall_score = support_score × 5 + utility_rating

其中:
  support_score:
    "完全支持" (fully supported)    → 3
    "部分支持" (partially supported) → 1
    "不支持"   (no support)         → 0

  utility_rating: 1 ~ 5

得分范围: 0 × 5 + 1 = 1  ~  3 × 5 + 5 = 20
图 6：综合评分公式——支持度权重（×5）远大于实用性，体现"有据可依"的优先级

评分示例

支持度 support_score 实用性 overall_score 解读
完全支持 3 5 20 理想回复：有据且有用
完全支持 3 3 18 有据但一般有用
部分支持 1 5 10 有用但部分缺乏依据
部分支持 1 3 8 一般
不支持 0 4 4 有用但完全无依据（可能是幻觉）
不支持 0 1 1 最差：无据且无用
💡 设计哲学

支持度权重（×5）远大于实用性（×1），这意味着 Self-RAG 优先考虑"有据可依"而非"听起来有用"。一个完全无依据但"听起来很好"的回复（0×5+5=5）得分低于一个有据但一般有用的回复（1×5+3=8）。这正是 Self-RAG 区别于传统 RAG 的核心理念：宁可有据但平淡，不可无据而花哨。

十三、优缺点与适用场景

✅ 优点

  • 动态检索决策：避免不必要的检索，节省时间并减少噪声
  • 相关性过滤：丢弃不相关文档，避免误导生成
  • 幻觉抑制：支持度评估能检测回复是否"有据可依"
  • 质量把控：实用性评分帮助从多个候选中选最优
  • 回退机制：当检索结果不佳时，自动回退到直接生成
  • 可解释性：每个反思点的判断结果都可追踪

❌ 缺点

  • API 成本高：每个查询需要多次 LLM 调用（决策 + 评估 × K 个文档）
  • 延迟显著：六步流程远慢于传统 RAG 的单次检索+生成
  • 语言一致性陷阱：LLM 返回值的语言必须与代码逻辑一致
  • 评估本身可能出错：LLM 判断相关性/支持度也可能不准确
  • 过度保守风险：可能错误丢弃相关文档，导致回退到直接生成
  • 评分公式需调优：support_score 的权重（×5）是经验值，未必适用于所有场景

适用场景

✅ 适合 ❌ 不适合
对回复准确性要求极高的场景（医疗、法律、金融） 对延迟敏感的实时对话系统
查询类型多样（事实性 + 常识性混合） 查询类型单一（全部需要或全部不需要检索）
需要可解释性和审计追踪的企业应用 API 预算有限的项目
文档质量参差不齐，噪声较多 文档库小且质量统一的场景
需要防止幻觉的关键任务 创意写作等不需要严格依据的场景

十四、本篇小结

Self-RAG 的核心思想可以用一句话概括：

🎯 核心 takeaway

让 RAG 学会"自省"。传统 RAG 是"检索→生成"的单向管道，Self-RAG 在管道中嵌入了六个反思点——要不要检索、文档是否相关、回复是否有据、质量如何——让系统能够动态决策、自我纠错、选出最优回复。这种"LLM 评估 LLM"的模式虽然增加了成本，但显著提升了回复的可靠性和准确性。

技术要点回顾：

  1. 六个反思点：检索决策 → 文档检索 → 相关性评估 → 回复生成 → 支持评估 → 实用性评估
  2. 综合评分公式：overall_score = support_score × 5 + utility_rating，支持度优先
  3. 回退机制：当检索结果不佳时自动回退到直接生成
  4. 中英文匹配 Bug：LLM 返回中文"相关"/"不相关"，代码用英文"relevant"判断——导致反思机制完全失效
  5. 与第 12 篇的关系：第 12 篇的意图识别是 Self-RAG 的"简化版"（只有检索决策），Self-RAG 是完整的多步反思管道
⚠️ 实践建议

如果你要在生产环境中实现 Self-RAG，请务必注意：

  • 确保 LLM 返回值的语言与代码逻辑一致（建议在 prompt 中指定英文返回值）
  • 考虑缓存反思点的判断结果，减少重复 API 调用
  • 对延迟敏感的场景，可以只保留部分反思点（如只做检索决策 + 相关性过滤）
  • 评分公式中的权重需要根据实际场景调优
