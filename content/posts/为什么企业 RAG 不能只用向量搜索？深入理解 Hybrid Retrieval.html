为什么企业 RAG 不能只用向量搜索？深入理解 Hybrid Retrieval

从“语义正确但搜索失败”的真实困境出发，探讨 Dense 与 Sparse 检索的天然互补性，构建覆盖面更广的企业级混合检索架构。

一、开篇：从“语义正确但搜索失败”开始

在构建企业级 RAG 系统时，很多架构师在引入向量数据库后，会陷入一种错觉：“既然模型能理解语义，那搜索问题应该彻底解决了。” 然而，生产环境往往给我们上了一课。

让我们看一个真实的故障排查场景。用户输入的查询非常具体：

“RTC SDK 4.6.2 出现 RTC-10027 怎么解决？”

假设知识库中存在以下几份文档：

  • Document A：《RTC SDK 4.6.2 Android 错误码说明》
  • Document B：《RTC SDK 4.5.0 Android 故障排查》
  • Document C：《RTC SDK 4.6.2 Android 弱网优化》
  • Document D：《RTC-10027 错误处理指南》

Vector Search 的困境

对于向量检索，模型可能会认为“RTC SDK 4.6.2”、“RTC SDK 4.5.0”和“Android 弱网”在语义向量空间中高度相关，都能很好地回答关于“Android SDK”的问题。

但是，对于 RTC-10027、4.6.2、A3295、SKU-2026-00128 这类精确的字符串标识符，单纯的 Dense Retrieval 并不一定具有天然优势。在向量空间中，10027 和 10026 可能靠得很近，但对于排查故障的工程师来说，这两个错误码天差地别。

相反，BM25 这种传统的稀疏检索方法，可以很好地利用 Term Frequency（词频） + Inverse Document Frequency（逆文档频率） + Document Length（文档长度） 来精确匹配这些关键词。

核心问题： 如果 Dense Retrieval 擅长“理解意思”，Sparse Retrieval 擅长“匹配词”，为什么不把二者结合起来？

二、Dense Retrieval 到底擅长什么？

回顾前文，Dense Retrieval 将 Query 和 Document 都映射为低维稠密向量，通过计算向量相似度（如余弦相似度）来找出语义最相关的内容。

Dense Retrieval 的强项在于处理同义表达、语义相近以及Paraphrase（改写）。它解决了用户表达与文档表达不一致的问题。

举例：

Query：“网络很差的时候怎么降低 RTC 卡顿？”
Document：“弱网环境下实时音视频连接稳定性优化方案”

即使词面完全不同（“网络很差” vs “弱网”，“卡顿” vs “连接稳定性”），向量检索也能成功召回。这是传统基于关键词匹配的检索难以做到的。

三、Dense Retrieval 的天然弱点

然而，Dense Retrieval 并不是万能的。在企业级场景中，它有几块明显的短板：

  1. 精确标识符：如 RTC-10027, A3295。这些字符串对 Embedding 模型来说往往只是无意义的字符序列，容易被忽略或在向量空间中与其他相似 ID 混淆。
  2. 版本号：4.6.2 vs 4.6.1。对于用户来说这是天壤之别，但在高维向量空间中，它们可能极近。
  3. 专业术语与黑话：企业内部特有的缩写、行话，如果训练语料不足，模型难以精准捕捉其细微差别。
  4. 人名 / 项目名 / 系统名：这些专有名词通常需要精确匹配，模糊的语义相似度会导致错误的召回。

本质原因：Embedding 的目标是语义表示，压缩信息以保留核心含义；而精确字符串匹配关注的是字面完全一致。

Semantic Similarity ≠ Exact Term Matching

四、Sparse Retrieval 是什么？

在深度学习流行之前，信息检索（IR）领域长期统治的是 Sparse Retrieval（稀疏检索）。其核心思想是：一个文档可以被表示为海量词汇表中的词项及其权重。

最经典的实现是倒排索引。它记录了每个词出现在哪些文档中，以及出现的频率。当我们搜索时，系统会快速找到包含 Query 中关键词的文档，并根据 TF-IDF 或 BM25 等算法打分。

五、BM25：企业检索的定海神针

BM25 是目前稀疏检索中最流行、效果最稳健的算法。它的公式如下：

BM25(D,Q) = ∑t∈Q IDF(t) · (f(t,D) · (k1 + 1)) / (f(t,D) + k1 · (1 - b + b · (|D| / avgdl)))

让我们拆解一下每个参数在工程中的实际含义：

  • f(t, D)：词项 t 在文档 D 中的频率。出现次数多，相关性通常越高。
  • IDF(t)：逆文档频率。如果一个词在所有文档中都出现（如“的”、“是”），它的区分度就低，IDF 值就低；反之，稀有词的 IDF 值高。这解决了区分度问题。
  • |D| / avgdl：文档长度归一化因子。防止长文档仅仅因为词多而得分虚高。
  • k1：控制词频饱和度的参数。
    • k1 越大，词频对得分的影响越持久（词频增长持续贡献高分）。
    • k1 越小，词频很快达到饱和（出现几次就够了，再多也不加分）。
    • 通常取值在 1.2 到 2.0 之间。
  • b：控制文档长度归一化程度的参数。
    • b = 1：完全归一化，完全消除长文档优势。
    • b = 0：不考虑长度，长文档占优势。
    • 通常取值在 0.75 左右。

六、为什么 BM25 对企业知识特别重要？

企业的核心知识往往包含大量高精度的专有名词，这些具有高区分度和高精确性：

  • 错误码：RTC-10027 —— 只有这一个代码代表这个错误，不能有语义上的“近似”。
  • SDK Version：4.6.2 —— 指定版本，不能召回 4.6.1 的文档。
  • API 名称：joinChannel() —— 精确的方法名。
  • SKU：SKU-2026-00128 —— 唯一的库存单位。

在这些场景下，BM25 能够精确命中包含这些特定字符串的文档，而向量检索可能会因为语义泛化而“差不多就行”，导致召回错误的内容。

七、Dense vs Sparse：能力对比矩阵

我们需要客观看待两者的优劣，没有绝对的好坏，只有场景的适配。

能力维度 Dense Retrieval (向量检索) Sparse Retrieval (BM25)
同义表达理解 强（如：费用 -> 钱） 弱
语义/意图理解 强 弱
精确关键词匹配 弱/不稳定（依赖模型训练） 强
错误码/ID 查询 一般（可能受分词影响） 强
版本号/型号匹配 一般 强
长尾/生僻术语 视模型训练数据而定 强（只要分词正确）
长自然语言 Query 强 一般（关键词易被稀释）
Exact Match (精确匹配) 弱 强

八、为什么企业应该 Hybrid Retrieval？

既然两者各有优劣，企业级 RAG 的最佳实践显然是：Hybrid Retrieval（混合检索）。

其核心思想是利用两者的天然互补性：

Dense Retrieval 解决：“这句话是什么意思？”
Sparse Retrieval 解决：“这个关键词有没有出现？”

将两者结合，我们就能得到：语义召回 + 词法召回 = 更完整的候选集。

这里需要明确一点：Hybrid Retrieval 首先解决的是 Recall Coverage（召回覆盖率），而不是直接解决最终排序。 也就是说，我们的目标是先把所有可能相关的文档都找出来，建立一个高质量的候选池，至于谁排第一、第二，那是后续重排序的工作。这也为下一篇我们将要讲的 RRF（Reciprocal Rank Fusion）埋下了伏笔。

十、为什么不能直接把两个 Score 相加？

很多初次尝试 Hybrid 的开发者会犯一个直觉性的错误：把 Dense 的相似度分（例如 0.82）和 BM25 的分（例如 12.7）直接相加。

0.82 (Vector) + 12.7 (BM25) = 13.52 (Total Score) ❌

这样做是没有意义的。原因在于两者的分数空间完全不一致：

  • 数值范围：向量相似度通常在 [-1, 1] 或 [0, 1] 之间（取决于度量方式）；而 BM25 的分数范围是 [0, +∞)，取决于词频和文档集合。
  • 分布形态：Cosine Similarity 的分布可能是线性的或高斯的；BM25 的分布通常是长尾的。
  • 校准程度：它们没有被校准到同一个概率空间。

因此，直接相加会导致 BM25 的分数完全主导结果，或者向量分数被忽略。这引出了我们需要一种基于排序的融合方法，即下一章要讲的 RRF。

十一、Hybrid Retrieval 有哪些实现方式？

方案 1：Weighted Score Fusion（加权分数融合）

将两个分数归一化到同一区间（如 [0, 1]），然后加权求和：

Total Score = α × Normalized(Dense Score) + (1 - α) × Normalized(BM25 Score)

这需要解决归一化策略和权重 α 的调优问题。不同的业务场景，最佳 α 可能不同。

方案 2：Rank Fusion（排序融合）

不看具体的分数大小，只看文档在各自列表中的排名。RRF 是其中的佼佼者，它对分数的分布不敏感，鲁棒性极强。

方案 3：Learned Fusion（学习型融合）

使用机器学习模型（如 LambdaMART）来学习如何融合。这需要大量的标注数据，在数据量不足时容易过拟合，工程复杂度也最高。

十二、Hybrid Retrieval 的关键参数

在混合检索中，两个最关键的参数是：Dense Top-K 和 Sparse Top-K。

  • Top-K 的大小：决定了从各自的通道中取多少个文档进入候选池。常见的值有 20, 50, 100。
    • Candidate Pool 越大，理论上 Recall（召回率）越高。
    • 但代价是：后续 Reranker 的计算成本增加、噪声增加、整体 Latency 增加。

这存在一个 Trade-off：

Recall ↑  <=>  Candidate Size ↑  <=>  Rerank Cost ↑  <=>  Latency ↑

工程实践中，我们需要在精度和性能之间找到平衡点。

十三、Metadata Filtering 与 Hybrid Retrieval

回顾数据工程篇，Metadata（元数据）是提升检索效率的利器。在进行混合检索之前，我们可以先应用 Metadata Filter：

filter = {
    "product": "RTC",
    "version": "4.6.2",
    "platform": "Android"
}

这样可以大幅缩小搜索空间：

Metadata Filtering ↓
Search Space Reduction ↓
Dense + Sparse Retrieval (在缩小后的空间内执行)

优势：

  • 降低搜索空间，提升检索速度。
  • 提升相关性，直接过滤掉明显不相关的文档。
  • 实现基于权限的访问控制（如，只搜索用户有权限的部门文档）。

注意：不应过度过滤，否则可能导致 Recall 严重下降，甚至漏掉关键信息。

十四、Query Normalization

在将 Query 送入检索通道之前，进行规范化处理至关重要，尤其是对于 Sparse Retrieval。

例如，用户可能会输入： v4.6.2, V4.6.2, 4.6.2, SDK 4.6.2

或者错误码： RTC-10027, rtc-10027, RTC10027

规范化处理包括：

  • 统一大小写（Lowercasing）。
  • 移除特殊符号或统一符号（如将连字符替换为空格）。
  • 处理变体（如展开缩写）。

合理的 Analyzer/Tokenizer 配置是 BM25 发挥威力的前提，特别是针对 SKU、产品编码这类特殊文本。

十五、中文场景下的 Hybrid Retrieval

中文检索有其独特性。中文没有天然的空格分词，因此 Sparse Retrieval 对分词器（如 IK, Jieba, HanLP）的依赖性极高。

挑战：

  • 中文分词：“苹果手机”可能被切分为“苹果/手机”或“苹果/机”，不同的切分影响召回。
  • 中英文混合：“如何解决 iPhone 17 Pro 的发热问题？” —— 需要同时处理中文分词和英文 Tokenization。
  • 专业术语：“微服务架构”可能是一个整体，不能拆开。

Hybrid 的价值：在中文场景下，分词的不确定性可能导致 BM25 召回失败（例如，文档里写的是“苹果手机”，用户搜的是“苹果”，简单分词可能匹配不上）。此时，向量检索可以跨过分词障碍，基于语义召回；反之，对于精确的人名、地名，BM25 又能弥补向量检索的不足。

十六、一个完整 Query 的检索过程

让我们从头到尾跟踪一个查询：“RTC SDK 4.6.2 Android RTC-10027 怎么处理？”

此时得到的 Top-K 文档，才是最终输入给 LLM 的上下文。Hybrid Retrieval 的职责就是尽可能构建一个高质量、高覆盖率的候选集，剩下的精排任务交给 Reranker。

十七、如何判断 Hybrid Retrieval 是否真的有效？

一切优化都离不开评估。我们需要建立一套科学的评估体系来比较 Dense Only、BM25 Only 和 Hybrid 的效果。

关键指标：

  • Recall@K：前 K 个结果中包含正确文档的比例。这是衡量覆盖率的核心指标。
  • Precision@K：前 K 个结果中，真正相关的文档占比。
  • MRR (Mean Reciprocal Rank)：第一个正确文档的排名倒数的平均值，关注排序质量。
  • NDCG (Normalized Discounted Cumulative Gain)：考虑排序位置和相关性等级的综合指标。

建议：建立一个 Retrieval Evaluation Dataset，包含 Query 和对应的标准答案文档列表（Ground Truth）。通过离线评估快速验证不同策略的优劣。

十八、真实工程中的 Trade-off

最后，我们需要理性看待 Hybrid Retrieval 带来的工程复杂度。

方案 优点 缺点
Dense Only 架构简单，语义能力强，单一路径延迟低。 Exact Match 能力弱，对专有名词处理不佳。
BM25 Only 精确匹配，可解释性强，技术极其成熟稳定。 同义表达能力弱，难以理解复杂语义 Query。
Hybrid 覆盖面广，同时兼顾语义和精确匹配，适合复杂 Query。 架构复杂度高，需维护两套索引，两次检索，需处理分数融合，运维成本高。

核心观点：Hybrid Retrieval 不是免费的准确率提升，而是用系统复杂度换取Retrieval Coverage。在构建企业级系统时，这是一个值得的权衡，但必须要有充分的工程投入。

十九、常见失败案例

失败 1：认为 Vector Search 已经足够

现象：完全放弃 BM25，仅使用向量检索。

原因：高估了 Embedding 模型对精确匹配和专有名词的处理能力。

影响：在错误码查询、版本号排查等场景下，召回效果极差。

解决方案：引入 BM25 作为补充通道，构建混合检索。

失败 2：直接把 Vector Score 和 BM25 Score 相加

现象：融合结果偏向于某一通道，或者结果无法解释。

原因：忽略了两者分数空间的不一致性。

影响：融合后的排序不仅没有提升，反而可能变差。

解决方案：使用归一化加权融合，或更好的方案——RRF（基于排序的融合）。

失败 3：Dense Top-K 太小

现象：最终候选集几乎等同于 Sparse 的结果，混合效果不明显。

原因：Dense 通道提供的候选太少，无法补充 Sparse 未召回的内容。

影响：损失了语义召回的增益。

解决方案：适当增加 Dense Top-K，例如从 10 增加到 30 或 50。

失败 4：Sparse Top-K 太小

现象：无法召回包含精确关键词但语义分数不高的文档。

原因：BM25 通道截断得太早，漏掉了潜在的精确匹配项。

影响： Exact Match 能力未能发挥。

解决方案：增加 Sparse Top-K，保证低频词项也能被召回。

失败 5：Candidate Pool 无限扩大

现象：Top-K 设置得非常大（如各取 500）。

原因：盲目追求 Recall，忽略了后续 Reranker 的处理能力。

影响：系统延迟急剧上升，Reranker 成本高昂，且引入大量噪声干扰排序。

解决方案：根据评估结果，设定一个合理的 Top-K 上限，如各取 50-100。

失败 6：Metadata Filter 过度严格

现象：过滤条件太多，导致搜索空间几乎为空。

原因：担心召回过多无关内容，而设置了过多的必选过滤条件。

影响：Recall 大幅下降，可能完全漏掉正确答案。

解决方案：谨慎使用 Filter，优先考虑 Reranker 的过滤能力，或者在 Filter 失效时降级搜索。

失败 7：中文 Analyzer 配置不合理

现象：BM25 对中文 Query 的效果很差，经常搜不到。

原因：分词器选择不当，或未针对专业领域添加自定义词典。

影响：Sparse 通道失效，混合检索退化为 Dense Only。

解决方案：根据企业语料特点，选择并调优中文分词器，维护专业术语词典。

失败 8：版本号、错误码被错误分词

现象：4.6.2 被分词为 4, 6, 2；RTC-10027 被分词为 RTC, 10027（这还算好的）或更糟。

原因：默认的分词器或 Tokenizer 不适合处理这类混合字符。

影响：精确匹配失败，无法区分 4.6.2 和 4.6.1。

解决方案：配置 Char Filter 或 Word Delimiter Tokenizer，保护特定模式的字符串不被拆分。

失败 9：没有建立 Retrieval Evaluation Dataset

现象：靠感觉或几个随机 Query 来判断系统好坏。

原因：忽视了评估的重要性。

影响：无法量化改进效果，可能引入负向优化而不自知。

解决方案：投入资源构建评测集，作为所有迭代优化的基准。

失败 10：Hybrid 增加了复杂度，但没有验证 Recall 是否真正提升

现象：系统上线更复杂了，但用户反馈搜索体验没有明显改善。

原因：盲目跟风技术，未针对自身业务场景进行验证和调优。

影响：技术债务累积，维护成本高昂。

解决方案：始终以评估数据为驱动，确保每一次架构升级都能带来可量化的收益。

1. BM25 Python 示例 (简化版)

import math
from collections import Counter

class BM25:
    def __init__(self, corpus, k1=1.5, b=0.75):
        self.k1 = k1
        self.b = b
        self.corpus = corpus
        self.corpus_size = len(corpus)
        self.avgdl = sum(len(doc) for doc in corpus) / self.corpus_size
        self.df = {}  # document frequency
        self.idf = {} # inverse document frequency
        
        # Build DF
        for document in corpus:
            words = set(document)
            for word in words:
                self.df[word] = self.df.get(word, 0) + 1
        
        # Calculate IDF
        for word, freq in self.df.items():
            self.idf[word] = math.log((self.corpus_size - freq + 0.5) / (freq + 0.5) + 1)

    def score(self, document, query):
        score = 0
        doc_len = len(document)
        doc_counts = Counter(document)
        
        for word in query:
            if word not in doc_counts:
                continue
            # f(t, D)
            freq = doc_counts[word]
            # IDF(t)
            idf = self.idf.get(word, 0)
            # BM25 formula component
            numerator = freq * (self.k1 + 1)
            denominator = freq + self.k1 * (1 - self.b + self.b * (doc_len / self.avgdl))
            score += (idf * numerator) / denominator
        return score

# Usage
documents = [
    ["rtc", "sdk", "android", "error"],
    ["weak", "network", "optimization"],
    ["rtc", "10027", "guide"]
]
bm25 = BM25(documents)
query = ["rtc", "10027"]
scores = [bm25.score(doc, query) for doc in documents]
print(f"BM25 Scores: {scores}")

2. Dense Retrieval Python 示例 (伪代码)

from sentence_transformers import SentenceTransformer
import numpy as np

class DenseRetriever:
    def __init__(self, model_name, documents):
        self.model = SentenceTransformer(model_name)
        self.documents = documents
        # Pre-calculate embeddings for documents
        self.doc_embeddings = self.model.encode(documents)

    def retrieve(self, query, top_k=5):
        # 1. Embed Query
        query_embedding = self.model.encode([query])
        
        # 2. Vector Search (Cosine Similarity)
        # Using numpy for simplicity, production would use FAISS/Milvus/PGVector
        scores = np.dot(self.doc_embeddings, query_embedding.T).flatten()
        
        # 3. Top-K
        top_indices = np.argsort(scores)[::-1][:top_k]
        
        return [(self.documents[i], scores[i]) for i in top_indices]

# Usage
docs = [
    "RTC SDK 4.6.2 Android error guide",
    "How to optimize weak network connection",
    "Troubleshooting error code RTC-10027"
]
retriever = DenseRetriever('all-MiniLM-L6-v2', docs)
results = retriever.retrieve("How to fix RTC-10027 error?", top_k=2)
for doc, score in results:
    print(f"Score: {score:.4f} | Doc: {doc}")

3. Hybrid Retrieval Python 示例 (Candidate Pool 生成)

class HybridRetriever:
    def __init__(self, dense_retriever, sparse_retriever):
        self.dense_retriever = dense_retriever
        self.sparse_retriever = sparse_retriever

    def retrieve_candidate_pool(self, query, dense_top_k=10, sparse_top_k=10):
        # Parallel retrieval is ideal, simulated sequentially here
        dense_results = self.dense_retriever.retrieve(query, top_k=dense_top_k)
        sparse_results = self.sparse_retriever.search(query, top_k=sparse_top_k) # Assume returns list of docs
        
        # Combine into a set to remove duplicates (based on doc ID or content)
        # In real engineering, use IDs for faster lookup
        candidate_pool = {}
        
        # Add Dense results
        for doc, score in dense_results:
            candidate_pool[doc] = {"dense_score": score, "sparse_score": 0}
            
        # Add Sparse results (merge scores if doc exists)
        for doc, score in sparse_results:
            if doc in candidate_pool:
                candidate_pool[doc]["sparse_score"] = score
            else:
                candidate_pool[doc] = {"dense_score": 0, "sparse_score": score}
        
        # Return the raw candidate pool with scores
        # The next step would be Fusion/Reranking
        return candidate_pool
