RAG 效果差，真的都是模型的问题吗？
企业 RAG 的第一道门槛：数据工程

企业级 RAG 架构设计与工程实践 · 系列第 3 篇
作者：清言 | 日期：2026年09月09日

一、开篇：先从一个失败案例开始

不要从“什么是数据工程”这种教科书式的定义开始。让我们直接走进一个真实的企业故障现场。

场景：Android 接入故障排查

某技术支持团队正在接入一套新的 RAG 客服系统。企业内部知识库中明确存在一份最新的 《RTC SDK 4.6.2 Android 接入指南.pdf》。

用户提问：“Android 14 下 RTC-10027 怎么解决？”

这本该是一个简单的“查表”动作。然而，系统却回复“未找到相关解决方案”。技术团队排查后发现，这份 PDF 文件已经成功上传并切分进入了向量数据库，但在检索环节，它就是没有被召回。

问题究竟出在哪？很多人第一反应是：是不是 Embedding 模型不够强？或者是 Top-K 设置不对？当我们打开系统后台的数据处理日志，一条令人背脊发凉的链条浮出水面：

图 1：数据质量恶化导致的检索失败链条

这个案例非常典型。它揭示了一个残酷的事实：RAG 没搜到，表面上看是 Retrieval 的问题，根因往往是数据进入 Retrieval 之前就已经坏掉了。

如果一份 PDF 的标题、表格和正文在解析阶段已经被打乱，充满了页眉页脚的噪声，那么后面的 Embedding 模型再强，也只是在给错误的、充满噪声的文本建立更精确的向量表示。这就是我们常说的“Garbage In, Garbage Out”在 RAG 中的具体表现。

因此，RAG 的第一道质量控制，其实发生在数据进入向量数据库之前。今天我们要深入探讨的，正是这条经常被忽视，却决定系统生死的数据工程之路。

二、企业 RAG 面对的到底是什么数据？

在构建 RAG 系统之前，我们必须对“原料”有一个清醒的认知。很多 Demo 只展示了处理 TXT 或 Markdown 的能力，但真正的企业环境要复杂得多。

图 2：企业 RAG 的异构数据源全景

这意味着，企业 RAG 的输入根本不是干净的“文本”，而是复杂的异构数据。每种数据源都有其独特的结构、编码方式和噪声特征。一个鲁棒的数据 Pipeline 必须能够应对这种多样性。

三、为什么原始文档不能直接进入 Embedding？

我们经常看到一种极其危险的设计：直接调用 PDF 解析库提取文本，然后不做任何处理就送入 Embedding 模型。

危险设计

Raw Document -> Extract Text -> Embedding

这种设计等同于让模型吃下“带壳的生蚝”。原始数据中充斥着对语义理解毫无帮助，甚至起反作用的内容：

  • HTML 标签：如 <div>, <nav>, <script>。
  • 页面元素：页眉、页脚、页码、版权声明。
  • 重复内容：网站顶部导航栏、页脚链接在每一页都重复出现。
  • OCR 噪声：扫描文档中识别错误的字符、乱码。
  • 无意义符号：多余的空格、制表符、特殊编码字符。
  • 复杂结构：表格、多栏排版、公式、图片描述。

如果这些噪声被向量化，检索时会出现什么情况？假设用户问“如何配置 RTC SDK”，而系统召回了一个 Chunk，里面主要内容是页眉“版权所有 © 2024 XX公司”和页码“第 12 页”，仅仅因为Chunk里碰巧出现了“SDK”这个词。这将导致严重的相关性偏差。

核心结论：未经清洗的原始数据直接 Embedding，等于在向量化噪声。

四、企业 RAG Data Pipeline：设计一条完整的数据处理链路

为了解决上述问题，我们需要构建一条专业、严谨的数据处理流水线。这不是一次性脚本，而是一个可持续运行的数据平台核心组件。

图 3：企业级 RAG 数据处理全流程架构

这条 Pipeline 不仅仅是数据的物理流动，更是数据价值逐层升华的过程。每一层都有其特定的职责，且原始数据、标准化数据、Chunk 数据、Embedding 数据应该拥有不同的生命周期。例如，当 Embedding 模型升级时，我们只需要从 Chunk 数据开始重新处理，而不需要重新解析原始 PDF。

五、Data Ingestion：企业数据如何进入系统？

数据怎么进来？是手动上传还是自动同步？对于企业级应用，这是一个涉及数据新鲜度和一致性的关键设计。

我们通常需要支持多种摄入策略：

策略 描述 适用场景
Batch Ingestion (全量同步) 定期（如每晚）从源系统拉取全部数据。 初期冷启动、小规模数据、数据源不支持增量。
Incremental Sync (增量同步) 基于时间戳或版本号，只拉取变更的数据。 Wiki、CMS 等有明确版本管理的系统。
Event-driven Sync (事件驱动) 源系统在数据变更时发送 Webhook 通知。 要求实时性极高的场景。
Scheduled Sync (定时同步) 固定间隔（如每小时）检查并拉取更新。 折中方案，平衡实时性与资源消耗。
CDC (Change Data Capture) 监听数据库日志（如 Binlog），实时捕获增删改。 数据库直连，实时性要求高。

工程经验：企业知识库不是一次性导入，而是一个持续变化的“活”系统。你的 Pipeline 设计必须从一开始就考虑“更新”和“删除”的处理，而不仅仅是“创建”。

六、Raw Data 与 Knowledge Data 为什么要分离？

这是一个经常被忽视的架构原则。很多早期的 RAG 系统只保留了切分后的 Chunk，一旦发现 Chunk 效果不好，想调整 Chunk 大小或更换解析策略，却发现原始文件已经找不到了。

图 4：原始文件与结构化知识的分离存储架构

保留 Raw Data 是为了支持：

  • 重新解析：升级了更强大的 Parser 后，可以重新处理所有历史文档。
  • 更换策略：尝试不同的 Chunk 策略或 Embedding 模型。
  • 问题排查：当某个 Chunk 莫名其妙时，可以追溯到原始文件查看上下文。
  • 合规审计：满足数据治理和合规性要求，证明数据来源。

因此，Raw Data 是知识的“源头真理”，必须被永久、安全地存储在对象存储中，而绝不能只保留处理后的 Chunk。

七、Document Parsing：真正困难的第一步

现在，让我们聚焦到 Pipeline 中最棘手、最耗费精力的环节：文档解析。这是 RAG 系统基础设施的地基。

很多人低估了企业文档解析的难度，以为调用一个 pdfplumber 或 PyPDF2 就搞定了。实际上，企业文档解析不是简单的“Extract Text”，而是“Recover Document Structure”（文档结构恢复）。

PDF 的噩梦

PDF 本质上是打印指令的集合，而不是结构化文档。

  • 文本顺序混乱：双栏排版可能导致文本被从左到右、从上到下错误地串行读取。
  • 表格识别：没有边框的表格、跨页表格、合并单元格，对解析器是巨大挑战。
  • 扫描件：纯图片 PDF，必须上 OCR，且极易产生识别错误。
  • 页眉页脚干扰：每一页都重复出现的公司Logo、文档标题，需要被精准剔除。

Word 的复杂性

虽然 Word 是半结构化格式，但也充满陷阱。

  • 样式不规范：用户可能手动调整字体大小来模拟标题，而非使用真正的“标题1/2/3”样式。
  • 嵌套列表：多层级的列表结构在解析时容易丢失层级关系。
  • 文本框与形状：重要信息可能被放在浮动的文本框中，与正文流分离。

PPT 和 Excel

  • PPT：内容分散在各个 Slide 的文本框中，讲义备注里的信息往往更有价值。
  • Excel：行列含义依赖 Header，合并单元格会破坏数据的表格语义，不能简单地逐行读取。

如果 Parser 无法正确识别标题、段落、列表、表格，那么后续的 Chunking 就只能在错误的文本流上“盲切”。所以，投资一个高质量的、基于 Layout Analysis 的解析引擎，是回报率最高的工程投入之一。

八、OCR 与 Layout Analysis

对于扫描件或图片中的文字，OCR 是必经之路。但我们必须明确一个概念：

核心区别

OCR ≠ 文档理解

OCR 只能回答图片里有哪些字符，它不知道这些字符之间的逻辑关系。而 RAG 需要的，是理解后的结构。

图 5：从图片到语义化文档的理解过程

Layout Analysis 会识别出 Bounding Box（边界框），判断哪块区域是标题、哪块是正文、哪块是表格。只有完成了这一步，OCR 识别出的文字才能被正确地拼装成有意义的段落，而不是一堆杂乱无章的字符流。

九、Data Cleaning：清洗不是“越干净越好”

数据清洗是去除噪声的过程，但这里有一个微妙的工程权衡。

常见的清洗任务包括：

  • 去除重复的页眉、页脚、导航栏。
  • 清理空白字符、特殊符号、HTML 标签。
  • 修正 OCR 的明显错别字。
  • 过滤广告、模板文本。

然而，过度清洗是危险的。如果你为了追求“干净”，把所有看起来像格式的字符都删掉了，可能会导致：

  • Markdown 标题符号 # 被删，导致标题信息丢失。
  • 代码缩进被抹平，代码变成不可读的一行。
  • 表格边框字符被删，表格结构瓦解。

正确的清洗原则是：去除对检索产生干扰的噪声，但必须保留对语义理解有价值的信息。例如，一个标题前的星号 ** 虽然是格式符号，但它明确指示了这是一个标题，应该保留或转化为结构化字段。

十、Structure Reconstruction：为 Chunking 打好基础

清洗之后，我们的目标是将非结构化文本重建为具有层级结构的语义文档。这是 Chunking 质量的决定性因素。

理想情况下，我们应该重建出这样的树状结构：

Document
├── Title: "RTC SDK 接入指南"
├── Section 1: "环境准备"
│   ├── Paragraph: "系统要求 Android 10+..."
│   └── List: ["Gradle 7.0", "JDK 11"]
├── Section 2: "集成步骤"
│   ├── Code Block: "dependencies { ... }"
│   └── Table: "参数说明"
└── Appendix

工程观点：Chunking 的质量，很大程度依赖于前面的结构恢复。如果你知道哪一段文字属于“错误码”这个 Section，你就不会把它和“环境准备”的内容切在一起。

十一、Metadata：经常被低估的一层

Metadata（元数据）是关于数据的数据。在 RAG 系统中，Metadata 的重要性怎么强调都不为过。它不仅是文档的“身份证”，更是检索的“指路灯”。

一个设计良好的 Chunk 结构，其 Metadata 可能包含：

{
  "document_id": "doc_001",
  "title": "RTC SDK 4.6.2 Android 接入指南",
  "source": "wiki",
  "product": "RTC",
  "version": "4.6.2",
  "platform": "Android",
  "section": "错误码说明",
  "page": 27,
  "language": "zh-CN",
  "tenant_id": "tenant_001",
  "permission": ["研发部", "测试部"],
  "updated_at": "2026-08-01"
}

Metadata 的三大核心作用

  1. 检索过滤：在向量检索之前或之后，利用 Metadata 快速缩小搜索范围。例如，product = "RTC" AND version = "4.6.2"。
  2. 权限控制：确保用户只能搜到他有权限访问的内容。tenant_id 和 permission 字段在这里至关重要。
  3. 排序与引用：updated_at 可以让结果优先展示最新内容；page 和 section 则可以让 LLM 生成更精准的引用来源。

十二、Metadata 为什么会影响 Retrieval？

让我们回到开头的案例。用户问：“RTC 4.6.2 Android 的 RTC-10027 怎么处理？”

如果仅依赖向量相似度，系统可能会召回所有版本的 RTC 文档，因为它们在语义上非常相似。

  • RTC 4.5.0 文档（相似度 0.92）
  • RTC 4.6.1 文档（相似度 0.91）
  • RTC 4.6.2 文档（相似度 0.90）

但如果我们加上 Metadata 过滤：version = "4.6.2" AND platform = "Android"，那么只有 4.6.2 的文档会被送入最终的排序环节。这极大地提高了检索的准确率。

检索公式进化

Semantic Retrieval (向量检索) + Metadata Filtering (元数据过滤) = Better Retrieval (更好的检索)

十三、数据质量控制：像构建数据平台一样监控 RAG

工业级的 RAG 系统不能是一个“黑盒”。我们必须在 Pipeline 的关键节点建立质量检查机制。

图 6：嵌入数据 Pipeline 的质量监控体系

常见的检查项包括：

  • 空 Chunk 率：切分出来的内容是否为空？
  • 重复 Chunk 率：是否存在大量完全相同的内容？
  • 解析失败率：有多少文档解析超时或报错？
  • Chunk 长度分布：大部分 Chunk 是否在模型上下文窗口的合理范围内（如 512-1024 tokens）？
  • Metadata 完整性：关键字段（如 document_id, title）是否缺失？

这些指标应该被可视化地呈现在监控大盘上。一旦某个指标异常（例如，解析失败率突然飙升），系统应立即报警，让工程师介入排查。

十四、文档更新与删除：处理动态知识

企业知识是动态生长的。文档会被更新、删除、移动，权限也会变更。RAG 系统必须能够感知并响应这些变化。

这是一个经典的分布式一致性问题。我们的目标是确保：

图 7：知识变更与索引同步链路
  • 文档更新：通常需要重新解析、重新 Chunk、重新 Embedding。如果是小改动，是否可以只更新受影响的 Chunk？这是工程优化的方向。
  • Embedding 模型升级：当公司决定从 BGE 切换到 OpenAI text-embedding-3 时，意味着所有 Chunk 都需要重新 Embedding，并重建索引。这是一个庞大的工程，必须设计好全量重建的流程。
  • 权限变更：如果某份文档从“公开”变为“仅研发部可见”，必须在向量数据库层面通过 Metadata 过滤实现，或者直接删除公开索引中的相关数据。
  • 文档删除：这是最容易被忽视的。当文档被删除时，必须确保向量数据库中对应的旧 Chunk 也被彻底清除，否则会变成“幽灵数据”，持续产生错误的检索结果。

十五、为什么需要 Document Version？

企业环境中的文档协作频繁，版本控制是刚需。我们不能简单地在数据源更新时覆盖旧版本。

Document (doc_001)
├── v1 (2026-01-01)
├── v2 (2026-03-15)
└── v3 (2026-08-01 - Current)

保留版本的意义在于：

  • 版本追踪与审计：知道某个建议是依据哪个版本的文档做出的。
  • 回滚能力：如果新版本引入了错误，可以快速回退索引。
  • 差异比较：高级检索甚至可以支持“找出 v1 和 v2 之间关于‘配置’的差异”。

在 Metadata 中，我们应该始终维护一个 version 字段，并在检索时默认优先返回最新版本（is_latest: true），但也允许历史版本检索。

十六、数据工程最终应该输出什么？

经过上述千辛万苦的处理，我们的数据工程最终交付的不是一堆文件，而是标准化的、结构化的“知识单元”。

这是我们应该在 Pipeline 内部统一维护的数据模型（以 Python 为例）：

@dataclass
class Document:
    document_id: str
    title: str
    source: str
    content: str  # 清洗后的全文
    metadata: dict
    version: str
    updated_at: str

@dataclass
class Chunk:
    chunk_id: str
    document_id: str
    content: str  # 切分后的文本片段
    metadata: dict  # 继承并扩展 Document 的 metadata
    position: int  # 在原文中的位置

架构师的结论：企业 RAG 最终需要的是“结构化知识单元”，而不是一堆原始的 PDF。这些结构化知识单元才是真正能够被高效检索、理解和引用的资产。

十八、工程权衡：没有银弹，只有取舍

作为架构师，我们的工作不是追求最完美的技术，而是在资源、时间、质量之间做最优的权衡。

权衡点 选择 A 选择 B 如何决策
全量 vs 增量处理 全量：逻辑简单，一致性强。 增量：实时性好，资源消耗低。 初期冷启动用全量；日常运行尽可能用增量或事件驱动。
OCR vs 非 OCR 全 OCR：覆盖全，但慢、贵、易错。 文本提取：快、准，但漏扫描件。 先尝试文本提取，失败或检测到图片过多时再触发 OCR。
结构保留 vs 清洗 保留：信息全，但噪声多。 清洗：文本干净，但易丢失语义。 清洗时采用“白名单”策略，只移除明确的噪声（如页脚），保留所有疑似结构的标记。
Metadata 丰富度 丰富：检索强大，但存储、索引成本高。 精简：成本低，但过滤能力弱。 优先保证核心字段（id, title, time, permission），逐步按需扩展。
历史版本 全保留：审计完美，但存储爆炸。 仅留最新：成本低，但无回溯。 一般保留最近 N 个版本（如 3-5 个），或对重要文档做永久归档。
Parser 质量 vs 延迟 高精度 Parser（如 LayoutLM）：准，但慢、贵。 规则 Parser：快、便宜，但脆。 核心文档用高精度模型；非核心、时效性要求高的文档用规则快速处理。

十九、常见错误：避坑指南

最后，总结我们在企业项目中反复踩过的坑，希望能帮你避开。

  1. 错误 1：PDF 直接 Extract Text → Embedding。这是最常见的错误，直接导致表格乱码、内容错乱。
  2. 错误 2：所有文档统一 Chunk 大小（如 512）。忽略了文档结构，代码、表格、短说明都不应该被硬性切分。
  3. 错误 3：Metadata 只有 document_id。放弃了最强大的检索过滤能力，把压力全抛给向量检索。
  4. 错误 4：没有保存原始文档。一旦解析策略升级，无法回溯，只能重新上传所有文件。
  5. 错误 5：知识库更新后没有删除旧 Chunk。导致“知识僵尸”持续干扰检索。
  6. 错误 6：没有 Data Quality Monitoring。不知道 Pipeline 健康状况，直到用户投诉才发现问题。
  7. 错误 7：没有 Document Version。无法回答“这个回答是基于昨天还是上个月的文档？”
  8. 错误 8：权限信息没有进入 Metadata。导致用户可能搜到他无权查看的内容摘要，带来安全风险。

二十、最终结论

让我们用一张图来总结本文的核心观点：RAG 的质量，从根本上取决于数据质量。
