Chunking 决定 RAG 上限？企业知识切分策略深度解析

第 4 篇 · 从“搜得到但答不对”看企业知识库的颗粒度设计

真实场景：RTC 故障排查中的“断章取义”

在企业级知识库的实际运营中，我们经常遇到一种令人沮丧的现象：用户明明问了一个非常具体的问题，检索系统也找到了相关文档，但 LLM 就是不给正确答案。

比如，原始文档《RTC SDK 4.6.2 Android 接入与故障排查指南》中有一段完整的排障逻辑：

错误码 RTC-10027 通常发生在 Android 14 环境下，主要表现为音频中断。
需要首先检查系统权限设置（特别是录音权限）。
如果客户端版本为 4.6.2，则需要启用特定的兼容模式。
若同时开启了硬件加速（xxx 配置），则必须将其关闭。

如果我们采用简单的“固定长度切分”，这段极具上下文依赖的信息可能会被无情地拆散：

  • Chunk 1: RTC-10027 通常发生在 Android 14 环境下……
  • Chunk 2: 需要首先检查系统权限设置……
  • Chunk 3: 如果客户端版本为 4.6.2，则……

当用户提问：“RTC-10027 在 4.6.2 版本下怎么处理？”，检索系统可能只召回了 Chunk 1，因为它包含了错误码。结果就是，LLM 只能泛泛而谈“发生在 Android 14”，却漏掉了核心的解决方案。

反之，如果我们为了保全面面把 Chunk 切得过大（例如整整 8 页 PDF 合成一个 Chunk），虽然信息完整了，但会导致语义噪声剧增，检索精度大幅下降，且昂贵的 Token 成本都被浪费在无关的描述性文字上。

这就引出了架构师必须回答的三个问题：

Chunk 到底应该多大？
Chunk 到底应该在哪里切？
一个好的 Chunk 究竟应该满足什么条件？

Chunking 到底在解决什么问题？

很多工程师把 Chunking 仅仅看作是“数据预处理”的一个步骤，即把长文本切短以适应模型的上下文窗口。这种理解是片面的。

从检索机制的微观视角看，流程是这样的：

Embedding 模型的基本单位最终不是整篇文档，而是 Chunk。

这意味着，Chunk 实际上决定了检索系统“看”到的知识颗粒度。我们可以将其视为一条因果链：

Chunk Size → Retrieval Quality → Context Quality → Generation Quality
  • Chunk 太小 → 信息不完整 → Semantic Context（语义上下文）丢失。
  • Chunk 太大 → 噪声增加 → 相似度被稀释 → Context 成本增加。

什么是一个“好 Chunk”？

在深入具体策略之前，我们需要建立明确的判断标准。一个高质量的 Chunk 应该尽量满足以下五个维度：

1. 语义完整

不要把一个完整问题的条件、结论拆开。比如 API 的参数说明必须和参数名在一起。

2. 上下文独立

脱离原文后，仍然可以被理解。避免出现类似“该按钮位于上文所述的区域”这种指代不清的文本。

3. 检索可区分

不同知识单元之间应该有足够区别。如果所有 Chunk 都以“本公司规定...”开头，召回区分度会很差。

4. 长度适中

不能太短导致缺乏实体关系，也不能无意义地过长导致噪声。

5. 可以追溯

必须知道它来自哪个文档、哪个章节、第几页、什么版本。

从简单到复杂：主流 Chunking 策略

企业级架构并不是追求“最复杂”的算法，而是追求“最适合场景”的策略。以下从工程落地的角度逐一剖析。

1. Fixed-size Chunking (固定长度切分)

这是最简单的 Baseline。设定一个 Token 数量（如 500），机械地切分。

document_text = "..."
chunk_size = 512
chunks = [document_text[i:i+chunk_size] for i in range(0, len(document_text), chunk_size)]

优点： 简单、快、稳定、易并行、易工程化。
缺点： 极易切断语义、切断句子、切断代码、切断表格。
工程建议： 它非常适合作为 Baseline，用于初期快速验证系统可行性，但在生产环境中通常需要配合重叠窗口使用。

2. Sliding Window (滑动窗口)

为了缓解边界切断问题，引入 Overlap。

通过设置 `Chunk Size = 512` 和 `Overlap = 100`，尽量降低语义被切断的风险。
Trade-off： Overlap 越大，语义完整性越好，但会导致重复召回、存储成本和 Embedding 成本线性增加，且在生成阶段会导致 Context 中存在大量冗余信息。

3. Recursive Chunking (递归切分)

这是 LlamaIndex 等框架常用的策略。按照层级逐步切分：Document → Paragraph → Sentence → Token。
它的核心逻辑是：“尽可能保留自然边界。” 比如优先按段落切，如果段落还是太长，再按句子切。这比纯固定长度更符合人类阅读习惯。

4. Semantic Chunking (语义切分)

不是根据字符数，而是根据语义变化切分。通过计算相邻句子的 Embedding 相似度，当相似度发生突降（意味着话题转换）时进行切分。

优点： 语义完整性极强。
缺点： 需要对整个文档进行 Embedding 计算，计算成本高；参数复杂（阈值难定）；对数据类型敏感（例如代码、表格的语义边界很难用相似度衡量）。

5. Document-aware Chunking (文档结构感知切分)

这是企业场景的重中之重。 不同文档应该使用不同 Chunk Strategy。

  • Markdown/技术文档： 按 Heading（#、##）层级切分。
  • FAQ： 严格按 Question/Answer 对切分。
  • API 文档： 结构化提取（Description、Parameters、Example、Notes）。
  • 表格： 将表格作为整体单元，或将每一行与表头组合成独立 Chunk。

企业级 Chunking 的核心不是寻找一个“万能 Chunk Size”，而是让切分策略理解文档结构。

进阶架构：解决精度与上下文的矛盾

Parent-Child Chunking (父子文档索引)

这是解决“检索精度 vs. 上下文完整性”这一矛盾的最佳实践之一。

原理： 将文档切分成较大的 Parent Chunk（用于提供上下文），然后对每个 Parent Chunk 再进行细分，生成小的 Child Chunk（用于检索）。检索时只对 Child 做向量索引，召回后通过 ID 关联回 Parent Chunk。
价值： 小粒度保证了检索的高 Precision，大粒度保证了生成时的丰富 Context。

Hierarchical Chunking (层级切分)

保留文档的树状结构（Document → Section → Subsection → Paragraph）。检索时不仅可以召回段落，还能携带其所属章节的摘要作为额外的背景信息。这对法律文档、长篇技术手册尤其有效。

Chunk Metadata：被忽视的隐形成本

一个“裸奔”的 Chunk 在生产环境是几乎没用的。每个 Chunk 都应该携带结构化 Metadata。它不只是用来展示引用，更是检索质量的关键。

{
  "chunk_id": "chk_rtc_10027_01",
  "document_id": "doc_rtc_android_v4.6.2",
  "title": "RTC SDK 4.6.2 Android 接入指南",
  "section_hierarchy": ["故障排查", "错误码", "RTC-10027"],
  "page": 27,
  "version": "4.6.2",
  "platform": "Android",
  "created_at": "2024-01-15",
  "token_count": 458,
  "content_type": "troubleshooting_log"
}

Metadata 的工程价值：

  • Filter (过滤)： 用户查“iOS 相关问题”，直接在向量检索前过滤掉 `platform=Android` 的 Chunk，极大提高准确率。
  • Ranking (排序)： 某些字段（如 `version`）可以作为 Reranker 的特征。
  • Permission (权限)： 确保用户只能检索到他有权限访问的 Chunk。

核心决策：Size 与 Overlap

Chunk Size 到底应该多大？

没有绝对答案，但有以下工程经验值（基于主流 Embedding 模型如 bge-m3/openai）：

Token 大小 适用场景 风险
128 - 256 Q&A 匹配、精确事实查询（如“谁什么时候加入的”） 极易丢失上下文，导致 LLM 无法回答 Why 类问题。
512 - 768 通用场景推荐区间。平衡了语义完整性和检索精度。 对于特别复杂的技术步骤可能仍然不够。
1024 - 2048 小说总结、法律合同条款、长代码块 噪声极多，检索时容易被看似相关实则泛泛的内容混淆。

判断依据： 必须考虑 Query 长度、Embedding Model 的特性（有的模型对长文本语义理解能力强）、Reranker 的能力以及 LLM 的 Context Window。

Overlap 到底应该设置多少？

Overlap 是为了解决边界问题，而不是为了提升数字本身。

  • Overlap = 0： 极大概率切断语义，不推荐。
  • Overlap = 10% - 20%： 常用设置。对于 512 的 Chunk，重叠 50-100 tokens 足以覆盖大部分句尾的关联词。
  • Overlap > 30%： 存储和计算成本急剧上升，召回重复内容变多，对结果提升有限，除非是极其密集的代码文档。

评估与决策框架

如何评估 Chunking 的好坏？

不应该只通过人工阅读几个 Chunk 来判断。必须建立自动化评估指标：

  • Retrieval Metrics: Recall@K (召回率), Precision@K (准确率), MRR (平均倒数排名), NDCG。
  • Chunk Quality Metrics: Semantic Completeness (人工打分或模型评估), Boundary Quality (是否截断句子/代码), Average Length。
  • System Metrics: Token Cost, Latency (Embedding 耗时), Storage 占用。

企业数据类型决策表

数据类型 推荐策略 原因
FAQ Question-Answer Pairing 问题和答案必须绑定，不能拆散。
技术文档 Hierarchical / Document-aware (Markdown headings) 保留章节结构，知识有层级性。
API 文档 Structure-aware (JSON/YAML parsing) API 信息高度结构化，参数不能脱离定义。
法律合同 Clause-aware (按条款切分) 条款边界重要，不能把条件和责任分开。
表格 Table-aware (HTML to Markdown or Row extraction) 避免行列关系丢失，通常将表头追加到每一行。
代码 Function / Class slicing (AST-based) 保持逻辑完整性，不要在函数中间切断。

常见失败案例

失败 1: “一把梭”式切分

现象： 统一 500 tokens 切所有文档。
原因： 忽略文档类型差异。
影响： 表格错乱、代码截断、FAQ 被拆成两半。
解决： 引入 Document Classifier，分流处理。

失败 6: 表格惨案

现象： 检索结果中只有一堆孤立的人名或数字。
原因： 表格被简单的按行或字符切分，丢失了 Header 信息。
影响： LLM 无法理解这些数字代表什么。
解决： 表格转 Markdown 或进行结构化提取，将表头作为 Metadata 或前缀拼接到每个单元格 Chunk 中。

失败 8: 上下文孤儿

现象： Chunk 内容是“请执行上述步骤中提到的配置”。
原因： 没有保留 Parent / Section 信息，也没有使用 Parent-Child 索引。
影响： 生成回答时 LLM 产生幻觉或无法回答。
解决： 使用 Parent-Child 策略或在 Chunk 文本中追加路径信息。
