SECTION 01

为什么一个「几十行代码」的 RAG Demo，进企业就变成复杂系统？

几乎所有团队的 RAG 之路都是这样开始的：几百份文档，一个 Embedding 模型，一个开源向量库，一段 System Prompt。五十行代码，问答效果看起来还不错，团队开始兴奋地向业务方演示。

然后它被接入了真实的企业场景——企业内部知识库问答。第一个真实用户提出了一个真实问题，系统开始接受真实的检验。这时你会发现，这个系统实际上需要同时回答以下问题：

  • 用户是谁？
  • 用户属于哪个租户？
  • 用户有没有权限看这份文档？
  • 企业知识在哪里？分散在多少个系统？
  • 扫描版 PDF 怎么解析？
  • 这个问题应该检索哪些内容？
  • 关键词匹配和语义理解如何同时工作？
  • 召回的 50 个片段里哪些真正相关？
  • 上下文超长怎么办？
  • 如何避免模型胡编？
  • 答案如何返回引用出处？
  • 系统出了问题如何定位？
  • 延迟和成本如何控制？
这 13 个问题里，没有一个和「模型调用」有关。
它们全部属于检索系统工程、数据工程、安全与可观测性

所以结论在写第一行架构代码之前就已经确定了：

企业 RAG 本质上已经不是一个「模型调用」，而是一套完整的信息检索与生成系统。 LLM 只是这套系统最末端的「渲染引擎」，系统的上限恰恰由它之前的所有环节决定。

Demo 的几十行代码只覆盖了这张架构图里最中间的一条快乐路径（Happy Path）。企业级的全部工程量，都在这条路径的上下两侧。

SECTION 02

一张完整架构图：离线入库 + 在线查询 + 企业基础设施

先看全景，再逐层拆解。这张图是整个系列的「主地图」，后续每一篇文章都会落回这张图上的某一块。

看这张图时，请记住三个关键观察：

第一，离线和在线是两条完全不同的数据流。 入库链路跑在异步任务队列上，可以慢，可以重跑，追求的是吞吐与质量；查询链路跑在同步请求上，预算通常只有秒级，追求的是延迟与准确。把它们揉在一起设计，是很多 RAG 系统后来推倒重来的根源。

第二，权限是检索的前置条件，不是后置过滤器。 图中编号 ① 的连线指向 Hybrid Retrieval 而不是 Answer——这条连线位置错了，系统就会出现数据泄露。

第三，基础设施是横切的，不是纵列的。 缓存、观测、评测、配置中心不属于任何一层，它们贯穿每一条链路。这也是「能跑的 RAG」与「能运维的 RAG」之间的分界线。

SECTION 03

把系统拆成两条主链路

链路一：Knowledge Ingestion Pipeline（知识入库）

它回答的问题是：企业知识如何进入 RAG 系统。

数据源 ↓ 数据采集 ↓ 解析 ↓ 清洗 ↓ Chunking ↓ Metadata ↓ Embedding ↓ Index
环节核心职责做错的后果
数据采集连接 Confluence、SharePoint、Git、数据库等异构源；处理增量同步、版本变更、删除传播知识陈旧，用户拿到过期答案而不自知
解析把 PDF / Word / PPT 转为结构化文本；OCR 兜底扫描件与图片表格、双栏、页眉页脚内容碎片化，检索命中也无法阅读
清洗去噪、去重、归一化编码与格式脏数据污染索引，垃圾片段反复被召回
Chunking按语义与结构切分，控制块大小与重叠语义被切断，召回的片段「半句无关、半句有理」
Metadata抽取部门、密级、版本、时间、来源、权限标签无法做权限过滤、时效过滤与溯源引用
Embedding & Index向量化并写入向量库与搜索引擎检索阶段无从谈起

链路二：Online Query Pipeline（在线查询）

它回答的问题是：用户问题如何最终变成答案。

User Query ↓ Authentication ↓ Permission ↓ Query Understanding
↓ Query Rewrite ↓ Retrieval ↓ Fusion ↓ Rerank
↓ Context Construction ↓ LLM ↓ Answer

为什么两条链路必须分开设计？

因为它们的时间预算、失败语义和优化目标完全不同：

Offline

  • 时间预算：分钟到小时级，异步执行
  • 失败语义：可重试、可回滚、可重跑全量
  • 优化目标：吞吐量与数据质量
  • 演进频率：Chunking 策略月级迭代
  • 成本特征：批量计算成本，一次投入摊薄到所有查询

Online

  • 时间预算：亚秒到秒级，同步阻塞
  • 失败语义：快速失败 + 降级，不能挂死用户
  • 优化目标：P99 延迟与答案准确率
  • 演进频率：Query 理解策略周级迭代
  • 成本特征：每次查询都产生 Token 与检索成本
工程权衡：两条链路唯一的耦合点是索引本身。一旦你允许在线链路直接修改索引（例如「查询时动态入库」），你就同时破坏了两条链路的所有假设——延迟不可控、索引质量不可审计、权限校验路径断裂。坚持「写入走离线、查询走在线」，是这张架构图最重要的纪律。
SECTION 04

Data Layer：企业知识从来不是「天然可用」的

企业知识的真实形态是这样的：

  • PDF（含扫描件）
  • Word / PPT / Excel
  • Markdown / HTML
  • Wiki（Confluence 等）
  • 数据库 / API
  • 图片（需 OCR）
  • 视频字幕
为什么这些知识不能直接丢进 Vector DB？
因为 Vector DB 消费的是「干净的、带元数据的、语义完整的文本块」——而企业里几乎没有一样知识天然处于这个状态

一份典型的企业合同 PDF：扫描 + 盖章 + 手写批注 + 跨页表格。直接嵌入的结果是一堆语义破碎、互相污染的向量。所以数据层必须先回答一个存储职责划分的问题：

存储组件职责边界存什么
Object Storage原始事实的最终归属地原始 PDF/Word/图片二进制，永不修改，只增版本
Metadata DB知识的「户口系统」文档 ID、来源、版本、部门、密级、Chunk 与原文的偏移映射
Search Index关键词与结构化检索倒排索引、字段索引、过滤条件
Vector DB语义检索Chunk 向量 + 关联的元数据过滤字段
常见架构错误：把 Vector DB 当成「知识的唯一存放地」。一旦 Embedding 模型升级、Chunking 策略调整，你需要全量重建索引——此时如果原始文档只存在于向量库里，你就回不去了。原始文件永远留在 Object Storage，向量只是它的派生物，随时可丢弃、可重建。
SECTION 05

Document Processing Layer：被低估的核心基础设施

Document→ Parser→ OCR→ Layout Analysis→ Cleaning→ Structure Reconstruction→ Chunking→ Metadata

很多团队把文档解析当成「简单的数据预处理」，安排初级工程师用周末写完。六个月后他们会发现：检索效果差的根因调查里，60% 的问题最终追溯到解析环节——表格被拆散、双栏 PDF 串行、页眉被当作正文嵌入。

文档解析是 RAG 的核心基础设施，而不是数据预处理。
检索层的所有下游组件，消费的都是解析层的输出——垃圾进，垃圾出，且下游无法自救

为什么它是「基础设施」？三个判断标准：

1. 错误会被放大而非被吸收。 Reranker 可以过滤掉不相关的片段，但无法修复一个被切碎的表格；LLM 可以忽略无关上下文，但无法还原丢失的行列关系。解析错误是单向不可逆地进入系统的。

2. 它决定了 Chunking 的天花板。 好的切分依赖好的结构（标题层级、段落边界、表格完整性），而结构恰恰是解析层重建出来的。这也是为什么我们把 Structure Reconstruction 放在 Chunking 之前——先恢复文档逻辑结构，再谈怎么切。具体算法留待后续章节展开。

3. 它有独立的 SLA 和演进节奏。 新文档类型（比如内部 CAD 图纸说明）需要扩展解析器；OCR 引擎需要独立升级和评测。这种组件值得独立的团队归属、独立的监控面板。

SECTION 06

Index Layer：企业为什么通常不只有一个索引

「把数据全丢进 Vector DB 就结束了」——这是 Demo 思维的典型残留。企业检索的真实查询形态决定了你需要至少三类索引并存：

索引类型承载组件擅长的问题典型场景
Vector Index向量数据库（Milvus / Qdrant / pgvector 等）语义相似：「怎么处理部署后服务不可用的问题」换一种说法也能找到答案
Keyword IndexElasticsearch / OpenSearch精确匹配：错误码 RTC-10027、型号 SDK 4.6.2、法规编号用户搜的是一个「标识符」，语义相似反而帮倒忙
Metadata IndexMetadata Store（关系库 / 文档字段）结构化过滤：部门 = 支付、密级 ≤ 内部、生效日期 ≥ 2025权限、时效、范围控制的第一道闸门

注意三者的关系不是并列竞争，而是分工协作：Metadata Index 通常作为前置过滤器叠加在另外两类索引的查询上（关于 Metadata Filtering 与检索的关系，见 §12）；Vector 与 Keyword 并行服务同一个查询，在检索层融合。

如果去掉 Keyword Index 会怎样？ 你的系统会在「错误码查询」这类最高频、最高价值的企业场景上整体失效——语义模型无法保证 RTC-10027 的向量与文档中同一错误码的向量足够接近，但 BM25 可以 100% 命中。反过来，去掉 Vector Index，系统会退回到 2015 年的关键词搜索，无法处理任何「换了说法」的问题。企业两种问题都存在，所以两个索引都必须在。
SECTION 07

Query Layer：检索之前发生了什么

Query→ Intent Understanding→ Rewrite→ Expansion→ Filter Construction→ Retrieval

用户输入的 Query 和「适合检索的 Query」之间，通常隔着一道鸿沟。真实用户的提问往往是：口语化的、有错别字的、带上下文指代的（「那这个呢？」）、或混合了多种意图的。直接拿原始 Query 去检索，等于把最脏的数据喂给了最敏感的环节。

环节它解决的问题如果去掉会怎样
Intent Understanding判断用户要什么：是知识问答、闲聊、还是检索型查询？知识库能答吗？「帮我写周报」也触发检索，浪费一次全链路成本
Rewrite消解指代、补全上下文、纠正拼写，产出独立完整的检索查询多轮对话中「那第二种方案呢」检索不到任何东西
Expansion扩展同义表述，提高召回覆盖面术语体系不一致（用户说「退款」，文档写「撤单」）时漏召回
Filter Construction从 Query 中抽出时间、产品、版本等结构化条件，转为 Metadata 过滤「2024 年之后的政策」检索到 2019 年的文档，答案直接错误

本篇只建立架构位置认知：Query Layer 是检索质量的第零道工序，它不产出答案，只产出「更好的查询」。具体算法与实现策略在后续 Query Understanding 专章展开。

SECTION 08

Retrieval Layer：为什么企业必须 Hybrid Retrieval

这是整个系统的心脏。先回答那个绕不开的问题：为什么不直接用纯 Vector Search？

因为两种检索模式的失败模式恰好互补：

Dense Retrieval · 语义通道

  • ✅ 擅长：同义改写、跨语言、模糊描述
  • ✅ 「服务挂了怎么办」→ 匹配「部署故障排查」
  • ❌ 弱项：精确标识符——错误码、零件号、法条编号可能被「平滑」掉
  • ❌ 弱项：新词、专有名词、未登录术语的向量质量差

Sparse Retrieval · 关键词通道

  • ✅ 擅长：精确匹配——RTC-10027、SDK 4.6.2
  • ✅ 擅长：术语型查询、缩写、型号规格
  • ❌ 弱项：换一种说法就完全失配
  • ❌ 弱项：无法理解「不稳定 ≈ 挂了 ≈ crash」

两个通道不是「谁更好」的关系，而是覆盖不同的失败面。企业查询既包含「怎么解决线上服务抖动」（语义主导）也包含「RTC-10027 是什么」（精确主导），任何单通道架构都会在另一半查询上系统性失败。

架构要点：融合（Fusion / RRF）的本质是把两套不可直接比较的打分体系（余弦相似度 vs BM25 分值）统一成一个排序，取长补短。RRF 为什么用排名倒数而不是原始分、各通道权重如何调——这些数学细节留给后续 Hybrid Retrieval 专章，本文只需记住它在架构图上的位置：融合发生在召回之后、精排之前。
SECTION 09

Reranking Layer：从「找得全」到「排得准」

High Recall
召回优先→ Candidate Retrieval
Top 50~100→ Reranker
交叉精排→ High Precision
Top 5~10

一个常见质疑：「Hybrid Retrieval 不是已经打分排序了吗，为什么还要 Reranker？」答案藏在检索系统的第一性原理里：

Retrieval 负责「尽可能找全」，Reranker 负责「尽可能排准」。
这是一个刻意的分工——用便宜的模型扩大搜索面，用昂贵的模型做最终裁决

原因在于两类模型的计算模式差异：

召回模型是「双塔」架构：Query 和文档分别独立编码成向量，离线算好文档向量，在线只算 Query 向量然后做近邻搜索——所以它能毫秒级扫描百万级文档，但 Query 和文档从未真正交互，精度天然受限。

重排模型是「交叉编码」：把 Query 和每个候选文档拼在一起送进模型深度交互，精度显著更高——但代价是每个候选都要一次完整前向计算，只能负担几十个候选。

所以架构上的解法是漏斗：双塔负责从 10 万文档里捞出 50 个「大概相关」，Reranker 负责从 50 个里挑出 5 个「真正相关」。这不是过度设计，而是精度与成本的必然分工。

如果去掉 Reranker 会怎样？ 上下文里会混入大量「弱相关」片段。LLM 面对五段半相关材料时，注意力被稀释，错误引用率和幻觉率同步上升——而且这类问题在上线前很难发现，因为 Demo 阶段的测试问题往往「检索得太容易」了。
SECTION 10

Context Engineering Layer：检索对了 ≠ 生成对了

Retrieved Docs→ Deduplication→ Relevance Filtering→ Compression→ Context Selection→ Token Budget→ Prompt

Reranker 输出的 Top-K 依然不能直接塞给 LLM。在「检索结果」和「Prompt」之间，存在一个经常被省略、但省略必出事的工程层：

处理步骤它防御的真实问题
Deduplication同一文档的多个 Chunk 同时命中，重复内容白白消耗 Token，还放大单一来源的偏见
Relevance FilteringRerank 分数低于阈值的候选直接丢弃——「宁缺毋滥」，弱相关上下文比没有上下文更容易诱发幻觉
Compression长文档只保留与 Query 相关的段落/句子，砍掉背景噪音
Context Selection多样性选择，避免 Top-K 全部来自同一篇文档
Token Budget为系统提示、检索上下文、对话历史、回答空间分配预算，防止上下文溢出或答案被挤压
Lost in
the Middle
长上下文中间位置的信息，LLM 的利用率显著低于两端——塞得越多≠用得越好
∝ Context
长上下文成本随 Token 数线性甚至超线性增长，直接打在每次请求的账单上
P99 Latency
输入 Token 数是推理延迟的一阶因素，上下文失控等于延迟失控
本层存在的根本理由：Retrieval 正确，不意味着 Generation 正确。检索层交付的是「排序后的候选」，生成层需要的是「结构化、去噪、预算内的证据包」——这是两种完全不同的产品。把前者直接交给后者，等于让 LLM 自己做它并不擅长的信息工程。
SECTION 11

Generation Layer：LLM 在企业 RAG 中到底负责什么

Context+ Prompt→ LLM→ Grounded Answer→ Citation

走到这一层，很多人以为终于到了「主角」。但在企业 RAG 的架构里，LLM 的职责被严格限定为一件事：在给定证据内做推理与表达。它不是知识源——知识源是检索层交付的 Context。

能力含义
Grounded Generation答案中的每个事实性断言都应能追溯到上下文中的证据，禁止模型动用「记忆」补充企业知识
Citation / Source Attribution输出引用标注，指向原文档与位置——这是企业用户建立信任的最低门槛，也是审计的硬性要求
Answerability 判断评估「检索到的上下文是否足以回答问题」，不足以回答时触发拒答而非强行作答
Abstention（拒答）主动说「知识库中没有找到相关依据」，并给出替代建议
Hallucination 抑制通过 Prompt 约束 + 引用校验 + 评测回归三道手段，把幻觉率压到业务可接受线以下

企业 RAG 为什么必须有「拒答能力」？

C 端产品里，一个自信但错误的答案可能只是个小尴尬；企业场景里，它可能是一次错误的安全操作、一份错误的法律依据、一次错误的报销审批。对银行、医疗、法务场景而言：

一次诚实的「我不知道」，其业务价值远高于十次流畅的胡编。 拒答不是能力缺陷，而是企业级系统与玩具系统之间的分水岭——它意味着系统知道自己「知识边界在哪里」，并且敢于承认。而拒答能力的前提，是上游 Relevance Filtering 与 Answerability 判断已经为它准备好「证据不足」的信号。拒答是整个链路协作的产物，不是 Prompt 里的一句「不知道就说不知道」。
SECTION 12

Security & Permission Layer：企业级与 Demo 的真正分界线

User→ Identity→ Tenant→ Role→ Permission→ Metadata Filter→ Retrieval

这一节请务必记住图上那个箭头的位置：

权限控制必须进入 Retrieval，而不是等答案生成之后再过滤。
事后过滤防不住的，恰恰是最危险的两条泄露路径

为什么「生成后再过滤」是错误的架构？两条致命路径：

路径一：无权文档没有进入生成，但影响了检索排序。 无权文档参与召回会挤占有权文档的名额（结果错误），其标题或摘要还可能在调试日志、中间态展示中泄露（数据泄露）。

路径二：无权文档进入了上下文并污染了答案。 模型可能综合了无权文档的信息却没有直接引用它——事后过滤引用根本挡不住这种「间接泄露」。

正确做法是把权限转换成检索时下推的元数据过滤条件，让无权文档从一开始就不进入候选集。

机制在企业 RAG 中的角色
RBAC基于角色授权：「HR 角色」可查薪酬制度库。实现简单，适合粗粒度场景
ABAC基于属性动态判断：「文档密级 ≤ 用户 clearance 且 部门 ∈ 用户可见部门」。灵活，覆盖细粒度企业需求
Multi-Tenant租户级隔离，是 SaaS 化 RAG 平台的前提：数据、索引、配置三层都要隔离
Metadata Filtering权限模型的「执行器」——把 RBAC/ABAC 判定结果编译成检索过滤条件，在向量库与 ES 查询中同时生效
Tenant Isolation物理隔离（独立索引）或逻辑隔离（租户字段强制过滤），需要在索引设计期决定，事后改造成本极高
架构纪律：权限过滤条件必须同时下推到 Vector DB 查询和 BM25 查询——两个通道漏掉任何一个，Hybrid Retrieval 就变成了「权限旁路」。具体的权限模型设计、过滤性能优化、缓存与权限一致性问题，后续安全专篇单独展开。
SECTION 13

Infrastructure Layer：让系统可运维、可迭代、可信任

Cache：延迟与成本的杠杆

缓存类型命中场景收益
Embedding Cache相同/相似 Query 不重复调用 Embedding API降低首环节延迟与 API 成本
Retrieval Cache相同 Query 直接复用检索结果跳过整个检索链路
Semantic Cache语义等价的问题（「怎么退款」≈「退款流程是什么」）直接复用答案高频 FAQ 场景成本大幅下降，但需警惕误命中
Response Cache完全相同请求复用完整响应兜底热点，需与权限、时效联动失效
缓存的企业级陷阱：Semantic Cache 的 key 是「语义」，而权限是「身份」——A 用户缓存的答案直接回给 B 用户，可能构成越权泄露。任何缓存的 key 都必须包含权限上下文，这是 Demo 架构绝不会想到、企业架构必须面对的问题。

Model Gateway：模型的统一入口

统一管理 LLM、Embedding、Reranker 三类模型的调用：路由与降级、限流与配额、成本核算、A/B 分流、密钥管理。它的存在意味着——换模型不改业务代码。在企业里，Embedding 模型的更换是必然事件（模型在进步），没有 Gateway 的团队每次换模型都要全链路发版。

Observability：看得见，才谈得上治理

每次请求至少记录：Query（原文 + 改写后）、每路检索的召回与分数、Rerank 后排序、最终 Context、Token 消耗、各环节 Latency、错误与降级事件。RAG 系统的故障排查是典型的「跨七层链路追凶」，没有 Trace 等于蒙眼修车。

Evaluation：质量是回归出来的，不是测出来的

Offline Evaluation ↓ Regression（回归基线） ↓ Online Evaluation ↓ Feedback（用户反馈回流） ↺ 回到离线

评测闭环把「改 Chunking 策略」「换 Embedding 模型」「调 Rerank 阈值」从赌博变成工程：每次变更跑离线回归，确认指标不倒退再灰度上线，用线上反馈验证离线结论。没有评测体系的 RAG 团队，最终都会陷入「每次优化这里、那里就悄悄变差」的循环。

企业级 RAG 必须可观测、可评估、可回归。
这三者共同构成「敢持续迭代」的前提
SECTION 14

一次完整请求到底发生了什么？

架构图看再多遍，不如跟着一个真实请求走一遍。设定场景：一家做 RTC SDK 的公司，内部知识库包含 SDK 文档、FAQ、故障案例库，RAG 系统面向内部技术支持团队。

用户提问：「RTC SDK 4.6.2 在 Android 14 上出现 RTC-10027 错误怎么办？」
  1. Authentication验证 Token，确认这是支持团队员工「小张」的合法请求
  2. Tenant Identification解析出租户 = 内部技术支持域，路由到对应索引与配置
  3. Permission CheckRBAC 判定：小张拥有「SDK 文档（全部）+ 故障案例库（普通级）」权限，不含薪酬类知识域；权限被编译为 Metadata 过滤条件，随请求下推
  4. Query Understanding意图 = 技术故障排查；抽取结构化信号：产品 = RTC SDK，版本 = 4.6.2，平台 = Android 14，错误码 = RTC-10027
  5. Query Rewrite改写为独立完整的查询：「RTC SDK 4.6.2 Android 14 RTC-10027 错误原因与解决方案」，并生成同义扩展（如 crash / 异常 / 中断）
  6. Dense Retrieval向量通道召回 40 条语义相关候选：故障排查指南、Android 14 兼容性说明、类似案例
  7. BM25 Retrieval关键词通道精确命中所有包含 RTC-10027 的已知 issue 条目——这正是语义通道容易漏掉的
  8. Fusion（RRF）两路结果按排名倒数融合，得到约 60 条去重候选
  9. Top-K保留前 30 名，同时执行权限过滤下推——无权文档在这一步之前已不存在于候选集中
  10. Rerank交叉编码器对 30 条逐一精排，同时版本匹配度（4.6.2）与平台匹配度（Android 14）获得高权重，最终保留 Top 6
  11. Context Construction去重后按「已知问题条目 → 根因分析 → 解决方案」组织证据包，控制在 4K Token 预算内，并为每段标注来源文档与章节
  12. LLM Generation模型基于证据生成回答：错误原因（Android 14 前台服务限制 + 旧版 SDK 未适配）、分步解决方案、规避建议；判定证据充分，无需拒答
  13. Citation每个结论性断言挂接引用：〔FAQ-2231 §3〕〔Release Notes 4.6.x〕〔Case #5821〕，用户可一键跳转原文
  14. Logging / Trace全链路 Trace 入库：原始与改写 Query、两路召回分数、精排分数、最终 Context、Token 消耗、各环节耗时——这次请求进入评测数据集，未来每次系统变更都要在这个案例上不倒退
14 步
一次「简单提问」穿过的最小组件链
2 通道
检索阶段并行的召回路径
3 次过滤
权限过滤、相关性过滤、去重压缩
1 条 Trace
全部环节可回溯、可评测、可回归

这就是为什么「几十行代码的 Demo」与「企业级系统」之间隔着一整个工程学科。用户看到的是一秒钟的等待，系统里是 14 个组件的精确协作——而其中任何一个环节掉链子，用户看到的都会是一个「看起来自信但错了」的答案。

SECTION 15

为什么企业 RAG 必须分层？

从软件架构的经典视角看，分层从来不是目的，隔离变化才是。RAG 系统各层的变化速率差异极大——这是分层的根本依据：

层核心职责典型组件如果去掉这一层
Data Layer知识的采集、存储与治理Object Storage · Metadata DB · 连接器知识不可追溯、不可重建，模型升级即灾难
Retrieval Layer高召回地找到候选Vector DB · ES · Fusion漏召回，语义与关键词二选一必然偏废
Ranking Layer高精度地排序筛选Reranker噪音上下文拉高幻觉率与成本
Context Layer构建预算内的证据包去重 · 压缩 · Token Budget延迟与成本失控，Lost in the Middle 发作
Generation Layer有据生成与引用溯源LLM · Citation · 拒答答案不可信、不可审计、不敢上线
Security Layer权限与租户隔离RBAC/ABAC · Metadata Filter数据越权泄露，企业直接一票否决
Infrastructure Layer缓存 / 网关 / 观测 / 配置Cache · Model Gateway · Tracing成本与延迟失控，故障无法定位
Evaluation Layer质量回归与反馈闭环离线评测 · 线上反馈每次迭代都是赌博，优化互相打架

分层带来的七项工程价值，本质上都来自同一件事——把耦合的复杂度拆成可独立处理的问题：

  • 独立优化：Chunking 调整不必动检索代码
  • 独立扩展：检索层 QPS 高就单独扩检索集群
  • 独立替换模型：换 Embedding / Reranker / LLM 互不影响
  • 降低耦合：新人的改动被限制在单层内爆炸半径
  • 方便监控：每层有独立指标与告警
  • 方便 A/B Test：单层灰度，效果归因清晰
  • 方便问题定位：答案错了，逐层 Trace 找到元凶
反例即证明：见过太多「一体化 RAG 服务」——解析、检索、生成、Prompt 全在一个函数里。它的第一次成功很容易，第一次重大变更（比如换 Embedding 模型）就会发现：无法评估影响面、无法灰度、无法回滚、无法归因。分层的意义在系统演进到第二个月之后才开始真正显现。
SECTION 16

哪些组件不是必须的？——警惕架构过剩

读完前面的架构图，最危险的误读是：企业 RAG = 图上所有东西一次性全上。 恰恰相反。架构复杂度应该由业务问题驱动，而不是由技术名词驱动。正确的路径是分级演进：

MVP · 先证明价值

Parser → Chunk → Embedding
→ Vector DB → LLM
  • 目标：两周内让业务方看到可能性
  • 只选最高价值的文档集（几百篇，非扫描件）
  • 不接权限（数据本身可全员可见）
  • 不建评测（靠人工抽检验证）
  • 明确告诉业务方：这是验证品，不是产品

Production · 真实用户上线

+ Hybrid Retrieval
+ Reranker
+ Permission
+ Cache
+ Observability
+ Evaluation
  • 触发条件：真实用户 + 真实权限 + 真实文档规模
  • Hybrid 解决精确标识符查询失效
  • 权限进入检索，这是上线的硬门槛
  • 观测 + 评测让迭代不再靠感觉

Complex Enterprise · 问题驱动再引入

以下组件只有在对应的业务问题真实出现时才值得引入：

组件它解决什么真实问题
Query Planning复杂问题需要拆解为多个子查询时（多跳推理类问题占比显著时才值得）
Adaptive Retrieval简单问题不需要检索、复杂问题需要多轮检索——当「一律检索」造成明显成本/延迟浪费时
Agentic RAG问题需要「检索 → 思考 → 再检索」的循环决策时
Multi-Agent跨域协作（如同时查工单系统 + 文档库 + 监控数据）时
Knowledge Graph多跳关系查询密集（「A 部门负责的产品的负责人向谁汇报」）时
一个诚实的判断标准：如果你无法说出「引入组件 X 是为了解决我们系统的哪个已观测到的问题」，就不要引入它。每一个组件都是真实的运维负担、延迟成本和故障面。技术选型的成熟，不是「都用上了」，而是「知道为什么不用」。
SECTION 17

架构演进：从 Naive RAG 到 Agentic RAG

阶段解决的核心问题遗留的问题（推动下一阶段）
Naive RAG让「知识问答」这件事成立换说法找不到、错误码查不到、噪音上下文多
Hybrid RAG语义与精确关键词双覆盖召回多但排序差，弱相关内容诱发幻觉
Rerank RAG精度问题：把「找得全」升级为「排得准」无权限即不可上线；效果不可度量、不可回归
Enterprise RAG企业落地工程：安全、观测、评测、成本「一律检索」对简单问题浪费、对复杂问题不足
Adaptive RAG按问题复杂度动态决定检索策略固定的「判断 → 检索」流程仍无法处理开放式任务
Agentic RAG自主规划、多轮检索、工具协同——（本系列后续专篇展开）

两个提醒：其一，这张演进图不是淘汰关系而是叠加关系——Enterprise RAG 内部依然包含 Hybrid 与 Rerank，Adaptive 是在 Enterprise 基座上加策略层。其二，演进路线的终点不一定是 Agentic：多数企业的知识问答场景，打磨好 Enterprise RAG 的基线质量，收益远大于追逐新范式。

SECTION 18

最终总结：建立统一认知

如果说第 1 篇回答的是「Why RAG」，这一篇建立的架构认知就是后续所有章节的「地图」。请把它压缩成一行：

Enterprise RAG
= Data + Retrieval + Ranking + Context + Generation
+ Security + Evaluation + Infrastructure

本篇的五个关键结论，值得在团队内对齐：

1. 企业 RAG 是检索系统，不是模型调用。 LLM 是渲染引擎，系统的上限由检索与数据质量决定。

2. 离线入库与在线查询是两条链路，唯一耦合点是索引。 写入纪律决定系统可维护性。

3. 权限必须在检索时下推，而非生成后过滤。 这是企业级与 Demo 的分界线，也是安全底线。

4. 召回找全、精排排准、上下文工程控本、生成层有据可拒。 每层职责单一，去掉任何一层都有明确的失败模式。

5. 架构复杂度由业务问题驱动。 从 MVP 到 Production 到 Complex Enterprise，每一级都应有明确的触发条件。

真正困难的从来不是「让 RAG 跑起来」，
而是让它在真实企业环境中
长期稳定、准确、可控、可观测、可扩展地运行。
—— 本系列贯穿始终的核心观点
