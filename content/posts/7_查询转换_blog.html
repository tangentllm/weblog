1. 问题动机：用户的问题不一定适合检索

在 RAG 系统中，我们通常直接把用户的原始查询拿去做向量检索。但用户的提问方式往往不是最优的检索语句：

  • 过于简短：缺少关键上下文词，导致检索到的片段语义偏移
  • 过于宽泛：匹配到大量低相关片段，噪声淹没了真正有用的信息
  • 多主题混合：一个查询包含多个子问题，向量检索只能捕捉其中一个方向
💡 核心思路

与其改检索算法或换更大的向量库，不如在检索之前用 LLM 对用户查询做一次"预处理"——这就是查询转换（Query Transformation）的核心思想。

本篇实现三种经典的查询转换技术，并通过 LLM-as-Judge 评估它们对最终回答质量的影响。

2. 三种查询转换技术一览

技术 目标 策略 适用场景
查询重写
Rewrite		 使查询更具体、更详细 LLM 补充关键词、时间范围、相关概念 原始查询过于简短或模糊
后退提示
Step-back		 生成更宽泛的查询 LLM 抽象化问题，获取背景上下文 需要补充背景知识或上下文
子查询分解
Decompose		 拆解复杂查询为多个子问题 LLM 将问题按维度拆分为独立子查询 查询包含多个子主题或方面
⚠️ 直觉对比

以 "中国政府在AI上有哪些政策?" 为例：

  • 重写 → "2023年中国政府在人工智能领域的政策和战略有哪些具体内容？请包括涉及技术研发、产业应用、数据隐私保护、伦理规范以及国际合作等方面的最新政策文件和指导意见。"

5. 代码解读：查询重写

查询重写的核心思路：让 LLM 充当"检索优化师"，把用户简短的查询补充为包含关键术语、时间范围和具体维度的详细查询。

def rewrite_query(original_query, model="gpt-4o"):
    """将原始查询改写得更加具体、详细，补充相关关键词和概念。"""

    system_prompt = (
        "你是一名擅长优化检索查询的AI助手。"
        "你的任务是将用户的查询改写得更加具体、详细，"
        "并包含有助于检索准确信息的相关术语和概念。"
    )
    user_prompt = f"""
请将下列查询改写为更具体、更详细的表达，
补充相关的关键词和概念，以便更好地检索到准确的信息。

原始查询：{original_query}

改写后的查询：
"""
    response = client.chat.completions.create(
        model=model,
        temperature=0.0,  # 确定性输出
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_prompt}
        ]
    )
    return response.choices[0].message.content.strip()
🔑 关键点

temperature=0.0 保证重写结果稳定可复现。系统提示中明确要求"补充相关术语和概念"，引导 LLM 扩展查询的语义覆盖面。

6. 代码解读：后退提示

后退提示（Step-back Prompting）来自 Google 2023 年的论文，核心思想是退一步思考——将具体问题抽象化，先获取背景知识再回答。

def generate_step_back_query(original_query, model="gpt-4o"):
    """生成更通用的'后退一步'查询，以检索更广泛的上下文。"""

    system_prompt = (
        "你是一名擅长检索策略的AI助手。"
        "你的任务是将具体的用户查询改写为更宽泛、更通用的问题，"
        "以便检索到相关的背景信息和更广泛的上下文。"
    )
    user_prompt = f"""
请将下列查询改写为更宽泛、更通用的问题，
以便有助于检索相关的背景信息和更广泛的上下文。

原始查询：{original_query}

后退一步的查询：
"""
    response = client.chat.completions.create(
        model=model,
        temperature=0.1,  # 稍高温度，允许一些变化
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_prompt}
        ]
    )
    return response.choices[0].message.content.strip()
⚠️ 温度设置

后退提示使用 temperature=0.1，比查询重写略高。适度的随机性有助于生成更多样化的宽泛问题，避免后退方向过于单一。

7. 代码解读：子查询分解

当用户的问题涉及多个维度时，单一向量检索只能命中其中一个方向。子查询分解将复杂问题拆成多个聚焦的子问题，分别检索后合并结果。

def decompose_query(original_query, num_subqueries=4, model="gpt-4o"):
    """将复杂查询拆解为 num_subqueries 个更简单的子问题。"""

    system_prompt = (
        "你是一名擅长将复杂问题拆解为简单子问题的AI助手。"
        "你的任务是把复杂的用户查询分解为若干个更简单、"
        "聚焦不同方面的子问题，所有子问题的答案合起来"
        "可以完整回答原始问题。"
    )
    user_prompt = f"""
请将下列复杂查询拆解为 {num_subqueries} 个更简单的子问题。
每个子问题应关注原始问题的不同方面。

原始查询：{original_query}

请生成 {num_subqueries} 个子问题，每行一个，格式如下：
1. [第一个子问题]
2. [第二个子问题]
以此类推……
"""
    response = client.chat.completions.create(
        model=model,
        temperature=0.2,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_prompt}
        ]
    )

    # 解析编号列表
    content = response.choices[0].message.content.strip()
    lines = content.split("\n")
    sub_queries = []
    for line in lines:
        if line.strip() and any(line.strip().startswith(f"{i}.")
                                for i in range(1, 10)):
            query = line.strip()
            query = query[query.find(".") + 1:].strip()
            sub_queries.append(query)
    return sub_queries

8. 代码解读：转换后搜索

transformed_search() 根据转换类型路由到不同策略。分解模式需要特别注意去重——多个子查询可能检索到相同的文本块。

def transformed_search(query, vector_store, transformation_type, top_k=3):
    """使用转换后的查询进行搜索。"""

    if transformation_type == "rewrite":
        transformed_query = rewrite_query(query)
        query_embedding = create_embeddings(transformed_query)
        results = vector_store.similarity_search(query_embedding, k=top_k)

    elif transformation_type == "step_back":
        transformed_query = generate_step_back_query(query)
        query_embedding = create_embeddings(transformed_query)
        results = vector_store.similarity_search(query_embedding, k=top_k)

    elif transformation_type == "decompose":
        sub_queries = decompose_query(query)
        sub_query_embeddings = create_embeddings(sub_queries)

        # 每个子查询检索 top-2，合并后去重
        all_results = []
        for embedding in sub_query_embeddings:
            sub_results = vector_store.similarity_search(embedding, k=2)
            all_results.extend(sub_results)

        # 去重：保留最高相似度
        seen_texts = {}
        for result in all_results:
            text = result["text"]
            if text not in seen_texts or \
               result["similarity"] > seen_texts[text]["similarity"]:
                seen_texts[text] = result

        # 按相似度排序取 top_k
        results = sorted(seen_texts.values(),
                         key=lambda x: x["similarity"],
                         reverse=True)[:top_k]
    else:
        # 无转换：直接检索
        query_embedding = create_embeddings(query)
        results = vector_store.similarity_search(query_embedding, k=top_k)

    return results
✅ 去重策略

分解模式下，4 个子查询各检索 2 条结果（共 8 条），通过文本精确匹配去重后保留相似度最高的，最终截取 top_k=3 条。这确保上下文窗口不会被重复内容浪费。

9. 代码解读：完整 RAG 管道

最终的 rag_with_query_transformation() 将文档处理、查询转换、检索、回复生成串联为一个端到端管道。

def rag_with_query_transformation(pdf_path, query,
                                   transformation_type=None):
    """运行完整的 RAG 管道，支持可选的查询转换。"""

    # 1. 文档处理 → 向量存储
    vector_store = process_document(pdf_path)

    # 2. 查询转换 + 检索
    if transformation_type:
        results = transformed_search(
            query, vector_store, transformation_type
        )
    else:
        query_embedding = create_embeddings(query)
        results = vector_store.similarity_search(query_embedding, k=3)

    # 3. 组合上下文
    context = "\n\n".join(
        f"PASSAGE {i+1}:\n{r['text']}" for i, r in enumerate(results)
    )

    # 4. 生成回答
    response = generate_response(query, context)

    return {
        "original_query": query,
        "transformation_type": transformation_type,
        "context": context,
        "response": response
    }

对此特定查询和文档，原始查询的表现反而最好——它列举了最多的地方政府具体措施。Rewrite 回答虽然结构清晰且引用了具体文件名，但地方细节减少。Step-back 和 Decompose 各有侧重但都不够全面。这并不意外：当原始查询已经足够清晰且文档内容高度匹配时，额外的转换可能引入噪声或偏移检索方向。

13. 优缺点与适用场景

✅ 优势

  • 无需修改检索基础设施：纯查询侧优化，即插即用
  • 可组合：三种技术可并行使用，取各自检索结果的并集
  • 适配性强：针对不同查询类型选择不同策略
  • 提升召回率：特别是分解模式，能覆盖更多语义维度

⚠️ 局限

  • 额外 LLM 调用：每次查询增加 1~N 次 LLM 调用，延迟和成本上升
  • 可能引入噪声：重写/后退可能偏离原始意图
  • 依赖 LLM 质量：转换效果直接取决于 LLM 的理解能力
  • 简单查询无需转换：当原始查询已经足够好时，转换反而降低性能

何时使用哪种技术？

查询特征 推荐技术 理由
简短、模糊、缺少关键词 查询重写 补充语义信息，提高精确度
需要背景知识或上下文 后退提示 先获取宽泛背景，再精确定位
多主题、多维度复合问题 子查询分解 分而治之，确保每个维度都被检索到
已经足够具体的查询 不转换 避免引入不必要的噪声和延迟

14. 本篇小结

🎯 核心收获
  • 查询转换是 RAG 的"查询侧增强"——不改索引、不改向量库，只优化查询本身
  • 三种技术各有侧重：重写让查询更精确，后退让查询更宽泛，分解让查询更全面
  • 没有银弹：评估显示原始查询在此场景下表现最好，说明查询转换并非总是有益
  • 实践建议：可以先判断查询复杂度，再决定是否启用转换以及使用哪种策略
