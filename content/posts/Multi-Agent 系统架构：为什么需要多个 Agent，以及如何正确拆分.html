SECTION 01

从一个真实场景开始：一个 Agent 的「膨胀之死」

需求不是一次性来的，是一点点堆上来的。问题也是。

假设你在做一个企业级深度研究系统，初版架构非常朴素——一个 Agent，一个循环，一坨工具：

v1_architecture.txtnaive 
Single Agent
 ├─ Prompt: 角色设定 + 研究方法论 + 引用规范 + 输出格式
 ├─ Tools:  web_search / vector_rag / sql_query / python_repl
 │          crawl / citation_check
 └─ Loop:   理解问题 → 检索 → 分析 → 撰写 → 自查 → 输出

上线第一个月，它工作得很好。第三个月，需求开始堆叠：支持多语言、接入内部知识库、输出带引用、跑数据分析、生成图表。于是你做了所有工程师都会做的事——往同一个 prompt 里塞规则、往同一个 tool 列表里加函数。

然后问题出现了，而且几乎是以固定顺序出现的：

  • 1
    Prompt 膨胀与指令冲突系统提示词从 2K token 涨到 15K，「写报告时」的规则和「做数据计算时」的规则开始互相覆盖。模型在第 30 轮循环时，已经「忘记」了第 3 轮的系统约束——这是典型的 lost in the middle 现象：不是模型变笨了，是关键指令被淹没了。
  • 2
    Tool 数量膨胀导致选错率上升Function calling 的准确率与候选工具数量强相关。当工具从 5 个涨到 25 个，模型开始把 web_search 当 vector_rag 用，把 sql_query 的 schema 传错。这是信号噪声问题，不是能力问题。
  • 3
    上下文被工具结果污染一次 web search 返回 8K token 的原始 HTML 片段，一次 SQL 查询返回 200 行表格。这些「原始材料」对下游推理是必要输入，但对上游的意图理解是纯噪声。单一上下文窗口里，所有角色共享同一份脏上下文。
  • 4
    决策路径不可控同一个问题，今天跑 3 步出答案，明天跑 18 步还在循环搜索。你无法预判一条请求在 Agent 内部会走出怎样的轨迹——因为控制流和 LLM 的自由判断纠缠在了一起。
  • 5
    权限边界模糊这个 Agent 既能读内部知识库，又能写 SQL，还能调用外部 API。安全团队问「它能不能把内部数据发到外网」，你答不上来——因为它理论上可以。
  • 6
    错误难定位、评测难拆解答错了，是检索没找到？是推理错了？是撰写时曲解了？还是 Fact Check 这步根本没执行？单 Agent 的 trace 是一锅粥，评测只能对最终答案打分，无法对中间环节归因。
  • 7
    成本失控每轮循环都要把全量上下文（含所有工具结果）重新送入模型。在单 Agent 里，token 消耗以更隐蔽的方式累积——上下文越长，每一轮的单价越高。

到这里，问题已经不再是「我的 Agent 不够聪明」，而是一个执行主体被迫同时扮演七个角色，而每个角色的最优上下文、工具集、模型和权限都不一样。这就是拆分的起点。

SECTION 02

什么时候应该拆：八个工程边界

「职责单一」是结论，不是判据。真正驱动拆分的是可观测的工程边界。

下面是八个边界。当其中任意两个以上同时被突破时，就该考虑拆 Agent 了。

TABLE 1八个工程边界与拆分方式对照
边界判断信号拆分方式
能力边界一个 Agent 需要两套互相冲突的「专业人格」（如严谨的分析师 vs 有创意的写手）按角色拆
Context 边界一次任务的中间产物已塞不下一个窗口，或 A 阶段的原始输出对 B 阶段是噪声按 context 生命周期拆
Tool 边界工具数量 > 15，或两个工具的 schema 互相干扰按工具域拆
权限边界不同操作需要不同的凭证 / 审计 / 沙箱（读内网 vs 访问公网）按权限域硬隔离
模型边界有的子任务用小模型就够，有的必须用前沿模型；混用拉高整体成本按模型分层拆
成本边界高频低价值步骤和低频高价值步骤被绑定在同一计费路径上按成本敏感度拆
故障边界一个工具超时会拖垮整条链路，没有局部降级的可能按失败域拆
评测边界无法对中间环节单独建立 ground truth 和指标按可评测单元拆
其中两条边界最「硬」

Context 边界和权限边界：前者决定了系统能不能工作，后者决定了系统敢不敢上生产。其余六条边界影响的更多是效率与可维护性。

什么情况下，不应该使用 Multi-AgentANTI-PATTERNS

拆分是有代价的，而且代价常常被低估。以下情形请留在 Single Agent 或 Workflow：

  • !
    任务能塞进一个上下文窗口，且步骤 ≤ 5 步这时 Multi-Agent 只会增加 2–4 倍 token 和延迟，不带来任何质量提升。
  • !
    决策路径可完全枚举固定 ETL、固定问答模板、固定审批流——这是 Workflow 的主场，用 LLM 做调度纯属浪费。
  • !
    需要严格的端到端一致性Multi-Agent 的每个交接点都是潜在的状态丢失点，链条越长，一致性越难保证。
  • !
    团队规模太小，撑不起观测与评测基建一个人的团队维护 5 个 Agent，最终一定会退化成 5 个互相打架的 prompt。
  • !
    延迟极度敏感Supervisor 模式下每次子 Agent 返回都要经过一次主 Agent 汇总，多一次模型调用就是多几百毫秒到几秒。
先加工具，再上 Workflow，最后才上 Multi-Agent。—— 经验法则：让架构跟随复杂度演进，而不是预支未来复杂度

SECTION 03

Multi-Agent 的四种核心架构模式

Supervisor · Planner-Worker · Hierarchical · Peer-to-Peer —— 没有最好的，只有匹配的。

3.1 Supervisor（主管模式）CENTRALIZED ROUTING

工作机制：Supervisor 持有全部路由逻辑，根据当前上下文决定调用哪个子 Agent；子 Agent 执行完把结果交回 Supervisor；Supervisor 汇总后决定下一步，或在信息足够后产出最终答案。

路由：可以是规则（关键词 → Agent），也可以是 LLM 结构化输出（返回 {"next": "agent_b", "task": "..."}）。生产系统里两者混合——高频路径走规则，低频路径走 LLM。

汇总：这是 Supervisor 的隐形瓶颈。子 Agent 返回的可能是一段 10K token 的原始结果，Supervisor 要在有限上下文里消化多个 Agent 的产出。工程上通常要求子 Agent 返回结构化摘要 + 完整产物存对象存储、只传引用。

单点瓶颈

所有信息流经 Supervisor，意味着它的上下文压力是 O(总任务规模) 的。当子 Agent 数量 > 5 或子任务产出 > 5K token 时，Supervisor 自身就会出现第一节提到的「单 Agent 膨胀」问题——Supervisor 本质上是一个受约束的 Single Agent，它有同样的天花板，只是推后了一步。

TABLE 3Supervisor 模式速览
维度评价说明
优势可控 · 可审计控制流集中在中心节点，每次调度可记录、可回放、可审计
劣势上下文压力 O(N)N 个子 Agent 的产出全部汇入 Supervisor，容易重演单 Agent 膨胀
适合域路由型任务多域个人助理（日历/邮件/CRM 各一个子 Agent）、企业知识助手

3.2 Planner-Worker（规划-执行模式）DECOMPOSE & PARALLELIZE

工作机制：Planner 先把一个复杂问题拆解成带依赖关系的任务图（DAG），然后把任务分发给 Worker 并行执行，最后由 Aggregator 汇总。

与 Supervisor 的本质区别：Supervisor 是反应式的——走一步看一步，根据上一步结果决定下一步；Planner 是前瞻式的——先有全局计划，再执行。这带来两个直接后果：

  • ∥
    可以并行Planner 知道 T2 和 T3 互不依赖，就能同时派发给两个 Worker。Supervisor 想并行，就必须在一次模型调用里同时发起多个 tool call，可控性差很多。
  • ↑
    Planner 的质量决定系统的上限如果 Planner 拆出的任务粒度不对、依赖关系错了，Workers 执行得再好也救不回来。这是该模式最大的失效模式：Planner 失控——常见症状包括任务重复、依赖成环、把一个原子任务拆成 10 个碎片导致通信开销爆炸。

缓解 Planner 失控的四个工程手段

  1. 给 Planner 输出强 schema 约束（JSON Schema + 任务依赖 DAG），拒绝不合规模划；
  2. 限制任务数量上下界（如 3–7 个子任务），超界要求重新规划；
  3. 引入 Replanner：Worker 执行中发现任务不可行，可请求局部重规划而非全量重来；
  4. Planner 用最强模型，Worker 用性价比模型——规划是杠杆点，值得花贵的 token。

3.3 Hierarchical（层级模式）RECURSIVE SUPERVISION

本质：Supervisor 的递归。Manager 不直接面对所有 Specialized Agent，而是先把任务路由到 Domain Agent，Domain Agent 在自己的域内再做二级调度。

扩展性：这是四种模式里唯一能支撑大规模 Agent 集群的——Manager 的上下文压力从 O(N) 降到 O(D)（D 为域数）。当系统要接入几十个业务域、几十个团队时，这是唯一可扩展的形态。

复杂度代价：

  • 信息跨层传递时会衰减（每层都会摘要压缩，细节丢失）；
  • 故障排查要穿透多层 trace；
  • 域间通信需要显式协议，否则容易形成「封建割据」——Domain Agent 之间互相不透明，出现重复建设；
  • 评测矩阵从 N 个 Agent 变成 N×N 的交互组合，测试空间爆炸。

3.4 Peer-to-Peer（对等模式 / Swarm）HANDOFF NETWORK

工作机制：没有中心调度者。每个 Agent 根据自己看到的共享状态和对方的能力描述，自主决定把控制权移交给谁（handoff）。OpenAI 的 Swarm 和 LangGraph 的 Swarm 实现都是这个思路。

灵活性：最高。任何 Agent 可以和任何 Agent 对话，新增一个 Agent 不需要改中心调度代码。但代价同样最高：

  • O
    通信复杂度 O(N²)Agent 数量翻倍，潜在交互路径变四倍。
  • O
    状态一致性噩梦没有中心节点维护唯一真相，两个 Agent 同时修改共享状态时需要显式并发策略——乐观锁、冲突合并、或强制序列化。
  • O
    调试困难一条请求的 trace 可能穿过 5 个 Agent，没有全局视角的话几乎无法复现问题。
适合场景与建议

Agent 数量少（通常 ≤ 5）、每个 Agent 都足够自治、交互模式高度动态、且团队有较强分布式系统经验。客服系统的「转接专家」是经典场景，但也几乎只有这种场景适合它。对多数团队，Peer-to-Peer 是最后的选择，不是第一步。

SECTION 04

架构选择：不是排名，是匹配

控制性、灵活性、复杂度、调试难度、并行度——五个维度上的权衡矩阵。

TABLE 4四种架构模式的选择矩阵
模式控制性灵活性复杂度调试难度并行度典型场景
Supervisor ★★★★★★★★★★★★★★★ 多域个人助理、企业知识助手
Planner-Worker ★★★★★★★★★★★★★★★★★★★★ 深度研究、代码重构、复杂分析
Hierarchical ★★★★★★★★★★★★★★★★★★★★★ 多团队企业平台、Agent 集群
Peer-to-Peer ★★★★★★★★★★★★★★★★★★★ 少量自治专家的动态协作

选择依据不是「哪个最好」，而是四个问题的答案：

  • 1
    任务路径的可预测程度高度可预测 → Workflow；部分可预测 → Supervisor；完全开放 → Planner-Worker。
  • 2
    子任务间是否需要并行需要 → Planner-Worker 或 Router；不需要 → Supervisor 或 Handoffs。
  • 3
    Agent 数量和团队规模< 5 个 Agent / 单团队 → 扁平架构；> 10 个 / 多团队 → Hierarchical。
  • 4
    审计与合规要求强审计 → 中心化（Supervisor / Hierarchical）；弱约束 → 可以考虑 P2P。
务实的演进路线

从 Supervisor 起步，当出现明确的并行需求时升级为 Planner-Worker，当出现多团队、多域需求时再引入 Hierarchical。让架构跟随复杂度演进，而不是预支未来复杂度。

SECTION 05

生产级 Multi-Agent 的分层架构

不管上层用哪种协作模式，可维护的系统都需要硬边界分层。每层职责必须足够硬，否则 Agent 数量的增加会让系统迅速失控。

  • L1
    API Gateway认证、限流、配额、会话粘性。Agent 系统的请求成本是普通 API 的几十倍，必须在网关层就把预算和配额管住，而不是等 token 烧完才发现。
  • L2
    Orchestrator —— 系统的脊梁骨不参与业务判断，只负责：维护会话级状态机；传递 trace 上下文（trace_id、span 层级）；执行超时、重试、降级、熔断；持久化中间产物，支持断点恢复和人工接管。LangGraph 的 checkpoint、Temporal 的 workflow 引擎，本质上都在做这一层的事。
  • L3
    Agents 层每个 Agent 是独立的部署单元，有自己的 system prompt、tool 白名单、模型选择、超时策略。Agent 之间不直接调用，所有交互经 Orchestrator 中转。
  • L4
    Tools / RAG / Memory工具的统一注册与鉴权；向量库与检索服务；会话记忆（短期工作记忆 + 长期知识记忆）。这一层要做到「工具即资源，Agent 即租户」——每个 Agent 只能看到被授权的工具子集。
  • L5
    Infrastructure模型网关（统一计费、路由、降级）、全链路可观测（LangSmith / Langfuse / 自建 trace）、离线评测流水线、Agent 代码沙箱、密钥与权限管理。

分层的核心价值在于故障隔离和独立演进——你可以把 Writer Agent 换个模型，不影响 Search Agent；可以给 Analysis Agent 加沙箱，不碰其他层。这是微服务架构的老原则，在 Agent 时代依然成立。

SECTION 06

真实案例：企业级深度研究系统

把前面的所有原则串起来，看一个完整的拆分过程——为什么拆、怎么拆、每个 Agent 的边界是什么。

6.1 业务需求

用户提出一个复杂问题，如「分析过去三年国内新能源车市场的竞争格局变化，并评估某新进入者的可行性」。系统需要：检索互联网 + 内部研究报告；提取结构化数据并做定量分析；对关键结论交叉验证；产出带引用的长文报告；经审核后发布。

6.2 为什么拆、怎么拆

初始版本是一个单 Agent，上线后遇到第一节的全部问题。拆分方案如下：

TABLE 5七个 Agent 的边界定义（输入 / 输出 / 模型 / 工具 / 拆分理由）
Agent职责模型关键工具边界理由
Research Agent
(Orchestrator)		 理解问题、制定研究计划、分配子任务、汇总 前沿模型 无直接工具，只调度 Planner 角色要用最强推理能力；不碰工具，避免上下文被污染
Search Agent 互联网检索、结果去重、相关性初筛 小模型 web_search crawl 高频调用，用性价比模型；工具白名单仅限搜索
Retrieval Agent 内部知识库 RAG 检索 小模型 vector_search kb_api 权限域独立：只能读内部 KB，禁止外联
Data Analysis Agent 对提取的数据跑统计分析、生成图表 中档模型 python_repl sql_query 必须跑在沙箱里，故障域隔离；权限独立
Fact Checker 对 Writer 的关键论断做交叉验证 中档模型 search retrieval（只读） 独立于 Writer，避免自我确认偏误
Writer 组织成结构化长文、插入引用 前沿模型 无工具（纯生成） 隔离上下文——只看整理好的材料，不看原始搜索结果
Reviewer 检查引用完整性、口径一致性、合规 中档模型 无工具 最后的质量门

6.3 协作流程

采用Planner-Worker 为主、Supervisor 语义为辅的混合架构：Research Agent 担任 Planner，先产出研究计划；Search 和 Retrieval 并行执行；Data Analysis 依赖 Retrieval 产出后启动；Writer 串行在最后；Fact Checker 和 Reviewer 构成质量关卡。

6.4 五个关键工程决策

  • 1
    Research Agent 不直接调工具这是整条链路上最重要的约束。让 Planner 亲自做搜索，会让它的上下文被原始网页污染，规划质量迅速下降。Planner 只消费结构化的中间结果。
  • 2
    子 Agent 之间不传原始数据，只传结构化产物 + 存储引用Search Agent 返回的不是 8K token 的网页原文，而是 [{url, title, snippet, relevance}]；原文存对象存储，Writer 需要时通过引用拉取。
  • 3
    Fact Checker 必须独立于 Writer如果让 Writer 自查，它会有强烈的确认偏误——倾向于相信自己写的东西。独立 Agent + 独立上下文，是打破偏误的唯一工程手段。
  • 4

SECTION 07

收束：六个问题的最终回答

Q1Multi-Agent 为什么出现？

不是因为多个 Agent 比一个「更聪明」，而是因为单一执行主体在 Context、Tool、权限、模型、成本等多个维度上都存在物理性上限。Multi-Agent 的本质是通过上下文隔离换取能力的可组合性——每个 Agent 在自己的小世界里保持干净，靠协议组合成复杂行为。

Q2Agent 应该按什么原则拆？

按边界拆，不按「职责」拆。八个边界里，Context 边界和权限边界最硬，能力边界和模型边界次之。每次拆分都要能回答：这个 Agent 的输入输出契约是什么？它的工具白名单是什么？它挂了会影响谁？

Q3Workflow 与 Multi-Agent 如何选择？

路径可完全枚举 → Workflow；路径不可枚举但子任务域清晰 → Supervisor；路径开放且需要并行 → Planner-Worker。判断标准不是「任务多复杂」，而是「控制流应该由谁持有」——代码能写清楚的逻辑永远不要交给 LLM。

Q4Supervisor 与 Planner-Worker 的区别是什么？

Supervisor 是反应式调度，每一步根据当前状态做局部决策，天然串行，适合域路由；Planner-Worker 是前瞻式规划，先有全局任务图再执行，天然支持并行，适合复杂分解。前者可控性强、上下文压力集中；后者上限更高、但 Planner 的质量成为单点风险。生产系统常常两者混用：外层 Planner 拆解，内层每个子任务用 Supervisor 管理局部执行。

Q5Agent 数量是不是越多越好？

不是，且通常正好相反。每多一个 Agent，就多一个交接点、多一份通信成本、多一个需要评测和监控的对象。Agent 数量应该由边界决定，而不是由架构野心决定。大多数生产系统的甜蜜点在 3–7 个 Agent；超过 10 个就需要 Hierarchical 架构和专门的平台团队支撑。

Q6为什么拆分后系统复杂度会迅速上升？

因为 Multi-Agent 本质上是分布式系统，把单进程内的函数调用变成了跨网络的协议交互。复杂度上升来自四个方面：

状态从「一个变量」变成「多处副本」（需要一致性策略）；失败从「一次异常」变成「部分失败」（需要补偿和幂等）；观测从「一个 stack trace」变成「跨 Agent trace」（需要专门的观测基建）；评测从「端到端打分」变成「组合爆炸的中间指标矩阵」。

拆 Agent 是把复杂度从「prompt 里的纠缠」搬到「系统里的协议」——如果团队没有驾驭分布式系统的能力，拆完只会更糟。
