别再迷信复杂框架：
Agent 系统的六种简约模式

解读 Anthropic 工程团队《Building Effective Agents》一文的核心方法论—— 为什么给几十个团队做完 Agent 落地咨询之后，他们得出的结论居然是「越简单越好」。

过去两年，"Agent" 几乎成了大模型应用领域最拥挤的赛道：LangChain、AutoGPT、CrewAI、各种带图形界面的编排平台层出不穷，每家都在强调自己的编排能力有多强、多灵活。但当 Anthropic 的工程团队真正深入到几十个生产环境的客户项目里去看时，他们发现一个反直觉的事实：做得最好的团队，用的往往不是最花哨的框架，而是几个可以用几十行代码写清楚的简单模式。

这篇发布于 2024 年底的工程博客，与其说是在介绍一个新技术，不如说是在做一次"祛魅"——把 Agent 这个被过度营销的概念，拆解成几种可以被工程师理解、调试、组合的基础构件。这也是为什么它至今仍被广泛引用：它给出的不是某个框架的用法手册，而是一套判断"什么时候该用什么"的思维框架。本文将在原文脉络的基础上，结合具体代码示例和工程实践中的取舍，做一次更贴近开发者视角的拆解。

原文：Building effective agents（Anthropic Engineering，2024-12-19）。站内相关阅读：深入理解 MCP、Claude Code 最佳实践。

一、Workflow 与 Agent：一个常被混用却至关重要的区分

在深入具体模式之前，有一个概念上的分野必须先厘清，因为它直接决定了你的系统该怎么设计。行业里很多人把"Agent"当作一个筐，什么都能往里装。Anthropic 的做法是把这个筐拆成两个边界清晰的子类：

  • 工作流（Workflow）：LLM 和工具的调用路径是预先写死在代码里的。也就是说，"第一步做什么、第二步做什么"是开发者决定的，模型只负责在每一步里把具体的内容填好。
  • 智能体（Agent）：LLM 动态地决定自己下一步要做什么、要调用哪个工具、要不要继续。控制权从代码转移到了模型本身。

这个区分之所以重要，是因为它对应着完全不同的工程权衡。工作流可预测、可测试、成本可控，但灵活性差；Agent 灵活、能应对开放式问题，但代价是更高的延迟、更高的 token 成本，以及"模型可能在第 15 步就走偏了"的不确定性。原文给出的建议非常朴素：先问自己是否真的需要 Agent。很多时候，一次优化好的单轮 LLM 调用，配合检索和上下文示例，就已经足够解决问题——而这几乎是零成本、零风险的选项。

补充延伸：这里可以类比传统软件工程里"该不该引入微服务"的讨论。微服务解决的是规模化协作和独立部署的问题，但如果你只有一个小团队和一个不算复杂的业务，强上微服务只会带来额外的运维成本。Agent 也是一样——它是用延迟和成本，换取任务处理的灵活性和上限，这笔账不是在所有场景下都划算。

二、构建的基本单元：从「被增强的 LLM」到五种工作流模式

原文的核心贡献，是把生产环境中反复出现的编排模式归纳成了几种"积木"。理解它们最好的方式不是死记定义，而是看清楚每种模式里信息和控制权是怎么流动的。

基础单元：被增强的 LLM（Augmented LLM）

所有模式的起点，都是一个具备检索、工具调用、记忆能力的 LLM 调用。现在的模型已经能够自主生成搜索查询、挑选合适的工具、决定要记住什么信息。Anthropic 自家的 Model Context Protocol（MCP） 就是为了让这种"增强"标准化——开发者只需要实现一个客户端，就能接入一个不断扩张的第三方工具生态（站内长文：MCP 完全技术指南）。后面所有的模式，都默认每一次 LLM 调用背后都带着这些能力。

模式一：Prompt Chaining（提示链）

把一个任务拆成一串顺序执行的子任务，前一步的输出是后一步的输入。你还可以在中间插入程序化的检查点（原文称为 gate），一旦发现中途跑偏就提前终止，避免把错误一路带到最后。这本质上是用"多次简单调用"替代"一次困难调用"，用延迟换准确率。

→

prompt-chaining · 每一步只做一件容易的事

典型场景：先写营销文案，再翻译成目标语言；先出大纲、校验大纲是否符合要求，再基于大纲成文。

模式二：Routing（路由）

先对输入做分类，再分发给专门优化过的下游处理流程。它的价值在于"专精"：如果你用同一个 prompt 既要处理退款请求又要处理技术支持，为了照顾一类输入而做的优化，很可能会拖累另一类的表现。路由把这种耦合拆开。

routing · 用分类换专精，也可以是「简单问题给小模型」

一个很实用的延伸用法：把"简单/常见"的问题路由给成本更低的小模型（比如 Claude Haiku），把"疑难/罕见"的问题路由给能力更强的模型（比如 Claude Sonnet），用分类换成本。

模式三：Parallelization（并行化）

让多个 LLM 调用同时跑，再把结果聚合。原文区分了两种玩法：Sectioning（把任务切成互相独立的子任务并行处理）和 Voting（让同一个任务跑多次，取多数结果或综合判断）。

parallelization · sectioning 拆分任务 / voting 拆分置信度

Sectioning 的一个很典型的应用是护栏机制：让一个模型专心生成回复，另一个模型专门审查内容是否合规——比让同一个调用既要回答又要自我审查效果更好，因为每次调用只需要专注一件事。Voting 常用于代码安全审查：多个 prompt 分别审查同一段代码是否有漏洞，用"多数发现"来降低误判和漏判。

模式四：Orchestrator-Workers（编排者-执行者）

这个模式和并行化在拓扑上很像，但关键区别在于子任务不是提前定义好的，而是由中枢 LLM 根据具体输入动态拆解、分派给多个 worker，再综合结果。适合那些"你没法提前预测需要拆成几步"的复杂任务——比如一次代码改动到底要动几个文件，只有看到具体需求才知道。

模式五：Evaluator-Optimizer（评估-优化）

一个 LLM 生成内容，另一个 LLM 专门负责挑毛病、给反馈，如此循环，直到评估者认为满意。这很像人类写作时"自己写、别人审、反复改"的过程。它对场景有两个前提：评估标准足够清晰；模型确实能根据反馈给出有效的改进意见。

三、真正的 Agent：什么时候该把方向盘交给模型

以上五种都还是"工作流"——路径是人定的。而真正的 Agent，是当模型具备了足够的理解、规划和错误恢复能力之后，把控制权交出去：LLM 在一个循环里持续调用工具，根据环境反馈（比如工具返回结果、代码执行结果）判断下一步该做什么，直到任务完成或触碰到终止条件（比如最大迭代次数）。

agent-loop · 循环直到完成，或触发人工介入的检查点

这类系统最典型的例子，是 Anthropic 自己在 SWE-bench 上的编码 Agent——它需要根据一份 PR 描述，自主决定要改哪些文件、怎么改，这种"步骤数量无法提前预测"的开放式问题正是 Agent 的用武之地。日常工程里更接近落地形态的，是 Claude Code 这类编码助手工作流。但代价也很直白：更高的成本，以及错误会随着步数不断累积的风险。原文的建议是——在沙箱环境里做充分测试，并配上合理的护栏，而不是直接放到生产环境里"裸奔"。

适用场景子任务边界清晰的固定流程步骤数无法预知的开放式任务

四、Agent-Computer Interface（ACI）：容易被忽视的最后一公里

原文有一个非常工程化的洞察：Agent 的失败，很多时候不是因为模型"不够聪明"，而是因为工具的接口设计得不好。这里提出了一个很有意思的类比——我们花了几十年时间打磨人机交互（HCI），却常常随手写一个 JSON schema 就把工具扔给模型。Anthropic 把这件事称为 Agent-Computer Interface（ACI），并给出了几条具体建议：

  • 格式要贴近模型"自然见过"的形式。比如要求模型输出完整文件重写，比输出精确的 diff（需要提前数好改动的行号）要容易得多；在 Markdown 里写代码，也比塞进 JSON 字符串（需要转义换行和引号）更顺手。
  • 给模型留出"思考"的 token 空间，不要让它在还没想清楚之前就被迫下笔。
  • 像写给新人同事的文档一样打磨参数名和说明，边界情况和示例用法都要写清楚。
  • 用 Poka-yoke（防呆设计）思路改造参数，让模型更难犯错。

原文举了一个非常具体的例子：在 SWE-bench 项目里，团队发现模型在切换出根目录之后，经常在使用相对路径的工具时出错；解决办法不是优化 prompt，而是直接把工具改成强制要求绝对路径——问题就消失了。这也印证了原文的另一句话：他们在这个项目上花在打磨工具本身的时间，甚至超过了打磨整体 prompt 的时间。

实践启示：落地时该怎么选、怎么避坑

把上面这些模式对照到实际项目里，有几条经验值得在动手之前先想清楚：

  1. 先用最朴素的方案验证问题。很多团队一上来就搭多 Agent 系统，结果发现问题本可以用一次带检索的单轮调用解决。复杂度应该是"因为简单方案不够用"而增加的，而不是默认起点。
  2. 先用原生 API 手写，再考虑框架。原文明确建议开发者先直接调用 LLM API 把模式跑通——很多模式几十行代码就能实现。如果一定要用框架（比如 Claude Agent SDK、AWS 的 Strands），一定要搞清楚框架底层到底在做什么，"对底层实现的错误假设"是原文点名的最常见客户错误之一。框架省的是搭积木的时间，省不了你对系统行为负责的义务。
  3. 把工具文档当成一等公民来打磨。参数命名、边界条件说明、示例用法，都值得像写给团队新人的文档那样反复推敲，并在 Workbench 之类的环境里跑大量样例，观察模型具体在哪里"犯迷糊"。
  4. 给 Agent 设计"止损点"，而不是让它无限跑下去。最大迭代次数、关键节点的人工审核、程序化的 gate 检查——这些看似"限制自由度"的设计，恰恰是 Agent 能安全上生产的前提。
  5. 透明地暴露规划过程。原文把"透明地展示 Agent 的规划步骤"列为核心原则之一，这不仅方便调试，也让人类审核者能在关键节点介入，而不是面对一个黑箱等结果。

以上第 1、4 条为原文明确观点的直接提炼；第 2、3、5 条在原文基础上结合了通用工程实践做了延伸阐述。

总结与展望

这篇文章最有价值的地方，不是提出了什么惊天动地的新技术，而是把"Agent"这个被过度包装的词，重新还原成几种可以被工程师理解、测试、组合的基本模式。它传递的核心原则可以浓缩成三句话：保持简单、保持透明、把工具接口当成一等工程问题来对待。

往前看，随着模型在长上下文理解、多步推理和错误自我纠正能力上的持续进化，"Agent"和"Workflow"之间的边界大概率会继续模糊——未来的系统很可能是两者的混合体：核心链路用可预测的工作流兜底，在需要开放式探索的局部环节，才把控制权临时交给模型。而 MCP 这类标准化协议的普及，也会让"给 Agent 接工具"这件事，从每个团队各自手搓 JSON schema，逐渐变成像装应用商店插件一样即插即用。但无论工具链怎么变，"先问自己是否真的需要 Agent、再决定复杂度"这条判断准则，大概率会一直有效——这本来就不是一个关于技术细节的结论，而是一个关于工程判断力的结论。
