🎯 问题背景：为什么切块大小如此重要？

在上一篇文章中，我们介绍了语义分块——根据文本的语义边界来切分文档。但在很多实际场景中，我们使用的仍然是固定大小的字符分块（Fixed-size Chunking）。这就引出了一个关键问题：块大小（chunk size）应该设为多少？

块大小的选择本质上是一个精度-覆盖率的权衡：

💡 直觉类比

想象你在用搜索引擎查找资料。如果每个搜索结果只给你一句话（块太小），你可能看到关键词匹配但缺乏上下文；如果每个结果给你一整章（块太大），相关信息可能被大量无关内容淹没，模型也很难抓住重点。

💻 代码解读：分块与嵌入的关键实现

4.1 文本分块函数

分块逻辑非常直接：按固定字符数滑动窗口切分文本，窗口之间保留一定的重叠（overlap），以避免在块边界处截断关键信息。

chunk_text — 固定大小重叠分块 PYTHON 
def chunk_text(text, n, overlap):
    """
    将文本分割为重叠的块。
    参数:
        text (str): 需要分块的文本
        n (int): 每个块的字符数
        overlap (int): 块之间的重叠字符数
    """
    chunks = []
    for i in range(0, len(text), n - overlap):
        chunks.append(text[i:i + n])
    return chunks

核心逻辑解读：

  • 步长为 n - overlap，即每次跳过「块大小 - 重叠量」个字符
  • 重叠量设为块大小的 1/5（如块大小 256 → 重叠 51 字符），确保边界处的语义不会完全丢失
  • 最后一个块可能不足 n 个字符，Python 的切片机制会自动处理

实验中测试了三种块大小，产生的块数量差异显著（详见后文第 7 节的图表）：

块大小 重叠量 分块数量
128 字符~26 字符326
256 字符~51 字符164
512 字符~102 字符82
🔑 关键观察

块大小翻倍，块数量近似减半。这意味着 512 的块只有 82 个向量需要索引和检索，而 128 的块有 326 个——索引规模和检索延迟会有显著差异。

4.2 嵌入向量生成

使用 OpenAI 的 text-embedding-ada-002 模型将每个文本块转化为高维向量。这个模型能捕捉文本的语义信息，使得语义相近的文本块在向量空间中距离更近。

create_embeddings — 批量生成嵌入向量 PYTHON 
def create_embeddings(texts, model="text-embedding-ada-002"):
    """为一组文本生成嵌入向量。"""
    response = client.embeddings.create(model=model, input=texts)
    return [np.array(embedding.embedding) for embedding in response.data]

# 为每种块大小批量生成嵌入
chunk_embeddings_dict = {
    size: create_embeddings(chunks)
    for size, chunks in text_chunks_dict.items()
}

注意这里直接将所有块一次性传给 API。在实际生产环境中，如果块数量很大（如本例中 128 块大小产生了 326 个块），需要考虑批量处理和速率限制。

🔍 代码解读：语义检索与回答生成

5.1 余弦相似度检索

检索的核心是计算查询向量与所有块向量之间的余弦相似度，然后取 Top-K 个最相关的块。

retrieve_relevant_chunks — 语义检索核心逻辑 PYTHON 
def cosine_similarity(vec1, vec2):
    """计算两个向量之间的余弦相似度。"""
    return np.dot(vec1, vec2) / (np.linalg.norm(vec1) * np.linalg.norm(vec2))

def retrieve_relevant_chunks(query, text_chunks, chunk_embeddings, k=5):
    """提取与查询最相关的 k 个文本块。"""
    # 1. 将查询转化为向量
    query_embedding = create_embeddings([query])[0]

    # 2. 计算查询与每个块的相似度
    similarities = [
        cosine_similarity(query_embedding, emb)
        for emb in chunk_embeddings
    ]

    # 3. 取相似度最高的 k 个块的索引
    top_indices = np.argsort(similarities)[-k:][::-1]

    return [text_chunks[i] for i in top_indices]

为什么用余弦相似度？ 因为嵌入向量的方向代表语义，余弦相似度衡量的是两个向量方向的夹角——值越接近 1，说明语义越相似。它不受向量长度（模长）的影响，更适合文本语义比较。

5.2 LLM 回答生成

将检索到的 Top-K 个块拼接为上下文，连同用户查询一起发送给 GPT-3.5-Turbo，要求其严格基于给定上下文回答。

generate_response — 基于检索上下文生成回答 PYTHON 
system_prompt = (
    "You are an AI assistant that strictly answers based on the given "
    "context. If the answer cannot be derived directly from the provided "
    "context, respond with: 'I do not have enough information to answer that.'"
)

def generate_response(query, system_prompt, retrieved_chunks,
                      model="gpt-3.5-turbo"):
    # 将检索块拼接为结构化上下文
    context = "\n".join(
        [f"Context {i+1}:\n{chunk}" for i, chunk in enumerate(retrieved_chunks)]
    )
    user_prompt = f"{context}\n\nQuestion: {query}"

    response = client.chat.completions.create(
        model=model,
        temperature=0,  # 确保输出确定性
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ]
    )
    return response.choices[0].message.content
🔑 设计细节

temperature=0 确保每次生成的结果可复现；system_prompt 中的严格约束减少了模型「幻觉」——如果上下文中没有答案，模型会直接说「信息不足」而不是编造。

📊 代码解读：忠实性与相关性评估

如何量化 RAG 管道的输出质量？本实验采用 LLM-as-Judge 方法，让 GPT-3.5-Turbo 充当评审员，从两个维度打分：

评估维度 含义 评分标准
忠实性 (Faithfulness) AI 回答是否与事实一致，有无幻觉 1.0 = 完全忠实 / 0.5 = 部分忠实 / 0.0 = 不忠实
相关性 (Relevancy) AI 回答是否切题，是否回答了用户的问题 1.0 = 完全相关 / 0.5 = 部分相关 / 0.0 = 不相关
evaluate_response — 双维度评估 PYTHON 
def evaluate_response(question, response, true_answer):
    """根据忠实性和相关性评估 AI 回答质量。"""

    # 忠实性评估：回答是否与真实答案一致
    faithfulness_prompt = FAITHFULNESS_PROMPT_TEMPLATE.format(
        question=question,
        response=response,
        true_answer=true_answer,
        full=1.0, partial=0.5, none=0.0
    )

    # 相关性评估：回答是否切题
    relevancy_prompt = RELEVANCY_PROMPT_TEMPLATE.format(
        question=question,
        response=response,
        full=1.0, partial=0.5, none=0.0
    )

    # 分别请求 LLM 评分
    faithfulness_score = float(
        client.chat.completions.create(...).choices[0].message.content
    )
    relevancy_score = float(
        client.chat.completions.create(...).choices[0].message.content
    )

    return faithfulness_score, relevancy_score
⚠️ LLM-as-Judge 的局限

使用 LLM 做评估虽然方便，但存在评分偏见和不稳定性。同一个回答多次评估可能得到不同分数。在严肃的实验中，建议结合人工评估或使用更成熟的评估框架（如 RAGAS）。

🔎 深入分析：结果背后的原因

8.1 为什么 128 和 256 得分相同？

两种块大小在这个查询上得到了完全相同的评分。可能的原因：

  • 检索到了相似的上下文：由于重叠量占块大小的 1/5，128 和 256 的块在内容上存在大量重叠，Top-5 检索结果可能覆盖了相似的文本区域
  • 单条查询的局限性：仅用一条查询做对比，结果偶然性较大，不具有统计显著性
  • 评估器的粗糙度：0/0.5/1.0 的三级评分粒度太粗，难以区分细微差异

8.2 回答偏移问题

最值得关注的是回答偏移现象：模型回答了个性化医疗而非政务应用。这说明：

💡 检索 ≠ 回答

即使检索到了相关块（相关性 1.0），模型仍可能「跑偏」。原因可能是：检索到的 5 个块中，关于政务的内容被其他主题的块「稀释」了；或者模型在整合多个上下文片段时，选择了信息量更大的段落来回答，而非最切题的段落。

📝 总结与实用建议

核心收获

✅ 本文要点

1. 块大小是 RAG 管道中最重要的超参数之一，它同时影响索引规模、检索精度和生成质量。

2. 小块（128）精度高但上下文碎片化，大块（512）上下文完整但可能引入噪声。

3. 256 字符是一个合理的默认起点，但最终选择应基于你的具体文档和查询特征。

4. 单条查询的评估不够可靠，实际项目中应在多条查询上取平均值，并使用更精细的评估指标。

实用建议

✅ 推荐做法

  • 从 256 字符开始，作为 baseline
  • 重叠量设为块大小的 10%~20%
  • 在多条查询上评估，取平均指标
  • 根据文档类型调整：结构化文档用小块，叙述性文档用大块
  • 结合语义分块（第 2 篇）使用效果更好

⚠️ 常见陷阱

  • 只看一条查询的结果就下结论
  • 忽略重叠量的影响——重叠太少会丢失边界信息
  • 盲目追求大块以「保留上下文」——可能引入大量噪声
  • 使用过于粗糙的评估指标（三级评分不够）
  • 不考虑索引成本和检索延迟
