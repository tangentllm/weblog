SECTION 01

为什么 Multi-Agent 很容易被过度设计

先看一个典型的架构图，你可能在不同团队的方案评审中见过它的变体：

七层节点，每个都有名字，每个名字后面都跟着一个 LLM 调用。评审会上很少有人说它不好——因为它看起来符合“职责单一”的直觉。

但只要追问四个问题，这个架构就会开始动摇：

Search Agent 为什么不能只是一个 Tool？

Writer Agent 为什么不能只是一个 Prompt 模板？

Reviewer Agent 为什么不能只是 Workflow 中的一个校验步骤？

Planner Agent 是否真的需要独立存在，还是一个 Router 就够了？

如果这些问题都答不出来，那么它不是 Multi-Agent Architecture，而是 Agent 数量堆砌。

拆分本身不是价值，拆分所解决的问题才是价值。 —— 本文的核心命题，也是全文所有判断的出发点

承接系列前两篇的结论：第一篇回答了“这个任务需不需要 Agent”——流程可预定义就用 Workflow；第二篇回答了“需要 Agent 后，一个够不够”——优先 Single Agent + Tools。本文回答第三个问题：当 Single Agent 开始出现复杂度问题，什么时候真正值得拆？

SECTION 02

Multi-Agent 真正解决的是什么

回答“什么时候拆”之前，先回答“为什么一个 Agent 会开始失控”。

一个健康的 Single Agent，本质是一个受控的决策空间：它接收 Context，调用 Tools，遵循 Policies，产出 Decision。

问题在于，系统会持续增长。每接一个新需求，团队的默认动作往往是：加 Prompt、加 Tool、加 Context、加 Memory、加 Policy。增长到某一天，你会得到这个：

SECTION 03

第一原则：职责边界

这是全文最重要的一节。绝大多数错误的 Multi-Agent 拆分，都发生在这一步。

不要因为“Research Agent 听起来很专业”就创建 Research Agent。创建任何一个 Agent 之前，必须回答一个问题：

这个 Agent 是否拥有独立的目标？ 如果它的目标和相邻 Agent 完全一致，它就不是 Agent，只是另一个 Prompt

举一个成立的例子：

AGENT A
Research Agent

Goal：尽可能完整地收集事实和证据。

它关心覆盖率、来源可信度、遗漏风险。允许它多花时间、多花 Token 去把事情查全。

AGENT B
Analysis Agent

Goal：基于已有证据形成判断。

它关心推理链质量、结论是否被证据支撑。它不应该再花 Token 去搜索，而是专注于判断。

这两个 Agent 的目标本质不同，甚至存在张力——Research 追求“多”，Analysis 追求“准”。把它们放在一个 Agent 里，你需要在一条 Prompt 里同时约束两种互相冲突的行为模式；拆开之后，每个决策空间只服务一个目标。这就是值得拆的职责边界。

反过来，如果所谓的 Research Agent 和 Writer Agent 目标都是“帮用户完成任务”、输入输出和评价标准完全一样，那只是给同一段逻辑起了两个名字。

SECTION 04

什么样的职责边界才是真正有效的

“有独立目标”只是第一道筛选。一个真正有效的 Agent 边界，需要同时满足四个条件：

COND 1
独立目标

Agent 有自己明确的 Objective，可以独立于其他 Agent 陈述出来。

COND 2
独立输入

它需要的数据与其他 Agent 明显不同，不需要共享完整的上游 Context。

COND 3
独立输出

它的产出可以被清晰定义，并且可以被程序或评审标准验证。

COND 4
独立评价标准

不同 Agent 的 Success Criteria 不同，可以分开打分。

用研究场景验证一遍：

Agent独立目标独立输入独立输出独立评价标准
Research Agent收集证据检索源、查询策略事实清单 + 引用Evidence Coverage
Analysis Agent形成判断证据清单结论 + 推理链Reasoning Quality
Writer Agent组织表达结论与结构要求最终报告Presentation Quality

四个条件都成立，这个边界就是天然的。如果四个条件中大部分都不存在，不建议拆 Agent——不管这个模块的名字听起来多像一个独立的“角色”。

SECTION 05

Tool、Workflow、Agent：到底应该拆成什么

发现了一个“职责边界”，下一步不是创建 Agent，而是先判断：这个职责属于哪一层？

ARCHITECTURE LADDER
Capability（能力）      →  Tool          确定性调用，无决策
Process   （流程）      →  Workflow      步骤可预先定义
Decision  （决策）      →  Agent         下一步依赖动态判断

三者的判据只有一个：这个环节里是否存在 LLM 需要做的动态决策。

5.1搜索 → 通常是 Tool

调用一次 Search API，输入 query、返回结果。没有决策空间，没有多步规划。把它包装成 Agent，你只得到了一次额外的 LLM 调用和一层的失败概率。它应该是 search(query) → results。

5.2固定流程的分析 → 应该是 Workflow

Load Data → Clean Data → Calculate → Validate。每一步做什么，工程师可以提前写死。这正是系列第一篇的结论：流程可以被提前定义的，优先 Workflow。给每一步套一个 Agent，只是把确定性问题伪装成决策问题。

5.3开放式研究 → 才可能需要 Agent

Search → Read → Discover → Re-search → Compare → Re-plan。下一步行动取决于上一步的发现，无法提前画完流程图。这里才存在真正的决策空间，才值得引入 Agent。

RULE

不是所有职责都值得成为 Agent。一个实用的自检：如果你能把这个“Agent”的行为画成一张不含分支判断的流程图，它就是 Workflow；如果你连 LLM 都不需要，它就是 Tool。

SECTION 06

第二原则：Context Isolation

职责边界解决“谁做什么”，Context 边界解决“谁知道什么”。这是生产级 Multi-Agent 最常被低估的拆分理由。

Single Agent 的 Context 是一份单一大上下文：

随着系统增长，大 Context 会带来四类问题：

问题机制典型症状
推理质量下降Context Pollution：无关信息干扰注意力客服 Agent 回答里混入风控口径
Token 成本膨胀每次调用都携带全量上下文简单查询也付出完整 Context 的费用
Prompt 管理失控一份 Prompt 服务所有职责任何修改都可能影响其他职责的表现
安全边界模糊所有数据对所有逻辑可见低权限场景意外读到高权限数据
Context Isolation 本身就是一种架构价值——即使不谈智能，仅凭它对成本、质量和安全的改善，就已经构成拆分理由。 但它有边界条件，见下
BOUNDARY

不是 Context 大就一定要拆。只有当不同职责真正需要不同的上下文，并且隔离能明显改善推理质量、Token 成本、Prompt 管理或安全边界之一时，才值得拆。如果几个“Agent”处理任务时需要的是同一份完整 Context，拆开只会强迫你在 Agent 之间反复传递这份 Context——隔离没有发生，传递成本却真实发生了（详见第 18 节的 Shared Context Hell）。

SECTION 07

第三原则：不同模型能力

当系统中同时存在多种模型时，模型差异本身会成为一条天然的拆分边界。

生产环境常见的模型池：

MODEL A
Small Model

分类、抽取、格式化。便宜、快。

MODEL B
Reasoning Model

多步推理、研究、规划。贵、慢。

MODEL C
Coding Model

代码生成与修复，针对代码语料特化。

MODEL D
Vision Model

图表、截图、文档影像理解。

这里的拆分目的不是“Agent 越多越好”，而是让不同任务使用最合适的模型。四维收益需要同时评估：

维度混合模型 Multi-Agent全用旗舰模型的 Single Agent
Cost分类任务用小模型，成本大幅下降所有任务都支付旗舰模型价格
Quality各任务用各自最优模型，但需逐个评测旗舰模型通才，专精任务可能不如专用模型
Latency简单任务走小模型，尾延迟可控简单任务被复杂任务的推理时间拖累
演进模型可按 Agent 独立升级换模型 = 全系统回归测试

注意：如果你只有一个够用的模型、所有任务对模型的要求一致，这条原则不构成拆分理由。模型隔离只在模型差异真实存在且带来可量化的成本/质量收益时成立。

SECTION 08

第四原则：权限隔离

企业级系统里，权限边界可能是所有拆分理由中最“硬”的一条。

考虑一个电商客服系统中的三种操作：

Research Agent      →  Read Only          只读知识库
Order Agent         →  Read / Modify      可查询和修改订单
Payment Agent       →  Payment Permission 可触发退款/支付
Agent Boundary = Permission Boundary

如果所有 Tool 都暴露给一个 God Agent，会发生什么：

风险机制
权限过大低风险对话路径上，模型始终持有高危工具（如退款）
Tool MisuseTool 越多，模型选错工具的概率越高，且错误后果不可控
Security RiskPrompt Injection 一旦得手，攻击面 = 全部工具的并集
Audit Difficulty审计时无法回答“谁在什么权限范围内做了这个操作”
PATTERN

Agent Boundary = Permission Boundary。每个 Agent 只持有其职责所需的最小工具集，高危操作被物理隔离在独立 Agent 内，审计日志天然按权限域分组。

BOUNDARY

Agent 拆分不是唯一安全方案，更不是充分方案。拆分只收窄了模型的选择空间，真正的安全闭环仍然需要：Policy Engine（策略引擎做最终裁决）、Authorization（工具层鉴权）、Validation（参数校验）、Audit（操作审计）、Human Approval（高危操作人工确认）。Agent 边界是纵深防御的一层，不是替代品。

SECTION 09

第五原则：并行执行

这是 Multi-Agent 最直观、最容易量化的性能收益——前提是任务真的相互独立。

当三个子任务相互独立时，总耗时从串行加和变成并行取最大：

串行：T_total ≈ T₁ + T₂ + T₃          （例如 90s）
并行：T_total ≈ max(T₁, T₂, T₃)       （例如 40s）
Parallel fan-out：收益 = 任务独立性 × 单任务耗时
BOUNDARY

并行不是免费午餐。获得 max() 之前，你需要先支付：

· Coordination——谁决定扇出哪些任务？
· Synchronization——汇聚点要等所有分支，最慢的分支决定整体（Head-of-line blocking）。
· Result merging——不同 Agent 对同一事实给出矛盾结论怎么办？
· Failure handling——一个分支失败，是整体失败、重试，还是接受部分结果？
· Partial results——超时后，两份子报告 + 一份缺失，比一份完整但延迟三倍的好吗？

如果任务之间有数据依赖（B 需要 A 的结论），并行不成立，强行拆分只剩协调成本。

SECTION 10

第六原则：独立演进

前六条原则都来自技术侧，这一条来自组织侧。

当不同能力由不同团队维护时——Research 团队维护研究能力、客服团队维护问答能力、风控团队维护风控能力——Single Agent 意味着：

One Prompt        一次修改影响所有团队
One Release       所有团队共享同一个发布节奏
One Evaluation    所有团队共用同一套评测集
One Failure Domain  一个团队的改动可以让所有人一起故障

这本质上是康威定律在 Agent 系统上的投影。Multi-Agent 允许每个团队独立持有自己的 Prompt 版本、评测集和发布节奏：

维度Single AgentMulti-Agent
Prompt 变更全系统回归仅本 Agent 回归
评测集一份混合评测集，信号互相污染每个 Agent 独立评测集
发布节奏锁步发布独立版本、独立回滚
责任归属故障定位后仍难归因到团队Agent 边界即团队边界
组织边界也可能成为 Agent 边界。 但需要警惕反面：不要为了组织结构而过度 Agent 化。如果两个团队维护的其实是同一段逻辑、共用同一份 Context 和评测标准，拆开的收益是政治性的，不是架构性的
SECTION 11

第七原则：故障隔离

生产系统中容易被忽略的价值：Multi-Agent 可以建立Failure Boundary（故障边界）。

Single Agent 中，任何一个环节的不可恢复失败，通常意味着整个请求失败。而拆分后，失败可以被降级处理：

Research Agent 失败
    ↓
Fallback：切换备用检索源重试
    ↓
仍失败 → Partial Result（标注"行业数据缺失"）
    ↓
Synthesizer 基于部分结果出报告，
并显式声明覆盖范围

“一份 80% 覆盖但按时交付、且诚实标注缺失的报告”，在很多业务里优于“等一份 100% 覆盖但随时可能整体失败的报告”。Failure Boundary 让降级成为架构能力，而不是临场发挥。

TRADE-OFF

但必须直面反面：Agent 数量增加，故障节点同步增加。Single Agent 的故障面是一个 LLM 调用链；N 个 Agent 的故障面是 N 条调用链 + 它们之间的所有协调点。Failure Boundary 带来的是“故障的可隔离性”，不是“故障的减少”——

More Agents = More Isolation + More Failure Surface

只有当你真的为每个 Agent 设计了 Retry、Timeout、Fallback 策略时，故障隔离才成立；否则拆分只是让系统以更难调试的方式失败。

SECTION 12

关键问题：什么情况下不值得拆

如果说第 3–11 节回答了“什么时候值得拆”，这一节回答同样重要的问题：哪些常见的拆分理由是伪命题。

12.1反例一：“Prompt 太长，所以拆 Agent”

为什么不成立：Prompt 太长是信息组织问题，不是决策主体问题。先尝试更便宜的手段：

Prompt 模块化     →  拆分成可组合的指令段
Tool 描述优化     →  压缩 Tool Schema，删掉冗余说明
Context Pruning   →  只保留与当前任务相关的历史
Retrieval         →  按需注入，而不是全量预置

什么时候才成立：Prompt 长的根因是职责混杂——同一段 Prompt 里写着两套互相冲突的行为规则、需要两套互斥的 Context。这时 Prompt 模块化解决不了问题，因为冲突本身就在一个决策主体内，拆分才是对的。判断标准回到第 4 节：四个边界条件是否成立，而不是字数。

12.2反例二：“Tool 太多，所以一个 Tool 一个 Agent”

为什么不成立：“20 个 Tools → 20 个 Agents”是把工具组织问题升级成了系统架构问题。Tool 数量本身有更轻的解法：

Tool Router          →  先路由到工具组，再选具体工具
Tool Grouping        →  按领域分组，每组一个命名空间
Dynamic Tool Loading →  按任务阶段动态注入工具集

什么时候才成立：当 Tool 的分组恰好对应权限边界（见第 8 节）或模型边界（见第 7 节）时——例如“支付类工具必须与对话类工具物理隔离”。这时拆分的理由是权限和模型，而不是工具数量。数量本身从来不是理由。

12.3反例三：“任务很复杂，所以必须 Multi-Agent”

为什么不成立：这是最流行也最危险的推理。复杂有两种：一种是决策复杂（下一步依赖动态判断），一种是流程复杂（步骤多但可预先定义）。后者是 Workflow 的问题域——

Step 1 Agent → Step 2 Agent → Step 3 Agent
                ✘ 错误答案

Step 1 → Step 2 → Step 3   （State Machine / Workflow）
                ✓ 正确答案

系列第一篇的结论在这里完全适用：能被工程师提前定义的流程，不该由 Agent 的 Token 去重新“决策”一遍。什么时候才成立：复杂度体现在多个彼此独立、需要不同能力、可并行推进的决策空间上——即本文第 3–11 节的边界真实存在时。复杂度是拆分的线索，天然边界才是拆分的依据。

12.4反例四：“想体现角色专业性”

Research Agent / Writer Agent / Reviewer Agent，如果它们：Context 一样、Model 一样、Goal 一样、Evaluation 一样——那么你只是给同一段逻辑起了三个名字。这时用 Prompt 模板 + 输出校验就能覆盖全部需求。四个“一样”里出现任何一个“不一样”，再回到第 4 节重新评估。

SECTION 13

Multi-Agent 最大的代价：Coordination Cost

前面所有收益都不是免费的。评估拆分时，成本侧必须和收益侧放上天平，而且要用同样的精度。

Single Agent 的执行路径是一条直线；Multi-Agent 把直线变成了一张图：

SINGLE AGENT 执行路径
Agent
 ↓
Tool
 ↓
Result

一次决策主体，一次上下文，一条故障链。

MULTI-AGENT 执行路径
Agent A
 ↓  Message
Agent B
 ↓  Message
Agent C
 ↓  Synthesis
Result

每一次箭头，都是新增的成本项。

每一跳新增的成本项：

成本项具体含义被低估的程度
Message PassingAgent 间通信的序列化、Schema 设计、版本兼容通常被低估 10 倍
State Sync哪个 Agent 持有真相？冲突以谁为准？几乎总被低估
Context Transfer下游 Agent 需要多少上游 Context？传多传少都出错Token 成本的主要来源
Result Validation上游输出的格式/质量校验，失败后重试策略Debug 时间的主要来源
Error Handling每个协调点的超时、重试、降级故障面随跳数相乘
Routing“下一个该谁上”本身成为一个新的决策问题Router 自己也会出错
Multi-Agent 的系统复杂度不是随 Agent 数量线性增长的。 System Complexity ≈ Σ Agent Complexity + Coordination Complexity + State Complexity + Evaluation Complexity

其中 Coordination Complexity 大致随交互边数增长——3 个 Agent 串成一条链是 2 条边，3 个 Agent 两两自由通信是 3 条边加状态一致性问题。这就是为什么通信模式本身需要被架构约束（第 14 节），而不是放任 Agent 自由对话。

Evaluation 也同步变难：Single Agent 只需评价“最终结果好不好”；Multi-Agent 需要同时评价每个 Agent 的独立指标（第 4 节的四个条件此时成为资产）加上系统级端到端指标，而两者的归因关系并不总是清晰。

SECTION 14

Agent 之间的三种基本协作模型

本文不展开通信协议与消息 Schema——那属于后续文章《Multi-Agent 协作与通信》。这里只建立最小的心智模型：Agent 拆开之后，协调关系基本落入三种模式。

模式协调方式适用注意
Handoff控制权在 Agent 间移交线性场景：售前 → 交付 → 售后移交链过长时延迟累积
Supervisor中心调度器决定派发任务可分解、需要全局编排Supervisor 本身是新的故障点和瓶颈
Shared State通过共享状态读写协作并行 Agent 需要沉淀共同事实并发写冲突、状态一致性

本文只需要记住一件事：无论选哪种模式，只要 Agent 拆分了，协调成本就必然发生。模式选择的本质，是决定这份成本以什么形状分布。

15.2第二版：需求增长，Single Agent 开始失控

半年后，需求演化为：行业趋势、竞品分析、企业工商信息、财务数据、政策研究、新闻追踪、数据图表。Single Agent 开始出现可观测的症状：

症状对应第几节的原则
Prompt 膨胀：七种研究各自的行为规范写在一条 Prompt 里，互相干扰职责隔离（§3）
Context 污染：财务 Agent 不需要政策全文，却背着全部检索历史推理Context Isolation（§6）
Tool 泛滥：60+ 工具，错误调用率上升能力专业化（§5）
策略差异：财务数据需要精确查询（结构化 API），新闻需要模糊检索（语义搜索）模型/能力差异（§7）
时延不可接受：三个独立子课题本可以并行，却被串成 6 分钟并行执行（§9）
评测失焦：无法单独回答“竞品分析做得好不好”独立评价（§4）

注意：这些症状指向的不是“该上 Multi-Agent 了”，而是系统中已经出现了天然边界——行业、竞品、财务三个子领域，恰好满足第 4 节的四个条件：独立目标（各自的研究范式不同）、独立输入（不同的数据源）、独立输出（各自的子报告）、独立评价（各自的覆盖率指标）。

V1 不拆是对的，V3 拆也是对的。变的是需求的复杂度，不变的是判断方法：先找天然边界，再算 Value > Cost。

SECTION 18

Multi-Agent 的三个危险信号

即使按决策树走到了 Multi-Agent，也要在运行中持续监测这三个反模式。它们一旦出现，通常意味着边界设计出了问题。

ANTI-PATTERN 01
Agent Explosion（Agent 爆炸）

1 个需求 → 拆出 10 个 Agent → 半年后 20 个。每个 Agent 只完成一个很小的动作，系统图变成毛线团。

诊断：如果某个“Agent”的行为可以用一张无分支的流程图描述，它应该是 Workflow；如果它连决策都没有，它应该是 Tool。数量从来不是专业度的证明。

ANTI-PATTERN 02
Chatty Agents（喋喋不休的 Agent）

A → B → A → B → C → A → B……Agent 之间高频往返通信。结果：Token 爆炸、延迟爆炸、一次失败的 Trace 长到没人读完，Debug 变成考古。

诊断：频繁通信说明职责被切在了错误的层面——本该在一个决策空间内完成的多步推理，被强行分散到多个主体之间。Agent 边界可能设计错误，合并比优化通信协议更有效。

ANTI-PATTERN 03
Shared Context Hell（共享上下文地狱）

名义上拆成了 Agent A / B / C，实际上三者共享同一份巨大 Context，所有数据对所有 Agent 可见。

诊断：你没有获得 Context Isolation，只获得了额外的调用开销——你只是把一个 God Agent 拆成了几个函数。回到第 6 节：隔离必须真实发生，否则拆分的核心理由不成立。

SECTION 19

八条生产级原则

把全文压缩成可以直接贴在架构评审文档首页的八条：

01
先问职责是否独立，而不是先问能不能拆。
“可以拆”和“应该拆”之间隔着第 4 节的四个条件。
02
Tool 解决能力扩展，Workflow 解决流程控制，Agent 解决动态决策。
三层各归其位，是避免 Agent Explosion 的根本方法。
03
Context Isolation 是拆 Agent 的重要理由。
但隔离必须真实发生——共享大 Context 的多 Agent 是伪拆分。
04
Permission Boundary 可以成为 Agent Boundary。
同时记住：拆分只是纵深防御的一层，Policy Engine、鉴权与审计不可省略。
05
能够并行执行的独立任务，是 Multi-Agent 的高价值场景。
前提是任务真正独立，且你已设计好同步、合并与部分结果的策略。
06
不同模型能力可以成为 Agent 拆分边界。
目的是让每个任务用最合适的模型，收益要按 Cost / Quality / Latency 分别验证。
07
Multi-Agent 引入的协调成本必须被显式计算。
通信、状态同步、Context 传递、失败处理——低估协调成本是 Multi-Agent 项目失败的首要原因。
08
如果拆分不能降低复杂度，就不要拆。
复杂度的守恒与转移：拆分把 Agent 内复杂度转化为 Agent 间复杂度，只有后者更可控时，拆分才有意义。
SECTION 20

结论

不要用“Multi-Agent 更先进”作为结论。正确的决策路径始终是：

Single Agent
  ↓ 复杂度增加
  系统中出现天然边界？（§3–§11）
    ├── No  → 优化 Single Agent（多数情况的最优解）
    └── Yes → 拆分收益 是否 > 协调成本（§13、§16）
             ├── No  → 保持 Single Agent
             └── Yes → Multi-Agent（并显式设计协调机制）
Multi-Agent 的价值不是把一个 Agent 变成很多 Agent，而是把一个不可控的复杂系统，拆成多个可以独立理解、独立评估、独立演进的决策单元。
“真正成熟的 Multi-Agent 架构，
不是‘拆得足够细’，而是‘每一次拆分都有理由’。”
