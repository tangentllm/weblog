MemoryBank 深度拆解：给 LLM 装一颗会遗忘的大脑

模型能聊得很好，但它真的"认识你"吗？从论文原理到生产级 Agent 记忆架构，站在资深 LLM 应用工程师的视角重新理解这篇 AAAI 2024 论文。

📄 arXiv:2305.10250 · AAAI 2024 🏫 中山大学 / 哈工大 / KTH ⏱ 约 14 分钟阅读

如果你最近在做 AI Agent 或者陪伴型聊天机器人，大概率已经绕不开"长期记忆"这四个字。RAG、向量数据库、摘要压缩……各种方案层出不穷。但这些方案背后，有一篇容易被忽略却值得重读的早期工作，第一次系统地把"记忆该如何存、如何取、如何忘"这三件事捏合到了一起——它就是 MemoryBank，最终发表于 AAAI 2024。

引言：模型会聊天，但它真的"认识你"吗？

LLM 可以在一段对话中表现得非常聪明，却不意味着它拥有真正的长期记忆。它能使用当前 Context，却不会天然地把几个月前的重要经历沉淀成稳定、可持续更新的用户认知。2023 年上半年 ChatGPT 的爆发，让所有人第一次意识到大语言模型可以"聊"得像个人；但只要对话拉长到几天、几周，问题就会暴露：模型记不住你上周提过的烦恼，更谈不上理解"你是一个什么样的人"。

这不是简单地把上下文窗口从 4K 扩到 128K 就能解决的问题——真正的长期陪伴场景，比如心理咨询助手、私人秘书、AI 伴侣，需要的是模型能在几个月甚至几年的时间尺度上，有选择地记住重要的事，同时不被无关信息淹没。MemoryBank 没有把长期记忆简单理解成"更大的 Context"，而是把 Memory 独立成一个系统能力：记忆的形成、存储、检索、摘要、用户画像，以及随时间变化的更新，这正是它值得被重新翻出来读的原因。

背景与动机：Context Window ≠ Long-Term Memory

笔者补充 · 工程师视角

从 LLM 应用架构的角度看，"聊天记录""上下文"和"长期记忆"其实是三层不同的东西：聊天记录是原始事件流；Context 是当前一次推理真正送给模型的信息；Memory 则是经过选择、压缩和保存之后，未来还能再次影响 Agent 行为的信息。为什么不能把全部历史直接塞进 Prompt？一是 Context Window 依然存在边界；二是历史内容并非都与当前问题相关，大量噪声会稀释关键事实；三是反复传输旧消息会带来 Token 成本与延迟。这三层区分论文本身没有明说，但理解它是读懂 MemoryBank 设计初衷的前提。

在 MemoryBank 出现之前，业界处理长对话记忆大致有两条路径，但都有明显短板。一是持续拼接历史消息，随着对话变长成本迅速失控；二是基于记忆增强神经网络（如 Neural Turing Machines）的路线，通过外部可读写的记忆矩阵扩展模型容量，但这类方法主要停留在学术研究阶段，也没有真正解决"记忆如何随时间自然演化"的问题。此外，一些面向长程对话数据集的研究（如围绕多轮众包对话构建的长期对话数据集）通常只覆盖有限的几轮交互，跟真实场景里动辄跨越数周、数月的陪伴式对话相去甚远。

作者观察到，这些方案共同缺失了两样东西：一是用户画像的持续演化——AI 应该像朋友一样随相处时间增长而对你有更深理解，而不是每次对话都从零开始；二是拟人化的遗忘机制——人类记忆本身就是有损压缩的，重要的事反复被提起会被强化，无关紧要的细节会自然淡忘。这恰恰是让 AI "更像人"而不是"数据库查询接口"的关键，MemoryBank 正是围绕这两个缺口设计的。

核心原理与技术架构

MemoryBank 的整体设计可以概括为三根支柱：记忆仓库（Memory Storage）、记忆检索（Memory Retrieval）、记忆更新（Memory Updating），三者环环相扣，构成一个闭环系统。

3.1 记忆仓库：不只是流水账

论文原意

MemoryBank 的存储系统会记录带时间戳的多轮原始对话，用来支撑精确检索；同时把每日对话浓缩成"每日事件摘要"，再进一步聚合成"全局摘要"，形成鸟瞰视角。用户画像采用同样的三层结构——先总结当日展现出的性格与情绪特征，再逐步聚合成稳定的全局人格描述。这一整套摘要与归纳完全依赖 LLM 自身完成，论文给出的提示词大致是"总结对话中的事件和关键信息"以及"根据对话总结用户的性格特征和情绪"。

这套三层结构相当于把"短期事件"逐步加工成"长期认知"：原始事件适合回溯细节，摘要适合构造长期上下文，Profile 更适合回答"这个用户是谁"。这也是为什么今天做 Agent Memory 时，不应该只是把所有对话原样丢进 Vector DB 里当成一堆 chunk。

3.2 记忆检索：一次"面向过去"的 RAG

论文原意

检索环节本质上是一次类似 Dense Passage Retrieval 的开放域问答任务：每条历史对话或事件摘要被编码成向量表示，整个记忆库预先用 FAISS 建好索引；当用户说出新的一句话，这句话同样被编码成向量去记忆库中做相似度检索，取出最相关的若干条记忆拼进当前对话 Prompt。这套流程用 LangChain 落地，英文场景用 MiniLM 做编码器，中文场景用 Text2vec，编码器本身可插拔替换。

# Memory Retrieval（示意）
def retrieve_memory(query, memory_bank, top_k):
    # 第一步：把当前这句话编码成向量，作为检索的 query
    query_vec = encoder.encode(query)
    # 第二步：在预先建好索引的记忆库里做相似度检索，取回最相关的 top_k 条
    memories = index.search(query_vec, top_k)
    return memories

# 调用示例：K 是希望召回的记忆条数，越大越全面，但也越容易引入噪声
memories = retrieve_memory(user_input, bank, top_k=K)
# 第三步：把召回的记忆和已有的对话历史一起拼进 Prompt
prompt = build_prompt(history, memories)
# 第四步：交给 LLM 生成最终回答，回答中就能引用到历史记忆
answer = llm.generate(prompt)
笔者补充 · 工程师视角

可以把 Memory Retrieval 理解成一种特殊的 RAG：普通 RAG 检索的是外部知识库，Memory 检索的是"这个 Agent 与这个用户过去发生过什么"。区别在于，普通 RAG 的知识库通常是静态的，而 Memory 会随着后续互动不断被修改、强化甚至覆盖——这正是接下来"记忆更新"要解决的问题。

3.3 记忆更新：遗忘曲线的工程化简化

论文原意

只会写入和检索的系统，最终必然面临记忆膨胀。MemoryBank 因此借鉴心理学中经典的艾宾浩斯遗忘曲线理论，为每条记忆维护一个随时间衰减、又能被重新强化的"强度"值。

R = e−t / S

其中 R 是记忆保留率，t 是距离上次学习/强化经过的时间，S 是记忆强度（随学习深度和重复次数变化）。为了简化工程实现，论文把 S 建模成一个离散值：

# R：当前的记忆保留率（0~1 之间，越大表示越容易被想起）
# t：距离上次学习/强化经过的时间
# S：记忆强度，初始固定为 1，之后会随"被回忆"的次数增长
def retention(t, S):
    # 指数衰减：t 越大、S 越小，R 衰减得越快，即记忆越容易被遗忘
    return math.exp(-t / S)

# 每条记忆第一次出现在对话中时：memory.S = 1, memory.t = 0

# 当这条记忆在后续对话中被检索命中（即被"回忆"起来）时调用：
def on_memory_recalled(memory):
    memory.S += 1   # 记忆强度 +1：被复习/提及的次数越多，之后越难被遗忘
    memory.t = 0    # 遗忘计时器清零：重新从"刚学过"的状态开始衰减

直觉上理解：一条记忆刚被存入时强度最低，随时间流逝被成功提取的概率呈指数下降；但只要它在某次对话中被重新提起、成功命中检索，强度就会加一，遗忘速度随之变缓——这正是心理学"间隔效应"（复习会让记忆更牢固）的工程化实现。

笔者补充

论文作者自己也坦诚这是一个"高度简化"的模型，真实的人类记忆机制还涉及"过度学习""意义效应"等更复杂的因素。但作为工程近似，这个离散化的强度衰减模型已经足够捕捉"越常提越难忘"这一核心行为——对今天的 Agent 开发者来说，真正值得学习的不是这套公式本身，而是"记忆写入之后仍需要生命周期管理"这个设计原则。

为了验证这套机制的通用性，作者打造了具体应用 SiliconFriend——一个 AI 陪伴聊天机器人，分别接入闭源的 ChatGPT 和开源的 ChatGLM、BELLE 三个基座模型，其中开源模型部分还额外用 3.8 万条心理咨询对话数据做了 LoRA 微调（rank=16，训练 3 个 epoch），让模型在共情能力上更进一步，这一步和记忆机制本身是解耦的两件事，共同构成"有记忆 + 有温度"的产品闭环。

论文原意 · 案例

用户在 5 月 3 日提到"最近压力大、睡眠不好"，AI 给出了运动、听音乐、阅读、找朋友聊天等建议；一周后用户问"你之前建议我用什么方法缓解压力来着"，三个版本的 SiliconFriend 都能准确复述当时的建议，其中 ChatGPT 版本还能在复述基础上做进一步的解释和延展，而不只是机械地"背书"。

实验与结果分析

作者的评测分为定性和定量两部分。定性分析通过真实用户对话展示共情陪伴对比、记忆召回准确性、基于人格画像的个性化回应；定量实验则构造了一个覆盖 10 天、15 个虚拟用户（人格设定各不相同）的模拟记忆库，每天至少覆盖两个话题，全部由 ChatGPT 代入不同人格自动生成对话，并在此基础上人工编写了 194 道记忆探测问题（中英文各 97 道），考察模型在数天后能否准确回忆此前提到的细节。

评测采用四个维度：记忆检索准确率、回答正确性、上下文连贯性，以及三个模型变体之间的相互排名得分：

语言模型检索准确率回答正确性上下文连贯性排名得分
英文SiliconFriend (ChatGLM)80.9%43.8%68.0%0.498
SiliconFriend (BELLE)81.4%47.9%58.2%0.517
SiliconFriend (ChatGPT)76.3%71.6%91.2%0.818
中文SiliconFriend (ChatGLM)84.0%41.8%42.8%0.510
SiliconFriend (BELLE)85.6%60.3%56.2%0.565

数据来自论文的模拟长期对话实验。Retrieval 衡量相关记忆是否被找回；Correctness 衡量最终回答是否正确；Coherence 衡量回答与上下文及记忆之间的一致性。

几个值得注意的规律：第一，检索准确率普遍不低（71%～86%），说明基于向量检索的记忆召回机制本身相当可靠，验证了 MemoryBank 架构对不同基座模型的通用性；第二，ChatGPT 版本在"回答正确性"和"连贯性"上明显领先，说明记忆系统只是地基，最终答案质量很大程度上仍取决于底座模型自身的推理与表达能力。

笔者补充 · 工程师视角

这个实验对今天做 Agent 有一个非常重要的启示：Memory Recall ≠ Answer Quality。最典型的例子是 ChatGLM 中文实验：检索准确率高达 84.0%，是全表最高，但回答正确率只有 41.8%，是全表倒数第二。也就是说，找到正确的记忆只是第一阶段，后面仍然存在 Context Construction（如何把召回的记忆组织进 Prompt）、Reasoning 和 Generation 环节的误差——评估一个记忆系统时，检索指标和最终答案质量必须分开衡量，不能只看召回率。

从论文走向生产：今天应该如何设计 Agent Memory？

该技术最适合的场景很明确：陪伴型聊天机器人、心理支持类应用、需要跨会话保持上下文的私人助理/秘书类 Agent——凡是"用户会持续、反复地和同一个 AI 交互数周乃至数月"的场景，都值得引入类似的分层记忆结构。如果把 MemoryBank 放进现代 Agent 系统，笔者不会简单照搬它，而会把 Memory 独立成 Agent Runtime 的一层基础能力：

具体可以参考三条落地原则：第一，区分 Memory 类型——Episodic Memory 保存"发生过什么"，Semantic Memory 保存从历史事件中沉淀出来的稳定事实，Profile Memory 保存长期偏好和用户属性，这比论文里"事件摘要 + 用户画像"的二分更细一些，方便针对不同类型设置不同的衰减速率。第二，不要让所有对话永久入库，应加入重要性、置信度、来源和时间等元数据。第三，必须支持事实冲突处理，例如用户过去喜欢跑步、现在明确表示不再跑步时，旧事实应该被更新而不是让两条记忆永久并存——这一点论文完全没有涉及，是 MemoryBank 架构里比较明显的一个缺口。

# 每次对话结束后调用一次，负责把这轮对话"消化"成记忆
def memory_pipeline(conversation):
    # 第一步：从原始对话里抽取出候选的记忆片段（事实、偏好、事件等）
    candidates = extract_memories(conversation)

    for m in candidates:
        # 第二步：去已有记忆库里找语义相近的旧记忆，判断是否在讲同一件事
        related = retrieve_similar(m)

        # 第三步：如果新旧记忆冲突（比如"喜欢跑步"vs"不再跑步了"），
        # 用新记忆覆盖/合并旧记忆，而不是让两条互相矛盾的记忆同时存在
        if has_conflict(m, related):
            m = resolve_conflict(m, related)

        # 第四步：只有"重要"的记忆才写入长期存储；
        # 不重要的记忆直接走衰减/丢弃逻辑，避免记忆库无限膨胀
        if is_important(m):
            upsert(m)          # 写入或更新记忆库
        else:
            decay_or_discard(m) # 降权或直接丢弃

    # 第五步：无论单条记忆是否重要，都用这批候选去更新用户的长期画像
    update_profile(candidates)

需要注意的坑：一是摘要质量高度依赖底座模型能力，弱模型生成的每日摘要如果本身有偏差，会在层层聚合后被放大，这一点也能解释上一节 ChatGLM 召回高但正确率低的现象；二是遗忘机制需要谨慎调参，衰减太快用户会觉得"AI 记性差"，衰减太慢又失去了压缩存储、聚焦重点的意义；三是错误记忆的影响是持续性的，它不像一次 RAG 检索出错那样只影响单轮回答，可能在未来很多轮对话中持续误导 Agent，因此生产系统建议为每条记忆保留 `memory_id`、`source`、`created_at`、`confidence`、`importance`、`ttl` 等元数据，并支持用户查看、修正和删除。

创新与局限

MemoryBank 的核心贡献，是较早把长期记忆明确拆解为 Storage、Retrieval、Updating 三个环节，并第一次把"遗忘"这个此前几乎被忽视的环节，用一个源自心理学的经典理论提供了简单却可解释的数学模型。它同时验证了外部 Memory 可以与不同 LLM 后端（闭源 / 开源、中文 / 英文）自由组合，而不必把全部记忆写进模型参数。

笔者补充

但从今天的 Agent 工程视角回看，它的局限也很明显：记忆强度模型较为简单，只有"衰减"和"命中强化"两种状态，没有真正的重要性打分；记忆形成主要依赖摘要与 Prompt Engineering，缺少更系统的事实抽取、实体级合并和冲突解决机制；实验的时间跨度（10 天）和用户规模（15 人）相对有限，能否扩展到数月甚至数年的真实陪伴场景仍待验证。因此，它更适合作为理解 Agent Memory 的架构起点，而不是今天可以直接部署到复杂企业场景的完整方案。

总结与展望

MemoryBank 真正值得记住的，并不是某个具体的 Embedding 模型，也不只是遗忘曲线公式，而是它把一个容易被忽略的问题正式化了：Agent 需要管理自己的过去。当系统从一次性问答进入长期服务，RAG 解决的是"外部知识能否被正确检索"，Memory 解决的则是"什么应该被记住、为什么记住、何时使用、如何更新、何时忘记"——这会直接影响个人助手、智能客服、销售 Agent、陪伴 Agent 乃至 Multi-Agent 系统的长期稳定性。

放在今天回看，这篇论文更像是一份"设计范式"而非终局方案：检索环节可以直接替换为如今更强的 Embedding 模型和向量数据库，摘要环节可以结合更精细的记忆分类继续演化，简化的遗忘曲线也完全可以被更复杂的重要性评估模型取代。但"记忆需要有衰减、需要能被强化"这个核心洞察，在 Agent 记忆系统持续爆发的今天，依然是每个从业者值得认真对待的设计原则——毕竟，一个什么都记得、什么都不忘的 AI，未必是一个真正"懂你"的 AI。设计生产级 Agent 时，比"要不要加一个向量数据库"更重要的问题始终是：Agent 到底应该记住什么？这些记忆如何形成、验证、更新和删除？这才是 Memory System 真正的工程边界。
