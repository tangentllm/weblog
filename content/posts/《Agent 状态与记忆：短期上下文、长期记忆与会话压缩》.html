01Agent 为什么需要状态与记忆

先从一个我真实遇到过的生产场景说起。

某新能源汽车销售 Agent，用户第一次使用时说：

"我是做新能源汽车销售的，主要负责华东地区，客户 mostly 是 fleet 采购方。"

几天后，用户回来：

"帮我准备一份客户跟进话术。"

一个合格的 Agent 应该知道：这是 fleet 采购客户、在华东、属于 B 端销售场景，话术应该面向采购决策链，而不是个人消费者。

一个平庸的实现会怎么办？把历史所有 Session 的所有消息全部拼进 Prompt。用户用了三个月后，Prompt 里塞着 300k token 的对话历史，其中 90% 是一次性问题和过期的 Tool 输出——成本翻了 30 倍，Latency 从 2 秒涨到 20 秒，而模型反而开始混淆"用户上周说过预算 50 万"和"上上个月说过预算 80 万"。

这暴露了 Agent Memory 的核心矛盾：

Agent 需要记住过去，但 LLM 不应该看到全部过去。

解决这个问题，你需要同时回答三个问题：

  1. 当前任务进行到哪里了？（State）
  2. 过去发生了什么，什么值得继续记住？（Memory）
  3. 这一次模型调用，到底给它看什么？（Context）

大部分 Memory 系统的失败，不是因为没有存储，而是因为没有把这三个问题分开。

02State、Context、History、Memory 的边界

先建立一张我认为最值得钉在墙上的表：

表 1 · 六个核心概念的定义边界
概念解决的问题生命周期数据特点
History过去发生过什么长期原始记录，append-only
Context当前模型需要知道什么单次请求精选信息，有 Token 预算
State当前任务进行到哪里Task / Session当前运行状态，结构化
Short-Term Memory当前任务需要保留什么Session高频变化，易失
Session Summary历史被压缩后留下什么Session / 长期压缩信息，有损
Long-Term Memory跨 Session 什么值得保留长期稳定、有价值、有置信度

两个关键认知：

Memory ≠ Chat History。History 是流水账，Memory 是从流水账中提炼出的、带有元信息（类型、置信度、来源、时效）的可用知识。

Storage 只是 Memory 的一部分，Context 才是最终进入 LLM 的信息边界。你存了一万条记忆，但如果每次调用只召回三条不相关的，Memory 系统等于不存在。

更准确地表达：

Memory 是对历史信息进行写入、存储、检索、更新、压缩、冲突处理和淘汰的一套机制；Context 则是某一次模型调用实际获得的信息集合。

03Agent State：被忽视的"运行时记忆"

这是我见过最多团队踩坑的地方——把 State 和 Memory 混为一谈，或者干脆没有 State，让 Agent 的"进行状态"隐式地活在 Chat History 里。

State 和 Memory 的根本区别一句话说清：

State： "现在进行到哪里？" Memory： "过去发生了什么，什么值得继续记住？"

一个任务型 Agent 的 State 长这样：

JSON · task_state.json
{
  "goal": "完成客户跟进方案",
  "current_step": "生成第二版话术",
  "pending_action": "等待用户确认",
  "retry_count": 1,
  "tool_status": {
    "crm_lookup": "succeeded",
    "draft_generator": "completed_v2"
  },
  "workflow_node": "refine_draft",
  "intermediate_results": {
    "draft_v1_rejected_reason": "语气过于正式"
  }
}

State 至少包含这些维度：

  • Task State：目标、当前步骤、已完成/未完成子任务
  • Workflow State：处于工作流哪个节点、哪些分支已走过
  • Tool State：每个工具调用的状态、是否持锁、幂等键
  • Pending Actions：等待用户确认的事项、定时任务
  • Intermediate Results：中间产物（草稿 v1 被否的原因）
  • Retry State：重试次数、上次失败原因、退避时间

为什么 State 必须独立存在、不能依赖 Chat History？三个理由：

  1. 可恢复。进程崩溃后，从 State 快照恢复任务，而不是让 LLM 重新读历史"推理出"自己进行到哪一步——那既贵又不可靠。
  2. 可重试。重试需要知道 retry_count 和幂等键，这些是结构化事实，不是自然语言能稳定表达的。
  3. 可暂停。用户说"先停一下，我明天继续"，Agent 明天必须知道 pending_action: 等待用户确认，而不是靠回放全部对话。

State 更像 Agent 的 Runtime Snapshot，Memory 更像 Agent 的知识沉淀。前者驱动执行，后者注入 Context。

04短期上下文：Agent 的 Working Memory

Short-Term Context 是单次模型调用的工作记忆，典型构成：

  • 最近对话轮次
  • 当前用户请求
  • 当前任务目标与计划
  • 最近的 Tool Calls 及其 Results
  • 临时变量（scratchpad）
  • 未完成任务清单

为什么不能走"全部历史 → Prompt"这条最简单的路？随着 Session 增长：

表 2 · 全量历史进 Prompt 的代价
问题后果
Token 成本上升线性甚至超线性增长，生产成本失控
Latency 上升Prefill 时间变长，用户体验崩坏
Context Noise 增加无关历史稀释关键信息，模型"分心"
Tool Result 污染早期的大体积 JSON 输出长期驻留
历史错误持续传播模型早期的误判被后续轮次不断引用

最后一条尤其隐蔽：模型第 5 轮给了一个错误结论，第 40 轮时它还在引用这个错误，因为"历史里写着"。完整历史给了错误信息与正确信息同等的地位。

完整历史 ≠ 有效 Context。历史是记录，Context 是预算内的信息精选。

这张表也解释了为什么两者不能共用一套机制：短期记忆的问题是"太满"，长期记忆的问题是"太脏"——前者靠压缩解决，后者靠准入和生命周期管理解决。把短期上下文直接"落库"变成长期记忆，等于把满和脏两个问题合成了一个。

05长期记忆：什么真正值得保存

长期记忆至少覆盖五类：

  • 用户事实：职业、所在地区、客户类型
  • 用户偏好：喜欢简洁回复、偏好摄氏度、习惯中文输出
  • 稳定身份信息：账号角色、组织归属
  • 长期任务：正在进行的项目、待办承诺
  • 可复用经验：之前同类问题的有效解法

这里必须正面回答一个反直觉的问题：

为什么"什么都记"反而会让 Agent 变得更差？

因为 Memory 的下游是 Retrieval + Context Injection。记的越多：

  • 检索噪声越多，无关记忆挤占 Token 预算
  • 冲突概率越高（新旧信息打架）
  • 过期信息污染回答（Stale Memory）
  • 用户一旦要求"忘掉"某件事，你根本不知道它扩散到了哪些记忆条目里

所以需要一个 Memory Admission Policy（记忆准入策略），本质是对每条候选记忆打分：

Admission Score = Persistence × Utility × Confidence
  • Persistence：这条信息是长期稳定，还是临时性/一次性的？"我现在有点累"不该入库；"我负责华东地区"应该入库。
  • Utility：未来任务中会被用到吗？用户随口一句废话，Utility 接近零。
  • Confidence：来源是用户明确声明（高），还是 LLM 从对话推断（低）？推断需要更低的默认分数。

准入维度展开：

  1. 是否长期有效（TTL 估计）
  2. 是否未来有用（与用户任务画像的匹配度）
  3. 是否用户明确表达（explicit vs inferred）
  4. 来源是否可信（用户原话 > 模型推断 > 工具副作用）
  5. 是否值得存储成本（一条记忆的写入、检索、维护成本不为零）

Long-Term Memory 不是 Chat History Archive。它是有准入门槛、有质量分、有生命周期的知识库。

06Memory Record：长期记忆应该长什么样

生产级的 Memory 条目至少长这样：

JSON · memory_record
{
  "id": "mem_123",
  "user_id": "u_001",
  "type": "preference",
  "content": "用户偏好简洁的技术文章",
  "confidence": 0.92,
  "source": "explicit_user_statement",
  "session_id": "sess_20260115_084",
  "created_at": "2026-01-15T10:23:00Z",
  "updated_at": "2026-03-02T08:11:00Z",
  "expires_at": null,
  "supersedes": "mem_098",
  "version": 2,
  "access_count": 17,
  "last_accessed_at": "2026-06-10T14:00:00Z"

为什么不能只是 "user said xxx" 一段裸文本？因为缺少了这些字段，你后面所有机制都建不起来：

一个只有裸文本的 Memory 系统，等冲突发生时你只能回答"两条都在，随缘"。

07Memory Read / Write Pipeline：把 Memory 当成一个数据系统

很多人把 Memory 理解成"调用一次 embedding 然后 write"，这不是 Memory 系统，这是记忆垃圾桶。生产级的 Memory 是读写闭环：

Memory 不是"存进去"，而是"读写闭环"。只设计写入的 Memory 系统，等于只修了下水道的上半截。

08Memory Lifecycle：记住之后怎么办

记忆不是 write once, read forever。完整生命周期：

各阶段要处理的工程问题：

  • Memory Update：用户说"我现在改用华氏度了"——不是新增一条，而是更新旧条目（或新条目 supersede 旧条目）。
  • Memory Expiration / TTL：临时性信息（"我这周在外地出差"）设置 TTL，到期自动降权或删除。
  • 用户主动修改：提供用户可编辑的记忆视图，用户改过的条目 confidence 拉满、source 标记为 user_edited。
  • 用户要求忘记："忘掉我说过的事"——必须能定位到具体条目并硬删除。这就是为什么裸文本 Memory 不行：你不知道"这件事"对应哪些条目。没有 type、没有 scope 的记忆，删除等于误伤或漏删。
  • 版本化：每次更新保留版本链，可回溯，也用于排查"Agent 为什么突然变了一个说法"。
  • Memory Garbage Collection：基于 TTL + access_count + confidence 的定期清理。半年没被访问、置信度中下的推断类记忆，是 GC 的首要目标。

长期记忆不是永久事实，而是带有时间和可信度的信息。你保存的不是"真相"，而是"截至某时刻、以某种置信度成立的说法"。

09Memory Conflict：记忆为什么会互相矛盾

最典型的场景：

旧记忆：用户在上海工作 (mem_045, 2026-01, confidence 0.95) 新证据：用户现在在北京工作 (本轮对话, explicit, 2026-06)

如果两条都注入 Context，模型输出大概率变成精神分裂："您在上海……也提到北京……"。

冲突处理管道：

Resolution Policy 的优先级序列（从高到低）：

  1. 用户明确声明 > 一切："不对，我在上海"——直接覆盖，无论旧记忆多自信。
  2. 来源可信度：explicit_user_statement > user_edited > inferred > tool_side_effect。
  3. 时间优先：同等可信度时，新信息覆盖旧信息（现实世界人会换工作、换偏好）。
  4. 无法仲裁时不硬选：当置信度接近且来源同级，宁可两条都保留但标记冲突状态，在注入时附加"以下两条信息存在时间上的演变，以较新为准"，让模型有元认知。
  5. 版本化：任何覆盖都产生新 version，旧版本不物理删除（除非用户要求），保证可回滚。

最坏的策略是"后写赢，且不留痕迹"——你将永远无法回答用户"你之前为什么一直说我在上海"。

背景：个性化写作助手项目，用户 1 月说"我是后端工程师"，6 月转岗后说"我现在做解决方案架构"。旧实现是 append-only：两条记忆都在，检索时按相关度都可能命中。结果是 7 月起用户连续投诉 Agent "人格分裂"——技术建议夹杂售前话术风格。

排查与修复：我们把两周内的 4,200 条活跃记忆跑了冲突对账（同 user + 同 type + embedding 相似度 > 0.82 再人工比对），发现 11% 存在类似新旧并存。修复后写入管道强制走 Conflict Detection，同型冲突默认"新覆盖旧 + supersede 链"，用户明确声明绝对优先。

教训：没有冲突仲裁的 Memory 系统，跑半年后十分之一的记忆是互相打架的。

10会话压缩：Context Compression

长 Session 必须压缩，这不是可选项而是成本项。四种主流策略：

Sliding Window

只保留最近 N 轮。实现最简单，问题也最明显：第 3 轮确立的预算约束，第 40 轮被切掉了，Agent 开始推荐超预算的方案。

Conversation Summary

把被裁掉的历史用 LLM 压成摘要。摘要质量完全取决于压缩 Prompt 的设计（见第 11 节）。

Structured State

把历史压缩成结构化状态而非自由文本：

JSON · structured_summary
{
  "goal": "为 fleet 客户挑选跟进方案",
  "constraints": ["预算 50 万以内", "非 SUV", "需支持车队管理 API"],
  "decisions": ["最终确定 B 方案"],
  "open_questions": ["B 方案交付时间未确认"],
  "preferences": ["话术偏正式", "需要数据支撑"]
}

这对任务型 Agent 是保真度最高的压缩方式——约束、决策结构化地活下来，而不是赌摘要模型"记得"提它们。

11Compression 的核心：不是变短，而是保留有效信息

这一节是整个压缩话题的灵魂。

Compression 本质上是一种信息损失。问题不是"压得多短"，而是"丢了什么"。

反例：

原始信息： 预算 50 万以内 不要 SUV 必须支持车队管理 API 最终确定 B 方案 朴素摘要： 用户最终选择 B 方案

压缩率很高，看起来很干净。但下一轮用户问"那 C 方案呢？"，Agent 已经不知道预算上限和"非 SUV"的约束了，开始自由发挥。关键约束全部丢失，压缩变成了失忆。

所以我要提出这个观点：

做 Decision-Relevant Compression（决策相关压缩），而不是长度最小化压缩。

压缩时优先保留的信息类别：

  • Goal：任务目标是什么
  • Constraint：硬约束（预算、格式、禁止项）——最高优先级
  • Decision：已做出的决定及其理由
  • Dependency：决策之间的依赖关系
  • Pending Task：未完成事项
  • User Preference：影响输出形态的偏好
  • Important Tool Result：影响决策的关键工具输出（如 CRM 查到的客户等级）

摘要 Prompt 应该明确指令："先提取约束和已做决策，再概括过程；宁可摘要长一点，不可丢失任何约束。" 压缩率是预算的奴隶，不是目标。

这就是后面第 20 节最终架构的 Context Builder 的四个输入源。

13Memory Storage Architecture

一个常见误区："上 Vector DB 就完事了"。

生产级 Memory 不是一个 Vector Database 打天下。按访问模式选存储：

Memory 类型推荐存储原因

SummaryDB / KV直接读取，整块注入
Execution TraceLog / OLAP只用于调试与审计，永不进 Prompt

为什么 User Facts 用 KV 而不是 Vector DB？因为它的访问模式是精确的：构建 Context 时，该用户的职业、地区是必然要注入的，不需要"语义相似检索"，直接 get(user_id) 更快更可靠。语义检索只服务于"模糊召回"的场景。

不同类型的信息应该根据访问模式选择不同存储，而不是根据"是不是 Memory"统一选型。

一个务实的落地形态：主存储用 Postgres（Memory Record 全量字段），语义检索用一个 Vector 索引层（pgvector 或独立 Vector DB）做 ANN，Redis 承担 Session State 和热点缓存。三套东西，一个逻辑 Memory 系统。

14Tool Calling 与 Memory

Tool-heavy Agent 很容易掉进另一个坑：把 Tool 执行痕迹当记忆存。

必须严格区分：

Execution Trace ≠ Memory

一次 Tool Calling 产生：

Request / Arguments / Result / Retry / Error / Intermediate Result

这些全部属于 Runtime / Trace，归宿是日志和审计系统，而不是 Memory Store。

什么才可能从 Tool 执行中沉淀为 Long-Term Memory？只有跨任务稳定的用户偏好，例如：

  • 用户长期偏好摄氏度（从天气工具调用的反复参数修正中推断）
  • 用户长期偏好 Markdown 表格输出（从多次格式反馈中确认）

判断标准还是那把尺子：Persistence × Utility × Confidence。一次性的 CRM 查询结果是 Temporary Data，用户稳定的输出格式偏好才够格进 Memory。

大量执行信息不等于大量值得记忆的信息。把 Trace 当 Memory 存，等于给 Memory Store 倒垃圾，最后检索质量全面崩塌。

15Memory Retrieval：什么时候应该读取长期记忆

不能每次请求都全量加载 Memory——那回到了"全量历史塞 Prompt"的老路。

需要建一个 Memory Retrieval Gate：

Query Intent ← 这类意图通常需要记忆吗？ + Task Type ← 任务画像与记忆类型的匹配 + Memory Relevance ← 检索召回的相关度分数 + Memory Confidence ← 召回条目自身的置信度

四者综合，决定整条漏斗：

是否需要记忆？ ↓ 是 召回哪些？ ← Top-K 语义召回 + 结构化过滤（user_id 隔离） ↓ 过滤哪些？ ← 相关度 < 阈值、过期、低置信度的丢弃 ↓ 最终进入 Context 哪些？ ← Token 预算内裁剪 + 按类型排序注入

实践中的 Gate 判断举例：

  • "今天天气怎么样" → 不需要 Memory（或仅注入偏好类：摄氏度）
  • "帮我准备客户话术" → 需要（用户事实 + 偏好 + 长期任务）
  • "什么是 RAG" → 不需要
  • "接着上次那个方案改一下" → 需要（长期任务 + Session Summary + State）

Memory Retrieval 的目标不是找更多，而是找最相关的信息。Over-Retrieval 的害处不亚于 Under-Retrieval——它用噪声挤占了本该留给 Recent Context 和 Structured State 的 Token 预算。

背景：最初我们把 Retrieval Gate 做成了简单的意图分类器，结果踩了两个方向的坑。第一版过于保守——通用问答类请求一律不召回，用户问"帮我像上次那样整理成表格"时，Gate 判定"格式请求，无需记忆"，但"上次那样"恰恰指向记忆里的格式偏好，False Negative。

矫枉过正：第二版几乎全量召回，Context 从平均 3.8k tokens 涨到 11k tokens，成本涨了近 3 倍，而 Task Success 只提升了 1.2 个百分点——典型的 Over-Retrieval，多花的 Token 大部分在给模型喂噪声。

最终方案：Gate 输出三档决策（不召回 / 仅偏好类 / 全量漏斗），并在日志里记录每次决策，离线用探针问题回放校准阈值。

教训：Gate 不是一次性写对的分类器，而是需要数据回灌持续校准的策略组件。

16Production Failure Modes

真实生产里，Memory 系统的故障长这样。每个按 现象 → 原因 → 排查 → 解决方案 展开。

16.1 记忆污染MEMORY POLLUTION
现象
Agent 开始输出与用户无关的信息，"听说您在成都工作？"——用户从没去过成都。
原因
跨用户记忆泄漏（检索时 user_id 过滤失效），或 Trace 混入 Memory，或早期 Prompt Injection 让某用户写入污染数据。
排查
按用户维度导出 Memory 记录，做交叉 diff；检查 Retrieval 的过滤条件是否真的带上了 user_id。
解决
检索层强制 user_id 隔离（硬编码，不靠调用方自觉）；写入层来源标记；注入前做 ownership 校验。
16.2 记忆幻觉MEMORY HALLUCINATION
现象
Agent "记得"用户从没说过的事，且言之凿凿。
原因
Write Path 中 LLM 推断被当作事实存储（source=inferred 却给了高 confidence），摘要压缩时模型自行脑补细节。
排查
溯源该记忆的 created_at 和 session_id，回放原始对话，确认用户是否真的说过。
解决
inferred 类记忆强制低 confidence、标记 type，注入时用"（推断）"字样弱化；压缩 Prompt 禁止添加原文没有的信息。
16.3 检索失效MEMORY RETRIEVAL FAILURE
现象
记忆明明存了，但 Agent 表现得像不知道。
原因
embedding 模型升级后索引未重建；query 与记忆表述风格差异过大；K 值过小；门控误判"不需要记忆"。
排查
对失败 case 手动跑一遍检索，看相关记忆的召回排名；检查 Gate 的决策日志。
解决
embedding 版本化，升级时全量重嵌入；混合检索（语义 + 关键词）；Gate 决策记录日志可回放。
16.4 过度召回OVER-RETRIEVAL
现象
Context 里塞了 30 条记忆，Token 爆炸，回答反而变差。
原因
没有相关性阈值，只按 Top-K；没有 Token 预算控制。
排查
看 Context Token Count 指标随记忆条数的增长曲线。
解决
相关度硬阈值 + 动态 K；Memory 注入区域设独立 Token 预算；注入条数上限。
16.5 过期记忆STALE MEMORY
现象
用户换了工作半年后，Agent 还在说"您在上海负责华东"。
原因
没有 TTL；access_count 很高导致 GC 不敢清理；没有更新触发机制。
排查
对高频访问记忆做定期"事实核验"（在合适时机主动向用户确认关键事实）。
解决
事实类记忆设置复核周期（如 6 个月）；用户行为与记忆矛盾时触发更新管道。
16.6 记忆冲突MEMORY CONFLICT
现象
见第 9 节，新旧信息打架，Agent 输出自相矛盾。
原因
写入时跳过 Conflict Detection，两条矛盾记忆并存。
排查
冲突记忆对账（同 user + 同 type 语义矛盾检测任务，离线跑）。
解决
见第 9 节仲裁管道，版本化 + supersede 链。
16.7 压缩丢失COMPRESSION LOSS
现象
长会话后期，Agent 忘记了早期确立的硬约束，推荐超预算方案。
原因
摘要 Prompt 没有约束保护条款；压缩时约束被"概括"掉。
排查
构造约束记忆测试集，长会话回放后检查约束保留率（Compression 前后 diff）。
解决
Constraint 白名单字段，压缩永不丢弃；Structured State 承载约束。

背景：我们的客服 Agent 上线 Summary 压缩后，Compression Ratio 稳定在 85%，单次调用成本降了约 60%，跑了两个月没出事——直到分析长会话（>40 轮）工单时发现，"违反用户早期约束"类投诉占比从 2% 涨到 6%，翻了 3 倍。

根因：摘要把"只发邮件、不要打电话"这类否定性约束压没了——摘要模型把它判定为"非重点动作"。

85%
Compression Ratio
−60%
单次调用成本
2%→6%
约束违反投诉占比（3×）

修复：分两步——约束类信息改走 Structured State 白名单，物理上禁止进入摘要管道；同时摘要 Prompt 加了反向检查："逐条列出原文中的禁止性表述"。两周后该类投诉回落到 2.5%。

教训：摘要模型对"不要做什么"的注意力，天然低于"要做什么"。

16.8 注入失败CONTEXT INJECTION FAILURE
现象
检索成功了，但 Agent 没用上。
原因
注入位置太靠前被"lost in the middle"稀释；注入格式模型不敏感；模板渲染 bug 导致内容为空。
排查
导出实际发送的完整 Prompt 检查——永远要有原始 Prompt 的 trace。
解决
关键记忆注入在 System 区靠后 + 用户消息前；结构化分块 + 明确标签；注入层单元测试。

17Memory Evaluation：如何证明 Memory 真有用

一个必须先立的规矩：

Observability ≠ Evaluation。

Observability 回答"系统发生了什么"；Evaluation 回答"Memory 到底有没有提高 Agent 效果"。

你可以在 Dashboard 上看到"已保存 5000 条记忆、召回率 95%"——然后用户满意度纹丝不动。因为召回率高 ≠ 召回的对、 ≠ 用得上。

Memory Evaluation 指标体系：

TEXT · eval_metrics
── 写入侧 ──────────────────────────────
Memory Write Accuracy      ← 写入的记忆是否真实（对照原始对话标注）
Memory Precision           ← 写入的里面多少是对的
False Write Rate           ← 不该记却记了

── 读取侧 ──────────────────────────────
Memory Recall              ← 应该被用到的记忆，实际被注入的比例
Memory Precision           ← 注入的记忆里，真正相关的比例
Memory Relevance           ← 注入记忆与当前任务的相关度评分

── 质量侧 ──────────────────────────────
Memory Conflict Rate       ← 冲突记忆对占比
Stale Memory Rate          ← 过期记忆占比
Memory-induced Error Rate  ← 因记忆错误直接导致的回答错误率

── 最终指标 ─────────────────────────────
Task Success Rate          ← 一切上层指标最终服务于此

其中最值得投入标注资源的是两类错误：

应该记住，却没有记住 → False Negative（漏记） 不应该记，却记住了 → False Positive（误记）

False Negative 伤害个性化体验，False Positive 伤害正确性。两者的代价不对称——生产上通常宁可漏记（退化成无记忆的通用回答），不可误记（输出错误事实），所以准入阈值应偏保守。

构建 Eval 集的实操方法：录制真实多 Session 对话 → 人工标注"应记忆信息点"清单 → 回放对话跑 Memory 系统 → 在后续 Session 用探针问题（"我上次的预算是多少？"）验证记忆可用性 → 计算上述指标。

Memory 系统应该以任务成功率和信息质量，而不是"保存了多少条记忆"作为最终评价标准。

18Observability：如何知道 Agent 到底记住了什么

Evaluation 管离线，Observability 管在线。Memory 系统的最小指标集：

80% 看起来很漂亮，对吧？但必须同时观察：

单独的高压缩率只说明"扔得多"。如果压缩率 80% 的同时 Task Success 从 85% 掉到 62%，这个压缩策略在生产上是灾难。所以我建议每个压缩策略上线时都做 A/B：对照组（低压缩率高保真）vs 实验组，核心指标是 Task Success，Compression Ratio 只作为成本侧指标。

19Security：Memory 的权限与隐私边界

轻量但必要的生产视角，不展开成合规文章，只讲 Agent 工程。

核心隔离原则：

User A Memory ≠ User B Memory ≠ Organization Memory

三层记忆（Personal / Org / Public）必须在存储和检索两层都显式标注 scope，检索时按当前请求身份过滤。Org 层记忆的写入要更严格——因为污染会扩散到全体成员。

需要明确的权限问题清单：

  • Sensitive Data Filtering：写入管道前置过滤器，身份证号、银行卡、密码类内容在入库前脱敏或直接拒绝。不是"存了再防读取"，是"根本不存"。
  • User-level Isolation：硬编码在 Retrieval 层，不依赖上游正确传参。
  • Organization-level Memory：团队共享知识（如"本团队方案模板走 D 流程"），有独立的准入和审计。
  • Access Control：谁能读、谁能改、谁能删，Memory Record 上要有 scope 字段支撑。
  • Memory Delete：用户"忘掉我说的"请求必须能执行到硬删除级别（包括向量索引中的副本！——常见漏洞：删了主库，向量库里的 embedding 还能被检索到）。
  • Audit：每条记忆的写入、读取、修改、删除都要有日志，回答"Agent 为什么说了这句话"时能溯源到具体记忆条目。

工程上的底线是：什么可以记、什么不能记、谁可以读取、谁可以修改、谁可以删除——这五个问题在设计阶段就要有答案，而不是出事后补丁。

20完整生产级 Memory Architecture

把前面所有东西拼起来：

核心是 Context Builder 这个组件：所有信息源（State、近期上下文、摘要、长期记忆）汇聚于此，经过统一的 Retrieve → Rank → Filter → Compress → Token Budget 管道后拼装成最终 Prompt。它是对"Context 是最终信息边界"这一原则的组件化落地。

Context Builder 的伪代码（Python 风格）：

Python · context_builder.py
def build_context(session, user_query, budget: TokenBudget) -> Prompt:
    # ---------- 1. 不可压缩区：结构化 State ----------
    state = state_store.get(session.id)              # Redis
    state_block = render_state(state)                # goal/constraints/decisions/pending

    # ---------- 2. 长期记忆：Gate + 检索漏斗 ----------
    memory_block = ""
    if memory_gate.needs_memory(user_query, session):        # 意图/任务类型判断
        candidates = memory_store.hybrid_search(             # 语义 + 结构化过滤
            query=user_query,
            filters={"user_id": session.user_id},            # 硬隔离
            k=20,
        )
        candidates = [m for m in candidates
                      if m.relevance > RELEVANCE_THRESHOLD   # 相关度过滤
                      and not m.is_expired()]                 # TTL 过滤
        ranked = rank(candidates,                             # 相关性+置信度+时效
                      weights=(0.5, 0.3, 0.2))
        memory_block = render_memories(
            ranked[: budget.memory_top_k],                    # 条数上限
            annotated=True,                                   # 标注来源与置信度
        )

    # ---------- 3. 会话摘要：本 Session 更早历史 ----------
    summary_block = summary_store.get(session.id) or ""

    # ---------- 4. 近期上下文：原文最近 N 轮 ----------
    recent_block = render_messages(
        session.messages[-RECENT_TURNS:]
    )

    # ---------- 5. Token 预算分配与裁剪 ----------
    # priority 语义统一：数值越小，预算不足时越先保留
    blocks = [
        (state_block,   priority=1, compressible=False),  # 约束/决策，永不丢弃
        (recent_block,  priority=2, compressible=False),  # 近期轮次，尽量原文保留
        (memory_block,  priority=3, compressible=True),   # 记忆可裁剪、可合并
        (summary_block, priority=4, compressible=True),   # 摘要可二次压缩
    ]
    prompt = assemble_within_budget(blocks, budget.total)

    # ---------- 6. 触发压缩（后台异步，不阻塞本次请求） ----------
    if session.token_estimate() > COMPRESS_THRESHOLD:
        async_task.submit(compress_session, session, state)

    return prompt


def compress_session(session, state):
    """Decision-Relevant Compression：约束/决策走 Structured State，过程走摘要"""
    structured = extract_structured(                    # constraints/decisions 永不丢
        session.messages, protected=["constraint", "decision", "pending_task"])
    summary = llm_summarize(
        session.messages,
        prompt=SUMMARY_PROMPT,                          # 禁止脑补，保留约束
        preserve=state.constraints,
    )
    state_store.merge(state, structured)                # 更新 State
    summary_store.set(session.id, summary)              # 覆盖旧摘要

关键设计解释：

  1. State 块 priority=1 且不可压缩——约束丢失是任务型 Agent 最贵的失败。
  2. Memory 走完整漏斗——Gate 判断、user_id 硬过滤、相关度阈值、置信度排序，一个不少。
  3. 记忆带标注注入——（用户于3月明确提到） 让模型知道信息来源，降低被低置信推断误导的概率。
  4. 压缩异步化——压缩本身要调 LLM，放请求关键路径上会显著加 Latency。

※最终结论

回到开头那个问题：如果明天让我设计一个真正上线的 Agent State & Memory System，我的答案浓缩为三句话。

PRINCIPLE 01

State 管当前，Memory 管过去，Context 决定当前给 LLM 看什么。

三者角色不重叠：State 是 Runtime Snapshot，驱动执行、支撑恢复与重试；Memory 是带元信息的知识沉淀；Context Builder 是唯一的信息闸门。任何一个混进另一个，系统就开始在故障排查时让你怀疑人生。
PRINCIPLE 02

长期记忆保存稳定、有价值、高置信度的信息，而不是保存所有历史。

Memory Admission Policy（Persistence × Utility × Confidence）、读写闭环、生命周期管理、冲突仲裁——这些机制的存在，都是为了让 Memory 越用越准，而不是越用越脏。存了多少条记忆不是成绩，Task Success 才是。
PRINCIPLE 03

Context Compression 的目标不是最大限度压缩，而是在 Token 成本与信息损失之间找到最优点。

Decision-Relevant Compression：约束、决策、待办结构化永存，过程可摘要，垃圾可丢弃。Compression Ratio 是成本指标，不是质量指标——必须与 Memory Recall 和 Task Success 联合观测。

所以，不要把 Agent Memory 理解成"让 AI 永远记得更多"。

它真正的定义是：

在有限 Context、Token 和成本下，让 Agent 持续获得对当前任务真正有价值的信息。

记住的从来不是越多越好——记住对的，忘掉错的，管理好中间的一切。这才是生产级 Agent Memory 的全部工程学。
