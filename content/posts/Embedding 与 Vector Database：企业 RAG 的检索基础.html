企业级 RAG 架构设计与工程实践 · 第 5 篇

Embedding 与 Vector Database：
企业 RAG 的检索基础

文 / 清言（资深 AI 应用架构师）

一、开篇：从“关键词搜不到”开始

在企业落地 RAG 时，我们经常遇到这样一个令人沮丧的场景：

📄 知识库文档

“移动端弱网环境下的实时音视频连接稳定性优化方案”

🔍 用户提问

“网络很差的时候怎么降低 RTC 卡顿？”

传统的关键词搜索面对这种情况往往束手无策。为什么？因为 Query 里的词（“网络”、“差”、“卡顿”）和 Document 里的词（“弱网”、“稳定性”、“优化”）在字面上几乎没有重叠。

但人类一眼就能看出它们讲的是同一件事。这就引出了企业 RAG 的核心问题：如何让机器理解“意思相近但词不同”的两个文本？

二、Embedding 到底解决什么问题？

很多教程会告诉你：“Embedding 把文本变成了一串数字。” 这句话没错，但没讲透。

作为一名架构师，我更愿意这样定义：

Embedding 的本质，是把文本映射到一个高维向量空间，让“语义相近的文本”在这个空间中尽可能接近，让“语义无关的文本”尽可能远离。

在这个空间里，Retrieval 的问题就从“字符串是否匹配”，变成了“向量是否相似”。

三、为什么向量能够表达语义？

不要把 Embedding 模型神话成它“理解了人类思想”。它实际上通过海量数据训练，学到了一种非常适合做相似性计算的表示空间。

试想：

  • “退款流程” 和 “如何申请退款”：在向量空间中，距离极近。
  • “退款流程” 和 “如何修改头像”：在向量空间中，距离很远。

模型训练的目标，就是让这种距离关系符合人类的直觉。

四、Embedding Pipeline

在企业架构中，Embedding 是一条明确的流水线。最重要的是：Document Embedding 和 Query Embedding 必须处于同一个向量空间，否则就是鸡同鸭讲。

五、Cosine Similarity

我们如何衡量两个向量的距离？在 RAG 领域，余弦相似度 是最常用的指标，因为它关注的是“方向”而非“长度”。

$$ \cos(\theta) = \frac{A \cdot B}{\|A\|\|B\|} $$

其中：

  • A · B：点积，衡量两个向量在方向上的重叠程度。
  • ||A||：向量的模（长度）。

核心洞察：相似度越高，意味着夹角 θ 越小，两个向量在空间中的“指向”越一致。

六、Inner Product / Cosine / Euclidean

在工程实现中，这三种度量方式经常让人混淆。这里直接给结论：

Metric 数学含义 是否需 Normalize 工程特点
Euclidean 两点间的直线距离 否 直观，但对向量长度敏感，不常用。
Cosine 夹角余弦值 否 (逻辑上) 关注语义方向，抗干扰能力强。
Inner Product 点积 是 (通常) 计算最快。如果向量已经做了 L2 归一化，Inner Product 在数学上等价于 Cosine。
工程技巧： 大多数向量数据库内部使用 Inner Product 进行检索，原因仅仅是计算速度最快。我们只需要在写入数据前做一次 L2 Normalize 即可。

七、Embedding Model 到底怎么选？

企业实践不是模型比武大会。选型时我通常关注以下维度：

  • 中文能力：如果业务主要在国内，BGE (BAAI General Embedding) 系列往往优于 OpenAI。
  • 领域适应性：医疗、法律等垂直领域需要微调模型。
  • 向量维度：直接影响存储和内存。
  • 部署成本：私有化部署通常首选 BGE 或 E5，而不是依赖昂贵且数据出境的 OpenAI。

八、为什么 Embedding 维度不是越高越好？

维度从 384 到 3072，并非线性增长带来的收益。

📈 维度越高

  • 语义表达能力通常越强
  • 能容纳更精细的信息

📉 维度越高

  • 存储成本翻倍 (索引文件巨大)
  • 内存占用爆炸
  • 检索延迟显著增加

对于大多数通用场景，768 维往往是效果与成本的最佳甜点。

九、Embedding 的长度与 Chunking 的关系

回顾上一篇我们讨论的 Chunking。Embedding 的效果直接受制于 Chunk 的质量：

  • Chunk 太长：信息密度过大，多个主题混在一起，Embedding 被强制“平均化”，导致特征模糊。
  • Chunk 太短：上下文缺失，缺乏充分的语义信息，向量指向性不强。

十、Query Embedding 与 Document Embedding

很多新手容易犯的错误是：随便拿一个模型分别对 Query 和 Doc 编码。

实际上，现代 Embedding 模型（如 BGE, E5）通常采用非对称检索 思路：

  • Document：通常是长文本，包含详细描述。
  • Query：通常是短文本，甚至是疑问句。

训练时，模型会专门针对这种差异进行优化（例如给 Query 加上指令前缀 "represent this sentence for searching relevant passages:"）。请务必在代码中遵循模型官方推荐的 Instruction 模板。

代码实践：Embedding 与 归一化

from sentence_transformers import SentenceTransformer
import numpy as np

# 加载模型 (以 BGE 为例)
model = SentenceTransformer('BAAI/bge-base-zh-v1.5')

# 1. 准备数据
docs = ["移动端弱网环境下的实时音视频连接稳定性优化方案", 
        "网络很差的时候怎么降低 RTC 卡顿？"]

# 2. 带上 Instruction (非常重要！)
query_prefix = "为这个句子生成表示以用于检索相关文章："
docs_with_prefix = [query_prefix + d for d in docs]

# 3. 生成 Embedding
embeddings = model.encode(docs_with_prefix)

# 4. 关键步骤：L2 Normalization
# 归一化后，Dot Product == Cosine Similarity
def normalize(vectors):
    norms = np.linalg.norm(vectors, axis=1, keepdims=True)
    return vectors / norms

norm_embeddings = normalize(embeddings)

# 5. 计算相似度 (使用点积模拟余弦相似度)
similarity = np.dot(norm_embeddings[0], norm_embeddings[1])
print(f"Similarity: {similarity:.4f}")

十一、离线 Embedding 与在线 Embedding

在生产环境中，我们严格区分离线和在线流程：

  • 离线：处理所有历史文档，支持 Batch 处理，最大化 GPU 利用率。支持重试、幂等性校验。
  • 在线：处理用户 Query，要求极低延迟。通常使用 CPU 推理或轻量级 GPU。

十二、Embedding Cache

用户提问往往具有重复性。在 Query 进入 Embedding 模型前，先做一层基于 Redis 的 Hash 查询。

警示： Cache Key 必须包含 {model_version}。否则当你升级模型版本后，旧缓存产生的向量将严重污染检索结果。

十三、Vector Database 到底解决什么问题？

既然有了向量，存在 MySQL 里不行吗？

当数据量从 1 万涨到 1 亿时，暴力计算 的成本是不可接受的。每次查询都要和所有向量算一遍距离？这会拖垮系统。

Vector Database 的核心价值就是解决海量数据下的高维向量检索性能问题。它不存储数据本身，而是存储一种加速结构（索引）。

十四、ANN 是什么？

ANN 代表 Approximate Nearest Neighbor（近似最近邻）。

它的核心思想是：为了速度，我们愿意牺牲一点点精度。 我们不再保证找到 100% 最近的那一个，但能极快地找到 Top-K 个“足够近”的。

  • Exact Search (暴力)：100% Recall，耗时随数据量线性增长。
  • ANN Search (近似)：95%-99% Recall，耗时与数据量对数相关。

十五、HNSW

HNSW (Hierarchical Navigable Small World) 是目前企业落地最主流的索引算法。你可以把它想象成多层高速公路网：

搜索时，算法先从最顶层的稀疏网络快速定位到大概区域，然后逐层下沉到最底层进行精细搜索。

关键参数 Trade-off：

  • efSearch：搜索时扫描的邻居数量。efSearch 越大，Recall 越高，但 Latency 越高。

十六、IVF 与 PQ

除了 HNSW，还有两种常见的加速技术：

  • IVF (Inverted File Index)：聚类索引。把向量空间划分成几千个桶，搜索时只去最近的几个桶里找，极大缩小搜索范围。
  • PQ (Product Quantization)：乘积量化。把一个长向量切成好几段，每段单独聚类压缩。能显著降低存储，但会损失精度。

十七、Vector Database 与 Search Engine 的边界

很多架构师困惑：“我是用 Milvus 还是 Elasticsearch？”

答案是：成年人全都要。

  • Vector DB (Milvus/Qdrant)：专精于 Dense Retrieval（向量检索）。
  • Search Engine (ES)：专精于 Sparse Retrieval（关键词 BM25）、Metadata 过滤、文本高亮。

企业级架构通常是两者并存，或者使用像 Elasticsearch 这样本身就支持 dense_vector 的全能型引擎。

十八、主流 Vector Database 如何选择？

没有绝对的最优，只有最适合：

维度 FAISS Milvus Qdrant ES / OpenSearch
核心定位 算法库 分布式向量数据库 轻量级/云原生向量DB 搜索引擎 (带向量能力)
分布式能力 弱 (需自建) 极强 (云原生) 强 (Raft) 极强
Metadata Filter 不支持原生过滤 支持 支持且强大 支持 (基于倒排)
运维复杂度 低 (库) 高 (多组件) 中 中
适合场景 本地实验、离线评估 海量数据、多模态 中规模、RAG 应用 已有 ES 基础设施、混合检索

十九、FAISS 为什么仍然重要？

虽然 FAISS 不算一个完整的“数据库”（没持久化、没 CRUD 接口），但在 POC 阶段和离线评估中，它依然是王者。不过从 FAISS 迁移到 Milvus 等生产级 DB 时，你需要自己解决数据一致性、备份和监控问题。

二十、企业向量索引设计

不要只存 Vector！一个合格的 Row 必须包含：

{ "vector": [...], "doc_id": "abc-123", "tenant_id": "tenant_x", "version": "v2", "perm_level": 1, "update_time": 1678888888 }

没有 Metadata，Vector DB 就是瞎子。我们经常需要在向量检索后，根据 tenant_id 或 version 进行过滤。

二十一、一次 Vector Retrieval 到底发生了什么？

当用户问：“RTC SDK 4.6.2 Android RTC-10027 怎么处理？”

# 伪代码流程：Vector Search
def vector_search(query_text, top_k=5):
    # 1. Query Embedding
    q_vec = embedding_model.encode(query_text)
    
    # 2. ANN Search (向量近似搜索)
    # Vector DB 内部通过 HNSW 算法快速寻找
    raw_candidates = vector_db.search(
        vector=q_vec, 
        limit=top_k * 2 # 多取一些，因为后续还要过滤
    )
    
    # 3. Metadata Filtering (后过滤或预过滤)
    final_results = []
    for item in raw_candidates:
        # 比如必须匹配 Android 平台
        if item.metadata.get('platform') == 'Android':
            final_results.append(item)
            
    return final_results[:top_k]

二十二、为什么 Vector Search 不是 RAG 的终点？

召回语义相似文档 ≠ 召回真正最相关文档。

比如，用户问“RTC 4.6.2 的 Bug”，向量检索很可能把 RTC 4.5.0 和 4.6.1 的文档都召回，因为它们在语义上极度相似。但在工程上，版本号必须精确匹配。这时，纯向量检索就不够了，必须引入关键词匹配或结构化过滤。

二十三、常见失败案例

❌ 失败 1：维度迷信

认为 3072 维的模型一定比 768 维的好。结果存储成本翻 4 倍，检索延迟超时，但效果提升微乎其微。

❌ 失败 2：版本污染

升级 Embedding 模型后，直接复用旧的 Vector DB 索引。旧向量与新 Query 向量不在同一空间，导致 Recall 接近 0。

❌ 失败 3：盲目暴力流

千万级数据仍使用 FLAT（暴力）索引，导致每次查询耗时数秒，完全无法在线服务。

二十四、最终企业 Embedding + Vector Search 架构

二十五、工程 Trade-off

更大的 Embedding Model ↔ 更低延迟

更高向量维度 ↔ 更高存储成本

更高 efSearch ↔ 更高 Recall / 更高 Latency

更频繁重新 Embedding ↔ 更高数据一致性

二十六、最终结论

Embedding 建立了语义表示，Vector Database 提供了高效的检索引擎。这两者构成了 RAG 系统的“双腿”。然而，正如我们在第二十二章所看到的，向量检索并非万能。

在真实的企业级场景中，为了解决“版本号精确匹配”或“专有名词强匹配”的问题，我们通常需要结合传统搜索技术：

Dense Retrieval (Vector) + Sparse Retrieval (BM25) + Metadata Filtering + Reranking
