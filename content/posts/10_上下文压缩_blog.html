一、问题动机：检索回来的内容，太多"噪声"怎么办？

在前面的篇章中，我们陆续用语义分块、上下文增强、重排序、相关段落提取等手段提升了检索质量。但检索质量高并不等于送入 LLM 的上下文质量高。

典型场景：你检索了 10 个文本块（每块约 1000 字符），总共约 10000 字符的上下文。但其中可能只有 30% 的内容与用户查询真正相关——其余都是"陪跑"的噪声文本。

⚠️ 噪声上下文带来的三大问题
  • Token 浪费：大量无关内容占用上下文窗口，增加 API 调用成本
  • 注意力稀释：LLM 的"注意力"被无关信息分散，容易遗漏关键细节
  • 幻觉风险：无关文本中可能包含与答案矛盾的信息，诱导模型产生幻觉

上下文压缩（Contextual Compression）的核心思路：在检索之后、生成之前，用 LLM 对每个检索块进行"信息提纯"——只保留与查询相关的内容，丢弃噪声。

二、什么是上下文压缩？

上下文压缩是一种后检索（post-retrieval）技术。它不改变检索策略本身，而是在检索结果送入生成模型之前，增加一道"压缩"工序：

四、三种压缩方式详解

本系列实现了三种不同的压缩策略，它们在"保真度"和"压缩率"之间各有取舍：

🔵 Selective（选择性保留）

  • 保留与查询直接相关的原始句子
  • 不改写，保留原始措辞
  • 保持文本原始顺序
  • 压缩率适中（~72%）
  • 信息保真度最高

🟢 Summary（摘要）

  • 生成简洁摘要
  • LLM 重新组织语言
  • 只关注与查询相关的信息
  • 压缩率高（~86%）
  • 可能丢失细节

🟠 Extraction（提取）

  • 逐字提取相关句子
  • 只输出原文中的匹配句
  • 用换行符分隔
  • 压缩率最高（~89%）
  • 最激进，可能丢失上下文
💡 如何选择？

Selective 是最安全的默认选择——它保留原始措辞，不会引入改写偏差。Summary 适合需要极度精简的场景（如上下文窗口紧张）。Extraction 最激进，适合查询非常聚焦、只需"一句话答案"的场景。

五、核心代码：compress_chunk 函数

所有三种压缩方式都通过同一个函数 compress_chunk() 实现，区别仅在于系统提示（System Prompt）：

def compress_chunk(chunk, query, compression_type="selective",
                   model="gpt-3.5-turbo"):
    """
    压缩从检索中获取的文本块，仅保留与查询相关的内容。
    """
    # ---- 根据压缩类型选择不同的系统提示 ----
    if compression_type == "selective":
        system_prompt = """你是一位信息过滤专家。你的任务是分析文档片段，
并仅提取与用户查询直接相关的句子或段落。删除所有不相关的内容。

你的输出应当：
1. 仅包含有助于回答查询的文本
2. 保留相关句子的原始措辞（不要改写）
3. 保持文本的原始顺序
4. 包含所有相关内容，即使看起来冗余
5. 排除任何不相关的文本"""

    elif compression_type == "summary":
        system_prompt = """你是一位摘要专家。你的任务是创建一个简洁的摘要，
专注于与用户查询相关的信息。

你的输出应当：
1. 简明扼要地涵盖与查询相关的信息
2. 仅关注与查询相关的信息
3. 省略不相关的细节
4. 以中立、事实的语气撰写"""

    else:  # extraction
        system_prompt = """你是一位信息提取专家。你的任务是从文档片段中
仅提取包含与用户查询相关信息的句子。

你的输出应当：
1. 仅包含原文中与查询直接相关的句子
2. 保留原始措辞（不要修改文本）
3. 用换行符分隔提取的句子
4. 不要添加任何评论或额外文本"""

    # ---- 构造用户提示 ----
    user_prompt = f"""
查询: {query}

文档片段:
{chunk}

仅提取与回答此查询相关的内容。
"""

    # ---- 调用 LLM ----
    response = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user",  "content": user_prompt}
        ],
        temperature=0  # 确保输出确定性
    )

    compressed_chunk = response.choices[0].message.content.strip()

    # ---- 计算压缩率 ----
    original_length   = len(chunk)
    compressed_length = len(compressed_chunk)
    compression_ratio = (original_length - compressed_length) \
                        / original_length * 100

    return compressed_chunk, compression_ratio
🔑 关键设计点
  • temperature=0：压缩是确定性任务，不需要创造性，设为 0 保证输出稳定
  • 三种策略的差异完全由 Prompt 驱动——不需要微调或额外训练
  • 返回值包含压缩率，方便后续统计和可视化

六、批量压缩与完整管道

6.1 批量压缩

对检索到的多个块逐一调用 compress_chunk()，并汇总总体压缩率：

def batch_compress_chunks(chunks, query,
                          compression_type="selective",
                          model="gpt-3.5-turbo"):
    """分别压缩多个片段，返回 (压缩文本, 压缩率) 列表。"""
    results = []
    total_original_length = 0
    total_compressed_length = 0

    for i, chunk in enumerate(chunks):
        compressed_chunk, ratio = compress_chunk(
            chunk, query, compression_type, model
        )
        results.append((compressed_chunk, ratio))
        total_original_length   += len(chunk)
        total_compressed_length += len(compressed_chunk)

    overall_ratio = (total_original_length - total_compressed_length) \
                    / total_original_length * 100
    print(f"Overall compression ratio: {overall_ratio:.2f}%")
    return results

6.2 完整 RAG 管道

将压缩步骤嵌入标准 RAG 流程：

def rag_with_compression(pdf_path, query, k=10,
                         compression_type="selective",
                         model="gpt-3.5-turbo"):
    """带上下文压缩的 RAG 管道完整实现。"""

    # 1. 文档处理：提取 → 分块 → 嵌入 → 入库
    vector_store = process_document(pdf_path)

    # 2. 查询嵌入 + 语义检索
    query_embedding = create_embeddings(query)
    results = vector_store.similarity_search(query_embedding, k=k)
    retrieved_chunks = [r["text"] for r in results]

    # 3. ⚡ 上下文压缩（核心新增步骤）
    compressed_results = batch_compress_chunks(
        retrieved_chunks, query, compression_type, model
    )
    compressed_chunks  = [r[0] for r in compressed_results]
    compression_ratios = [r[1] for r in compressed_results]

    # 4. 过滤空块 → 拼接上下文
    filtered = [(c, r) for c, r in zip(compressed_chunks, compression_ratios)
                if c.strip()]
    compressed_chunks, compression_ratios = zip(*filtered)
    context = "\n\n---\n\n".join(compressed_chunks)

    # 5. 生成回答
    response = generate_response(query, context, model)

    return {
        "query": query,
        "original_chunks":    retrieved_chunks,
        "compressed_chunks":  list(compressed_chunks),
        "compression_ratios": list(compression_ratios),
        "context_length_reduction":
            f"{sum(compression_ratios)/len(compression_ratios):.2f}%",
        "response": response
    }

9.2 评估分析

📊 排名解读

  • Standard 回复最详细全面，因为保留了所有原始信息
  • Selective 较简洁但缺细节——去除了噪声，也偶尔去除了边缘相关信息
  • Summary 因改写可能引入信息损失
  • Extraction 最激进，丢失了上下文连贯性

⚖️ 权衡思考

  • 压缩并非总是提升回复质量——信息保真度是关键
  • 但压缩显著节省 token 和成本
  • 在上下文窗口紧张时，压缩的价值更大
  • Selective 是最佳平衡点：压缩 72% 同时质量损失最小
⚠️ 重要发现

压缩并不总是提高回复质量。在本例中，标准 RAG（无压缩）的回复被评为最佳，因为它保留了最完整的信息。但 Selective 压缩在仅使用 28% 原始 token 的情况下，仍达到了接近的质量水平——这意味着性价比最高。

十、何时使用压缩？决策流程

上下文压缩并非万能药。是否需要压缩，取决于两条硬约束和两类性能目标：

决策维度 典型触发条件 说明
模型与接口限制 超过 LLM 单次最大输入 tokens / API 成本过高 无法直接塞进 prompt 或成本不划算时，先压缩
场景性能目标 对时延要求严苛 / 需多轮检索，上下文不断膨胀 压缩能减少 I/O 量和推理时间

10.2 决策流程

IF (输入 token 预计超限 OR 成本/延迟过高) THEN
  压缩上下文
  ├─ IF 在检索后 → 聚合/摘要当前文档块
  │    • 推荐 Selective（保真度最高）
  │    • 适用：n×chunk_size 接近入口 token 上限
  │
  ├─ ELSE IF 离线数据准备阶段 → 预压缩存库
  │    • 推荐 Summary（极度精简）
  │    • 适用：知识库规模极大，文档格式杂乱
  │
  └─ ELSE IF 多轮推理中 → 对历史对话 & 中间结果滚动摘要
       • 推荐 Summary
       • 适用：历史对话窗口 > 4K tokens
ELSE
  直接拼接 prompt（无需压缩）
💡 实践建议

可以用启发式阈值（如 total_tokens > 0.8 * max_context）或自适应调度器来自动决定是否启动压缩。在大多数 RAG 场景中，检索后压缩是最容易集成、收益最明显的位点。

十一、优缺点与适用场景

✅ 优点

  • 节省 Token：压缩率可达 72%~89%，大幅降低 API 成本
  • 减少噪声：去除无关信息，提高上下文信噪比
  • 即插即用：不改变检索策略，仅在管道中增加一步
  • Prompt 驱动：不需要微调模型，更换 Prompt 即可切换策略
  • 灵活可调：三种策略覆盖不同压缩强度需求

❌ 缺点

  • 额外 LLM 调用：每个块需要一次压缩调用，增加延迟和成本
  • 信息损失风险：压缩可能误删边缘相关信息
  • 改写偏差：Summary 模式可能引入 LLM 的改写偏差
  • 回复质量可能下降：如评估所示，压缩后回复质量不一定提升
  • 依赖 LLM 能力：压缩质量取决于压缩模型的理解能力

适用场景速查

场景 推荐策略 理由
上下文窗口紧张，需大幅压缩 Summary 压缩率最高（86%），信息密度大
需要平衡质量与成本 Selective 保留原始措辞，质量损失最小
查询非常聚焦，只需关键句 Extraction 最激进压缩，只留核心句
对回复质量要求极高 不压缩 保留全部信息，避免任何损失
多轮对话 / Agent 链式推理 Summary（滚动） 控制历史上下文膨胀

十二、本篇小结

上下文压缩是 RAG 管道中检索后、生成前的一道"信息提纯"工序。它用 LLM 对检索到的文本块进行压缩，只保留与查询相关的内容，从而减少噪声、节省 token。

🎯 核心要点回顾
  • 三种压缩策略：Selective（保留原句）、Summary（生成摘要）、Extraction（逐字提取）
  • 压缩率：Selective 72% < Summary 86% < Extraction 89%
  • 回复质量：Standard > Selective > Summary > Extraction
  • 最佳平衡：Selective 在压缩 72% 的同时，质量损失最小——性价比之王
  • 决策依据：token 超限 / 成本过高 / 多轮推理膨胀时启用压缩

压缩本质上是一种信息保真度与效率之间的权衡。在实际项目中，建议先用 Selective 模式作为基线，根据 token 预算和回复质量要求调整策略。
