《企业级 RAG 架构设计与工程实践》系列 · 第 14 篇

为什么你的 RAG 上线之后效果变差了？
10 个典型失败案例与系统化排障方法

在前面 13 篇里，我们沿着 Data → Chunking → Embedding → Hybrid Retrieval → RRF → Reranker → Query Understanding → Context Engineering → Permission → Performance → Evaluation 这条主线，把企业级 RAG 的每一层拆开讲清楚了。

这一篇不介绍任何新技术。这一篇做一件更接近我日常真实工作的事：从故障出发，反向拆解整条 Pipeline。

RAG 的失败 ≠ LLM 的失败。RAG 的失败可能发生在 Data、Query、Retrieval、Ranking、Context、Generation、Security、Infrastructure 中的任何一层——而排障的全部价值，就在于快速回答"是哪一层"。

一、最危险的不是 RAG 做不出来，而是"看起来很好"

先设计一个几乎所有团队都经历过的场景。

POC 阶段：

100 个测试问题
      ↓
大部分都能回答
      ↓
团队认为效果不错
      ↓
上线

生产环境，现实的模样：

真实用户          → Query 表达千奇百怪
复杂 Query        → 多条件、多约束、口语化
多轮对话          → 指代、省略、话题漂移
版本混用          → 新旧制度并行
历史文档          → 三年前的 Policy 还在索引里
权限差异          → 同一个 Query，不同人不同答案
数据持续更新      → 昨天对的答案今天错了
长尾 Query        → 测试集从未覆盖

然后反馈涌进来：搜不到、搜错、排错、答错、引用错、延迟高、成本高、权限异常。

我把整个企业 RAG Pipeline 的故障面抽象成 11 层。后面所有的案例、排障方法、故障树，都是围绕这张图展开的：

图 1 · 企业 RAG Pipeline 的 11 层故障面（全文的分析框架）

请记住这张图的三个颜色分区：

  • 蓝色（①–⑦）：数据与检索链路。故障表现是"找不到 / 找错 / 排错"。
  • 黄绿色（⑧–⑨）：上下文与生成链路。故障表现是"答错 / 不按文档答 / 幻觉"。
  • 红色（⑩–⑪）：横切层。故障表现是"越权 / 慢 / 挂"，其中 Security 是系统级风险，不是质量问题。

全文核心问题由此引出：RAG 的失败究竟发生在哪里？

二、先建立故障定位框架，再谈案例

没有框架的排障，就是"感觉 Prompt 不行就改 Prompt，感觉 Embedding 不行就换 Embedding"。企业 RAG 的排障必须像传统分布式系统一样分层定位。

2.2 标准排障六步法

所有案例都将复用这条流程，我称之为 RAG 排障六步法：

1问题现象谁的 Query、什么表现、影响面多大
2故障层定位Data / Retrieval / Context / Generation / Security / Infra
3根因在定位层内继续下钻，直到可操作的根因
4验证方法用 Trace / 复现 Query 证实假设
5修复方案最小改动 + 可回滚
6回归验证入测试集，防止复发

三、十个典型案例：逐层击穿

案例 1Embedding 很强，但 Recall 很低

不要一看到 Recall 低就换 Embedding Model。这是我见过最常见的错误决策。

发生了什么：系统用的是表现不错的通用 Embedding Model，但用户持续反馈："知识库里明明有答案，系统就是找不到。"

Query："Android 14 RTC-10027 如何处理？"
正确文档：《RTC SDK 4.6.2 Android RTC-10027 排查指南》
结果：Retrieval Top-K 中没有该文档

为什么发生：沿写入与查询链路逐层检查，可能的原因至少有六类：

位置可能根因
Chunking错误码与排查步骤被切开，Chunk 内关键实体残缺
表达不一致Query 写 RTC-10027，文档里写"错误码 10027"，向量距离被拉开
Metadata硬编码的 Filter（如 status=approved）把文档筛掉了
Index 参数HNSW 的 ef_search 过小，高维空间里没搜到
领域适配通用模型对专有缩写（RTC）完全不敏感
Query 改写Rewrite 把"RTC-10027"改写成"实时通信错误"，关键实体丢失

怎么定位：系统化排查顺序，从便宜到昂贵：

1. 直接用文档原文的一句做 Query，看能不能召回自己
   → 召回不了：问题在 Index / Metadata 层（写入侧）
   → 召回了：问题在 Query / 表达一致性层（查询侧）
2. 去掉 Metadata Filter 重试 → 确认是否被过滤误伤
3. 检查该文档的 Chunk 内容，确认实体完整性
4. 打印 Rewrite 前后的 Query，确认关键实体是否丢失
5. 最后才考虑：换 / 微调 Embedding Model

怎么修复 & 避免复发：本例的修复通常是组合拳——Chunking 时保证"错误码 + 处理步骤"落在同一 Chunk；建立领域实体词表保护 Query 改写中的关键实体；Metadata Filter 从硬编码改为配置化。避免复发的方式是把这类 Query 加入第 13 篇说的回归测试集。

案例 2Recall 很高，但最终答案仍然错误

发生了什么：排查发现正确文档已经进入 Top-10，用户拿到的答案却还是错的。

为什么发生：这是最容易被误诊的一类问题——团队看到 Recall 高就说"检索没问题"，然后一头扎进 Prompt 调优。但正确文档进了 Top-10 ≠ 它最终能影响答案。中间还有三道关：

Retrieval ✅（正确文档在 Top-10）
      ↓
Reranker ?   ← 正确 Chunk 可能被排到第 9 位，刚好被 Context 截断
      ↓
Context ?    ← 新旧两个版本同时进入，互相冲突
      ↓
Generation ? ← 模型选了排位更靠前（但更旧）的证据

怎么定位：直接看最终的 Prompt 快照（这就是为什么 Trace 必须记录最终 Context）：

  1. 正确 Chunk 在 Rerank 后排第几？是否进入了最终 Context？
  2. Context 里有没有与它冲突的 Chunk（旧版本、其他部门口径）？
  3. 正确 Chunk 是否被 Token Budget 截断掉了关键条件句？

怎么修复：Rerank 后按分数做 Context 选择而不是固定 Top-N；Context 中按版本号 / 生效日期去重；关键限定条件句（"仅适用于…""但…"）所在 Chunk 给予截断保护。

核心结论：Recall 高 ≠ Answer 正确。Recall 是必要条件，不是充分条件。

案例 3检索到了正确文档，但模型没有使用

发生了什么：

Context 中明明白白写着：
"退款申请必须在签收后 7 天内提出。"

模型回答：
"通常需要在 14 天内申请。"

为什么发生：这是模型参数知识与 Retrieved Context 发生冲突的典型场景。模型预训练语料里见过大量"14 天退款"的通用表述，当 Context 的"权威性信号"不够强时，参数知识赢了。必须打破一个幻觉："把文档放进 Prompt"不等于"模型一定按照文档回答"。

怎么定位：

  • 检查 System Prompt：有没有明确的 Grounding 指令（"仅依据提供的资料回答，资料未覆盖时明确说明"）？
  • 检查 Context 结构：文档来源是否有权威性标注（如"现行有效制度"）？
  • 检查冲突 Chunk：Context 里是否同时有一个旧的、或论坛式的"一般 14 天"表述被模型采纳了？

怎么修复（按优先级）：

  1. System Instruction 强化 Grounding，要求引用来源编号；
  2. Context Priority：给官方制度类 Chunk 加权 / 置顶，明确标注 Source Authority；
  3. 若冲突频繁，在 Query Understanding 层做时效性意图识别，主动过滤过期口径。

避免复发：把"Context 与参数知识冲突"设计成一类固定测试用例——故意在 Context 中放置与常识不同的数字，验证模型是否遵循文档。

案例 4Chunk 切得太"好"，反而导致答案不完整

发生了什么：团队按最佳实践做了语义切分，每个 Chunk 都语义完整：

Chunk 1：退款申请条件……
Chunk 2：特殊情况……
Chunk 3：例外条件……

用户问："这个订单满足退款条件吗？"
只召回了 Chunk 1。

答案看起来头头是道，实际是错的——因为 Chunk 2/3 里的例外条件（比如"定制类商品不适用"）根本没进 Context。

为什么发生：Chunking 的隐含假设出了问题：我们一直追求"每个 Chunk 独立完整"，但很多业务问题的答案天然横跨多个 Chunk。独立完整的 Chunk 服务的是检索命中率，不是答案完整性。

怎么定位：用 Trace 里记录的 Chunk ID，把命中的 Chunk 与源文档对照：答案所需的完整知识单元是否被切散了？

怎么修复：四个层次的方案，按工程成本递增：

方案原理成本
调整 Overlap让边界信息冗余低，但治标
Adjacent Chunk Retrieval命中后自动带上前后相邻 Chunk低
Parent-Child 检索用小 Chunk 检索，用父级大 Chunk 进 Context中
章节结构重建以标题层级为切分边界（依赖解析质量）中高

核心观点：Chunking 的目标不是"让每个 Chunk 独立"，而是让 Retrieval 能够获得回答问题所需的最小完整知识单元。

案例 5BM25 和 Vector 各自都很好，Hybrid 之后却没有提升

发生了什么：两套检索系统单独评估都不错，团队满怀期待上了 Hybrid，结果指标几乎不动，个别 Query 甚至变差。

为什么发生：画个图就明白了——

图 3 · 两路高度重叠时，Hybrid 的理论增益上限本来就低

两路结果高度重叠时，Hybrid 的理论增益上限本来就低。真正能带来增益的是两路的互补部分（如 E），但如果：

  • Top-K 太小：每路只取 5，互补文档挤不进候选；
  • RRF 参数不合适：k 值让某一路系统性压过另一路；
  • 两路 Metadata Filter 不一致：一边过滤了某租户文档，另一边没过滤，融合后引入本不该出现的候选；
  • 某一路噪声大：BM25 对长尾词的误匹配把大量噪声送进 Fusion，稀释了有效候选。

怎么定位：分别计算两路 Top-K 与 Ground Truth 的 Overlap 率和互补命中率。如果互补命中 ≈ 0，问题不在 Fusion，而在"为什么两路如此相似"（通常是 Chunking 粒度让两路退化为同一信号）。

怎么修复 & 避免复发：

  • 上 Hybrid 前先做离线互补性分析：两路候选重叠度多高？互补命中能带来多少 Recall 增益？——没有增益预期的 Hybrid 不值得付双倍的检索成本；
  • 明确每一路的 Top-K 预算，确保互补文档有机会进入 Fusion 阶段。

核心观点：Hybrid Retrieval 不是"两个检索器相加"就一定更好。它是互补性投资，不是免费午餐。

案例 6Reranker 上线后准确率提高，P95 却炸了

发生了什么：

Reranker On
  → Recall / Ranking Quality ↑
  → P95 Latency ↑↑   ← 用户体验断崖

为什么发生：Reranker 是整个链路中唯一需要逐 Query 逐 Pair 推理的组件，成本随 Candidate Size 线性甚至超线性增长：

Candidate 20  → 推理 20 对，延迟可控
Candidate 100 → 推理 100 对，P95 直接爆炸

Candidate Size 一旦从检索阶段"顺手"调大（比如为了保 Recall），Reranker 就成了全链路的延迟瓶颈。此外 Batch Size 与 GPU 利用率、模型体积、量化与否、下游队列排队时间，都会叠加。

怎么定位：在 Trace 中拆分 Rerank 阶段的耗时：排队时间 vs 推理时间 vs 序列化时间。P95 与 P50 的差值往往暴露的是排队（Queue Delay），而不是推理本身。

怎么修复（按优先级）：

  1. Candidate Size 回调：用第 13 篇的评估确认"20 → 50 候选"带来的质量增益是否值回延迟；
  2. Reranker 模型量化 / 换小模型（Cross-Encoder 蒸馏版）；
  3. 设置 Rerank 阶段 Timeout + Fallback：超时直接使用 RRF 排序结果——降级到"次优质量"远好于"用户超时"；
  4. 第 12 篇讲过的缓存与批量合并。

核心结论：一个效果更好的 Reranker，不一定是一个更好的生产方案。真正的优化目标是三元组：

Quality+Latency+Cost

案例 7知识库更新了，但模型还在回答旧答案

这是企业 RAG 中最具代表性的生产问题，值得单独放大。

发生了什么：Policy v1 已入库并上线。业务侧发布了 Policy v2 并推送更新。用户提问，拿到的仍是 v1 的答案。业务方在群里 @ 你："你们的 RAG 是不是坏了？"

为什么发生：因为"数据更新"和"RAG 已更新"之间，隔着一条长长的失效链，任何一环断掉，旧答案都会继续存在：

图 4 · Freshness 失效链：数据更新 ≠ RAG 更新

怎么定位：沿这条链从上游往下逐环验证：源文档版本 → 索引中的 Chunk 版本 → Embedding 时间戳 → 各层缓存的 TTL 与失效事件。特别注意：向量库的 upsert 不会删除旧 Chunk 中已经切出去的孤儿片段；语义缓存命中判断基于向量相似度，新版本文档写入后它不会自动失效。

怎么修复：

  • 建立文档级版本号贯穿全链路（Source → Chunk → Index → Cache Key）；
  • 更新事件触发级联失效，而不是各自等待 TTL 过期；
  • 高时效性语料（政策、价格、制度）使用更短的语义缓存 TTL 或直接绕过。

核心观点：真正需要的不是"某次修好了"，而是一条 End-to-end Freshness Pipeline——让"数据更新"自动等价于"RAG 更新"。

案例 8用户没有权限，但文档却进入了 Context（高风险）

发生了什么：User A 发起 Query。向量检索由于缺少有效过滤，敏感文档（其他部门 / 其他租户）进入 Top-K，随后进入 Context，送入 LLM。

即使最终答案没有明确泄露内容——敏感信息已经进入了系统内部的处理链：它会出现在 Prompt 里、可能出现在日志里、可能被语义缓存以向量形式缓存、可能在极端 Prompt 注入下被吐出来。

为什么发生：

根因机制
无 Permission Filter向量检索天然不理解权限，纯 ANN 搜索就是"全球无墙"
Post-filter 而非 Pre-filter先取 Top-K 再过滤，且没有补位逻辑，恰好把越权文档留在候选里
Tenant ID 缺失多租户共库时 Namespace / Partition 配置错误
缓存跨权限共享语义缓存按 Query 向量命中，不校验请求者权限
Citation 泄露答案没引用敏感文档，但 Citation 列表暴露了文档标题

怎么定位：这不是靠看答案能发现的问题。必须用带越权标记的探针 Query 做主动审计：定期以低权限账号发起 Query，检查 Trace 中的候选文档集合是否包含越权 ID。

怎么修复：

  1. 权限过滤必须是 Pre-filter，在 ANN 检索阶段生效，而不是事后剔除；
  2. 缓存 Key 必须包含权限维度（至少是权限组 / 租户 ID），或低权限请求绕过共享缓存；
  3. Citation 与答案走同一套权限校验。

Security Failure 不是普通的 RAG Quality Failure，而是系统级风险。它不参与"效果提升 3%"这类权衡，它的处理优先级、响应流程、审批路径都应该与普通质量故障完全隔离。后面故障分级中，它独占 P0。

案例 9Context 越来越长，效果反而越来越差

发生了什么：

Top-K = 5   → 效果不错
Top-K = 20  → 信息更多，团队觉得"更保险"
Top-K = 50  → 效果明显下降，且延迟成本翻倍

为什么发生："More Context ≠ More Useful Context"。当 K 增大：

  • Noise：低相关 Chunk 稀释了模型的注意力；
  • Duplication：同一文档的多个相似 Chunk 重复出现，占用 Token 预算却不增加信息；
  • Lost in the Middle：关键证据落在 Context 中段时，模型利用率显著下降；
  • Conflicting Sources：新旧版本、不同口径同时在场，模型随机站队；
  • Token Budget 挤压：真正的关键 Chunk 可能因预算被截断。

怎么定位：做一个简单的 K-敏感性实验：固定评估集，扫 K ∈ {3, 5, 10, 20, 50}，同时记录质量指标与 P95 延迟。曲线通常呈现"先升后降"，而且质量下降点往往比延迟爆炸点更早出现。

怎么修复：

  • Rerank 后按分数做动态选择，而非固定 Top-N；
  • 相似 Chunk 去重（MMR 或基于 Chunk ID 的去重）；
  • 高分证据置于 Context 首尾位置（利用 Lost in the Middle 特性）；
  • 引入版本一致性检查，冲突来源只保留最高权威版本。

核心观点：Context 应该追求最小充分证据集，而不是最大信息量。

案例 10Offline Evaluation 很好，上线后效果崩了（最重要）

发生了什么：Offline 阶段 Recall@10、Faithfulness、Answer Relevance 全部漂亮。上线后用户反馈持续偏差，且离线指标完全无法解释。

为什么发生：五个 Drift，每一个都足以让离线指标失效：

Drift 类型机制典型表现
Distribution Shift测试 Query 与真实 Query 分布不一致测试集是工程师生造的短句，真实用户写 60 字长段落
Long-tail评估集没覆盖边缘问题测试集 100 条，真实 Query 空间是 10⁵ 级
Data Drift生产数据持续变化测试当天对，两周后语料变了没人知道
Behavior Drift用户表达方式变化产品改版后 Query 风格整体迁移
System Drift模型 / Embedding / Index / Prompt 在变每次变更都没有重跑完整回归

怎么定位：抽样真实失败 Query，与评估集 Query 做分布对比：长度分布、意图类型分布、实体领域分布。差异通常一目了然。

怎么修复：

  • 建立真实 Query 采样管道（脱敏后）持续补充评估集；
  • 评估集按意图 / 领域 / 难度分层采样，避免只测"好写的题"；
  • 任何系统组件变更（换 Embedding、改 Prompt、升级模型）必须触发全量回归；
  • 上线后用第 12 篇的在线指标 + 用户反馈做持续监控，与离线指标形成双保险。
Offline Quality≠Online Quality

四、RAG 故障树：统一的 Failure Taxonomy

十个案例讲完，现在把它们收拢到一个统一的分类体系里。不同类型的故障，应该走完全不同的排障路径——这正是故障树存在的意义。

图 5 · RAG Failure Tree：不同故障进入不同排障路径

使用方法：拿到故障现象后，先归类到三大主枝之一，再进入对应子项下钻。Security 永远优先处理，且不与质量问题共享排障通道。

五、从 "Answer Wrong" 反查整条 Pipeline

这是全文最具实践价值的部分。当你拿到一个错误答案，按这棵诊断树走：

图 6 · Answer Wrong 诊断树：两分钟内确定责任层

两个判断问题的操作定义要说清楚，避免执行时扯皮：

  • "正确文档被检索到了吗？"——看 Trace 中 Retrieval / Fusion / Rerank 各阶段的候选 ID 集合。注意它分两级：进了候选但被排出去，责任在 Rerank；候选里根本没有，责任在 Retrieval 或 Data。
  • "正确证据在最终 Context 里吗？"——看 Prompt 快照。在 Context 里但没被用，责任在 Generation；不在 Context 里，责任在 Context 构建（排序、截断、预算）。

这棵树的价值在于：任何纠纷，两分钟内确定责任层。

六、RAG Debugging Checklist

诊断树定层之后，用清单逐项过。建议直接做成内部工具的表单模板：

🗂 Data

  • 文档在源系统是否存在？
  • 解析是否成功（表格 / 扫描件 / 版式）？
  • Chunk 边界与内容是否正确？
  • Metadata 是否完整（版本 / 日期 / 部门 / 状态）？
  • 是否为最新版本？旧版本是否已删除？

🔍 Query

  • 原始 Query 是什么（原样保留）？
  • Rewrite 后变成了什么？
  • 是否发生 Intent Drift / 关键实体丢失？
  • 多轮对话中指代是否正确消解？
  • Metadata Filter 是否正确生效？

🎯 Retrieval

  • Dense Top-K 是什么？分数多少？
  • BM25 Top-K 是什么？
  • RRF 融合后的排序？
  • Ground Truth 是否进入 Candidate？在哪一路？
  • 两路 Filter 条件是否一致？

⚖️ Reranker

  • Candidate 数量是多少？
  • Rerank Score 分布如何？
  • 正确文档 Rerank 后排第几？
  • Rerank 阶段耗时与超时？
  • 是否触发了 Fallback？

📦 Context

  • 最终 Context 全文是什么（快照）？
  • 是否存在重复 Chunk？
  • 是否存在版本 / 口径冲突？
  • 是否超过 Token Budget？截断发生在哪？
  • 证据的位置（首 / 中 / 尾）？

✍️ Generation

  • 完整 Prompt 快照（含 System）？
  • Model 名称与版本？
  • 原始 Output（含被后处理删掉的部分）？
  • Citation 与证据 ID 的映射？
  • 是否被安全策略拦截 / 改写？

🔐 Security

  • 请求者身份 / Tenant ID？
  • 本次请求实际应用的权限范围？
  • 候选中是否存在越权文档？
  • 缓存命中是否校验了权限？

⚙️ System

  • 各阶段 Latency 分解？
  • 各层缓存命中情况？
  • 是否发生 Error / Retry / 降级？
  • Fallback 路径是否被激活？

七、RAG Trace：排障体系的地基

上面所有方法有一个共同前提：你能在事后看到当时发生了什么。没有 Trace，诊断树就是空中楼阁。

7.1 一条完整的 Trace 应该覆盖

Request ID
│
├── User / Tenant            ← 谁，什么权限范围
├── Original Query           ← 用户原话，永不改写
├── Rewritten Query          ← 改写后（可多条）
├── Metadata Filter          ← 本次实际生效的过滤条件
├── Dense Retrieval          ← Top-K + Scores + Chunk IDs
├── BM25 Retrieval           ← Top-K + Scores + Chunk IDs
├── RRF                      ← 融合后排序
├── Reranker                 ← 输入输出 + Scores + 耗时
├── Context                  ← 最终上下文快照（受控记录）
├── Prompt                   ← 完整 Prompt（含 System）
├── LLM                      ← 模型版本 + 原始输出
├── Citation                 ← 引用与证据映射
└── Final Answer

每一步记录：latency、inputs、outputs、IDs、scores、model version、cache hit、errors。

7.2 一个可落地的 Trace 数据结构示例

from dataclasses import dataclass, field
from datetime import datetime
from enum import Enum
from typing import Any, Optional

class Stage(Enum):
    QUERY_UNDERSTANDING = "query_understanding"
    DENSE_RETRIEVAL     = "dense_retrieval"
    BM25_RETRIEVAL      = "bm25_retrieval"
    FUSION              = "fusion_rrf"
    RERANK              = "rerank"
    CONTEXT_BUILD       = "context_build"
    GENERATION          = "generation"
    POST_CHECK          = "post_check"   # 权限 / Citation 校验

@dataclass
class StageTrace:
    stage: Stage
    started_at: datetime
    latency_ms: float
    inputs: dict[str, Any]        # 只存 ID / Query / 参数，不盲目存全文
    outputs: dict[str, Any]       # 候选 ID + Score 列表、Prompt 引用而非全文
    model_version: Optional[str] = None
    cache_hit: bool = False
    error: Optional[str] = None
    fallback_triggered: bool = False

@dataclass
class RAGTrace:
    request_id: str
    tenant_id: str
    user_id: str
    permission_scope: str          # 本次请求的权限集合摘要（哈希）
    original_query: str
    rewritten_queries: list[str] = field(default_factory=list)
    metadata_filter: dict[str, Any] = field(default_factory=dict)
    stages: list[StageTrace] = field(default_factory=list)
    final_context_chunk_ids: list[str] = field(default_factory=list)
    citations: list[dict] = field(default_factory=list)
    final_answer: str = ""
    evaluation_labels: dict[str, Any] = field(default_factory=dict)  # 人工标注回流用

    def stage(self, s: Stage) -> Optional[StageTrace]:
        return next((t for t in self.stages if t.stage == s), None)

    def find_chunk_first_appearance(self, chunk_id: str) -> Optional[Stage]:
        """定位某个 Chunk 最早出现在哪个阶段——诊断树的核心查询"""
        order = [Stage.DENSE_RETRIEVAL, Stage.BM25_RETRIEVAL,
                 Stage.FUSION, Stage.RERANK, Stage.CONTEXT_BUILD]
        for s in order:
            t = self.stage(s)
            if t and chunk_id in t.outputs.get("chunk_ids", []):
                return s
        return None

find_chunk_first_appearance 这个方法值得单独说明：给定一个"正确文档"，它出现在 Dense 里但没出现在 Context 里，责任就在 Rerank 或 Context 构建；它连 Dense 都不在，责任就在 Retrieval 或 Data。一个函数，自动完成诊断树的第一层分流。

安全红线（必须写进规范）：敏感数据记录必须遵守企业安全策略。不是为了 Debug 就无限制地记录完整 Context 和用户 Query。采用：日志脱敏、Context 存哈希 + 按需解引用、Trace 保留期限、越级访问 Trace 的审计。

八、RAG Failure 与 Evaluation 的闭环

第 13 篇讲 Evaluation 时强调过：评估集不是一次性的，而是活的。这一篇补上它真正的落地方式——失败回流：

图 7 · Failure → Regression → Evaluation 闭环（第 13 篇的真正落地）

每一个真实线上失败案例，都应该尽可能转化成未来不会再犯的测试样本。

操作上很简单：故障修复后，把该 Query（脱敏后）连同 Ground Truth、故障类型标签写入评估集。以后任何组件变更——换 Embedding、改 Prompt、升级 Reranker——回归测试都必须包含它。这一步也是后面 Postmortem 的必要交付物。

九、失败不是单点问题，而是链式问题

看一个完整的链式故障案例。这是生产中最常见的故障形态——最终错误发生在 Generation，根因却埋在 Data Layer：

图 8 · 链式故障：从 PDF Parsing Error 到 Wrong Answer

这个案例的团队第一反应是"换更强的模型""改 Prompt"，折腾两周无效。最后是靠 Trace 回放，沿着 find_chunk_first_appearance 发现那个 Chunk 从未出现在任何检索候选里，一路追到 PDF 解析层才找到根因。

最终错误发生在 Generation，但根因可能发生在 Data Layer。这是全文最重要的架构思想之一：永远不要只修症状出现的层。

十、故障分级与 Incident Response

10.1 故障分级

参考 SRE 实践，建议按影响性质（而非仅影响规模）分级：

P0 · Critical
  • 权限泄露 / 越权访问
  • 跨租户数据泄露
  • 敏感信息进入处理链或输出

安全事件独立流程：立即阻断 + 上报，不适用普通排障节奏

P1 · High
  • 大规模错误答案
  • 知识库整体失效
  • 检索 / 模型全面异常

拉起 Incident Response，全链路排查

P2 · Medium
  • 特定领域 Recall 下降
  • 某类 Query 集中失败
  • 延迟显著升高

限时排查，纳入下一个迭代修复

P3 · Low
  • Citation 格式问题
  • 非关键长尾错误

记录回流评估集，低优修复

注意：具体等级名称、响应时间应由企业内部 SLA 定义，这里给的是结构性参考。

10.2 Incident Response 流程

企业 RAG 出问题后，不应该只"把 Prompt 改一下"。应该形成与生产系统一致的 Incident Management：

图 9 · Incident Response 流程（Mitigation 止血与 Fix 根治分离）

注意 Mitigation（止血）和 Fix（根治）是分开的两步：先降级 / 回滚 / 关缓存止血恢复服务，再慢慢根治。P0 安全事件的 Mitigation 只有一个动作——立即阻断相关检索路径。

10.3 Postmortem 模板

Incident              ← 什么事，何时发现
Impact                ← 影响多少用户 / 哪些业务 / 数据风险
Detection             ← 怎么发现的（告警 / 用户反馈？多久才发现？）
Root Cause            ← 哪一层、什么根因（引用 Trace 证据）
Contributing Factors  ← 哪些设计让它可能发生且难发现
Immediate Fix         ← 止血动作与恢复时间
Permanent Fix         ← 根治方案
Regression Case       ← 加入评估集的具体样本（必须给出）
Monitoring Improvement← 下次如何更早发现

一次故障真正的价值，是让系统以后不再重复犯同样的错误。没有 Regression Case 的 Postmortem 是不合格的。

十三、最终核心认知

回顾全文，我想留下的不是十个案例，而是一次思维方式的替换：

RAG Failure≠LLM Failure

更准确的理解是：

RAG Failure
=
      Data
  ∨   Query
  ∨   Retrieval
  ∨   Ranking
  ∨   Context
  ∨   Generation
  ∨   Security
  ∨   Infrastructure

因此，RAG 排障思维应该完成一次根本转变：

从 "答案为什么错？"
转变为 "错误是在数据、检索、排序、上下文、生成还是基础设施哪一层产生的？"

前一个问题通向无限次的 Prompt 微调；后一个问题通向工程。
