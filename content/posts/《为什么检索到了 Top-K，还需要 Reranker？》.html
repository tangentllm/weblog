SECTION 01

Top-K 不等于 Top Relevant

先从一个真实的企业 Query 开始。

用户 Query

「RTC SDK 4.6.2 在 Android 14 出现 RTC-10027，官方推荐怎么处理？」

这个 Query 经过我们前几篇搭建的链路——Chunking → Embedding → Dense Retrieval + BM25 → Hybrid Retrieval → RRF——之后，系统返回了这样一份 Candidate Set：

RRF 融合后的 Candidate Set（节选）
  1. 《RTC SDK 4.6.1 错误码说明》 版本不对
  2. 《Android 14 兼容性问题汇总》 太泛
  3. 《RTC SDK 4.6.2 错误码说明》 ✓ 真正的答案
  4. 《RTC SDK 弱网优化指南》 主题偏移
  5. 《RTC-10027 历史工单》 可能有用
  6. 《RTC SDK 4.6.2 API 文档》 相关但非答案

看起来 Top-K 里的每一篇都「沾边」——错误码、Android 14、SDK 版本号，关键词都能对上。但真正最应该出现在第一位的，是第 3 篇。第 1 篇甚至是版本号差一个小数点的高危陷阱：4.6.1 和 4.6.2 的错误码说明，在 Embedding 空间里几乎无法区分。

于是问题来了：

为什么 Retrieval 能找到很多相关文档，
却不能准确判断「哪个最应该排在前面」？

答案并不神秘：这不是 Retrieval 的 bug，而是它的设计目标本来就不是这个。要回答这个问题，我们需要先把 Retrieval 和 Ranking 这两件事彻底分开。

SECTION 02

Retrieval 和 Ranking 到底是什么关系？

在很多 RAG 教程里，「检索」被描述成一件事。但在任何一个真实的搜索引擎架构里——从传统 Web Search 到企业知识库——它从来都是两个阶段、两种目标、两套模型。

Query→ Retrieval→ Candidate Set→ Ranking→ Top Relevant

Retrieval：尽可能找全

Retrieval 的任务，是从几十万、上千万的文档库中，快速找到「可能相关」的候选。它面对的是全量语料，必须在毫秒级完成，所以它天然要牺牲精度换速度和覆盖面。它优先优化的指标是 Recall——宁滥勿缺，正确答案绝不能在这一步丢掉。

Reranking：尽可能排准

Reranking 的任务则完全不同。它面对的是一个已经被缩小到几十条的 Candidate Set，它有充裕的时间（几百毫秒）和算力预算去仔细判断：Query 与这每一篇文档，到底有多相关。它优先优化的是 Precision / Ranking Quality。

CORE MENTAL MODEL
Retrieval 负责尽可能找全，Reranker 负责尽可能排准。
用一个类比：Retrieval 是把全图书馆里「可能提到这个话题」的书都搬到桌上，Reranker 是坐下来逐本翻目录、判断哪一本真正回答了你的问题。这两件事的能力模型、计算成本、优化目标完全不同——所以它们在架构上必须分开。
SECTION 03

为什么不能直接让 LLM 排序？

看到这里，一个「聪明」的方案会自然浮现：既然 LLM 理解能力最强，为什么不直接这样？

# 看似合理的方案：让 LLM 自己排
Query
  ↓
Retrieve 50 Documents
  ↓
LLM 逐个判断相关性
  ↓
输出排序结果

这个方案在 Demo 里能跑通，在生产里会立刻撞上一堵墙：

LLM 直接排序的七个工程问题
  • ▸ 成本高：每个请求都要为 50 篇文档的全文付费，而 Reranker 是一个小得多的专用模型
  • ▸ 延迟高：LLM 的生成速度远慢于一次 Cross-Encoder 前向计算，P95 会被拖垮
  • ▸ Token 消耗大：50 × 平均 1K token 的输入，仅排序环节就可能吃掉数万 token
  • ▸ 输出稳定性差：LLM 输出的是自然语言，排序结果需要解析、可能格式错乱、可能拒绝输出
  • ▸ 并发能力受限：昂贵的大模型推理资源被排序任务占满，影响真正的生成请求
  • ▸ 工程复杂度高：需要额外的解析、校验、重试逻辑
  • ▸ 任务错配：排序本质是一个判别式打分任务，不适合作为普通 Generation 来做

核心矛盾在于：排序是一个「打分」问题，不是一个「生成」问题。它需要的是对一个 (Query, Document) 对输出一个确定性的相关性分数——这正是专用 Ranking Model 存在的理由。所以在一个成熟架构里，Reranker 必须是一个独立的、专用的 Ranking Model，而不是 LLM 的一个附加任务。

SECTION 04

Reranker 到底做什么？

抛开所有术语，Reranker 做的事情极其简单：

Query
+
Candidate Document
  ↓
Reranker
  ↓
Relevance Score

它接收一个 Query 和一篇候选文档，输出一个相关性分数。回到开篇那个例子：

Query：RTC SDK 4.6.2 Android RTC-10027 怎么处理？
A · RTC SDK 4.6.2 Android 错误码说明
0.96
B · RTC SDK 4.5.0 错误码说明
0.73
C · Android 14 通用兼容性说明
0.51

注意两个关键点：

第一，Reranker 不是重新做一次数据库搜索。它的工作范围被严格限制在 Candidate Set 之内，它不会去发现「库里有第 51 篇文档更相关」——那是 Retrieval 的职责边界。第二，它输出的分数是精细的、有区分度的：同样的 Query，Reranker 能把「4.6.2 的错误码说明」和「4.5.0 的错误码说明」拉开明显差距——这正是 Embedding 相似度做不到的事。

SECTION 05

Bi-Encoder vs Cross-Encoder

这是本文最核心的技术部分。为什么 Reranker 通常比 Embedding 模型「看得更清楚」？根源在于两种架构的交互方式根本不同。

Bi-Encoder：先各走各的路，再见面对答案

  ↓

维度Bi-Encoder（双塔）Cross-Encoder（交叉编码）
计算时机Doc 向量可完全离线预计算，在线只需算 Query 向量每次 Query 都要对每个候选重新做一次联合前向计算

Bi-Encoder → Fast Retrieval
Cross-Encoder → Accurate Reranking
SECTION 06

为什么 Cross-Encoder 通常更适合做 Reranker？

很多文章到这里就一句话带过：「Cross-Encoder 更准确。」这句话是对的，但如果你不知道为什么，你就无法判断自己的场景是否需要它、需要付出多少代价。

关键在于交互发生的时机：

Bi-Encoder 的路径

Q → Vector    D → Vector    →  再计算相似度

Query 在编码时完全不知道会匹配到什么文档，Document 在编码时也不知道 Query 是什么。所有语义都被压缩成「事先固化」的一个向量。换句话说，Bi-Encoder 只能在表示层对齐语义，无法在推理时针对这个具体 Query 重新审视文档内容。

Cross-Encoder 的路径

[CLS] Query [SEP] Document [SEP]  →  单个 Encoder 联合建模  →  Score

Query 和 Document 被拼成一条输入，Attention 机制可以让 Query 里的每个 token 直接「看到」Document 里的每个 token。回到我们的例子：模型可以在同一个计算图里完成「4.6.2 ≠ 4.5.0」「RTC-10027 同时出现在 Query 和 Doc 的错误码表格中」这类细粒度比对——这正是区分「很像但不是答案」的候选所必需的能力。

WHY IT MATTERS
Cross-Encoder 可以直接建模 Query 与候选文档之间更细粒度的 token-level 交互，因此通常更适合做精排。但注意「通常」二字——它更强的判断能力是用每候选一次前向计算的成本换来的。这个代价是否值得，取决于你的业务对排序质量的真实敏感度。
SECTION 07

为什么不能直接拿 Cross-Encoder 扫全库？

既然 Cross-Encoder 这么准，为什么不跳过 Embedding，直接用它对全库打分？我们算一笔账。

10,000,000
企业知识库文档数（典型量级）
×10M
每个 Query 需要的 Cross-Encoder 前向计算
~50
两阶段架构下每个 Query 的实际计算量

1 个 Query × 10,000,000 个文档，逐一做 Cross-Encoder 前向计算——这在任何成本模型下都不可行。而且 Cross-Encoder 的文档表示无法离线预计算（它依赖具体的 Query），你连用缓存摊薄成本的余地都没有。

所以答案只能是一个折中架构：

Large Corpus
  ↓
Fast Retrieval（Bi-Encoder / BM25）
  ↓
Top-K Candidates（几十条）
  ↓
Cross-Encoder
  ↓
Final Ranking
这也是 Retrieval + Reranking
两阶段架构存在的核心原因。
SECTION 08

Two-Stage Retrieval：经典的分层架构

把前面所有的分析合在一起，就是信息检索领域几十年沉淀下来的经典范式——Two-Stage Retrieval：

两个阶段的分工必须刻进骨子里：

First Stage 追求 Recall——候选池宁大勿小，正确答案绝不能在这里被截断；Second Stage 追求 Precision——在已经可控的小集合里，用最重的模型把最相关的顶到最前面。整个系统的质量 = Candidate Recall ＋ Ranking Precision，两者缺一不可。

SECTION 09

Reranker 放在 RRF 前面还是后面？

这是一个高频架构问题。上一篇我们建立了 Hybrid Retrieval + RRF 的融合链路，现在要插入 Reranker，插入点有两种选择。

方案 A：Per-Retriever Rerank（每路检索后各自 Rerank）

Dense  → Reranker ↘
                    RRF → 输出
BM25   → Reranker ↗

方案 B：先融合，再统一 Rerank

Dense ↘
        RRF → Candidate Set → Reranker → 输出
BM25  ↗

对比分析

维度方案 A（RRF 前 Rerank）方案 B（RRF 后 Rerank）
Reranker 调用量每路各一次，成本 ×2全程一次
融合语义两套 Reranker 分数进入 RRF，跨模型分数不可直接比RRF 处理排名，Reranker 只处理统一候选集
架构复杂度高：需维护多路精排链路低：一条清晰的流水线
可观测性 / 调参每一层都影响下游，归因困难Retrieval / 融合 / 精排三层可独立评估
ARCHITECTURE DECISION
在典型企业 Hybrid Retrieval 中，更常见、也更容易控制复杂度的方式是先融合 Candidate，再进行统一 Reranking。但请注意这不是教条：某些特殊场景（例如某一路检索器噪声极大、需要独立精排后再融合）确实会采用 Per-Retriever Rerank，只是成本和架构复杂度通常更高，需要明确理由后再引入。
SECTION 10

Retrieval Top-K 到底取多少？

两阶段架构引入了一个新的、必须在实践中反复校准的旋钮：喂给 Reranker 的 Candidate Set 有多大，以及 Reranker 最终输出多少条。

Retrieve Top 20  /  Top 50  /  Top 100
            ↓
Rerank   Top 5   /  Top 10  /  Top 20

Candidate 太少会怎样？

可能正确文档还没进入 Reranker，就已经被截断在召回阶段。此时 Reranker 再强也无能为力——它无法排序一条它从未见过的文档。这是所有排序系统的铁律：Reranker 的上限，是 Candidate Set 的 Recall。

Candidate 太多会怎样？

Reranker latency 线性上升；GPU 成本增加；高并发下吞吐能力下降；同时低质量候选进入精排，边际收益快速递减。

核心权衡链条
Retrieval K ↑
  → Recall ↑
  → Rerank Cost ↑
  → Latency ↑

这是一个单调权衡，不存在免费的午餐。不要期待一个「Top 50 一定最好」的答案——不存在这个数字。正确的做法是：用你自己的评测集，画出 Recall@K 与 P95 Latency 的关系曲线，在业务可接受的延迟预算内，取 Recall 的边际收益拐点。

SECTION 11

Reranker Score 能不能直接比较？

一个隐蔽但后果严重的误解：把 Reranker 的分数当作绝对概率来使用。必须明确：

Reranker 的分值，
主要用于当前 Query Candidate 集合内部排序。

两个例子：

  • 跨 Query 比较不可靠：「Query A 的最高分 0.9」和「Query B 的最高分 0.7」不代表 A 的文档更相关——不同 Query 的分数分布本身不同。
  • 跨模型比较更不可靠：Model A 输出 0.92、Model B 输出 0.81，不能因此判断 Model A 认为的文档「绝对更相关」——两个模型的分数空间完全没有对齐。
Model A = 0.92
Model B = 0.81
      ✗ 不能推出 Model A 更相关

如果你确实需要用分数做阈值过滤（例如「低于 0.3 的直接丢弃」）或跨模型对比，Score 的绝对值需要经过专门的 Calibration（校准）与验证——在你的标注数据上确认分数与真实相关性的映射关系，而不是直接相信模型输出。绝大多数系统应该只用分数做集合内排序，用固定 Top-N 做截断，绕开校准问题。

SECTION 12

Reranker Model 如何选择？

企业选型不是看社区榜单，而是在四个维度上同时约束求解。我不做任何具体模型的排名——榜单会过时，方法论不会。

维度需要考察的关键点
模型能力 中文 / 多语言支持；Domain 表现（你的领域文档它与通用语料的差距）；Query 类型覆盖（关键词型 vs 自然语言型）
性能 Latency（单条与 Batch）；Throughput；Batch 推理效率；是否需要 GPU、需要几张
工程 Context Length（能否吃下你的 Chunk + Query）；部署形态；Model Size；Quantization 支持；License 是否允许商用
业务 你的 Query 分布是关键词型（SKU-123456）还是自然语言型（「为什么下单后不发货」）？知识库是技术文档、FAQ 还是产品知识？不同分布下同一模型表现可能截然不同

实践建议：选 2–3 个候选模型，用你自己的评测集（而不是公开基准）做离线对比，再上线 A/B。你的数据才是唯一的裁判。

SECTION 13

Reranker 是否需要微调？

先回答现实问题：通用 Reranker 能不能直接用？能。在很多场景下，一个表现良好的通用 Cross-Encoder 作为 baseline 已经足够，先跑通、先建评测，再谈微调。

但企业领域往往存在一条「语义鸿沟」：

通用 Query
  ↓
领域术语（RTC-10027 是什么？）
  ↓
业务缩写（NPS、QBR、SLA 的内部含义）
  ↓
内部产品名（只有你们公司知道的系统名）
  ↓
专有知识（内部流程、私有 API 行为）

当通用模型在你的评测集上系统性地区分不出「版本号差一位的错误码文档」时，就需要考虑 Domain-specific Reranker Fine-tuning。涉及的核心概念包括：

  • Positive Pair：(Query, 正确文档) 对——通常来自点击日志、人工标注或 LLM 辅助标注；
  • Hard Negative：下一节专门讲，这是微调成败的关键；
  • Pairwise Training / Contrastive Learning：让模型学会「这篇比那篇更相关」，而不是只判断「是否相关」。

训练细节超出本文范围，但原则可以给出：微调的数据质量，尤其是 Hard Negative 的质量，决定上限。

SECTION 14

Hard Negative 为什么重要？

训练（或评估）Reranker 时，负样本怎么选？看一组对比：

Query：RTC SDK 4.6.2 Android RTC-10027 怎么解决？
类型文档模型需要学会什么
PositiveRTC SDK 4.6.2 Android RTC-10027 处理方案识别真正的答案
Hard NegativeRTC SDK 4.5.0 Android RTC-10027 处理方案识别「版本号差一位的陷阱」
普通 Negative公司行政报销流程几乎不用学——太容易了

「公司行政报销流程」这种负样本，模型看一眼就能排除，对训练几乎没有信息量。而 4.5.0 那篇——关键词全对上、错误码相同、句式一模一样，唯一错在版本号——才是模型真正需要学会排除的对象。

真正困难的不是区分「相关」和「完全不相关」，
而是区分「非常像、但其实不是答案」的候选。

这也解释了为什么企业场景特别需要 Hard Negative Mining：你的知识库里最危险的候选，往往就是上一版本的文档、相邻产品的文档、同主题不同条款的文档。它们在 Embedding 空间里与正确答案几乎重合，只有 Cross-Encoder 的细粒度交互才有机会分辨——前提是你训练时让它见过这样的样本。Hard Negative 的一个高效来源，恰恰就是现有检索系统召回的 Top-K 中未被点击的候选。

SECTION 15

Reranker 与 Context Engineering 的关系

Reranker 输出了 Top Relevant，是不是就可以直接拼给 LLM 了？还不是。Reranker 之后还有一整个 Context Construction 环节：

Retrieval→ RRF→ Reranker→ Top Relevant→ Context Construction→ LLM

Context Engineering 还可能负责：

  • 去重：RRF 融合后同一个 Chunk 可能以不同父文档出现多次；
  • 压缩：长文档只保留与 Query 相关的段落；
  • Parent Retrieval：Chunk 排序后，取其父文档/邻接段落补全上下文；
  • Context Ordering：最相关内容放在 Context 的头部或尾部（LLM 对中间位置的注意力较弱）；
  • Token Budget：在模型窗口内做取舍；
  • Metadata 注入：版本号、更新时间、来源权限信息。
POSITIONING
Reranker 是 Context Construction 的重要上游，而不是 Context Engineering 的全部。它决定「哪些候选值得进入下一步」，但不决定「这些信息最终以什么形态、什么顺序、多少预算交给 LLM」。

无 Reranker：Top 20 → 全部交给 LLM

  • ▸ 重复上下文：同一内容的多路召回副本挤占 Token Budget
  • ▸ 旧版本知识：4.6.1 的说明排在 4.6.2 前面，LLM 可能引用过时方案
  • ▸ 相似但错误的文档：恰好是本系列反复强调的那类「高度相似但非答案」的候选
有 Reranker：Top 50 → Rerank → Top 5 → LLM

有机会显著降低 Noise-to-Context Ratio——Context 中噪声信息的占比。LLM 面对的证据更干净、更聚焦，基于证据生成的答案质量自然更有保障。

但必须划清边界：Reranker 不能解决所有幻觉。如果正确文档根本不在知识库里（Recall 为零），如果文档本身内容是错的或过时的，如果 LLM 无视 Context 自由发挥——这些都不是排序能解决的。Reranker 提高的是「证据质量」，不是「生成质量」的全部。

SECTION 17

Reranker 的性能优化

进入生产环境，Reranker 就不再是一个模型，而是一个有 SLO 的在线服务。以下是常用的优化手段：

Batch Reranking

Query + [Doc1, Doc2, Doc3 ...]
  ↓
组装成 Batch（padding 对齐，控制 max_length）
  ↓
Reranker 一次前向
  ↓
批量输出 Scores

把 K 个候选打包成 Batch 推理，利用 GPU 并行，远快于逐条计算。

Async 并行

Dense Retrieval 与 BM25 天然可以并行执行，RRF 融合完成后再触发 Reranker。精排阶段不要阻塞其他独立步骤。

GPU / Quantization / Candidate Pruning

  • GPU：高吞吐场景几乎必选；CPU 推理只适合低 QPS 内部工具；
  • Model Quantization：INT8/FP8 量化降低推理成本，但上线前必须验证量化对排序质量的影响；
  • Candidate Pruning：在精排前先用轻量规则（权限过滤、时间过滤、文档类型过滤、Metadata 硬条件）剔除明显不相关的候选，让贵算力只花在值得的候选上。

Cache

Reranker 结果可以缓存，但缓存 Key 必须谨慎设计——缓存命中错误比不缓存更危险：

Key 组成为什么必须包含
Query归一化后的 Query 文本（含同义改写策略需保持一致）
Model Version换模型 / 微调后，旧分数全部作废
Candidate Set知识库更新后，同一 Query 的候选集已变化
Permission不同用户权限看到不同文档——缓存泄露是安全事故
SECTION 18

Reranker 什么时候反而不应该使用？

写了这么多 Reranker 的好处，这一节可能是全文最重要的「反面清单」。Reranker 是一个工程选择，不是 RAG 的宗教。

场景一：数据量很小

知识库只有几百个文档？全库直接塞进一个粗排甚至直接给 LLM 都可能绰绰有余。为一个中小型文档集合引入精排服务，是在为不存在的问题增加运维负担。

场景二：Query 极度结构化

典型 Query

「SKU-123456」

这种精确标识符 Query，BM25 加上 Metadata 索引可能一步命中，排序几乎没有歧义。Reranker 在这里没有发挥空间——它擅长的是语义分辨，不是精确匹配。

场景三：Latency 极度敏感

如果你的链路 P95 已经卡在秒级红线，而监控显示 Reranker 成为 P95 的主要瓶颈，正确动作不是硬扛，而是重新评估：缩小 Candidate Size、换更小的模型、量化、或者干脆砍掉这一阶段——先测量，再决策。

先跑通检索，建立评测，
再决定要不要引入 Reranker。
SECTION 19

如何评估 Reranker？

任何关于「Reranker 有没有用」的结论，都必须来自对照实验：

Baseline    ：Dense + BM25 + RRF
      ↓
Experiment  ：Dense + BM25 + RRF + Reranker

两组实验在同一评测集上对比，指标分两层看：

指标层指标回答的问题
排序质量Recall@K正确文档是否还在 Top-K 里
Precision@KTop-K 里有多少是真相关的
MRR第一个正确答案排得有多靠前
NDCG整体排序质量（考虑分级相关性）
系统指标P50 / P95 Latency排序质量是用延迟换的，代价多大
Throughput高并发下还撑得住吗
GPU Cost每千次请求的推理成本
端到端答案质量最终要回到「用户拿到的答案变好了吗」
KEY PRINCIPLE
不要只看模型 Offline Accuracy，还要看线上系统指标。NDCG 提升了 3 个点、但 P95 延迟翻倍、GPU 成本上涨 40%——这笔账要放在同一个表格里算。Reranker 的价值最终要以「端到端 RAG 效果 + 系统 SLO」来衡量。
SECTION 20

一个完整生产案例

把本篇所有内容串起来，回到开篇那个 Query 的完整生命周期：

Query：RTC SDK 4.6.2 在 Android 14 出现 RTC-10027，官方推荐怎么处理？
  1. Metadata Filter：权限过滤 + 产品线过滤 + 文档时效过滤 先剔除无效候选
  2. Dense Search → Top 50 语义召回
  3. BM25 Search → Top 50 关键词召回（RTC-10027 精确命中）
  4. RRF 融合 → Candidate 70 去重后不是 100
  5. Reranker 精排 → Top 5 4.6.2 错误码说明升到第 1
  6. Context Construction 去重 / Parent 补全 / Ordering
  7. LLM 生成 → 带 Citation 的答案 可溯源

一个值得注意的细节：Candidate 最终是 70 而不是 100。为什么？因为 Dense 和 BM25 的 Top 50 存在交集——正确的 4.6.2 错误码说明，两路检索都会召回它。RRF 融合去重后，实际候选数小于两路之和。这也意味着：不要想当然地按「两路 K 值相加」来规划 Reranker 的 Batch Size，要在自己的数据上统计真实交集率。

在这个案例里，Reranker 完成的关键动作是：把「4.6.1 错误码说明」——那个 Embedding 空间里与正确答案几乎重合、RRF 排名还可能更高的危险候选——压到了 Top 5 之外。

最终建立核心认知

走到这里，系列前八篇的组件可以各归其位了。每一个组件回答一个不同的问题：

每个组件的职责边界
组件回答的问题

Million Documents

  ↓
Candidate Set
  ↓

  ↓
Reranker（Precision-oriented）
  ↓

  ↓

最后重申本篇的边界，避免矫枉过正：Reranker 不是必选项，它是一个需要用评测数据验证的工程决策；Cross-Encoder 不是万能的，它的精度优势以计算成本为代价；Reranker 不能弥补召回缺失，不能替代 Context Engineering，更不能消除所有幻觉。它能做的，是在召回已经正确的前提下，把最好的证据放到最前面——而这恰恰决定了 LLM 拿到的是清晰的路标，还是一堆语义相近的干扰项。

不过，你可能已经注意到一个贯穿全文的隐含假设：我们始终默认 Query 是一个「已经理解清楚」的输入。但开篇那个 Query 里藏着多少信息？「RTC-10027」是错误码，「4.6.2」是版本约束，「Android 14」是环境条件——系统真的理解这些吗？如果用户的原始问题是「为什么我用不了你们的 SDK」，我们连该检索什么都不知道。
