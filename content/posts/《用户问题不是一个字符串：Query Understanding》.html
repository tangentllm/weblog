01

同一个问题，为什么人能理解，搜索系统却搜不到？

先看一个我在企业项目里真实处理过的 Case。这是来自一个 RTC（实时音视频）技术支持知识库的用户提问：

真实用户 Query · 企业知识库

"我们这个 Android 新版本最近一上线，RTC 老是偶发连接失败，之前有没有类似问题？怎么排查？"

任何人读完这句话，都能立刻提取出其中的关键信息。但请注意——这句话里其实压缩了至少六个维度的结构化信息：

平台
Android
版本
新版本
业务
RTC
问题
连接失败
时间
最近 / 上线后
目标
历史相似问题 + 排查方案

而如果按照第 2~8 篇建立的标准链路，直接把整句话送进 Embedding：

问题不在于 Embedding 模型不够好，而在于这种用法从一开始就浪费了信息。"Android"应该变成 Metadata Filter，而不是和"排查方法"一起被压进同一个向量；"有没有类似问题"和"怎么排查"是两个检索目标，却被当成一个语义整体处理。

用户说的是"自然语言"，而 Retrieval 需要的是"可检索表达"。这两者之间隔着的一整层工程，就是本文的主题：Query Understanding。
02

Query Understanding 到底在解决什么问题？

从架构视角看，Query Understanding 是插在用户输入和检索系统之间的一个翻译层——但它翻译的不是"语言"，而是表达形态：

这一层可能包含的能力模块包括：

Query Understanding 能力清单
  • Intent Detection —— 用户是在排查问题、查概念，还是要做版本对比？
  • Entity Extraction —— 提取产品名、错误码、模块名等关键实体
  • Metadata Filter Extraction —— version / platform / product / doc_type 等结构化约束
  • Query Rewrite —— 把口语化、指代化表达改写成可检索表达
  • Query Expansion —— 扩展同义词、缩写、英文术语，扩大召回面
  • Query Decomposition —— 把复杂问题拆成多个子问题
  • Time / Version / Platform Resolution —— "最近""新版本"这类相对表达的绝对化

这些能力共同产出的，往往不是一句话，而是一个结构化的检索意图对象：

structured_query.json
{
  "query": "RTC Android 连接失败",
  "platform": "Android",
  "version": "latest",
  "issue": "connection failure",
  "intent": "troubleshooting",
  "time_range": "last_30_days"
}
Query Understanding 的目标，不是"把用户问题改写得更漂亮"，而是让 Retrieval 更容易找到真正相关的知识。判断一切 Query 处理手段是否合理的唯一标准：它是否提升了"正确文档进入候选池"的概率。
03

为什么原始 Query 经常不能直接检索？

在企业环境中，我几乎每周都能看到这类检索失败。归纳下来，原始 Query 的"不可直接检索性"主要来自六类问题——每一类我在生产系统里都踩过真实的坑。

问题 1 · 口语化

"这个东西怎么突然不工作了？"

"这个东西"是什么？"不工作"是崩溃、超时还是返回错误？Embedding 模型对模糊指代的容忍度，远没有人类想象的那么高。

问题 2 · 指代

"它为什么这样？"

脱离上下文，这句话对任何检索系统都是噪声。它必须先被"还原"才有检索价值。

问题 3 · 上下文依赖

USER怎么配置 Android SDK？
ASSISTANT……（介绍了通用接入流程）……
USER那 4.6.2 呢？

第二轮 Query "那 4.6.2 呢？"单独拿去检索，几乎不可能命中"RTC SDK 4.6.2 Android 配置差异"这类文档。多轮对话中的当前 Query，语义是不完整的。

问题 4 · 信息缺失

"报错了怎么办？"

什么产品？什么错误码？什么平台？Query 缺失的关键信息，检索系统无法凭空补齐——但至少应该识别出"这是一个信息不足的 Query"，而不是硬着头皮去搜。

问题 5 · 多意图

"这个错误是什么原因？怎么解决？有没有历史案例？"

一句话里包含三个不同的检索目标。单个 Query 的向量表示会在这三个意图之间"平均化"，导致每个方向都召回得不充分。

问题 6 · 领域术语与黑话

"RTC 挂了"

在企业内部，"挂了"的真实含义可能是"RTC 通道连接失败"。知识库文档里写的是规范术语，用户嘴里说的是黑话——两个表达空间之间存在系统性错位。

Query Understanding 的价值，是把"人类表达"转换成"检索系统可以更好处理的表达"。注意：是"更好处理"，而不是"必须处理"——有些 Query 直接送进去效果就很好，这是后文 Adaptive Retrieval 的出发点。
04

Query Rewrite：把问题改写成"可检索的问题"

Query Rewrite 是 Query Understanding 中使用频率最高的手段。它的流程非常朴素：

一个典型的企业案例：

Rewrite 示例 · 企业技术支持场景

原始 Query：

"这个错误是不是 4.6.2 才有？Android 14 上怎么处理？"

Rewrite 后：

"RTC SDK 4.6.2 Android 14 RTC-10027 错误原因与解决方案"

注意这个 Rewrite 做了什么：补全了隐含实体（RTC SDK、RTC-10027）、消除了指代（"这个错误"→ 具体错误码）、把疑问句式转换成了文档式表达。知识库文档是工程师写的，Rewrite 的作用就是让 Query 的表达方式向文档的表达方式靠拢。

05

什么情况下 Query Rewrite 才有价值？

先说一个我在做架构评审时反复强调的原则：Rewrite 不是默认开启的免费午餐。它在以下场景中收益明确：

Rewrite 高价值场景
口语化"RTC 挂了" → "RTC 通道连接失败"
省略主语"怎么初始化？" → "RTC Engine 初始化方法"
多轮对话"那 4.6.2 呢？" → 完整独立问题（详见第 06 节）
指代消解"它为什么报错" → "XX 功能为什么报错"
复杂表达多重条件压缩的长句 → 聚焦核心检索语义

Rewrite 最大的风险：Intent Drift

Rewrite 由 LLM 执行，而 LLM 有一个根深蒂固的倾向：它不仅想改写你的问题，还想"帮"你回答你的问题。这就产生了 Query Rewrite 最危险的失败模式——Intent Drift（意图漂移）：

Intent Drift 典型案例

用户："为什么 RTC 会断线？"（意图：诊断原因）

错误的 Rewrite："如何配置 RTC 重连？"（意图：配置操作）

这里发生的是：Rewrite 模型擅自把"诊断原因"替换成了"给出解法"。检索会命中一大堆重连配置文档，而真正分析断线根因的故障排查文档被完全错过。用户拿到答案后会觉得"系统答非所问"——但每一步单看都"看起来在正常工作"。

工程铁律：Rewrite 的唯一合法操作是改变"表达"，而不是改变"意图"。Rewrite Prompt 中必须显式约束这一点，并且 Evaluation 中必须有专门的 Intent Consistency 检查（见第 20 节）。
06

多轮对话：Context-aware Rewrite 是刚需，不是优化

企业 RAG 通常不是单轮问答。真实的技术支持对话长这样：

USER怎么接入 RTC SDK？
ASSISTANT接入 RTC SDK 首先需要在控制台创建应用……
USERAndroid 呢？
ASSISTANTAndroid 平台需要在 build.gradle 中添加依赖……
USER4.6.2 有区别吗？

第三轮的"4.6.2 有区别吗？"如果直接去检索，向量空间里它和任何文档都对不上。但结合上下文，真正的检索 Query 应该是：

"RTC SDK 4.6.2 Android 接入方式及与之前版本的差异"

这就是 Context-aware Query Rewrite（有时也叫 Query Condensation 或 Standalone Question Rewriting），流程如下：

多轮对话中的当前 Query，往往必须先恢复成"独立语义"，才有资格进入检索。这是企业 RAG 和 Demo RAG 的一道分水岭：Demo 里没有人会连续追问，真实用户一定会。

工程细节上要注意两点：第一，送入 Rewrite 的 History 不需要全部轮次，通常最近 2~3 轮足够且更稳定；第二，Rewrite 产出的 Standalone Query 应该被持久化记录——它是后续排查"为什么搜到了错误文档"的第一线索。

07

Query Expansion：不是改写，是扩展

Rewrite 解决的是"表达不对"的问题，而 Expansion 解决的是另一个问题：用户的表达是"对的"，但不覆盖知识库中所有的相关写法。

用户查询"RTC 连接失败"，但知识库里的文档可能分别使用了这些表述：

expansion_result.txt
原始 Query: "RTC 连接失败"

扩展 Query 项:
  → RTC connection failure          # 英文术语表达
  → RTC reconnect                   # 相关但不同词
  → RTC connection timeout          # 失败的一种具体形态
  → RTC channel join failure        # 频道加入失败（子场景）
  → RTC-10027                       # 该问题对应的内部错误码

Expansion 的目标很明确：增加可能命中的词项和表达。尤其在企业场景中，同一种问题散落在故障报告、错误码手册、FAQ、英文文档中，用词各不相同——单一 Query 几乎不可能同时覆盖。

实现方式上，Expansion 通常输出多个 Query 变体，分别检索后做结果融合（Fusion）；对于 Term 级别的扩展，也可以直接注入 BM25 的同义词词典（Synonym Dictionary），这是更传统但延迟更低的做法。

08

Rewrite 与 Expansion：必须分清的两个概念

实践中我看到太多团队把这两者混为一谈，导致架构设计错位。它们的本质区别是：

能力Query RewriteQuery Expansion
核心目标改写表达，使问题可检索扩展召回面，覆盖更多表达
Query 数量通常 1 个通常多个
主要风险Intent Drift（意图漂移）Query Noise（查询噪声）
适合场景口语化 / 多轮 / 指代术语 / 同义词 / 缩写 / 黑话
主要作用提高可检索性提高 Recall
一句话记忆：Rewrite 改变的是"这句话怎么说"，Expansion 改变的是"用几句话去搜"。前者不增加检索次数，后者通常会增加。
09

Multi-Query Retrieval：从多个视角覆盖一个复杂问题

当用户的问题天然包含多个检索角度时，单个 Query——无论改写得多好——都只能提供一个视角。Multi-Query 的做法是让 LLM 从同一问题中生成多个互补 Query，分别检索后融合：

复杂企业 Query 示例

"Android 14 上 RTC 4.6.2 出现 RTC-10027，怎么排查、为什么发生、有没有解决案例？"

multi_query_plan.txt
Q1: RTC 4.6.2 Android 14 RTC-10027 发生原因
Q2: RTC-10027 排查方法与诊断步骤
Q3: RTC-10027 历史解决案例与修复记录
Multi-Query 的本质，是从多个检索视角覆盖一个复杂问题。第 8 篇的 Reranker 只能对"已经进入候选池"的文档排序——Multi-Query 决定的是"哪些文档有机会进入候选池"。
10

Multi-Query 不是免费的 Recall 提升器

很多团队上线 Multi-Query 后发现：Recall 指标确实好看了一点，但系统整体变"糊"了。原因在于 Multi-Query 有一条完整的代价链：

具体来说，Multi-Query 引入的问题包括：

  • Retrieval 次数增加 —— N 个 Query 意味着 N 路向量检索 + N 路 BM25；
  • Latency 增加 —— 即便并行执行，融合前的最慢一路决定尾延迟；
  • 成本增加 —— Query 生成需要一次 LLM 调用，检索需要 N 倍计算；
  • Query Noise 增加 —— 生成的子 Query 可能偏离原始意图，召回无关文档；
  • 结果重复增加 —— 同一文档被多路命中，需要去重与融合策略；
  • Fusion 复杂度增加 —— RRF 中各路权重的公平性成为新的调参问题。
Multi-Query 是以计算成本换取 Retrieval Coverage。它应该被路由触发，而不是被默认执行——这正是第 16 节 Query Router 存在的理由。
11

Query Decomposition：把复杂问题拆成子问题

有一类问题，不是"表达不好"，而是结构上就无法用一次检索回答：

需要 Decomposition 的企业 Query

"比较 RTC 4.6.1 和 4.6.2 在 Android 14 上的兼容性，并说明 RTC-10027 是否只存在于 4.6.2。"

这个问题需要三份互相独立的知识，缺一份答案就不完整。正确的做法是拆解：

decomposition_plan.txt
Q1: RTC 4.6.1 Android 14 兼容性
Q2: RTC 4.6.2 Android 14 兼容性
Q3: RTC-10027 出现在哪些 SDK 版本

三个子问题独立检索，各自召回各自的证据，最终由生成阶段汇总比较。Decomposition 产出的不是"同一个问题的不同说法"，而是"回答原问题所必需的多个信息块"。

12

Decomposition 与 Multi-Query：别再混用这两个词

这是本文需要第二次"划清界限"的地方。两者都会产出多个 Query，但动机完全不同：

  • Multi-Query 的多个 Query —— 为的是从不同表达方式寻找相似信息，子问题之间是并列冗余的，任意一路都独立可用；
  • Query Decomposition 的多个 Query —— 为的是把一个复杂问题拆成多个相互关联的子问题，子问题合在一起才构成完整答案，缺任何一个答案都不完整。
Multi-QueryQuery Decomposition
目标增加检索视角拆解复杂任务
子问题关系通常并列、可冗余可能有依赖关系
缺失子问题的后果影响不大（仍有召回）答案不完整甚至错误
适合场景提高召回覆盖多实体 / 多条件 / 比较类问题
实现复杂度中高（需考虑子问题依赖与答案合成）
一个实用的判别方法：把任意一个子 Query 单独拿掉，答案还完整吗？完整 → Multi-Query；不完整 → Decomposition。
13

HyDE：让 LLM 先"假装回答"，再拿回答去搜

HyDE（Hypothetical Document Embeddings）是 Query Understanding 中最"反直觉"的一个技术：不拿 Query 去搜，而是先让 LLM 生成一个假设性的答案文档，拿这个假设文档的向量去搜。

企业场景示例——用户查询：

"RTC-10027 怎么解决？"

LLM 先生成一段假设性文档：

"RTC-10027 错误通常与 Android 14 环境下的网络权限配置有关。排查时应首先检查 AndroidManifest 中的 INTERNET 权限声明，其次确认 SDK 初始化时传入的 AppKey 是否与当前环境匹配……"

注意：这段假设文档的内容可能是错的——但这不影响它的用途，因为我们只用它的向量，不用它的内容。

14

HyDE 为什么可能有效？又为什么会失效？

HyDE 有效性的根源在于向量空间的不对称性。"怎么解决？"是一个非常短的 Query：

asymmetry.txt
Query:        "怎么解决？"          # 4 个字，语义极稀薄

Hypothetical: "RTC-10027 可能与 Android 14 环境下…"  # 数百字
              # 充满领域术语、排比结构、文档式表达

Knowledge Doc: 与 Hypothetical 处于相近的表达空间

知识库文档都是"答案形态"的长文本，而用户 Query 是"问题形态"的短文本——两者在向量空间中存在系统性距离。HyDE 用一个"答案形态"的代理文本，跨越了这道距离。

但必须立刻说清楚它的另一面——HyDE 会引入生成误差：

更隐蔽的是，HyDE 的失败不表现为报错，而表现为"自信地搜错方向"——假设文档中的错误实体（比如幻觉出一个不存在的配置项）会把检索拉向一片错误的文档区域，而且系统没有任何告警。

结论：HyDE 不是"一定提高 Retrieval"的技术，而是一种在特定条件下有效的向量空间对齐手段。它最适合：Query 极短、语义密度低、且领域术语可预期的场景；最不适合：实体密集、错误码明确的 Query——这类 Query 直接走 BM25 效果更好也更便宜。
15

Query Understanding 的另一半：Metadata Filtering

前面讲的所有手段都在优化"语义匹配"，但企业 RAG 中有一类信息根本不需要语义匹配——结构化约束。

从 Query "4.6.2 Android 的 RTC 错误码"中，我们不应该只产出一个改写后的字符串，而应该同时提取出：

metadata_filter.json
{
  "version": "4.6.2",
  "platform": "Android",
  "product": "RTC",
  "doc_type": "error_code"
}

这些 Filter 在检索阶段作为硬约束生效：

Query Understanding 不只是改写 Query，还可以把自然语言转换成结构化 Retrieval Constraints。这是企业 RAG 与普通 Demo RAG 最重要的区别之一：企业知识天然带有版本、平台、产品线、文档类型等强结构，不用等于浪费。

依赖的前提是：Chunking 阶段（第 2 篇）必须为每个 Chunk 打好 Metadata。如果入库时没有 version / platform 字段，Query 侧提取得再准也无法过滤——Query Understanding 和 Index Schema 是一对必须共同设计的契约。

16

Query Routing：不同的 Query，不该走同一条流水线

到目前为止我们介绍了 Rewrite、Expansion、Multi-Query、Decomposition、HyDE、Metadata Extraction 六种手段。一个自然的诱惑是：把它们全串起来，让所有 Query 都走一遍。

这是企业 RAG 中最常见、代价也最高的架构错误。正确的做法是先问：这个 Query 属于哪一类？

routing_examples.txt
"什么是 RTC？"              → Semantic Retrieval（简单语义）
"RTC-10027"                 → Keyword / BM25 First（精确错误码）
"比较 4.5.0 和 4.6.2"       → Multi-Step Retrieval（拆解比较）
"帮我总结这三份文档"        → Document Retrieval + Summarization
不同 Query 使用不同 Retrieval Strategy，通常比所有 Query 强行经过复杂 Pipeline 更合理。Router 本身可以是一个轻量分类模型，也可以是一次廉价的 LLM 分类调用——关键是这个决策必须被记录，成为可分析的数据。
17

Adaptive Retrieval：让检索策略跟着 Query 走

Query Router 回答"走哪条路"，Adaptive Retrieval 更进一步：根据 Query 的复杂度和特征，动态决定 Pipeline 的深度。

Query 特征示例推荐策略
简单事实型"什么是 RTC？"Dense + BM25，直接检索
复杂排查型"偶发连接失败怎么排查？"Rewrite + Hybrid + Rerank
多实体比较"比较 4.6.1 和 4.6.2"Decomposition + 分步检索
明确错误码"RTC-10027"BM25 First，精确匹配优先
极短语义型"怎么解决？"+ 明确上下文可考虑 HyDE
工程经验：Adaptive 逻辑初期不需要做得很聪明。先用 3~5 条简单规则覆盖 80% 的流量（比如"包含错误码格式 → BM25 First"），剩余流量回退到默认 Hybrid Pipeline，再根据线上 Query 分布逐步细化。一上来就训练 Router 模型，往往是过度设计。

Query Understanding 的工程代价

任何 Query Transformation 都不是免费的。在架构评审时，我要求团队对每一项 Query 处理能力回答四个问题：

🎯
Accuracy
可能提高 Retrieval 质量——但"可能"意味着必须用 Evaluation 证明，而不是假设。收益因 Query 分布而异。
⏱️
Latency
Rewrite / HyDE / Multi-Query 生成均需 LLM 调用，通常增加 300ms~2s 的首字节延迟，是用户体感最敏感的代价。
💰
Cost
每次 Transformation 都是 Token 消耗。多轮场景下，每一轮都要为 Context + Rewrite 付费，成本随对话深度累积。
🎲
Stability
Rewrite 可能产生 Intent Drift，且 LLM 输出有随机性——同一个 Query 不同时刻可能被改写成不同检索意图。
🔍
Observability
每次请求必须完整记录：Original Query、Rewrite Query、Expanded Queries、Sub Queries、Metadata Filter、Router Decision。没有这条链路，Retrieval 出问题时你连"是搜错了还是没搜到"都分不清。
query_trace.log · 必须持久化的观测字段
original_query:      "那 4.6.2 呢？"
rewrite_query:       "RTC SDK 4.6.2 Android 接入方式及版本差异"
expanded_queries:    ["RTC 4.6.2 release notes", ...]
sub_queries:         []
metadata_filter:     {"version": "4.6.2", "platform": "Android"}
router_decision:     "hybrid_with_filter"
router_confidence:   0.93
latency_ms:          {"rewrite": 640, "retrieval": 120, "rerank": 210}
Query Transformation 必须可观测，否则 Retrieval 出问题时，你很难定位到底是"谁改变了 Query"。在事故复盘里，"原始 Query 和最终检索 Query 之间的每一次变换"都应该可以被逐帧回放。

如何评估 Query Understanding？

评估的核心思路是A/B 对照：同一批标注 Query，分别走 Baseline 和加 Query Understanding 的链路，比较检索指标：

指标层面，沿用第 8 篇的检索评估体系，额外增加成本维度：

  • Recall@K / MRR / NDCG / Precision@K —— 检索质量核心指标
  • Query Success Rate —— Top-K 中至少包含一条可用文档的 Query 占比（最贴近用户体感）
  • Latency P50 / P99 —— Transformation 引入的延迟增量
  • Token Cost / Query —— 单次问答的平均 Transformation 成本

质量专项层面，有三个指标无法用自动化指标覆盖，必须抽样人工审计：

三类专项审计
  • Rewrite Quality —— Rewrite 前后用户意图是否一致？重点抓 Intent Drift；
  • Filter Accuracy —— 提取的 version / product / platform 是否正确？错误 Filter 会让正确文档被硬过滤掉，这类错误比召回不足更致命；
  • Query Diversity —— Multi-Query 生成的多个 Query 是否真的产生互补的召回结果？如果各路召回高度重合，Multi-Query 只是白白多花了 N 倍成本。
一个容易被忽略的结论：如果 Query Understanding 带来的 Recall 提升小于 3~5 个百分点，而 Latency 增加了 1 秒以上，多数企业场景下这笔交易是不划算的。评估必须同时看质量和代价两端。

九个真实失败案例

以下案例全部来自真实生产环境或架构评审中发现的问题。每个案例我都附上了对应的修复方向。

失败 1 · Rewrite 改变了用户意图

用户问"为什么 RTC 会断线"（诊断原因），Rewrite 成"如何配置 RTC 重连"（配置操作）。检索命中的全是配置文档，根因分析文档被错过。

修复：Rewrite Prompt 中显式声明"不得改变问题的疑问类型和意图"，并建立 Intent Consistency 抽检机制。

失败 2 · Expansion 引入大量不相关同义词

"连接失败"被扩展出"推流失败""播放卡顿""回声"等十余个变体，候选池被噪声淹没，Reranker 压力剧增，最终排序质量反而下降。

修复：限制扩展数量（通常 ≤5），扩展项需与原 Query 做语义相似度校验后再进入检索。

失败 3 · Multi-Query 生成的是"换说法的同一个问题"

三个子 Query 召回结果重合度超过 90%，等于花了三倍成本做了一遍同样的事。

修复：Prompt 中要求子 Query 明确覆盖不同侧面（原因 / 排查 / 案例），并上线 Query Diversity 指标监控。

失败 4 · Decomposition 拆得过细

一个两跳问题被拆成七个原子子问题，每个子问题的答案都太碎片化，生成阶段无法把它们组装成连贯回答。

修复：Decomposition 粒度以"能独立检索到一段完整证据"为下限，并限制最大子问题数。

失败 5 · HyDE 幻觉出错误实体

假设文档中幻觉出一个不存在的配置参数，向量被拉向一片完全错误的知识区域，且全程无任何告警。

修复：HyDE 仅用于极短、低实体 Query；对含错误码、版本号等硬实体的 Query 强制关闭 HyDE。

失败 6 · Query Router 判断错误

包含错别字的复杂排查 Query 被误判为"简单 Query"，跳过 Rewrite 直接检索，结果惨不忍睹。

修复：Router 输出置信度，低置信度时回退到更"重"的默认 Pipeline（fail-safe 到复杂路径，而不是简单路径）。

失败 7 · Metadata Filter 提取错误

用户说"新版本"，系统错误提取为 version=4.6.3（实际是 4.6.2），正确的文档被硬过滤，召回为零。

修复：提取结果与知识库的实际枚举值做校验；无法确定时降级为软过滤（boost 而非 filter）。

失败 8 · 所有 Query 强制 Rewrite

"什么是 RTC？"这样的简单 Query 也被送进 Rewrite，P99 延迟从 1.2s 涨到 2.8s，效果几乎没有变化。

修复：按 Query 特征做条件触发——这是 Adaptive Retrieval 的直接动机。

失败 9 · 无法追踪"原始 Query → 最终 Query"的变换链

检索出问题后，团队争论了两天"到底是 Rewrite 改错了还是索引有问题"——因为没人记录中间变换。

修复：第 19 节的 Query Trace 持久化，作为所有 Query Transformation 的强制要求。

最后，给出整合了全部内容的端到端 Query Pipeline。它衔接第 8 篇的 Hybrid Retrieval + RRF + Reranker，是它们的"上游供给系统"：

Query Understanding 是 Retrieval 之前的"问题工程"。Chunking 决定"知识怎么存"，Query Understanding 决定"问题怎么问"——两者共同决定了正确文档能不能相遇。

最后给出一个 Python 层面的 Query Transformation 骨架，展示各模块如何在代码中协作：

query_transformation.py
from dataclasses import dataclass, field

class QueryTransformer:
    """企业级 Query Transformation 编排器。
    核心原则：默认最简，按需增强，全程可观测。"""

    def __init__(self, llm, router):
        self.llm = llm
        self.router = router          # Query Router：决定策略组合
        self.trace = []               # 强制记录变换链（失败案例 9 的教训）

    def transform(self, query: str, history: list) -> "TransformedQuery":
        plan = self.router.route(query, history)
        self.trace.append(("original", query))

        current = query
        # 1) 多轮对话 → Standalone Query（仅当 router 判定存在上下文依赖）
        if plan.needs_condensation and history:
            current = self.llm.rewrite_with_context(current, history)
            self.trace.append(("standalone_rewrite", current))

        # 2) 结构化提取：语义不变，只加约束
        filters = self.llm.extract_filters(current)
        filters = self.validate_against_schema(filters)  # 防失败案例 7

        # 3) 按策略生成检索 Query 集合 —— 三选一，而非全做
        if plan.strategy == "decompose":
            queries = self.llm.decompose(current)          # 子问题，缺一不可
        elif plan.strategy == "multi_query":
            queries = self.llm.multi_query(current, max_n=3)
            queries = self.dedup_and_check_diversity(queries)  # 防失败案例 3
        elif plan.strategy == "expand":
            queries = self.llm.expand(current, max_n=5)   # 防失败案例 2
        else:
            queries = [current]                            # 默认最简

        return TransformedQuery(queries=queries, filters=filters,
                                trace=self.trace)

@dataclass
class TransformedQuery:
    queries: list
    filters: dict
    trace: list = field(default_factory=list)
24

最终核心认知

整篇文章可以浓缩成一条思考链。面对任何用户输入，一个成熟的企业 RAG 系统应该依次回答这些问题：

Query 思考链
  1. What does the user mean? —— 用户真正想问什么？
  2. What entities are involved? —— 涉及哪些产品、版本、错误码？
  3. What constraints exist? —— 存在哪些结构化过滤条件？
  4. What retrieval strategy should be used? —— 该用哪种检索策略？
  5. What query should actually be searched? —— 真正应该拿去搜索的是什么？
  6. Retrieval. —— 然后才开始检索。
Query Understanding 的价值，不是把 Query 变复杂，而是让系统更准确地理解"用户真正想找什么"。一个成熟的企业 RAG，不应该只有一个固定 Retrieval Pipeline，而应该能够根据 Query 特征选择合适的检索策略。

回到开篇那个 RTC 连接失败的案例。经过本文的完整处理，那条口语化的长句最终变成了：一个 Standalone Query、一组 Metadata Filter、以及一个由 Router 决定的 Hybrid 检索策略——用户没有改一个字，但系统"听懂"了。
