SECTION 01

开篇：检索正确，答案却错了

这是我在生产环境里被问得最多的一个问题，也是本文唯一要回答的问题。

假设你负责一个 RTC（实时音视频）SDK 的企业技术支持 RAG 系统。一位 Android 开发者发起提问：

QUERY EXAMPLE 01 · 技术支持
"RTC SDK 4.6.2 在 Android 14 上出现 RTC-10027，官方推荐怎么处理？"

经过前九篇构建的检索链路——Chunking、Embedding、Dense + Sparse Retrieval、RRF、Reranker——系统成功召回了如下候选集：

候选文档内容相关性判定
Document ARTC SDK 4.6.2 Android 错误码说明✅ 高度相关（答案所在）
Document BRTC SDK 4.6.2 Android 接入指南✅ 相关
Document CRTC SDK 4.5.0 错误码说明⚠️ 旧版本，语义高度相似
Document DAndroid 14 通用兼容性问题⚠️ 部分相关
Document ERTC SDK 弱网优化方案⚠️ 弱相关

检索是成功的——Document A 明确就在候选集中。接下来最自然的做法是什么？把 A 到 E 全部拼接起来塞给 LLM：

Fig.1 — 朴素做法：全量拼接，把判断全部交给 LLM

结果呢？答案仍然可能出现以下任一问题：

  • 版本混淆：旧版本 4.5.0 的处理方式混入了 4.6.2 的答案；
  • 信息冲突：不同版本文档给出不同配置，模型"各取一半"；
  • Context 过长：正确内容被大量噪声包围，注意力被稀释；
  • 重复信息：同一事实在多个 Chunk 中反复出现；
  • 重点被稀释：真正关键的 RTC-10027 处理步骤，淹没在数千 Token 中。
Retrieval 找到"正确候选"之后，系统仍然需要决定：哪些信息真正值得进入 Context。这就是 Context Engineering 要解决的问题。
SECTION 02

Context Engineering 到底是什么？

很多人把 Context Engineering 理解为"给 Prompt 填充上下文"——这是 Demo 视角的理解。从系统工程角度，它是检索完成之后、生成开始之前的一整条信息加工流水线：

Fig.2 — Context Engineering：一条信息加工流水线，而不是一次字符串拼接
Context Engineering 的本质，是把大量候选信息转换成 LLM 最容易正确使用的最小有效上下文。
⚠️ 概念澄清
Context Engineering ≠ Prompt Engineering。Prompt Engineering 解决的是"告诉模型应该怎么工作"；Context Engineering 解决的是"告诉模型应该依据哪些信息工作"。两者是互补关系，不是同一件事，也不是替代关系。第 17 节会专门讨论这条边界。
SECTION 03

检索正确，为什么答案仍然可能错误？

先建立一个贯穿全文的认知模型。RAG 的生成质量不是由检索质量单方面决定的，而是经过两层传递：

Fig.3 — 检索质量不会自动传递到生成质量，中间隔着一层 Context 质量

这一层传递为什么会"漏"？我归纳为七类典型机制，每一种都在生产环境反复出现过：

① 太多
正确内容被大量噪声包围，信号被稀释
② 重复
同一事实多次出现，浪费 Token 与注意力
③ 冲突
新旧版本文档同时在场，模型混着用
④ 乱序
关键信息落在模型利用率最低的位置
⑤ 不完整
只召回孤立 Chunk，缺少必要上下文
⑥ 超预算
触发截断，恰好在答案附近被切掉
⑦ 不使用
模型忽略证据，退回自身参数知识作答

其中第 ⑦ 类最隐蔽：即使 Context 完美，LLM 也可能"读过但不信"，优先使用预训练时记住的旧答案。Context Engineering 无法完全消除这一问题，但结构清晰、来源明确、体量精炼的 Context，能显著提高模型依据证据作答的概率。

✕ 错误归因，错误修复
生产中我看到太多团队，遇到这类问题先去改 Prompt——"请严格依据上下文回答！"改了十轮没有本质改善。因为问题不在指令层，而在信息层。再漂亮的 Prompt，也无法弥补错误的 Context。
SECTION 04

Context Selection：Top-K 是不是越多越好？

Context Engineering 的第一步是 Selection——从 Candidate Set 里挑出真正进入 Context 的那一小部分。

先回答一个高频问题：为了保险，把 Reranker 的 Top-K 设成 50 行不行？看一下候选规模增长时各维度的变化：

候选规模RecallNoiseToken 成本Latency答案质量
Top 5较低低低低取决于命中率
Top 10较高可控中中通常最优区间
Top 20高明显上升高中高开始波动
Top 50很高高很高高经常不升反降

规律很清晰：候选越多，Recall 上升，但 Noise、Token 与 Latency 同步上升。检索阶段的 K 应该为 Recall 服务，Context 阶段应该为 Precision 服务——两者不应该是同一个数字。

Fig.4 — 从 Candidate Set 到 Context，是一个不断收窄的漏斗
Reranker 的 Top-K 是候选，不是Context。把两者混为一谈，是 Context Engineering 最常见的起点性错误。
SECTION 05

为什么不能只按 Reranker 分数选 Context？

假设 Reranker 给出如下分数：

Doc A = 0.95
Doc B = 0.93
Doc C = 0.92
Doc D = 0.91
Doc E = 0.90
Doc F = 0.87   # 分数最低，却可能最关键

一个看似合理的选择是：取 Top-5（A~E），丢弃 F。但请考虑一种生产中极其常见的情况——A~E 全部来自同一份文档的相邻 Chunk，比如《RTC SDK 4.6.2 错误码手册》被切成 5 段，每一段都在讲 RTC-10027 的描述。

把它们全部放进 Context，得到的是同一信息重复五遍。而 F——比如一篇讲"RTC-10027 实际是一个需要手动关闭硬件回声消除的已知问题及修复步骤"的 Release Note——虽然分数只有 0.87，却提供了 A~E 完全没有覆盖的关键解决步骤。

✕ 常见误判
"Reranker 分数最高的 Top-K，就是最好的 Context 组合。"

正确的认知是："相关性最大"不等于"Context 组合最好"。Reranker 评估的是单个 Chunk 与 Query 的相关性；而 Context 评估的应该是一组 Chunk 合起来能否完整支撑回答。前者是逐项打分，后者是组合优化。

这也说明了一件事：Reranker 和 Context Engineering 不能互相替代。Reranker 负责"排序候选"，Context Builder 负责"组装证据组合"——它们是流水线上前后两个职责不同的工位。

SECTION 06

Context Diversity：相关且不重复

既然"全选高分"会导致同质化，目标就变成了：Relevant + Diverse——每一条都相关，且彼此互补。

回到开篇的例子。一个理想的 Context 组合应该像这样：

❌ 只按分数选（同质化）✅ Diversity 选（互补）
组合内容Chunk A
Chunk A-1（A 的下一段）
Chunk A-2
Chunk A-3
Chunk A-4		Chunk A · 错误码定义与原因
Chunk F · 解决步骤
Chunk B · 配置要求
Chunk D · Android 14 已知兼容案例
信息增益每加一条，新增信息趋近于零每条都带来新的信息维度
可回答性能描述问题，答不出步骤原因 + 步骤 + 配置 + 案例，可完整作答

实现 Diversity 的常用手段有四类：

  • MMR（Maximal Marginal Relevance）：在相关性/冗余度之间做显式权衡（下一节展开）；
  • Deduplication：先去重再做多样性选择（第 8 节）；
  • Source Diversity：限制同一来源文档占据的席位上限，比如"单一文档最多贡献 2 个 Chunk"；
  • Section Diversity：结合 Chunk 的结构信息，优先覆盖"原因 / 步骤 / 配置 / 案例"等不同章节类型。
✓ 工程建议
Source Diversity 是其中投入产出比最高的一条：它只需要 Metadata 里记录 document_id，就能避免"一份文档垄断 Context"这类最常见的退化，几乎零额外成本。
SECTION 07

MMR：在"相关"与"不重复"之间做平衡

MMR（Maximal Marginal Relevance）是 Diversity Selection 中最经典、也最容易被误解的算法。它的选样标准是：

MMR(Di) = λ · Sim(Q, Di) − (1 − λ) · maxDj ∈ S Sim(Di, Dj)
Q 为 Query，S 为已选入 Context 的文档集合；每轮从未选中集合中选取 MMR 得分最高者加入 S

逐项拆解：

  • 第一项 λ · Sim(Q, Di)：候选与 Query 的相关性——保证选出来的东西"有用"；
  • 第二项 (1−λ) · max Sim(Di, Dj)：候选与已选集合中最相似成员的相似度，作为惩罚项——保证新成员"带来新信息"；
  • λ：权衡系数。λ 趋近 1 时退化为普通 Top-K 按相关性排序；λ 趋近 0 时过度追求差异性，可能选出"不相关但独特"的内容。
Fig.5 — MMR 的直觉：在 A/B/C 冗余簇中只取代表，把席位让给信息维度不同的 F、G
⚠️ 保持克制
不要把 MMR 神化。它不是唯一正确的 Context Selection 方法——Embedding 空间中的"相似"并不严格等于"语义冗余"，λ 也需要按业务调参。实践中，"Dedup + 单文档席位上限 + 分数阈值"这套简单策略，往往已经能解决 80% 的同质化问题，MMR 是在此之上的精调手段。
SECTION 08

Context Deduplication：重复从哪里来？

企业 RAG 的候选集里，重复几乎不可避免。重复的来源至少有四类，各自的成因和对策不同：

重复类型成因典型表现推荐检测方式
文档重复同一文档的多个版本/多次入库同一份手册的 v1、v1.1 同时在库文档指纹 / Hash + Metadata
Chunk 重叠Chunking 时设置了 Overlap相邻 Chunk 有 10~20% 内容完全相同精确匹配 / MinHash
多路召回重复Dense 与 BM25 召回同一 ChunkRRF 前同一 chunk_id 出现两次按 chunk_id 精确去重
Parent-Child 重复Child 命中后，Parent 整段也进入候选Child 内容是 Parent 的子集层级关系检查 / 包含判定

检测手段分两个层次：

  • Exact Dedup（精确去重）：Hash、chunk_id 对齐。快、零误杀，应无条件先做；
  • Semantic Dedup（语义去重）：Embedding 相似度超过阈值即视为重复。能抓住"换了措辞的同一事实"，但有误杀风险——两段相似的文字可能一个说 4.5.0、一个说 4.6.2，语义去重前必须先过版本检查。
Fig.6 — 分层去重：Document → Chunk → Semantic
SECTION 09

Context Compression：压缩是有损操作

当筛选和去重之后 Context 依然过大，就需要压缩：

Fig.7 — 压缩：从"大而全"到"小而准"

压缩有三条技术路线，风险特征完全不同：

Extractive Compression（抽取式）

只保留原文中与 Query 相关的句子，不做任何改写。保真度最高，因为每个字都来自原文；但抽取器本身可能漏掉关键条件句——比如"仅在关闭硬件 AEC 时生效"这种限定语被丢弃后，答案就从"正确"变成"部分正确"。

Abstractive Compression（摘要式）

由模型对原文做概括。Token 压缩率最高，但风险也最大：概括过程可能丢失数字、版本号、条件限定——这些恰恰是技术文档里最要命的细节。

LLM-based Compression（模型提取式）

让一个（通常是更便宜的）模型面对多份文档，只提取与 Query 相关的事实。它介于两者之间，且天然支持"跨文档对齐"——比如同时看到 4.5.0 和 4.6.2 的文档时，可以只提取 4.6.2 相关内容。但同样存在幻觉与丢细节风险。

⚠️ 核心原则
压缩本身是有损操作。不要默认"压缩一定提升质量"——它提升的是 Token 效率，换来的是信息损失风险。企业知识库（错误码、版本号、配置参数）这类高事实密度场景，应优先选择 Extractive 或不做压缩，把预算花在 Selection 的精度上；只有当 Context 远超预算、且内容以叙述性文字为主时，才启用 Abstractive / LLM-based Compression。
SECTION 10

Context Ordering 与 Lost in the Middle

同样的文档集合，摆放顺序不同，模型的使用效果不同。这不是玄学，而是 Transformer 注意力分布的真实特性。

Liu et al. 在 2023 年的论文《Lost in the Middle》中给出了关键发现：当关键信息位于长上下文的中间位置时，模型的利用率显著低于位于开头或结尾时的水平——利用率随位置呈 U 形分布：

Fig.8 — Lost in the Middle：关键证据放在中间，最容易被模型"视而不见"（示意曲线）

由此，Ordering 有几种可选策略，各自适配不同场景：

策略做法适用场景注意点
Most Relevant First最高分放最前通用默认；短 Context长 Context 时中段仍会衰减
Most Relevant Last最高分放最后（靠近 Query）Context 较长、Query 在末尾的 Prompt 结构与 Prompt 模板强耦合
两端放置最重要两条放首尾长 Context + 多证据支撑需要至少两条"关键证据"
Chronological按更新时间排序时效敏感的知识库需搭配"最新优先"而非纯粹时间序
Version / Authority Priority按版本与来源权威度排序企业多版本文档需要 Metadata 支撑

以开篇的 RTC 技术支持场景为例，一个合理的阅读顺序应该是：

Fig.9 — 企业技术文档的推荐排序：新版本在前，历史版本殿后并显式降权
Context Ordering 本质上是在设计"模型阅读这批证据的顺序"——它决定了模型在注意力分配时，谁先被看见、谁被反复回看。
SECTION 11

版本冲突：企业 RAG 最典型的坑

企业知识库天然是多版本的。用户这样问：

QUERY EXAMPLE 02 · 多版本文档
"RTC SDK 4.6.2 的音频前处理应该怎么配置？"

而知识库里同时存在：

RTC SDK 4.5.0 文档：  配置 A（已废弃，含已删除的参数）
RTC SDK 4.6.1 文档：  配置 A'（部分适用）
RTC SDK 4.6.2 文档：  配置 B（正确答案）

由于三个版本的文档在语义上高度相似（都讲"音频前处理配置"），检索几乎必然同时召回。如果一起进入 Context，LLM 的典型行为是：混合多个版本，给出一个现实中不存在的配置——参数名来自 4.6.2，默认值来自 4.5.0，调用时机来自 4.6.1。每一段都"看起来有出处"，合起来是错的。

因此 Context Builder 必须内建版本治理能力：

Fig.10 — 版本治理三步：识别 → 定优先级 → 消解冲突
✓ Metadata 的第二次生命
很多团队以为 Metadata（version、updated_at、source）只在检索过滤时有用。实际上，Metadata 在 Context Engineering 阶段依然发挥作用——版本优先级、时间排序、来源标注、Citation 结构，全部依赖它。Chunk 入库时省掉的每一个 Metadata 字段，都会在 Context 阶段加倍偿还。
SECTION 12

Source Authority：不是所有文档都同等可信

企业知识库里的信息来源五花八门，可信度天然不同：

来源类型典型内容可信特征
官方技术文档产品手册、API Reference最权威，但可能存在多版本
内部知识库内部 Wiki、运维手册权威度较高，更新可能滞后
FAQ高频问题标准答案经过审核，覆盖面窄
历史工单真实案例与处理过程实战价值高，但可能含过期结论
论坛 / 社区讨论帖、经验贴参考价值，噪音大
用户上传文档第三方资料可信度最低，需谨慎使用

一个常见的参考排序是：官方最新文档 > 官方历史文档 > 内部经验 > 非正式来源。它体现为两个动作：

  • Context Ranking：同分情况下，权威来源优先入选、优先排序；
  • Conflict Resolution：当权威来源与非正式来源冲突时，以权威来源为准，或在 Context 中显式标注分歧。
⚠️ 不要照抄别人的排序
上面这个排序只是示例。Source Authority 必须由业务定义——在某些企业里，内部运维手册的可信度高于官方文档（因为它记录了本企业环境的真实约束）；在某些场景里，最新工单结论比去年的官方文档更准确。架构师要做的是提供 Authority 机制，具体等级表交给业务方维护。
SECTION 13

Context Budget：Context Window ≠ 可用 Token

生产环境中最容易被低估的问题：Token 预算管理。先给定义：

Context Budget = 分配给"检索证据"的最大 Token 数。

很多团队的第一反应是：模型有 128K 窗口，Context 随便塞。但模型窗口是要被多个部分分食的：

Fig.11 — 完整 Token Budget：Context 只是窗口的一部分，且必须为 Output 预留空间

这带来一个违反直觉但极其重要的结论：

✕ 生产事故复盘中的高频发现
如果 Context 占满了整个窗口，模型连生成答案的空间都没有——轻则输出被截断，重则服务端直接报 context length exceeded。而在截断发生的场景里，被切掉的往往恰好是排在 Context 末尾、也就是排序策略刻意安排的关键证据。

Context Window ≠ Retrieval 可以使用的全部 Token。

预算划分没有放之四海皆准的比例——它取决于任务类型（FAQ 短答还是报告生成）、模型窗口大小、对话长度分布。架构师要做的是把预算显式化、参数化，而不是让各个模块无意识地争抢同一个窗口。

SECTION 14

长上下文模型，意味着 RAG 可以无限塞文档吗？

必须明确回答：不是。每当新的长窗口模型发布，都会有团队尝试"把整个知识库塞进去，省掉检索"。这条路在企业场景走不通，原因有六：

Token Cost
长 Context 按输入 Token 计费，成本随文档量线性甚至超线性增长
Latency
检索与 Prefill 时间显著上升，首 Token 延迟恶化
Attention Cost
注意力计算随序列长度增长，吞吐下降
Noise
无关内容比例上升，正确信息被稀释
Conflicts
更多新旧版本同场，冲突概率上升
Lost in Middle
窗口越长，中段利用率问题越严重
更大的 Context Window 不等于更大的有效 Context。长上下文模型改变的是"能装多少"，而 Context Engineering 解决的是"该装什么、怎么装"——后者不会因为窗口变大而消失，反而因为可塞的东西变多而更加重要。
SECTION 15

Conversation History 与 Retrieved Context：两本账要分开管

企业 RAG 几乎都是多轮对话形态。完整的 Prompt 结构是：

System Prompt
+ Conversation History   # 多轮对话，越聊越长
+ Retrieved Context      # 本轮检索证据
+ Current Query

问题在于：对话历史是无界增长的，而 Context Budget 是有限的。用户聊到第 15 轮时，历史可能已经吃掉大半窗口，Retrieved Context 反而没有足够空间——检索明明做得很好，却因为预算被挤占而只能放两三个 Chunk，答案质量随对话轮次持续劣化。

Fig.12 — 对话历史压缩：用摘要换取 Context 空间
✓ 核心原则
"历史对话"与"知识库上下文"应该分开管理——各自有独立的子预算、各自的压缩策略。历史回答的是"我们聊过什么"，检索证据回答的是"事实是什么"，混在一个池子里互相争抢，是长对话场景答案质量劣化的常见根因。

为什么结构化模板优于裸的 chunk1 + chunk2 + chunk3？

  • 证据边界清晰：模型能明确知道"这里有几份文档、各自说什么"，减少跨文档的内容粘连；
  • 可判定性：版本、来源、更新时间以结构化字段呈现，模型不需要从正文中猜测"这是哪个版本的文档"；
  • 可引用性：为 Citation 提供了锚点（下一小节）；
  • 可调试性：出问题时，工程师能直接看出 Context 里到底装了什么——裸拼接的 Context 是黑盒，结构化 Context 是白盒。

Citation / Grounding

企业级 RAG 的答案不仅要"对"，还要"可追溯"。用户需要知道每个结论出自哪里，审核者需要验证答案是否有依据。这要求 Context 从建库那一刻起就为 Citation 保留结构：

├── version         # 版本判定与冲突消解

如何评估 Context Engineering？

Context Engineering 的每一个策略（阈值取多少、λ 取多少、顺序怎么排）都不应该靠感觉决定，而应该通过对照实验验证。最小可行的实验设计：

Experiment Design

Baseline 组：Top-K → 直接拼接 → Prompt。这是绝大多数团队"能跑就行"的现状。

Experiment 组：Filter + Dedup + Diversity + Compression + Ordering + Budget 的完整 Context Pipeline，其余环节完全一致。同一评测集、同一模型、同一 Prompt 模板，只变 Context 策略。

评估维度至少覆盖七个，缺一不可：

指标衡量什么归因到哪个环节
Answer Accuracy最终答案的事实正确率整体效果
Faithfulness答案是否忠于所给证据（不编造）Context 质量 + 模型服从性
Groundedness答案中的关键论断能否回溯到证据Context + Citation 设计

✓ 实践要点
特别关注 Answer Accuracy 与 Token Usage 的联合变化：理想结果是 Accuracy 上升的同时 Token 下降；如果 Accuracy 持平但 Token 大降，也是值得上线的收益；如果 Accuracy 下降，回头检查是哪一级过滤误杀了关键证据——Context Engineering 的每个阶段都应该是可独立开关、可独立归因的。
SECTION 21

十个常见失败案例

以下是我在生产环境中见过频率最高的十种 Context 层失败。每一种都按"现象 → 原因 → 影响 → 解决方案"展开。

失败 1 ｜ "Top-K 越大越好"

现象
把 K 从 5 调到 50，期望覆盖率提升带来效果提升。
原因
混淆了检索阶段的 Recall 目标与 Context 阶段的 Precision 目标。
影响
噪声与 Token 成本暴涨，答案质量不升反降，延迟明显恶化。
方案
检索用大 K 保 Recall，Context 用小 N 保 Precision，中间用阈值和 Selection 收窄。

失败 2 ｜ Reranker 分数最高的全部塞进去

现象
把 Reranker Top-K 直接等于最终 Context，不做任何二次加工。
原因
把"单条相关性排序"当成了"组合优化"。
影响
同源内容垄断 Context，关键互补证据（低分但维度不同）被挤出。
方案
Reranker 只出候选序，Context Builder 做独立的组合选择。

失败 3 ｜ 同一文档重复出现大量 Chunk

现象
Context 里 8 个 Chunk 有 6 个来自同一份手册的相邻段落。
原因
缺少 Source Diversity 控制和 Chunk 级去重。
影响
信息增益趋近于零，Token 浪费，答案视角单一。
方案
单文档席位上限 + Chunk-level Dedup，必要时 MMR。

失败 4 ｜ 新旧版本混在 Context

现象
用户问 4.6.2，答案里混着 4.5.0 的已废弃参数。
原因
无 Version Detection 与 Conflict Resolution，语义相似的新旧文档全部入选。
影响
模型混合多版本信息，生成"现实中不存在的配置"。
方案
Version Priority 过滤 + 旧版本显式降权标注。

失败 5 ｜ Context 超预算后简单截断

现象
超长时直接对字符串做硬切（截取前 max_tokens 个字符）。
原因
没有预算前置管理，把截断当兜底。
影响
排在末尾的证据被整块切掉——往往恰是排序策略刻意安排的关键补充。
方案
按 Chunk 粒度做预算装填，超预算时丢弃低优先级整块，而不是切断某一块。

失败 6 ｜ Context 顺序完全随机

现象
检索结果什么顺序就什么顺序，甚至每次请求顺序不稳定。
原因
没有意识到 Ordering 是设计对象。
影响
关键证据随机落入 Lost in the Middle 区间，效果不可复现、难以排查。
方案
显式 Ordering 策略：版本优先 / 权威优先 / 首尾放置。

失败 7 ｜ Compression 丢失关键条件

现象
摘要式压缩后，答案丢失"仅在关闭硬件 AEC 时生效"这类限定条件。
原因
压缩模型倾向保留主干、丢弃条件从句，而企业文档的关键恰在条件里。
影响
答案从"正确"退化为"部分正确"——比明显错误更危险，因为难以察觉。
方案
高事实密度内容用 Extractive 或不压缩；压缩后对数字/版本号/条件做完整性校验。

失败 8 ｜ Conversation History 侵占 Context Budget

现象
长对话后期，答案质量持续下降。
原因
历史无界增长且无独立预算，挤占 Retrieved Context 空间。
影响
本轮检索明明成功，却只能塞进两三个 Chunk。
方案
历史与证据分开记账，历史做摘要压缩并设独立子预算。

失败 9 ｜ 没有保存 Source Metadata，Citation 不可靠

现象
答案附了引用，点进去发现文档对不上，或根本无法定位。
原因
Chunking 入库时未保留 document_id / section / page。
影响
用户与审核者无法验证答案，企业场景信任崩塌。
方案
Metadata 体系前移到入库阶段，Context 构建全程携带。

失败 10 ｜ 只优化 Prompt，不优化 Context

现象
答案错误后团队反复改指令措辞，"请严格依据上下文回答"改了十轮。
原因
把信息层问题误判为指令层问题。
影响
投入持续、收益趋零，团队对 RAG 失去信心。
方案
建立归因习惯：先看 Context 里装了什么，再决定改哪一层。

SECTION 23

Python Context Builder

最后给一个简化但工程化的参考实现，覆盖 Dedup、单源席位限制、版本优先、排序、Token Budget 与结构化输出。为控制篇幅省略了完整 Tokenizer，用近似估算代替——生产环境请替换为与模型一致的 Tokenizer。

from dataclasses import dataclass, field
from typing import Optional


@dataclass
class RetrievedChunk:
    chunk_id: str
    document_id: str
    content: str
    score: float                      # Reranker 分数
    metadata: dict = field(default_factory=dict)
    # metadata 约定字段：
    #   version: str          文档版本，如 "4.6.2"
    #   source: str           来源类型，如 "official"
    #   title / section / updated_at ...


def estimate_tokens(text: str) -> int:
    """近似估算 Token 数（生产环境请替换为真实 Tokenizer）。"""
    return max(1, len(text) // 2)


def exact_dedup(chunks):
    """Chunk 级精确去重：同 chunk_id 只保留分高者。"""
    best = {}
    for c in chunks:
        if c.chunk_id not in best or c.score > best[c.chunk_id].score:
            best[c.chunk_id] = c
    return list(best.values())


def version_adjusted_score(chunk, target_version):
    """版本加权：匹配目标版本加分，旧版本降权（不直接丢弃）。"""
    v = chunk.metadata.get("version")
    if target_version and v:
        if v == target_version:
            return chunk.score + 0.10
        return chunk.score - 0.15      # 旧版本降权，排到最后并打标
    return chunk.score


def build_context(chunks, max_tokens,
                  target_version=None,
                  max_per_document=2,
                  score_threshold=0.0):
    """
    Context Builder：Candidates -> Structured Context
    流程：精确去重 -> 阈值过滤 -> 版本优先
          -> 单源限制 -> 排序 -> 预算装填 -> 模板组装
    """
    # 1. Dedup
    pool = exact_dedup(chunks)

    # 2. Relevance Threshold
    pool = [c for c in pool if c.score >= score_threshold]
    if not pool:
        return ""

    # 3. Version Priority：按调整分排序（高分在前）
    pool.sort(key=lambda c: version_adjusted_score(c, target_version),
              reverse=True)

    # 4. Source Diversity：单文档最多贡献 max_per_document 个 Chunk
    selected = []
    doc_count = {}
    for c in pool:
        if doc_count.get(c.document_id, 0) >= max_per_document:
            continue
        selected.append(c)
        doc_count[c.document_id] = doc_count.get(c.document_id, 0) + 1

    # 5. Token Budget：逐块装填，超预算整块放弃（不做块内截断）
    header_cost = 30                    # 每块 Metadata 头的近似开销
    used = 0
    fitted = []
    for c in selected:
        cost = estimate_tokens(c.content) + header_cost
        if used + cost > max_tokens:
            continue                    # 放弃本块，尝试更小的下一块
        fitted.append(c)
        used += cost

    # 6. 模板组装：携带完整 Metadata，旧版本显式标注
    parts = []
    for i, c in enumerate(fitted, start=1):
        m = c.metadata
        v = m.get("version", "N/A")
        note = ""
        if target_version and v != "N/A" and v != target_version:
            note = "（历史版本 %s，仅作对比参考）" % v
        block = "[Document %d]\n" % i
        block += "Title:   %s\n" % m.get("title", "N/A")
        block += "Version: %s%s\n" % (v, note)
        block += "Section: %s\n" % m.get("section", "N/A")
        block += "Source:  %s\n" % m.get("source", "N/A")
        block += "Doc ID:  %s / Chunk: %s\n" % (c.document_id, c.chunk_id)
        block += "\nContent:\n%s\n" % c.content
        parts.append(block)

    return "\n---\n".join(parts)
✓ 实现说明
这是一个教学级简化版：省略了语义去重、MMR、压缩、权限过滤等环节，Token 估算是粗粒度的。但它体现了五个不可妥协的设计决策——去重先于选择、阈值先于排序、版本参与打分、单源设席位上限、超预算弃整块而非硬截断。这五条，建议在任何生产实现中都保留。
