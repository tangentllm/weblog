Claude Code 自发布以来，最佳实践已经快速演进。它从最初的终端助手，发展成了一个具备技能（Skills）、钩子（Hooks）、子代理（Subagents）、插件和多会话编排能力的完整智能体开发环境。那些从 Claude Code 中获得最大收益的开发者，往往不是提示词写得最好的人，而是最懂得工程化上下文的人。

本指南按工作流阶段组织——从项目初始化、开发实现到代码审查——内容综合了 Anthropic 官方文档、社区讨论以及真实生产环境的工作流。每一节都针对经验丰富的用户曾遇到过的痛点给出解决方案。

80% 问题：为什么最佳实践很重要

2026 年的一项调查显示，66% 的开发者遇到了 Addy Osmani 所说的"80% 问题"——AI 给出的方案接近正确，但差那么一点。更惊人的是：45% 的开发者表示调试 AI 代码比自己手写还慢。

当开发者遵循结构化实践时，这些数字会大幅下降。根本原因不难预测：模糊的提示词、被污染的上下文、缺失的验证环节，以及蝴蝶效应——模型在早期误解了某个点，然后在错误的前提上构建了整个功能，直到五个 PR 之后才有人发现。

66% 认为 AI 方案"接近正确但不完全对"
45% 认为调试 AI 代码比自己写还慢
5.5x 比 Cursor 消耗的 Token 更少

核心洞察

"把智能体当作杠杆，而不是魔法。在试错成本低的环节大胆使用，在代价高的环节保持谨慎。"

—— r/ExperiencedDevs 社区用户

本指南中的每一条最佳实践都服务于这一原则。

阶段一：项目搭建——把 CLAUDE.md 当作基础设施

2026 年的社区共识很明确：CLAUDE.md 不再是可选项。它和 .gitignore 一样重要。Martin Fowler 推广了"上下文工程"（Context Engineering）这一术语，用来描述为 AI 工具构建合适上下文的学科，而 CLAUDE.md 就是这门学科的基石。

运行 /init 可以生成一个 CLAUDE.md 模板，然后随着项目演进不断打磨。黄金法则：对每一行内容都问自己——"删掉这句话，Claude 会犯错吗？" 如果不会，就删掉。

✅ 应该包含 ❌ 应该排除
Claude 猜不到的 Bash 命令 Claude 读代码就能推断出的内容
与默认规范不同的代码风格 Claude 已知的标准语言惯例
测试指令和偏好的测试运行器 详细的 API 文档（放链接即可）
仓库礼仪（分支命名、PR 规则） 频繁变动的信息
架构决策和环境 quirks 逐文件描述代码库
常见坑点和非直觉行为 诸如"写干净代码"这种显而易见的废话

CLAUDE.md 的层级结构

位置 作用
~/.claude/CLAUDE.md 用户级默认配置，跨项目生效。个人偏好如提交风格、测试方法、编码习惯。
./CLAUDE.md（项目根目录） 团队共享的项目上下文。纳入 Git 管理。包含构建命令、架构说明、仓库礼仪。这是主文件。
父级目录 Monorepo 支持。在 packages/api/ 下工作时，会自动加载根目录和 api/ 下的 CLAUDE.md。
子目录 按需加载。当 Claude 处理某个子目录下的文件时，会自动拉取该目录的 CLAUDE.md。

实战有效的 CLAUDE.md 模板

开发者最大的错误是用 /init 生成 CLAUDE.md 后就再也不管了。以下是两个经过实战检验的模板，分别对应常见的技术栈。

Next.js / TypeScript 项目模板

# 常用命令
- 开发：`bun run dev`（端口 3000）
- 测试：`bun test`（单文件：`bun test path/to/file`）
- 代码检查：`bun run lint`
- 类型检查：`bun run typecheck`
- 构建：`bun run build`

# 代码风格
- 使用 ES 模块（import/export），不用 CommonJS
- 尽量解构导入
- 优先使用具名导出，少用默认导出
- TypeScript 严格模式——禁止 `any` 类型

# 架构说明
- Next.js 15 App Router，React 19，TypeScript 严格模式
- 数据库：PostgreSQL + Drizzle ORM
- 认证：Clerk 中间件保护 /dashboard/* 路由
- 支付：Stripe webhook 路由为 /api/webhooks/stripe
- REST 规范参见 @docs/api-patterns.md

# 工作流
- **重要**：每次批量改完代码后必须跑类型检查
- 优先运行单个测试，不要全量跑测试套件
- 提交信息用祈使语气，引用 issue 编号
- 禁止直接推送到 main 分支——必须新建分支提 PR

# 常见坑点
- **重要**：禁止在客户端组件中从 @/lib/server 导入任何内容
- /api/webhooks 路由不能被认证中间件拦截
- Drizzle 迁移：运行 `bun run db:push`，禁止直接编辑 SQL 文件

Python / Django 项目模板

# 常用命令
- 开发：`python manage.py runserver`
- 测试：`pytest`（单文件：`pytest path/to/test.py -k test_name`）
- 代码检查：`ruff check .`
- 格式化：`ruff format .`
- 迁移：`python manage.py makemigrations && python manage.py migrate`

# 代码风格
- Python 3.12+，所有函数签名必须加类型注解
- 路径操作优先用 pathlib，不用 os.path
- 优先使用 dataclass 或 Pydantic，不用裸字典

# 架构说明
- Django 5.1，DRF 做 API，Celery 处理后台任务
- 数据库：PostgreSQL，禁止写原生 SQL——必须用 ORM
- 认证：django-allauth + JWT token
- API 规范参见 @docs/api-standards.md

# 工作流
- **重要**：改完代码必须跑 pytest，不许跳过
- 每次模型变更都要写迁移文件
- Django signals 慎用——优先显式调用

# 常见坑点
- **严禁**未经审批修改 /core/auth/ 下的文件
- /tasks/ 中的后台任务必须是幂等的
- Stripe 相关的 WEBHOOK_SECRET 环境变量必须已设置
💡 强调标记确实有用

在关键规则前加上 重要 或 严禁 能显著提升遵守率。但要克制使用——如果所有内容都是重点，那就没有重点。把 CLAUDE.md 纳入 Git，让团队一起贡献和迭代。

Token 经济学：停止浪费上下文

Claude Code 在完成同等任务时，消耗的 Token 比 Cursor 少 5.5 倍。但大多数开发者仍然通过投喂过多上下文来浪费 Token。Claude 读取的每个文件都会消耗上下文，无论是否相关。

创建 .claudeignore

就像 .gitignore 保持仓库整洁一样，.claudeignore 保持上下文整洁。排除构建产物、依赖和生成的文件。

# 依赖
node_modules/
.venv/
vendor/

# 构建产物
dist/
build/
.next/
__pycache__/

# 生成文件
*.lock
*.min.js
*.map
coverage/

# 大资源文件
public/assets/
*.png
*.jpg
*.svg
5.5x 相比 Cursor 消耗的 Token 更少
40%+ 使用子代理搜索可节省的 Token
70% 建议触发压缩的阈值（不是 90%）

阶段二：任务定界——防止蝴蝶效应

蝴蝶效应是智能体编码中最具破坏性的失败模式。r/ChatGPTCoding 上的开发者报告说，让 AI 微调一个小东西，结果搞崩了完全不相关的功能。模型在早期误解了某个点，然后在错误的前提上构建了整个功能，直到五个 PR 之后才有人发现。

解决办法是极度严格的任务定界。你的指令越精确，需要的修正就越少。

策略 模糊提示（导致蝴蝶效应） 精确提示（防止蝴蝶效应）
限定任务范围 "给 foo.py 加测试" "给 foo.py 写一个测试，覆盖用户未登录的边界情况。不要用 mock。"
指向已有模式 "加一个日历组件" "参考 HotDogWidget.php 的实现模式，然后按同样结构实现一个日历组件"
描述症状 "修登录 bug" "会话超时后登录失败。检查 src/auth/ 中的认证流程，尤其是 token 刷新。先写个失败测试，再修复。"
追溯历史 "ExecutionFactory 怎么这么怪？" "查看 ExecutionFactory 的 Git 历史，总结它的 API 是怎么演变成今天这样的"

访谈模式（Interview Pattern）

对于较大的功能，在 Claude 动手实现之前，先让它"采访"你：

我要实现[简要描述]。请使用 AskUserQuestion 工具详细采访我。

问技术实现、UI/UX、边界情况、顾虑和权衡。不要问显而易见的问题——
深挖那些我可能没考虑到的难点。

持续提问直到我们覆盖所有方面，然后写一份完整的 SPEC.md 规范。

规范完成后，新开一个会话去执行它。新会话拥有干净的上下文，完全聚焦于实现。

Plan Mode：动手前先思考

Plan Mode 将调研与实现分离，防止 Claude 解决错误的问题。按 Shift+Tab 两次切换。

探索（Explore）

进入 Plan Mode。Claude 可以读取文件并回答问题，但不会做任何修改。

规划（Plan）

让 Claude 创建详细的实现计划。按 Ctrl+G 在你的编辑器中修改计划。

实现（Implement）

切回 Normal Mode。Claude 按照计划编码，边做边验证。

提交（Commit）

让 Claude 用描述性的信息提交并打开 PR。

⚠️ 什么时候跳过 Plan Mode

规划有额外开销。当范围明确且改动很小时可以跳过——比如修复错别字、加一行日志、重命名变量。如果你能一句话描述 diff，就跳过规划。Plan Mode 最有价值的情况是：你不确定实现方案、改动涉及多个文件、或者你对代码不熟悉。

阶段三：会话中——上下文卫生

来自 Claude Code 资深用户的头号实用建议：每个任务都开新会话。长会话会退化。Claude Code 和 Cursor 在长时间对话后都会质量下降。解决办法不是管理退化，而是防止退化。

命令 使用时机 效果
/clear 不相关的任务之间 重置整个上下文窗口
/compact 上下文占用达 70%+ 压缩摘要，保留关键信息
/compact <focus> 特定工作很重要时 定向压缩
Esc + Esc 会话中途恢复 回退到检查点，可选摘要
子代理 代码库调研 在独立上下文中搜索，返回摘要

两次修正法则

如果你对同一个问题纠正了 Claude 超过两次，说明上下文已经被失败方案污染了。运行 /clear 重新开始。一个带着更好提示词的干净会话，几乎总是胜过带着累积修正的长会话。

批量审查——避免决策疲劳

"智能体编码让工作更快了，但下属不停地要求你做决定，真的很累。"

解决办法：不要逐条批准每个修改。让 Claude 完成一系列相关改动，然后用 git diff 批量审查。

在 CLAUDE.md 中自定义压缩规则

# CLAUDE.md
压缩上下文时，必须保留：
- 已修改文件的完整列表
- 所有测试命令及其结果
- 当前实现计划
- 尚未解决的错误信息

用子代理保持上下文干净

子代理在独立的上下文窗口中运行，只返回摘要。当 Claude 调研代码库时，它会读取很多文件——全部消耗你的主上下文。子代理在隔离环境中探索，只返回相关内容，可节省 40%+ 的输入 Token。

串行搜索 vs 子代理搜索

串行搜索（主上下文）

  • Claude grep "auth" —— 读了 3 个文件
  • grep "validate" —— 又读了 4 个
  • grep "permission" —— 再读 5 个
  • 12 个文件进入上下文，大多无关
  • Claude 要在所有文件上推理——更慢、更不准

子代理搜索（隔离上下文）

  • 子代理并行探索 8 条路径
  • 返回前过滤结果
  • 返回：auth/validator.ts 第 45-89 行
  • 主上下文只增加约 400 行
  • Claude 保持对相关代码的专注

有效使用子代理

# 调研——在独立上下文中运行
"使用子代理调研我们的认证系统如何处理 token 刷新，
以及是否有现有的 OAuth 工具可以复用。"

# 验证——也在独立上下文中
"使用子代理审查这段代码的边界情况和安全漏洞。"

# 自定义子代理定义 (.claude/agents/security-reviewer.md)
---
name: security-reviewer
description: 审查代码安全漏洞
tools: Read, Grep, Glob, Bash
model: opus
---
你是一名资深安全工程师。审查以下安全问题：
- 注入漏洞（SQL、XSS、命令注入）
- 认证和授权缺陷
- 代码中的密钥或凭证泄露

WarpGrep：推荐的代码搜索子代理

Claude Code 默认的代码搜索使用 Haiku 或 Sonnet 作为搜索模型。WarpGrep 将其替换为一个专门的搜索子代理，在代码搜索任务上表现优于 Haiku 和 Sonnet，同时保持主上下文干净。

实际差异很显著。WarpGrep 专为代码检索设计——它理解代码结构、函数边界和导入链，这是通用小模型不具备的。当 Claude 把搜索委托给 WarpGrep 时，搜索在独立上下文窗口中运行，只返回相关行范围，而非整个文件。

更快 比 Haiku/Sonnet 的代码搜索更快
40%+ 相比串行搜索节省的上下文
语义 理解代码结构

在 CLAUDE.md 中配置 WarpGrep

# CLAUDE.md
# 代码搜索
使用 WarpGrep 作为主代码搜索子代理。
它在代码搜索上优于 Haiku 和 Sonnet。
用于宽泛查询："找到认证流程"、"支付系统怎么工作"、
"限流逻辑在哪处理的？"

不要用于精确关键词匹配——那种情况直接用 Grep。
WarpGrep 用于语义查询，需要理解代码上下文。

WarpGrep vs Grep 的使用场景

  • WarpGrep：宽泛的语义查询，如"找到认证流程"、"支付系统怎么工作"、"API 超时的错误处理在哪"
  • Grep：精确关键词匹配，如 className="auth"、import { foo }

WarpGrep 在独立上下文窗口中搜索，你的主会话保持干净，专注于实现工作。

智能体团队：并行编排

智能体团队允许你生成多个 Claude 实例，并行处理任务的不同部分。这是 Claude Code 中最强大的扩展模式——但需要对模型选择和通信规则保持纪律。

为每个队友指定模型

不同任务需要不同模型。调研和探索任务可以用更便宜更快的模型。实现和复杂推理任务应该用最强的模型。始终显式指定模型——不要依赖默认。

任务类型 推荐模型 原因
代码库探索 haiku 快、便宜——适合读取和摘要文件
代码搜索/检索 WarpGrep MCP 专为代码搜索设计，优于 Haiku/Sonnet
功能实现 sonnet 或 opus 需要强推理能力生成正确代码
复杂重构 opus 多文件改动、跨领域关注需要最强模型
测试生成 sonnet 速度和质量的平衡
代码审查 opus 安全和正确性审查受益于最强推理

团队通信规则

没有显式通信规则，智能体团队会陷入混乱——队友互相踩脚、重复劳动、产出冲突。在 CLAUDE.md 或智能体前言中定义这些规则。

CLAUDE.md — 智能体团队通信规则

# 智能体团队
生成智能体团队时：
- 必须为每个队友指定模型：
  - 调研和探索任务用 haiku
  - 实现和测试生成用 sonnet
  - 复杂重构和代码审查用 opus
- 通信规则：
  - 队友必须使用 SendMessage 通信——纯文本输出对其他智能体不可见
  - 团队负责人通过 TaskCreate 和 TaskUpdate 分配任务
  - 队友完成后通过 TaskUpdate 标记任务完成，然后进入空闲
  - 使用消息类型 "message" 进行直接通信（除非紧急情况不用 "broadcast"）
  - 每个队友一次只做一件事——禁止多任务
- 文件锁定：
  - 禁止两个队友同时编辑同一个文件
  - 如果文件需要顺序编辑，使用任务依赖（blockedBy）
- 工作完成后必须关闭所有队友

自定义智能体定义（含模型和规则）

# .claude/agents/test-writer.md
---
name: test-writer
description: 编写全面的测试套件
tools: Read, Grep, Glob, Bash, Edit, Write
model: sonnet
---
你是一名测试工程师。对每个分配的文件：
1. 读取源文件理解其 API
2. 检查现有测试
3. 编写覆盖以下场景的测试：正常路径、边界情况、
   错误处理、边界条件
4. 运行测试确保通过
5. 标记任务完成

通信：每完成一个文件给团队负责人发消息。
包含测试文件路径和通过/失败状态。

嵌套 CLAUDE.md 提供团队上下文

在 monorepo 或多包项目中，嵌套 CLAUDE.md 给每个团队或包提供专属上下文。Claude 按层级自动加载最近的 CLAUDE.md——根级规则全局生效，子级规则只在对应目录下生效。

Monorepo 的嵌套 CLAUDE.md 结构

# 项目结构
myproject/
├── CLAUDE.md              # 根目录：共享命令、仓库礼仪
├── packages/
│   ├── api/
│   │   └── CLAUDE.md      # API 专属："用 Drizzle ORM，禁止原生 SQL"
│   ├── web/
│   │   └── CLAUDE.md      # 前端："用 Tailwind，优先服务端组件"
│   └── shared/
│       └── CLAUDE.md      # 共享："此处改动影响所有包——必须跑全量测试"
└── .claude/
    └── agents/            # 自定义智能体定义
        ├── api-dev.md
        └── frontend-dev.md

# 根目录 CLAUDE.md（全局生效）
## 命令
- 安装：`bun install`（从根目录运行）
- 全量测试：`bun run test`
- 类型检查：`bun run typecheck:fast`

## 工作流
- **重要**：必须推送到分支，禁止直接推 main
- 每次批量改完代码后跑类型检查

# packages/api/CLAUDE.md（继承根目录）
@../CLAUDE.md
## API 专属规则
- 所有数据库操作用 Drizzle ORM
- 测试：`bun test packages/api`
- 迁移：`bun run db:push`（禁止直接编辑 SQL）

# packages/web/CLAUDE.md
@../CLAUDE.md
## 前端专属规则
- 优先 React Server Components，只在必要时用 'use client'
- 使用 Tailwind CSS，禁止内联样式
- 测试：`bun test packages/web`
⚠️ 推送到分支，不要直接推 main

在每个项目的 CLAUDE.md 中加入："重要：必须推送到分支并创建 PR。禁止直接推送到 main。" 这在运行智能体团队或并行会话时尤其关键——多个智能体同时推送到 main 会产生冲突和丢失工作。基于分支的工作流在改动落地前提供了审查检查点。

阶段四：审查与验证

给 Claude 提供验证标准，是杠杆效应最高的单一实践。当 Claude 能够验证自己的工作——跑测试、对比截图、验证输出——它的表现会大幅提升。

策略 之前（模糊） 之后（可验证）
提供测试用例 "实现邮箱验证" "写 validateEmail 函数。测试：user@example.com 返回 true，invalid 返回 false，user@.com 返回 false。跑测试验证。"
视觉验证 "把仪表盘弄好看点" "[贴截图] 按这个设计实现。截图结果与原图对比。"
根因分析 "构建失败了" "构建报错[贴错误信息]。修复根因，不要压制错误。验证构建成功。"

安全：不可妥协的审查

🛡️ AI 生成的代码安全漏洞多 1.5-2 倍

研究表明，AI 生成的代码比人工编写的代码包含更多安全漏洞——密码处理不当、不安全的直接对象引用、缺失输入验证最为常见。最佳实践：

  • 认证、支付、数据变更代码必须人工审查
  • 使用 hooks 在每次编辑时自动进行安全检查
  • 安全关键代码路径绝不完全委托给 AI
  • 创建 security-reviewer 子代理进行自动化安全审计

委托光谱：什么该全权委托，什么该密切监督

Anthropic 2026 年开发者报告显示，开发者在 60% 的工作中使用 AI，但完全委托的任务仅占 0-20%。最优秀的开发者会刻意决定哪些任务落在哪个区间。

类别 全权委托 密切监督
代码生成 测试生成、样板代码、脚手架 认证流程、支付逻辑、数据变更
重构 迁移、重命名、格式调整 安全关键重构、API 契约变更
文档 文档字符串、README、行内注释 安全文档、合规文档
调试 Lint 错误、类型错误、构建修复 竞态条件、数据损坏、认证 bug
基础设施 CI 配置、Dockerfile、环境搭建 生产部署、数据库 schema

终端优先工作流

"自从用 Claude Code 后，我用 IDE 的时间变少了。Claude 让我在终端里就能完成工作。"

工作流是：描述需求 → Claude 构建 → 审查 git diff → 提交或迭代。IDE 变成了查看器，而不是编辑器。

阶段五：高级模式

作者/审查者模式（Writer/Reviewer Pattern）

会话 A：作者 —— "为 API 端点实现一个限流器"

会话 B：审查者 —— "审查 @src/middleware/rateLimiter.ts 中的限流器。检查边界情况、竞态条件，以及与现有中间件的一致性。"

审查者拥有干净的上下文，不会因为刚写完代码而产生偏见。这比自己审查自己产生的审查质量显著更高。

Hooks：确定性护栏

Hooks 在特定生命周期点自动运行脚本。与 CLAUDE.md 的建议性规则不同，hooks 每次都会执行。用于编辑后自动 lint、阻止写入受保护文件、发送通知。

Skills：按需加载的知识

Skills 通过 .claude/skills/ 下的 SKILL.md 文件为 Claude 扩展项目专属工作流——与每次会话都加载的 CLAUDE.md 不同，Skills 是按需加载的。用于领域知识和可复用工作流，如 /fix-issue 1234。

Fan-Out：大规模迁移的并行分发

# 生成任务列表
claude -p "列出所有需要迁移的 Python 文件" > files.txt

# 并行处理每个文件
for file in $(cat files.txt); do
  claude -p "将 $file 从 unittest 迁移到 pytest。返回 OK 或 FAIL。" \
    --allowedTools "Edit,Bash(git commit *)" &
done
wait

常见失败模式与规避

大杂烩会话（The Kitchen Sink Session）

你从一个任务开始，问了不相关的问题，又绕回来。上下文塞满了无关信息。
解决：不相关的任务之间用 /clear。

过度指定的 CLAUDE.md

CLAUDE.md 太长。重要规则淹没在噪音中，Claude 忽略了一半。
解决：无情精简——删掉 Claude 无需提示就会遵守的规则。

蝴蝶效应

微小改动级联破坏了其他功能。模型早期误解了某个点，然后在错误前提上构建。
解决：严格的任务定界和 Plan Mode。

信任-验证缺口

Claude 生成了看似合理但不处理边界情况的代码。
解决：始终提供验证手段（测试、脚本、截图）。如果你无法验证，就不要上线。

常见问题

什么是 CLAUDE.md，为什么需要它？

CLAUDE.md 是一个 Markdown 文件，Claude Code 在每次会话开始时读取。它提供持久上下文——构建命令、代码风格规则、架构决策和 Claude 无法从代码本身推断出的坑点。2026 年的社区共识是，CLAUDE.md 和 .gitignore 一样重要——是基础设施，不是可选文档。

CLAUDE.md 应该多长？

根目录 CLAUDE.md 控制在 50-100 行，详细章节用 @imports。对每一行问自己："删掉这句话，Claude 会犯错吗？" 如果不会，就删掉。

如何防止 Claude Code 在长会话中丢失上下文？

资深用户的头号建议：每个任务开新会话。不相关任务之间用 /clear，上下文占用达 70% 时主动压缩，把调研委托给子代理，严格限定每个任务的范围。如果对同一问题纠正 Claude 超过两次，清空会话重新开始。

哪些任务该全权委托，哪些该密切监督？

全权委托：测试生成、样板代码、迁移、文档、格式化。密切监督：认证、支付、数据变更、安全逻辑。研究表明 AI 生成的代码安全漏洞多 1.5-2 倍，安全关键路径必须人工审查。

什么是 AI 编码的 80% 问题？

80% 问题指 AI 方案接近正确但不完全对——66% 的开发者报告遇到过。解决办法是严格的任务定界、提供验证标准、使用 Plan Mode 防止 Claude 解决错误的问题。

什么是 Plan Mode，什么时候用？

Plan Mode 将调研与实现分离。当你不确定实现方案、改动跨多个文件、或对代码不熟悉时使用。对于小且明确的改动（如修复错别字）可以跳过。

如何减少 Claude Code 的 Token 消耗？

用 .claudeignore 排除 node_modules/dist/build 等产物，把调研委托给子代理（节省 40%+ Token），任务之间用 /clear，在 70% 上下文占用时主动压缩。Claude Code 本身已经比 Cursor 少消耗 5.5 倍 Token。
