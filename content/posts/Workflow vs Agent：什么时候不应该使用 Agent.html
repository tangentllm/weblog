Workflow vs Agent：
什么时候不应该使用 Agent

Agent 不是 Workflow 的升级版。二者解决的是不同类型的问题——Workflow 定义路径，Agent 决定路径。本文从生产系统架构的角度，建立一套可以用于真实项目架构评审的判断方法。

01 · 开篇

为什么现在什么都想做成 Agent

过去一年，我参与了大量 LLM 应用的架构评审。一个越来越明显的现象是：很多团队在系统设计的第一天就决定"我们要做一个 Agent"，然后再反过来找理由。这不是技术选型问题，而是架构判断问题。

从一个真实场景开始。某团队的需求：用户上传一份合同，系统提取关键字段（甲乙方、金额、签署日期、条款摘要），生成结构化结果。他们的第一版设计是：

User ↓ Agent ↓ 读取文件 → 提取字段 → 检查结果 → 生成 JSON

看起来很合理，很"智能"。但仔细分析这个任务：

  • 处理步骤是什么？——解析、提取、校验、输出。
  • 步骤之间有分支吗？——校验失败就重试，没有其他分支。
  • 下一步取决于上一步的内容发现吗？——不。第二步永远是提取字段，无论第一步结果如何。

也就是说，工程师在写代码之前就已经知道完整的执行路径。那么——

如果下一步路径本身就是已知的，为什么要让 LLM 决定路径？

这个任务合理的架构是：

Document ↓ LLM Extraction（一次调用，Structured Output） ↓ Schema Validation（程序校验） ↓ Result / Retry

这是 Workflow。它更便宜、更快、更可测试，且失败时你知道该从哪里重试。这个案例暴露了一个普遍倾向：把"用了 LLM"等同于"需要 Agent"，把"Agent"当作系统先进性的标志。后文将系统性地拆解这个问题。

02 · 概念澄清

Workflow 到底是什么

先纠正一个浅层定义：Workflow 不是"一系列 API 调用"。从系统架构角度，它的准确定义是：

Workflow 是由工程师预先定义执行路径、状态转换和条件分支的程序化执行系统。

对应的伪代码：

PYTHON
def document_pipeline(doc):
    text = parse(doc)
    context = retrieve(text)
    result = llm_extract(text, context)      # LLM 在这里，但路径不归它管
    if not validate(result):
        result = llm_extract(text, context, hint=result.errors)
        if not validate(result):
            return fallback_to_manual(result)
    return save(result)

注意：Workflow 并不意味着系统没有 AI。一个 Workflow 完全可以包含 LLM、RAG、Embedding、OCR、Tool Calling、Vision Model。它的架构特性来自谁来决定下一步，而不是用了什么组件。因此必须建立一个关键区分：

AI ≠ Agent。 系统里有没有 LLM，和系统是不是 Agent，是两个完全独立的问题。Workflow 的架构特性：路径基本确定、状态显式、分支显式、错误处理显式、Retry 与超时可控、结果可预测、容易测试。
03 · 关键差异

Agent 到底多了什么

这一节不重新科普 Agent，只讨论 Workflow 和 Agent 之间的那一个关键差异。先看控制流的对照：

WORKFLOW
# 程序决定下一步
if condition:
    call_tool_A()
else:
    call_tool_B()
AGENT
# 模型决定下一步
while not finished:
    observation = observe()
    action = agent.decide(observation)
    result = execute(action)

抽象成一行：

WORKFLOW
Program decides —— 程序决定下一步
AGENT
Model decides —— 模型决定下一步

Agent 在架构上多出来的东西只有一个，但它是本质性的："下一步做什么"的决策权，从代码转移到了模型。这个转移是有代价的，而且代价不小（第 17 节展开）。这里先建立全文最重要的架构问题：

不要问"这个系统能不能做成 Agent"，而要问"这个系统是否需要把下一步行动的决策权交给模型"。几乎所有系统都能做成 Agent，问题在于是否值得。
04 · 核心判断

决策权应该交给谁

把上面的问题变成一个可直接使用的判断标准：

下一步行动是否可以被工程师提前定义？
—— 是 → 优先 Workflow；否，需要根据环境动态决定 → 才开始考虑 Agent。

用两个场景对照。

场景 A：订单退款

查询订单 ↓ 判断订单状态 ↓ 匹配退款规则 ↓ 执行退款 ↓ 发送通知

每一步的下一步都是确定的。退款规则可能有几十条，但那是数据层面的复杂度，不是路径层面的动态性。用规则引擎 + Workflow 处理，路径完全确定。

场景 B：深度研究

用户说："帮我研究一下 AI Agent 市场，找出值得关注的创业公司。"系统可能需要：

搜索 ↓ 阅读 ↓ 发现新线索 ↓ 继续搜索 ↓ 比较 ↓ 发现信息缺口 ↓ 换角度调查 ↓ 形成结论

下一步做什么，取决于上一步发现了什么。你无法在代码里写死"第三步之后必然要搜索融资数据"——也许第三步发现这家公司已经倒闭了，也许发现了一个更值得关注的方向。这种任务里，决策权交给模型才开始产生价值。接下来，我们把"不应该使用 Agent"的场景系统化。

05 · 反面场景 一

确定性业务流程

适用范围：支付、退款、订单处理、审批流、数据同步、ETL、定时任务、文件处理、通知流程。以订单支付为例：

支付成功 ↓ 更新订单状态 ↓ 扣减库存 ↓ 生成发票 ↓ 发送通知

不要设计成 Order Agent，然后每一轮问模型"你觉得下一步应该做什么"。原因不需要玄学解释，全部是工程常识：

A→B
可测试性
可以直接写 State A → State B 的单元测试，不需要评估"轨迹是否合理"。
StepN
可恢复性
失败后知道从哪个状态继续重试；Agent 失败时你需要先还原它"当时想干什么"。
100%
可审计性
资金相关流程每一步都有明确记录，供合规审计定位。
0
模型侧操作风险
模型错误不会直接变成资金操作错误。
边界条件辨析：有人会问——业务流程中会出现意外情况（库存不足、风控拦截），这不也是"不确定性"吗？注意区分：业务异常是可枚举的。库存不足走库存不足的分支，风控拦截走人工审核的分支。可枚举的分支属于状态机的转移边，属于 Workflow 的领地，不能据此推导出"需要 Agent"。
确定性业务流程应该尽可能保持确定性。
06 · 反面场景 二

固定的数据处理 Pipeline

典型如：

PDF ↓ OCR ↓ Text Cleaning ↓ Chunking ↓ Embedding ↓ Vector DB

即使中间嵌入了 LLM，例如 Document → LLM Metadata Extraction → Validation → Storage，它仍然不是 Agent，也不应该是：整条链路的拓扑在部署时已经固定，LLM 只是作为一个"能力组件"被调用——输入是什么、输出校验什么、失败怎么办，全部由程序定义。

是否使用 LLM，不是判断 Agent 的标准；是否需要动态决策，才是。
一个 Pipeline 里有十个 LLM 调用点，它依然是 Workflow；一个系统只有一个工具、只有一轮决策循环，它也可能是 Agent。判断依据永远是：下一步走向由谁决定。
07 · 反面场景 三

固定规则 + LLM 的路由模式

这是企业 LLM 应用中最高频、也最容易被过度设计的一类：客服消息进来，判断意图，根据意图执行对应流程。

PYTHON
intent = llm.classify(query, schema=INTENT_SCHEMA)   # LLM：理解

if intent == "refund":            # 程序：路由与执行
    refund_workflow(order_id)
elif intent == "logistics":
    logistics_workflow(order_id)
elif intent == "product":
    product_workflow(query)

这里确实用了 LLM，甚至用了 Structured Output。但整个系统不是 Agent——LLM 只负责理解（把自然语言映射为枚举意图），路由决策和后续执行全部由程序控制。很多团队的错误演进路径是：先做 Intent Agent → Intent Agent 自己决定调用退款工具还是物流工具 → 工具调用出错率上升 → 无法定位是分类错了还是路由错了。而在 LLM Classification + 程序 Router 的架构里，这两类错误是天然分离、可以独立监控和评估的。

08 · 反面场景 四

对延迟极其敏感的场景

Agent 的典型执行轨迹是 LLM → Tool → LLM → Tool → LLM → …，迭代次数动态，延迟随轮次累积。关键问题不是平均值，而是分布——P95 可能远高于均值，且难以给出硬性 SLA 承诺。

≈7s
Agent 最小延迟
3 次 LLM 调用（每次 2s）+ 2 次工具调用（每次 0.5s）的保守估算。
N 轮
迭代不确定
Agent 的循环次数取决于任务与模型表现，最坏情况无上界（除非强制 Max Iterations）。
可并行
Workflow 结构优势
固定调用次数 → 延迟上界可计算；独立工具调用可并发，而 Agent 的串行决策循环难以并行化。

对于实时客服首条响应、搜索联想建议、高频移动端 API、强 SLA 的在线服务，在引入 Agent 之前要认真问：用户能接受 P95 多少秒？Agent 的最坏情况延迟是否在这个范围内？

边界条件：延迟敏感不等于彻底排除 Agent。很多产品把 Agent 放在异步任务层（用户提交后离开，稍后收到通知），同步链路保持 Workflow——这是常见且合理的折中。真正不能接受的，是把不可控延迟的 Agent 放进同步链路。
09 · 反面场景 五

对成本高度敏感的场景

Agent 的每一轮循环都在消耗 Token：Thought（输出）→ Tool Call → Observation（重新进入 Context）→ Thought → …。Context 随迭代增长，Token 消耗随轮次非线性上升：

10万+
失控循环的 Token 量
一次陷入循环的 Agent 可能在单次会话里烧掉十万级 Token——这是真实的成本事故来源。
50×
单次成本波动倍数
日百万级请求的系统，单次成本从 0.01 元波动到 0.5 元，就是每月数万到数十万元级别的差异。
5 道
必配护栏
Token Budget · Max Iterations · Tool Call Limit · Timeout · 按租户的成本熔断。
WORKFLOW
固定调用次数 → 成本可预测，可以提前做容量与预算规划。
AGENT
动态循环 → 成本波动，尾部可能失控，护栏只能限制"失控"，不能消除"贵"。

注意：护栏解决的是"失控"，不是"贵"。如果 Workflow 版本已经能解决问题，多花的钱买不到对应价值。

10 · 反面场景 六

高风险操作

支付、删除数据、修改权限、发送正式法律文件、修改生产配置、执行金融操作——在这一类操作上引入 Agent 自主执行，问题不在能力，而在责任与可归因性。模型错误率哪怕只有 0.1%，在高风险操作上也是不可接受的，而且错误发生时你甚至难以归因：是 prompt 问题？上下文污染？还是工具返回误导了它？

需要落地的机制：Permission Boundary（工具按风险分级，Agent 只持有低风险工具的直接执行权）、Policy Engine（金额阈值、目标范围、租户白名单）、Human-in-the-loop（超阈值操作进入人工审批队列）、Audit Log（决策、提案、审批、执行全链路留痕）。

11 · 正面边界

那么，什么时候应该使用 Agent

以上六类反面场景勾勒出了边界。现在从正面定义 Agent 的适用条件。"任务复杂"不是理由——复杂任务可以拆解成多个 Workflow。Agent 的适用条件至少满足以下一条：

11.1　下一步行动无法提前确定

目标 → 搜索 → 发现信息 → 决定下一步 → 继续搜索 → 发现新问题 → 调整计划。路径本身是任务执行过程中"涌现"出来的，不是设计出来的。

11.2　环境具有不确定性

Web Research、开放式调研、故障排查、Coding Agent、数据分析、复杂调查。环境会给你惊喜和意外，需要 Observe → Decide → Act → Observe 的循环来应对。

11.3　工具选择动态变化

可选工具集里有搜索、数据库、代码解释器、浏览器、API、计算器——具体调用哪个，取决于当前掌握的信息和推理状态。如果工具调用顺序固定，那只是带工具的 Workflow。

11.4　需要动态规划

Goal → Plan → Execute → Evaluate → Re-plan。如果计划无法预先写死，执行中要根据评估结果重排计划，Agent 的价值才开始显现。

这些条件的共性：它们描述的都是"路径的动态性"，而不是"任务的难度"。一个很简单的任务（查天气）不需要 Agent；一个很难但路径固定的任务（生成季度报表，逻辑复杂但步骤确定）同样不需要 Agent。
12 · 组合视角

不要把世界分成二选一

到这里需要纠正一个可能形成的误区：这不是 Workflow 或 Agent 的选择，生产系统通常是三者的组合。图 3 已经给出了企业客服系统的例子——意图理解用 LLM、路由和退款物流用 Workflow、商品探索用 Agent。这往往比 Everything → Agent 更接近生产级设计：每个子任务用最便宜、最可控的执行模型，Agent 只覆盖真正需要自主决策的那一块。

13 · 架构原则

Deterministic Core + Agentic Edge

把上一节的思路提炼成一个可复用的分层架构原则：核心业务流程尽可能保持确定性，把 Agent 放在真正需要自主决策的边缘。

14 · 贯穿案例

电商智能客服：三种执行模型的演进

用一个案例把前面的判断串起来。注意它展示的不是"选 Workflow 还是选 Agent"，而是同一个产品里不同子任务选择不同执行模型。

阶段一：简单查询

"我的订单什么时候到？"——意图分类 = Logistics，进入 Logistics Workflow：查订单 → 查物流 → 生成回复。不需要 Agent，路径完全确定。

阶段二：复合请求

"这件商品为什么还没到？如果今天还不到，能不能退款？另外别人同款便宜了 50 元，有没有价格保护？"——需要订单、物流、价格、售后政策、价格保护政策的组合。复杂度上去了，但依然可以用 Workflow + LLM 解决：LLM 负责把复合请求拆解为多个结构化子任务，程序负责编排查询，LLM 负责把多路结果综合成回复。不需要 Agent——因为所有需要的查询在拆解完成的那一刻就全部可知了。

阶段三：开放式探索

"帮我找一款适合我孩子学习用的平板，预算 3000 左右，最好续航长一点，可以比较一下现在有哪些值得买的吗？"——下一步搜索什么、比较哪些维度、要不要换条件，取决于过程中发现了什么（比如某款阉割了护眼功能）。这进入了 Agent 的适用范围。

演进逻辑
简单问题 → Workflow
需要理解用户意图 → LLM + Workflow
AGENT 的进入时机
开放式探索任务 → Agent（动态决策价值明确，且不处于强 SLA 同步链路）

16 · 判断工具 二

Agent 必要性评分模型

决策树适合定性判断。如果团队在架构评审中需要把讨论结构化，可以用一个简单的评分模型：

加分项（每项 +2）—— 路径动态性

  • +2动态决策下一步依赖过程中的发现
  • +2环境不确定性需要探索开放环境
  • +2动态工具选择工具调用顺序无法预先确定
  • +2需要自主规划Plan → Execute → Re-plan
  • +2任务目标开放成功路径不唯一

减分项 —— 生产约束

  • −3强确定性流程
  • −2强 SLA
  • −2高调用量
  • −3高风险操作
  • −2成本极敏感
Agent Necessity Score架构建议
≤ 0Workflow
1 – 3Workflow + LLM
4 – 6值得认真评估 Agent（做 PoC 对比）
≥ 7Agent 值得认真考虑
这不是数学定律，而是一种架构讨论工具。分数本身不重要，重要的是它强迫团队逐项回答：Agent 到底增加了什么价值？每一分的依据是什么？实践中，多数团队填完这张表后会发现自己项目的分数远低于预期——因为"我们希望它更智能"这种模糊愿望，在这张表上得不了分。
17 · 成本核算

引入 Agent 的真实成本

前面分散提到了成本，这里系统汇总。引入 Agent 不是免费的，账要算全：

维度WorkflowAgent
决策主体程序模型
执行路径预定义动态
可预测性高较低
成本可预测（固定调用）波动（动态循环）

失败面：从"有限可枚举"到"组合爆炸"

Workflow 的失败点是你枚举过的分支（网络超时、校验失败、依赖不可用）。Agent 的失败面是每一个模型决策点——选错工具、错误解读观察结果、提前终止、无限循环。

可观测性：Debug 的代差

Workflow 出问题时看 trace：A → B → C，C 报错了，修 C。Agent 出问题时，你需要先回答"它当时为什么这么决定"——重放决策、检查 Context 里哪一条 Observation 误导了它。这需要为每个决策点记录完整的 Thought / Tool Call / Observation / State，观测成本显著高于 Workflow。

评估：复杂一个数量级

Workflow 可以直接测试 Input → Expected Path；Agent 的评估对象变成"从目标出发，哪些轨迹和结果是可接受的"——需要轨迹级评估与结果级评估的组合，评估集的构建和回归检测都复杂得多。

可靠性：护栏是前置条件

Max Iterations、Timeout、Loop Detection、预算熔断必须显式配置——否则一次失控循环就是一次事故。这些成本不是"Agent 不好的理由"，而是为自主决策支付的对价。判断标准始终是：这个任务带来的价值是否覆盖这份对价。

18 · 概念辨析

不要把"不可预测"误认为"需要 Agent"

这是一个容易踩坑的混淆。LLM 的输出天然具有随机性，有团队据此推理："我们的系统有不可预测性，所以需要 Agent 的灵活性。"这混淆了两个不同层面的概率性：

输出的概率性
LLM 生成内容有随机性 —— 可以被工程手段收敛：Structured Output、Schema Validation、低 Temperature、校验重试、Fallback。系统在路径层面依然是确定性的。
路径的动态性
执行路径需要在运行时决定 —— 这才是 Agent 的领地。下一步做什么，必须在运行时根据环境决定。
PYTHON
# 输出概率性 → 用工程手段收敛，路径仍然由代码控制
result = llm_extract(doc, schema=EXTRACT_SCHEMA, temperature=0)
while not result.valid and attempts < 3:
    result = llm_extract(doc, schema=EXTRACT_SCHEMA, hint=result.errors)
return result if result.valid else escalate_to_human()
输出具有概率性 ≠ 系统需要 Agent。
真正需要 Agent 的判断依据只有一个：执行路径本身具有动态性。这个区分把大量"看起来需要 Agent"的场景（提取、分类、生成、摘要、改写）正确地归回 Workflow + LLM 的范畴。

20 · 结论

决策权属于代码，还是属于模型

回到开头的问题：什么时候不应该使用 Agent？当路径可以被工程师提前定义时——确定性业务流程、固定数据处理 Pipeline、规则 + LLM 的路由模式、强 SLA 的同步链路、成本敏感的高流量场景、高风险操作——不要把决策权交给模型。把全文的判断浓缩成两句话：

不要问"这个系统能不能做成 Agent"，而要问"这个系统是否需要 Agent 的自主决策能力"。
如果工程师能够提前定义路径，就让程序定义路径；如果路径必须根据环境动态决定，再把决策权交给 Agent。
真正成熟的 Agent 架构，
不是让所有事情都交给 Agent，
而是知道哪些事情绝对不应该交给 Agent。
